# ТЗ: редактор накладных закупок (30.10.2026)

**Для кого:** разработчики кассы и программы владельца (десктоп) и Умар (сервер NurCRM).
**Просьба владельца:** «Нужен редактор накладных для истории закупок. Склад → Закупки, там документы (приходы/накладные) может редактировать только тот, у кого есть доступ к редактору документов (пока только владелец). Только в течение 24/48 часов. Добавить в настройки выбор 24 ч / 48 ч / всегда».
**Уточнение владельца:** редактор нужен **на десктопе** (Windows, Linux, macOS). Android-сборка десктопа — не приоритет (кнопку там прячем). Мобилка — потом, по запросу.

Код при подготовке ТЗ не менялся. Схема сервера — снимок `openapi.json` от 29.10.2026 (`C:\Users\User\NurMarket-test\audit-1029be\`).

## 0. Коротко

- **Рекомендуемый путь — (А):** сервер даёт `PATCH api/main/suppliers/receipts/{id}/`, который за одну транзакцию меняет приход, остатки, закупочную цену, долг поставщику или расход кассы, пишет версию и аудит. Касса показывает предпросмотр, отправляет правку и показывает результат сервера.
- **До готовности сервера** делаем всё, что от сервера не зависит: право, настройку окна, кнопку «Изменить» с таймером, окно редактора с предпросмотром, черновик, историю правок. Проведение — только через (А).
  По решению владельца можно включить временную **«Б-лайт»**: только «уменьшить количество / удалить строку» (возврат поставщику по этому приходу с причиной «Исправление документа») и «добавить недостающее» (доприход «к документу №…»). Цену, поставщика, оплату и дату в «Б-лайт» не меняем.
- Права: **только владелец** (роль `owner` в профиле NurCRM). Админ и программа владельца, открытая сотрудником, права не дают.
- Окно правки: **24 ч / 48 ч / всегда**, по умолчанию 24 ч, считается от времени проведения прихода по часам сервера.

### 1.3. Что происходит с деньгами и остатками при правке

| Правка | Остаток | Закупка в карточке | Долг / касса | Отчёты |
|---|---|---|---|---|
| Количество 10 → 8 | −2 сейчас | не меняется | долг или расход −2 × цена | закупки за период −, прибыль не меняется |
| Количество 10 → 12 | +2 | не меняется | долг или расход + | |
| Цена 120 → 100 | 0 | 100, если этот приход **последний** по товару, иначе прежняя | долг или расход −20 × кол-во | прибыль считается от закупки в карточке **сегодня** (`CategoryAnalyticsExport`), поэтому прошлая прибыль пересчитается |
| Удалить строку | −кол-во | откат к закупке прошлого прихода, если этот был последним | − сумма строки | |
| Добавить строку | +кол-во | новая, если приход последний | + сумма | |
| Сменить поставщика | 0 | 0 | долг уходит от одного поставщика к другому | закупки по поставщикам |
| Сменить оплату (наличные ↔ долг) | 0 | 0 | расход кассы сторнируется, создаётся долг (или наоборот) | касса, смена |

**Главный риск:** часть товара уже продана. Пример: пришло 10, продано 7, на складе 3. Количество можно уменьшить **не ниже 7**, иначе остаток станет −.

## 2. Что проектируем (правила)

### 2.1. Кто

- Новое право **«Редактор документов закупок»**: флаг `can_edit_purchase_documents`.
- Сейчас право есть **только у владельца**: роль `owner` в профиле (`OfflineAuthSessionStore.ResolveUserObject(payload).role == "owner"`). Админ, `can_view_settings` и сам факт программы владельца (`AppMode.IsOwner`) права **не дают**.
- В «Настройки → Сотрудники → 🔐 доступы» строка «Редактор документов закупок» видна, но выключена и заблокирована с подсказкой «Пока только владелец». Позже, если владелец решит, её можно будет выдавать сотрудникам (тогда решает серверный флаг).
- Автономный режим (без NurCRM): приходов сервера нет, редактор скрыт.
- Окончательную проверку права делает **сервер** (403 `permission_denied`). Клиент только прячет кнопку.

### 2.2. Когда (окно правки)

- Настройка компании **«Правка накладных закупок»**: `24 часа` (по умолчанию) / `48 часов` / `Всегда`.
- Где: **Настройки → Операции → карточка «Закупки: правка накладных»** (рядом с «Оплата долга», по образцу `DebtPaymentSettingsCard`), плюс ссылка ⚙ из окна «Закупки». Менять может только владелец, остальные видят значение.
- Отсчёт — от `created_at` прихода (время проведения), **по часам сервера**. Касса берёт `edit_window_until` из ответа сервера. Пока сервер его не отдаёт, считает `created_at + окно` с поправкой на разницу часов (заголовок `Date` последнего ответа).
- Показ:
  - в строке истории — метка «✎ ещё 13 ч» (зелёная) или ничего, если правка недоступна;
  - в «Позициях прихода» — «Можно править ещё 13 ч 20 мин» / «Время правки истекло 29.10 в 14:05» / «Правка без ограничения времени»;
  - если окно истекает, пока открыт редактор, — жёлтая полоса «Осталось 10 мин» и таймер. После истечения кнопка «Сохранить» выключается. Черновик сохраняется, но провести его уже нельзя. Сервер в любом случае откажет кодом `edit_window_expired`.
- Смена настройки действует сразу на все приходы, в том числе старые (при «Всегда» становятся доступны все). Об этом предупреждаем при выборе «Всегда».

### 2.3. Что можно менять

| Поле | Можно | Условия |
|---|---|---|
| Количество в строке | да | не ниже **проданного**: `min = max(возвращено по строке, старое кол-во − текущий остаток)`. Подсказка «Не меньше 7: 3 шт. на складе, остальное продано». Дробное — только у весовых единиц (3 знака) |
| Цена закупки в строке | да | > 0, до 3 знаков. У строки с возвратом цена заблокирована: возврат прошёл по старой цене |
| Добавить строку | да | поиск или скан из каталога, как в приёмке. Новый товар создаётся только через приёмку |
| Удалить строку | да | только если по строке не было возврата и `min = 0` |
| Номер и дата накладной поставщика | да | сервер пока не хранит, до (А) хранится в нашей подписи на ПК |
| Примечание | да | |
| Поставщик | только (А) | если по приходу нет возвратов и оплат долга |
| Способ оплаты (наличные / ящик смены / в долг / частично) | только (А) | если сделка-долг не оплачивалась. При «из ящика смены» и уже закрытой смене поправка денег идёт в основную кассу компании (предупреждение в предпросмотре) |
| Дата и время проведения | **нет** | от неё считается окно, на ней стоит журнал движения |
| Цена продажи | нет | меняется в карточке товара и переоценкой, а не в документе закупки |

Запреты (кнопка «Изменить» выключена, причина в подсказке):
- приход ещё в очереди кассы (`BackgroundReceivingQueue`: не отправлен или исход неизвестен) — «Приход ещё отправляется — правьте его в очереди»;
- приход полностью возвращён поставщику;
- период закрыт (`period_closed`, когда появится);
- идёт ревизия, в которой есть товары прихода — предупреждение, не запрет;
- нет связи — можно открыть редактор и сохранить черновик, провести нельзя (см. 2.8).

### 2.4. Предпросмотр «до / после» (обязательно перед сохранением)

Окно «Проверьте правку» (модалка поверх редактора):

```

│ Сумма прихода      12 400,00 → 11 900,00   (−500,00)                        │
│ Долг поставщику     8 400,00 →  7 900,00   (−500,00)   сделка «Долги Шоро»  │
│ Расход кассы                 —                                               │
│ ─ Остатки ──────────────────────────────────────────────────────────────── │
│ Товар                 Сейчас   Изменение   Станет   Закупка в карточке      │
│ Шоро Чалап 1 л           3        −2          1      120 → 120 (не послед.) │
│ Максым 0,5 л            40         0         40      55 → 50   ⚠ −9 %       │
│ ─ Затронуто ────────────────────────────────────────────────────────────── │

│ пересчитается от новой закупки.  Ревизии: нет.  Возвраты по приходу: нет.   │
```

- Расчёт делает клиент по свежему `GET receipt` и остаткам. При (А) — ещё и сервер: `dry_run: true`. Если цифры клиента и сервера разошлись, показываем серверные и полосу «Сервер посчитал иначе».
- Причина: список (опечатка в количестве / опечатка в цене / не тот товар / поставщик прислал исправленную накладную / недовоз / другое) и текст 5–500 знаков. Без причины кнопка выключена.
- Подтверждение: пароль владельца NurCRM (`PasswordPromptDialog`). Нужно, потому что программа владельца может стоять открытой на общем ПК. Вопрос владельцу 2 — может, хватит PIN.

### 2.5. Версии и история правок

- У прихода появляется номер версии: исходный документ — версия 1, каждая правка +1.
- В «Позициях прихода» — метка «Исправлен 2 раза, последний 30.10 10:15, владелец» и кнопка «История правок».
- «История правок»: список версий (кто, когда, устройство, причина, сумма до/после), раскрытие — разница по строкам (было → стало, добавлено, удалено).
- «Вернуть эту версию» (откат) — это **новая правка** с составом выбранной версии: та же проверка окна, предпросмотр, причина и пароль. Историю не стираем.
- До (А) история хранится на ПК в `%APPDATA%\<NurMarketKassa|NurMarketOwner>\purchases\receipt-edits.json` (атомарная запись, как `PurchasesStore`). Схему базы `pos_local.db` **не меняем**. После (А) источник истории — сервер, а локальный журнал нужен только для черновиков и очереди.

### 2.6. Печать и PDF

- В «Печать» и «Скачать PDF» (`PurchaseDocs.Build`) у исправленного прихода в шапке строка **«ИСПРАВЛЕНО · версия 3 от 30.10.2026 10:15 · причина: …»**, в имени файла — `_v3`.
- Кнопка «PDF исходной версии» в истории правок — для сверки с бумагой поставщика.
- Исходный файл накладной (`StoredFile`) открывается из редактора кнопкой «Открыть файл накладной» для сверки.

### 2.7. Журнал и уведомления

- Сервер пишет `audit-log` (`object_type=supplier_receipt`, `action=edit|revert`, разница, причина, устройство). Касса дублирует строку в свой журнал (`PosLogger`, уровень INFO), без сумм долга в открытом тексте сверх нужного.
- Владельцу в Telegram (бот кассы, `TelegramBotService`): «✎ Приход №A1B2C3D4 от «Шоро» исправлен: 12 400 → 11 900 сом (−500). Причина: опечатка в количестве. Кто: …, ПК: …». Текст на языке владельца, 5 языков.
- Другие кассы узнают о правке так: остатки и закупка приходят лентой `products/changes/` (8–10 с), история закупок перечитывается при открытии. При (А) сервер ещё отдаёт событие `receipt_changed` (см. 3.4).

### 2.8. Без связи

- Редактор открывается только по свежему приходу с сервера (`GET suppliers/receipts/{id}/`). Без связи приход берётся из кэша, но с полосой «Нет связи — правку можно сохранить черновиком».
- «Сохранить правку» без связи ставит её в **очередь правок** (`receipt-edits.json`, раздел `queue`): ключ повтора создаётся и пишется на диск до отправки, плюс `base_version` и порядковый номер. Правки одного прихода уходят строго по порядку.
- При появлении связи: (1) перечитать приход; (2) если `version` ≠ `base_version` — конфликт: правка не отправляется, владелец видит «Приход изменили с другого ПК: {кто, когда}. Открыть и сравнить»; (3) окно проверяет сервер на момент отправки: истекло — «Время правки истекло, пока не было связи», черновик остаётся. Льготное время — вопрос владельцу 4.
- Если сам приход ещё в фоновой очереди (`BackgroundReceivingQueue`), редактор не открывается. Строки задачи правятся в очереди, пока она не отправлена.
- Ответ сервера потерялся (таймаут, 5xx): тот же ключ при повторе; сервер отвечает `replayed: true`. Без ключа на сервере повтор правки запрещён — сначала перечитываем приход и сверяем версию.

## 3. Что нужно от сервера (Умар)

### 3.1. Вариант (А) — PATCH прихода с атомарным пересчётом (рекомендуем)

```

Заголовки: Idempotency-Key: <uuid>      (обязательно)
           If-Match: "<version>"        (или поле version в теле)
Тело:
{
  "version": 1,
  "reason": "Опечатка в количестве",              // обязательно, 5–500 знаков
  "reason_code": "qty_typo|price_typo|wrong_product|supplier_corrected|short_delivery|other",
  "dry_run": false,                               // true — только посчитать и вернуть дельты, ничего не менять
  "supplier_id": "<uuid>",                        // необязательно
  "document_number": "1245", "document_date": "2026-10-28",   // необязательно
  "comment": "…",                                 // необязательно
  "payment": { "type": "cash|debt|partial", "paid_amount": "0.00",
               "cashbox_id": "<uuid>", "shift_id": "<uuid>", "due_date": "2026-11-28" },   // необязательно
  "lines": [
    { "id": "<receipt_item_id>", "qty": "8.000", "purchase_price": "120.000" },   // изменить
    { "id": "<receipt_item_id>", "delete": true },                                 // удалить
    { "product": "<product_id>", "qty": "2.000", "purchase_price": "50.000",
      "client_row_id": "<uuid>" }                                                  // добавить
  ],                                              // только изменённые строки
  "update_product_purchase_price": "if_latest",   // if_latest (по умолчанию) | always | never
  "source": "kassa|owner|web|phone", "device": "Касса-1"
}
```

**Что сервер делает в одной транзакции:**
1. Проверки по порядку: ключ повтора → право → окно → версия → период → строки (возвраты, остаток) → деньги.
2. Остатки: на каждую изменённую строку — одно движение `receipt_correction` (дельта, `SET quantity = quantity + delta` под блокировкой строки, ссылка на приход и версию). Абсолютной записи нет.
3. Закупка в карточке: по правилу `update_product_purchase_price`. «Последний» — у товара нет более позднего прихода. Если строку удалили и она была последней — откат к закупке предыдущего прихода. Партии (`purchase-batches`): поправить `qty_in`, `qty_left`, `unit_cost`.
4. Деньги:
   - приход в долг — изменить сумму сделки-долга этого прихода (`deal_id`, или сделка с меткой `receipt:<id>` в `note` — так её создаёт касса) и пересчитать график; если новая сумма меньше уже оплаченного — 409 `debt_already_paid`;
   - оплачен сразу — проводка разницы в ту же кассу (сторно или доплата), если смена закрыта — в основную кассу (`expense_variable`), с пометкой;
   - смена оплаты или поставщика — сторно старой проводки или сделки и новая.
5. Версия: сохранить снимок версии N, `version = N+1`, `edited_at`, `edited_by`, `edit_count`.
6. Аудит: `audit-log` (`object_type=supplier_receipt`, `action=edit`, `diff`, `reason`, `user`, `device`, `ip`).
7. Лента: изменённые товары — в `products/changes/`; событие `receipt_changed`.

**Ответ 200:**

### 3.2. Коды ошибок (`{"code","detail","data"}`, `detail` по `Accept-Language`)

| Код | HTTP | Когда | `data` |
|---|---|---|---|
| `permission_denied` | 403 | нет `can_edit_purchase_documents` (сейчас только владелец) | `{required}` |
| `edit_window_expired` | 409 | `now > created_at + окно` | `{created_at, window: "24h|48h|always", expired_at}` |
| `version_conflict` | 412 (с If-Match) / 409 | версия устарела | `{current_version, edited_by, edited_at}` |

| `has_returns` | 409 | строка с возвратом: кол-во ниже возвращённого, смена цены, удаление, смена поставщика | `{lines: [{id, returned_qty}]}` |
| `debt_already_paid` | 409 | новая сумма меньше оплаченного по сделке, смена оплаты или поставщика при оплатах | `{deal_id, paid, new_total}` |

### 3.3. Ещё нужно

1. **Право** `can_edit_purchase_documents` у сотрудника (в `users/employees/`, профиле и форме доступов). У владельца всегда `true`, у остальных по умолчанию `false`.
2. **Настройка окна** на компании: `receipt_edit_window: "24h" | "48h" | "always"` (по умолчанию `24h`) в `users/company/` (или `main/company-settings/`). **Менять может только владелец** (админ — 403). Общие `app-settings` для этого не годятся: их меняет и админ.
3. **В приходе** (`GET suppliers/receipts/` и `/{id}/`): `version`, `edited`, `edit_count`, `edited_at`, `edited_by`, `edit_window_until`, `can_edit`, `edit_block_reason`, `number`, `document_number`, `document_date`, `comment`, `payment_type`, `paid_amount`, `debt_amount`, `deal_id`, у строки — `id` (уже есть), `returned_qty`, `sold_after_receipt` (по желанию).
4. **Версии:** `GET suppliers/receipts/{id}/versions/` → `[{version, at, user, device, reason, total, lines_diff}]`; `GET …/versions/{n}/` → снимок. Откат — `POST …/revert/ {to_version, reason}` с теми же проверками и ответом, что PATCH (или PATCH составом версии — тогда отдельный адрес не нужен).
5. **Событие** `receipt_changed {receipt_id, version, supplier_id, edited_by, at}`: в ленте изменений (`GET suppliers/receipts/changes/?since=` по образцу `products/changes/`) и в WebSocket, если он появится.
6. `Idempotency-Key` в `POST suppliers/{id}/returns/` — сейчас касса ключ туда не шлёт, и повтор после обрыва может провести возврат дважды. Нужно и без редактора, а для варианта (Б) обязательно.
7. В `GET capabilities/` — признак `receipt_edit`. Пока его нет, касса прячет проведение правки через (А).

### 3.4. Вариант (Б) — без нового эндпоинта (временный)

**Б1. «Сторно целиком»:** возврат поставщику всего прихода (`receipt_id`, `compensation=debt_offset` или `cash`) и новый приход с правильным составом.
Риски (поэтому **не берём**):
- товар частично продан — полный возврат невозможен или уводит остаток в минус;
- два документа на одну поставку: закупки за период завышены на сумму старого прихода, «Возвраты поставщикам» — на ту же сумму;
- новый приход получает сегодняшнюю дату, поставка попадает не в тот период, окно правки начинается заново;
- долг: `debt_offset` гасит долг поставщику в целом, а не сделку прихода; новая сделка-долг создаётся отдельно (`SupplierDebtRecorder`), сроки и график сбиваются;
- нет транзакции: возврат прошёл, а новый приход нет — остаток и долг уменьшены «впустую»;
- у возврата нет ключа повтора — обрыв может провести возврат дважды;
- партии и FIFO перемешиваются; бонусы и скидки поставщика (если появятся), статистика поставщика, ABC и «Поступления» товара показывают лишние строки; связь документов только в комментарии возврата (у прихода поля комментария нет).

**Б2 («Б-лайт», если владелец согласится до готовности (А)):** правим только разницу.
- Уменьшить количество или удалить строку — возврат поставщику **по этому приходу и строке** (`receipt_id`, `receipt_item_id`), `reason` «Исправление документа», `comment` «Исправление прихода №A1B2C3D4 v2: …», `compensation` = `debt_offset` для прихода в долг и `cash` (та же касса) для оплаченного.
- Добавить количество или строку — доприход того же поставщика тем же способом оплаты; в долг — новая сделка с меткой `receipt:<новый id>` и `correction_of:<старый id>` в `note`.
- Цена, поставщик, оплата и дата в Б2 **недоступны** — подсказка «Будет доступно после обновления сервера».
- Смягчение: свой журнал связей (`receipt-edits.json`) — в истории закупок такие документы показываются одной группой «Приход №… (исправлен)»; ключ повтора на каждый шаг, шаги по порядку, после обрыва сначала перечитать возвраты и приходы; прежде чем начать, проверить остаток (возврат не больше остатка); в отчётах «Закупки» кассы — пометка, что исправления выглядят как возврат и доприход.
- Минимальная помощь сервера для Б2: принять `correction_of` и `reason` в `POST receipt` и `returns` и не считать такие возвраты в «Возвраты поставщикам» как реальные. Плюс п. 3.3-6 — ключ повтора у возврата.

## 5. Критерии приёмки

1. Владелец видит «Изменить» у прихода моложе окна. Админ, кассир, программа владельца под сотрудником — не видят. Прямой PATCH от не-владельца — 403 `permission_denied`.
2. Настройка 24 ч / 48 ч / всегда меняется только владельцем, сразу действует на всех кассах и в программе владельца. Админ получает отказ.
3. Приход старше окна: кнопка выключена, видно «Время правки истекло …»; PATCH — 409 `edit_window_expired`. Перевод часов ПК на сутки назад ничего не меняет.
4. Количество 10 → 8 (продано 0): остаток −2, сумма −2 × цена, долг −2 × цена. Ровно на столько же — на второй кассе через ≤ 10 с.
5. Пришло 10, продано 7: ввести 6 нельзя («не меньше 7»); 7 — можно, остаток 0. Сервер на 6 — 409 `negative_stock`.
6. Цена 55 → 50 у последнего прихода товара: закупка в карточке 50, остаток не меняется, долг −5 × кол-во. У не последнего прихода закупка в карточке прежняя (`applied:false`).
7. Строка с возвратом: цена заблокирована, кол-во не ниже возвращённого, удаление недоступно.
8. Без причины и пароля сохранить нельзя. Причина видна в истории правок, в журнале сервера и в Telegram.

## 7. Риски

| Риск | Чем закрываем |
|---|---|
| Остаток уходит в минус из-за продаж после прихода | минимум по строке; серверный `negative_stock` |
| Задвоение при обрыве | `Idempotency-Key` + `version`; без ключа — сначала перечитать |
| Правка задним числом меняет прибыль прошлых дней (себестоимость считается по закупке сегодня) | предупреждение в предпросмотре «7 продаж — прибыль пересчитается»; окно 24 ч по умолчанию |
| Закрытая смена при оплате из ящика | деньги в основную кассу, предупреждение; Z-отчёт закрытой смены не меняется |
| Админ меняет окно через общие `app-settings` | настройка на сервере компании, PATCH только владельцу |
| Программа владельца открыта сотрудником | право по роли из профиля, не по режиму программы; пароль при сохранении |
| Б1/Б2 искажают отчёты и долг | Б1 не берём; Б2 — только с согласия владельца, только количество, со связями и пометками |
| Нет `period_closed` на сервере | код зарезервирован, клиент готов его показать |
| Возврат поставщику без ключа повтора (уже сейчас) | п. 3.3-6 у Умара |
