**Как понимаем задачу (допущение).** Торговый агент — выездной сотрудник магазина-дистрибьютора: ездит по точкам-клиентам по маршруту, берёт заявки или продаёт прямо из машины (машина = его склад), выписывает накладную, собирает деньги и долги, вечером сдаёт выручку и остатки. Поддерживаем обе схемы: **пресейл** (заявка → склад собирает → доставка) и **ван-селлинг** (продажа с машины). Модуля агентов на сервере NurCRM сейчас нет совсем (касса пробует `api/main/agents/me/products/` — 404/405).

## 1. Цели, персоны, метрики

### 1.1. Цели
1. Агент весь день работает **без интернета**: клиенты, цены, остатки машины, заявки, продажи, оплаты, накладные, печать.
2. Владелец и супервайзер видят **в реальном времени**: где агенты, сколько визитов, продаж, денег собрано, сколько долга.
3. Ни одна продажа или оплата **не теряется и не дублируется** (ключи идемпотентности, журнал).
4. Деньги и товар агента **сходятся каждый вечер**: загрузка − продажи − возвраты на склад ± списания = остаток машины; выручка в кассе агента = сдано.
5. Дебиторка под контролем: лимиты, сроки, блокировки, напоминания.

### 1.2. Персоны
| Персона | Где работает | Главные задачи |
|---|---|---|
| **Агент** | мобилка (Android, слабый телефон, улица, солнце, одна рука) | маршрут дня, визит, заявка/продажа, накладная, оплата, долги, сдача выручки |
| **Супервайзер** | мобилка (режим супервайзера) + программа владельца | планы маршрутов, контроль визитов на карте, одобрение отклонений (лимит, скидка, вне геозоны), KPI команды |
| **Владелец** | программа владельца (`--owner`) + мобилка | итоги, рейтинг агентов, дебиторка, бонусы, настройки правил |
| **Кладовщик** | касса/программа владельца или мобилка («Сборка», есть `/admin/pick`) | собрать заявки, загрузить машину (перемещение), принять возврат и пересчёт машины |
| **Бухгалтер / кассир** | касса / программа владельца | принять выручку (акт приёма-сдачи), акт сверки с клиентом, разбор расхождений |

### 1.3. Метрики успеха (через 1 месяц у первого клиента)
| Метрика | Цель |
|---|---|
| Потерянные/задвоенные продажи и оплаты | 0 |
| Доля визитов с чек-ином в геозоне | ≥ 90 % |
| Время оформления заказа на 10 позиций | ≤ 90 с |
| Расхождение остатка машины на вечернем пересчёте | ≤ 0,5 % позиций |
| Расхождение выручки при сдаче | 0 сом без объяснения |
| Задержка события у супервайзера (онлайн) | ≤ 5 с |
| Время до «данные свежие» после появления сети | ≤ 60 с |
| Расход батареи за 10-часовой день (с GPS по визитам, без трека) | ≤ 25 % |
| Трафик за день | ≤ 30 МБ без фото, ≤ 80 МБ с фото |

## 2. Роли и права, вход и безопасность

### 2.1. Роль «Агент»
Сейчас роли сервера: `owner/admin/rop/supervisor/salesperson` + свои роли `api/users/roles/custom/` + флаги `can_view_*`/`can_edit_*` **[есть]**. Агентских флагов нет **[нет]**.

Нужно: системный шаблон роли `agent` (можно копировать в свою роль) и флаги:

| Флаг | Что даёт | Агент | Супервайзер |
|---|---|---|---|
| `can_use_agent_app` | вход в режим агента | ✔ | ✔ |
| `can_agent_sell_van` | продажа с машины | ✔ | ✔ |
| `can_agent_preorder` | заявка на склад | ✔ | ✔ |
| `can_agent_take_payment` | приём денег и оплаты долга | ✔ | ✔ |
| `can_agent_sell_debt` | продажа в долг (в пределах лимита) | ✔ (по настройке) | ✔ |
| `can_agent_discount` + `agent_max_discount_percent` | ручная скидка до N % | до 0–5 % | до N % |
| `can_agent_return` | возврат от клиента | ✔ | ✔ |
| `can_agent_create_client` | новая точка (уходит на одобрение) | ✔ | ✔ |
| `can_agent_edit_client` | правка контактов/координат | ✔ (на одобрение) | ✔ |
| `can_agent_writeoff` | списание брака из машины | на одобрение | ✔ |
| `can_view_agent_team` | видеть других агентов, карту, KPI команды | — | ✔ |
| `can_edit_routes` | планировать маршруты | — | ✔ |
| `can_approve_agent_requests` | одобрять отклонения | — | ✔ |
| `can_view_purchase_price` | видеть закупку/маржу | — | по настройке |

**Ограничения видимости (на сервере, не только в приложении):**
- `agent_scope`: `own_clients` (по умолчанию) | `territory` | `branch` | `all`. Агент получает в выдачах только своих клиентов, их долги, их чеки.
- Склад: агент продаёт и видит остатки **только своего склада-машины** + (только чтение) остатки основного склада для заявок, если `can_agent_preorder`.
- Касса: у агента своя касса (`cashbox` с ролью `pos_agent`), деньги только в неё.
- Супервайзер видит агентов своей команды (`supervisor_id`).

### 2.2. Вход
- Первый вход: email/телефон + пароль (как сейчас `api/users/auth/login/` **[есть]**) → регистрация устройства (`POST api/main/agents/devices/register/`) **[нет]**.
- Дальше: **PIN 4–6 цифр** (+ отпечаток по желанию), хранится локально как хэш (PBKDF2/Argon2) в `flutter_secure_storage`. 5 ошибок PIN → нужен пароль. Блок экрана после 5 мин бездействия (настраивается).
- **Одно активное устройство на агента.** Вход с нового телефона → запрос супервайзеру «сменить устройство»; старое устройство при следующем запросе получает `device_revoked` → стирает офлайн-данные (неотправленную очередь перед стиранием пытается отправить; если нельзя — шифрованный экспорт в файл для супервайзера).
- **Начало дня** = открыть смену кассы агента (`shifts/open/` **[есть]**) + подтвердить загрузку машины. **Конец дня** = пересчёт машины → сдача выручки → закрыть смену.

### 2.3. Геозона
- У клиента координаты и радиус (по умолчанию 150 м, настройка компании).
- Чек-ин вне геозоны: разрешён, но нужна причина + флаг `out_of_zone`, супервайзеру событие; настройка компании «запрещать вне зоны» (P1).
- Детект поддельного GPS (Android `isFromMockProvider`) → флаг `mock_location`, событие супервайзеру.
- Время: в каждой записи `device_time` + `server_time`; при разнице > 10 мин флаг `clock_skew`.

## 3. Клиентская база агента

### 3.1. Закреплённые точки
- Клиент закрепляется за одним или несколькими агентами (`agent_ids`) и/или территорией. Список агента = закреплённые + из маршрута дня.
- Фильтры: сегодня по маршруту / все мои / с долгом / просрочка / давно не были (> N дней) / новые. Поиск — единый поиск мобилки (ё=е, раскладка, транслит) **[есть]**.
- Новая точка агентом: заполняет минимум (название, телефон, адрес, координаты с телефона, фото фасада) → статус `pending_approval`; продавать ей можно сразу только за наличные (настройка), в долг — после одобрения.

### 3.2. Карточка клиента
| Блок | Поля | Источник |
|---|---|---|
| Основное | название, юрлицо/ИП, ИНН, тип точки (магазин, киоск, кафе, аптека…), канал, категория A/B/C | клиент **[частично есть: `full_name, phone, email, address, type`]** |
| Контакты | контактные лица (имя, роль, телефон, WhatsApp, Telegram), часы работы, дни приёма товара | **[нет]** |
| Адрес | адрес, координаты, радиус геозоны, фото фасада, ориентир | **[нет]** |
| Деньги | долг, просроченный долг, лимит (`debt_limit` **[есть]**), условия оплаты (отсрочка N дней), статус блокировки, бонусы (`bonus_balance` **[есть]**) | частично |
| Цены | прайс-лист, тип цены (розница/опт), персональная скидка % | **[нет, кроме опта]** |
| История | последние заказы/продажи, оплаты, возвраты, визиты, средний чек, частота | чеки **[есть]**, визиты **[нет]** |
| «Обычно берёт» | топ-20 товаров за 90 дней с частотой и средним количеством | считает сервер (P1) или телефон по истории (P0, упрощённо) |
| Заметки и задачи | заметки агента (текст/голос/фото), задачи «привезти образец», «забрать долг 12.11» | задачи `api/main/tasks/` **[есть]**, привязки к клиенту **[нет]** |

## 4. Маршруты и визиты

### 4.1. План на день
- **Шаблон маршрута**: по дням недели (Пн: точки 1…25), периодичность (каждую неделю / через неделю / раз в месяц).
- **План дня** создаётся из шаблона автоматически (сервер, ночью, или при «начале дня») + ручные добавления супервайзера/агента + внеплановые визиты.
- Список дня: порядок, статус точки (не начат / в работе / сделан / отказ / пропущен), долг, задача, «заказ ожидается».
- Карта: точки дня и текущее положение. MVP — кнопка «Открыть в 2GIS/Яндекс/Google» (url_launcher, без новых библиотек); P1 — встроенная карта.

### 4.2. Оптимизация маршрута
- P1: переставить порядок по расстоянию (ближайший сосед + 2-opt на телефоне, до 60 точек, без интернета; учитывает часы работы точки).
- P2: серверная оптимизация с пробками / ИИ-подсказка (раздел 11).

### 4.3. Визит
1. **Чек-ин**: координаты + точность, время, проверка геозоны. Без GPS (подвал) — чек-ин с причиной «нет GPS».
2. **Фото витрины/полки** (настройка: обязательно / по желанию / нет; 1–5 фото; сжатие до 1280 px, JPEG 70, ~150 КБ; отправка отдельной медиа-очередью, только по Wi-Fi — настройка).
3. Действия в визите: заказ/продажа, оплата долга, возврат, задачи, опрос (P2: анкета мерчендайзинга), заметка.
4. **Причина без заказа** (обязательно, если визит без заказа): закрыто, нет ЛПР, есть запас, нет денег, долг/блок, ушёл к конкуренту, другое (текст). Список настраивается.
5. **Чек-аут**: координаты, время; **таймер визита** виден всё время; визит < 2 мин или > 60 мин — флаг для супервайзера (пороги — настройка).
6. Незакрытый визит при чек-ине в другую точку → автозакрытие с флагом `auto_closed`.

## 5. Заявки и продажи

### 5.1. Каталог
- Товары с **ценой этого клиента** (см. 5.2), остатком **машины** и (для заявки) остатком **основного склада** «на момент ЧЧ:ММ».
- Фильтры: категория, бренд, «есть в машине», «обычно берёт», акции, новинки. Плитка/список, фото из кэша (кэш на диск уже есть: 200 МБ/30 дней).
- Упаковки: продажа коробкой/блоком/штукой (упаковки уже есть в мобилке 1.18.7) **[есть]**.
- Сканер штрихкода/камера **[есть]**.

### 5.2. Цены клиента (порядок применения)
1. Прайс-лист клиента (P1; P0 — тип цены `retail` = `price`, `wholesale` = `wholesale_price` **[есть]**).
2. Персональная скидка клиента % (P0).
3. Акции (`promotion_rules` у товара **[есть]**; сервер применяет сам) + акции прайс-листа «N+1», «от суммы» (P1).
4. Ручная скидка агента ≤ `agent_max_discount_percent`; больше — запрос супервайзеру (онлайн-одобрение или код подтверждения офлайн — P1).
- **Цена ниже закупки** запрещена без одобрения (закупку агент не видит, сервер/телефон знают флаг `below_cost`).
- Цена фиксируется на момент оформления; правило офлайна — в 8.4.

### 5.3. Корзина
- Быстрый ввод количества (крупная цифровая панель, +/−, «коробка»), сумма, вес/объём заказа (для загрузки машины, P1), позиции «нет в машине» помечены.
- **Повтор прошлого заказа** (одной кнопкой, с правкой) — P0.
- **«Что обычно берёт»** — подсказка товаров, которых нет в корзине, но клиент брал в 3 из последних 5 заказов — P0 (на телефоне по истории), P1 — с сервера + ИИ.
- Проверки до проведения: лимит долга, блокировка клиента, минимальная сумма заказа (настройка), остаток машины.

### 5.4. Два вида документа
| | **Продажа с машины (ван-селлинг)** | **Заявка на склад (пресейл)** |
|---|---|---|
| Остаток | списывается со склада агента сразу | резерв на основном складе после приёма заявки |
| Деньги | сразу (нал/безнал/долг) | при доставке или по условиям |
| Документ | **реализация (расходная накладная)** с номером | заявка → накладная при отгрузке |
| Сервер | `pos/checkout/` + поля агента (см. 15.4) | новая сущность `agent-orders` |
| Статусы | проведена / отменена (только супервайзер) | черновик → отправлена → принята → собирается → собрана → отгружена → доставлена → закрыта / отклонена / отменена |

Смешанный случай: часть есть в машине — продаём, остальное — заявкой (одна кнопка «Остальное — заявкой»), P1.

### 5.5. Документы
- **Накладная/реализация PDF** (генерация на телефоне, пакет `pdf` **[есть]**, есть `admin/waybill_pdf.dart`): реквизиты продавца/покупателя, номер, дата, позиции, итог, оплачено/в долг, срок оплаты, **подпись клиента пальцем на экране** (свой `CustomPainter`, без новой библиотеки) + ФИО подписавшего, **QR** (ссылка/номер документа для проверки, `qr_flutter` **[есть]**).
- Нумерация офлайн: сервер заранее выдаёт устройству **пул номеров** (например `АГ7-000101…000200`), номер берётся из пула, когда пул < 20 % — запрос нового. Без пула — временный номер `АГ7-Т-<n>`, сервер присваивает постоянный при приёме.
- Отправка клиенту: PDF в WhatsApp/Telegram (share_plus **[есть]**), P1 — серверная ссылка (`share-link` уже в ТЗ серверу).
- **Печать на мини-принтер Bluetooth 58/80 мм** ESC/POS **[есть]** (`core/print/`): накладная коротким видом, копия клиенту/агенту, чек оплаты долга, акт приёма-сдачи.
- НДС/ЭСФ — только пометка (раздел 10).

## 6. Склад агента (машина)

> Склады, документы движения, партии, ревизии, перемещения — **по «ТЗ Склад 10 из 10 (30.10.2026)» [ТЗ-Склад]**. Здесь только требования агента: склад агента = **склад типа `agent` (машина)** с владельцем-агентом.

| Операция | Что нужно агенту | Основа |
|---|---|---|
| **Загрузка** утром | кладовщик создаёт перемещение «основной → машина агента» (по заявкам дня или вручную); агент **подтверждает приём** построчно (факт ≠ план → расхождение в документе) | перемещение [ТЗ-Склад] + статус «принято агентом» |
| **Остатки машины** | всегда офлайн на телефоне; = последняя выгрузка сервера + локальные движения из очереди | остатки склада [ТЗ-Склад] |
| **Ревизия машины** | супервайзер/кладовщик в любой момент; агент считает, сервер сравнивает | ревизия склада [ТЗ-Склад] |
| **Возврат на склад** | вечером непроданное или по просьбе; кладовщик подтверждает приём | перемещение «машина → основной» [ТЗ-Склад] |
| **Возврат от клиента** | годный — в машину; брак — на склад брака/списание | возврат продажи **[есть `pos/sales/{id}/return/`]** + выбор склада |
| **Списание/брак** | с фото и причиной, на одобрение супервайзеру | списание [ТЗ-Склад] |
| **Партии/сроки** | при продаже — FEFO (сначала ближний срок) автоматически; предупреждение «срок < N дней» | партии [ТЗ-Склад] |
| **Пересчёт в конце дня** | обязательный перед сдачей выручки (настройка: полный / выборочный / нет); расхождения → акт, супервайзеру | ревизия [ТЗ-Склад] |

Правила агента: продажа в минус со склада машины **запрещена** (кроме настройки компании); отрицательный остаток после офлайн-синхронизации (редкий случай, если кладовщик поправил остаток) → событие супервайзеру, продажа не отменяется.

## 7. Оплата, долги, касса агента

### 7.1. Приём денег
- Способы: наличные, перевод/QR (MBank и др. — реквизиты QR **[есть]**), смешанная, **в долг** (с отсрочкой по условиям клиента), частичная предоплата.
- Срок долга = дата продажи + `payment_terms_days` клиента (сервер ставит сам; сейчас мобилка PATCH-ит `deals/{id}/` после продажи — для агента так не делать).
- **Оплата долга** в визите: `clients/{id}/pay-debt/` **[есть]** (гасит от старых к новым) + выбор конкретной накладной (P1, `pos/sales/{id}/pay-debt/` **[есть]**). Чек оплаты — печать/PDF.
- **Акт сверки** с клиентом за период (PDF): начальный долг, продажи, оплаты, возвраты, конечный долг — P1, сервер **[нет]**.

### 7.2. Лимиты и блокировки
- Лимит долга (`debt_limit` **[есть]**, сервер проверяет в чекауте), лимит просрочки (дней), блокировка вручную.
- Превышение: продажа только за наличные **или** запрос одобрения супервайзеру.
- Офлайн: телефон проверяет по последнему известному долгу + своим неотправленным продажам. Если сервер потом видит превышение (клиент купил ещё где-то) — продажа **принимается** (товар уже отдан) с флагом `limit_exceeded_offline` + событие супервайзеру. Отказывать в приёме уже отгруженного нельзя.

### 7.3. Возвраты
- По накладной (выбор строк, количества), причина, фото брака. Деньги: уменьшить долг / вернуть наличными из кассы агента (настройка, по умолчанию — только уменьшить долг).

### 7.4. Касса агента и сдача выручки (инкассация)
- У агента своя касса (`cashbox`, роль `pos_agent`), смена на день **[смены есть]**.
- Расходы в пути (топливо, мойка) — `cashflows` **[есть]** с категорией и фото чека, по настройке (по умолчанию запрещено).
- **Сдача выручки**: агент формирует «к сдаче» (наличные по факту, безнал — справочно, расходы), кассир/бухгалтер на кассе или в программе владельца **принимает** (факт пересчёта) → **акт приёма-сдачи** (PDF, подписи обеих сторон), деньги перемещаются в основную кассу. Возможна частичная сдача днём.
- **Расхождения**: недостача/излишек фиксируются в акте; недостача → долг агента (P1: удержание из зарплаты — по решению владельца).

## 8. Офлайн-first и синхронизация

### 8.1. Что лежит на телефоне
Свои клиенты (+ контакты, координаты, долги, лимиты, условия), прайс-листы/цены клиента, каталог, остаток машины, остаток основного склада (только чтение, «от ЧЧ:ММ»), маршрут на 7 дней, история клиента (90 дней), задачи, пул номеров, шаблоны документов.

### 8.2. Очередь
- Основа — текущая очередь мобилки **[есть]**: `Outbox`, `Idempotency-Key`, повтор с тем же ключом и тем же телом, 409 `idempotency_conflict` = «уже проведено», замок очереди, фон через WorkManager.
- Новые виды (`kind`): `visit_start`, `visit_end`, `agent_sale`, `agent_order`, `pay_debt`, `return`, `load_accept`, `unload`, `van_recount`, `writeoff`, `cash_expense`, `handover`, `client_new`, `client_edit`, `note`, `task_done`, `media` (отдельная очередь: фото/подписи/голос, крупные файлы, Wi-Fi по настройке).
- **Порядок зависимостей**: `client_new` → `visit_start` → `agent_sale` → `pay_debt` → `visit_end`. Локальные ссылки (`local_id` клиента/визита) сервер принимает и связывает (`client_local_id`, `visit_local_id`); ответ возвращает серверный id, телефон переписывает ссылки в следующих записях.
- Ключ: UUID v4 на каждую запись, создаётся **один раз при оформлении**; тело хранится неизменным.
- Сервер обязан **сравнивать тело при повторе** (хэш): тот же ключ + другое тело → 409 `idempotency_conflict` (сейчас для чекаута не сравнивает — исправить для агентских запросов).
- Пачка: `POST api/main/agents/sync/batch/` до 50 записей, ответ по каждой (как `pos/checkout/batch/` **[есть]**).
- Проверка исхода: `GET main/idempotency/{key}/` **[есть]**.

### 8.3. Получение изменений
- Лента `GET api/main/changes/?since=&types=` **[есть]** + новые типы агента (15.6) с фильтром по `agent_scope` (агент получает только своё).
- Онлайн — WebSocket `wss://app.nurcrm.kg/ws/main/events/` **[есть на сервере, в мобилке нет]**: подключать **только когда приложение на экране**; в фоне — без сокета.
- Плашка **«Данные от ЧЧ:ММ»** (строки `dataAsOf`, `linkOfflineSince` **[есть]**) на каталоге, остатках склада, долгах; красная, если > 12 ч.

### 8.4. Конфликты (правила)
| Ситуация | Правило |
|---|---|
| Цена изменилась, пока агент был офлайн | принимаем цену телефона, если прайс-лист на телефоне не старше `agent_price_lock_hours` (по умолчанию 24 ч); иначе принимаем + флаг `stale_price` супервайзеру. Строгая проверка цены (`X-NurMarket-Strict-Price`) — только онлайн. |
| Лимит долга превышен (см. 7.2) | принимаем + `limit_exceeded_offline` |
| Остаток машины ушёл в минус | принимаем + событие; остаток машины не может «отменить» продажу |
| Клиента удалили/переназначили | продажу принимаем, клиент остаётся в истории; новые визиты нельзя |
| Две правки клиента (агент и офис) | поля контакта — последняя по времени устройства; финансовые поля (лимит, условия, цены) агент не правит |
| Заявку изменили на складе | статус и строки с сервера главнее; агент видит «изменено складом» |
| Неисправимая ошибка (400) | строка «Не принято» с текстом причины на 5 языках + кнопка «Сообщить супервайзеру»; очередь идёт дальше, кроме зависимых записей |

### 8.5. Трафик и батарея (учитывает `Оптимизация мобилки (30.10.2026).md`)
- Каталог — лента изменений с ETag/304 **[есть]**; поиск — по индексу SQL, не загружать все 15 000 строк (п. 2 отчёта оптимизации) — обязательно до запуска агентов.
- GPS: **только в моменты чек-ина/чек-аута** (один замер, точность ≤ 50 м, таймаут 20 с); без постоянного трека. Трек — опционально (9.4), интервал ≥ 5 мин / 200 м, foreground-сервис с уведомлением.
- Фото — сжатие, отправка пачкой, по Wi-Fi по настройке. Подпись — PNG ≤ 30 КБ.
- WorkManager — только когда есть неотправленное (как сейчас) **[есть]**; не будить каждые 15 мин впустую (п. 6 отчёта).
- Чистка очереди: проведённые > 30 дней, кроме последних 500 **[есть]**; экраны читают очередь постранично.
- Сборка APK по архитектурам (`--split-per-abi`) — для слабых телефонов.

## 12. UX
- **Один палец, одна рука**: главные кнопки внизу экрана, зоны нажатия ≥ 48×48 dp (главные ≥ 56 dp), без двойных тапов и мелких иконок.
- Главный экран агента — «Мой день»: следующая точка (крупно), кнопка «Начать визит», прогресс дня, «к сдаче».
- Визит — один экран-мастер: Чек-ин → Фото → Заказ → Оплата → Подпись/Печать → Чек-аут; можно пропускать необязательное.
- Читаемость на солнце: контраст ≥ 4,5:1 (лучше 7:1 для сумм), тёмная тема и «авто по времени» **[есть]**, шрифт 3 размеров (обычный / крупный / очень крупный), суммы крупно.
- **5 языков** (ru, ky, uz, en, tr) через `l10n/app_*.arb` **[есть]**; все новые строки — на 5 языках; документы (накладная, акт) — на языке, выбранном для документа (ru/ky по умолчанию).
- **Режим слабого телефона** (P0, т. к. у агентов дешёвые телефоны): без анимаций, без фото в списках (только иконки), меньше элементов в списке за раз, без фоновой предзагрузки фото; включается автоматически при RAM < 3 ГБ или вручную.
- Своя экранная клавиатура не нужна — системная, цифровой тип ввода для количеств и сумм.
- Ошибки — человеческим языком + что делать («Нет интернета — продажа сохранена, отправится сама»).
- Подтверждение денег всегда: «Принять 12 500 сом наличными от "Магазин Айгуль"?».

## 13. Нефункциональные требования
| Тема | Требование |
|---|---|
| Шифрование офлайн-данных | база drift шифруется (SQLCipher; **новая зависимость — согласовать с владельцем**); ключ в Android Keystore через `flutter_secure_storage`; фото/подписи — в приватной папке приложения |

| Приватность геоданных | координаты только в визитах (по умолчанию); трек — по согласию (9.4); хранение 90 дней; агент видит, что о нём хранится |
| Аудит | журнал действий на сервере: кто, когда, с какого устройства, координаты (если есть): продажи, отмены, скидки выше нормы, одобрения, правки клиента, списания, сдача выручки, смена устройства |
| Надёжность | ни одной потери: запись в очередь до показа «Готово»; крах приложения в середине визита → восстановление визита и корзины |
| Производительность | старт ≤ 3 с на слабом телефоне (2 ГБ RAM); поиск товара ≤ 150 мс на 15 000 позиций; формирование PDF накладной ≤ 2 с; печать ≤ 5 с |
| Объём | 300 клиентов, 15 000 товаров, 90 дней истории — до 150 МБ базы |
| Совместимость | Android 8+ (P0), iOS — P2 |
| Время | все даты ISO 8601 со смещением (`+06:00`), сервер хранит UTC |

## 15. Что нужно от сервера (Умар)

### 15.1. Общие правила для всех новых методов
1. Префикс: `api/main/agents/…` (касса уже пробует `api/main/agents/me/products/` — оставить этот путь как часть API).
2. Заголовок `X-NurMarket-Client: agent/<версия>` — включает строгое поведение (как `mobile/…`).
3. **Все POST, меняющие данные, — с `Idempotency-Key`**; повтор с тем же ключом и тем же телом → тот же ответ + `replayed:true`; **с другим телом → 409 `idempotency_conflict`** (хэш тела).
4. Офлайн-поля в каждой записи: `local_id` (UUID с телефона), `device_time` (ISO со смещением), `device_id`, `lat/lng/accuracy` (если есть). Сервер хранит и `device_time`, и `server_time`.
5. Ссылки на ещё не созданные объекты: `client_local_id`, `visit_local_id`, `order_local_id` — сервер находит по `local_id` того же устройства.
6. Формат ошибок — как сейчас: `{detail, code, errors[{index, field, code}], data}`; `code` **всегда строка** (сейчас иногда список — исправить).
7. Фильтрация по `agent_scope` **на сервере** во всех выдачах (клиенты, долги, чеки, `changes`, WebSocket).
8. `GET api/main/capabilities/` → `features` += `agents_v1`, `agent_orders`, `agent_visits`, `agent_handover`, `price_lists`, `agent_kpi`.
9. Пагинация `{count, next, results}`, `ETag`/304 на справочниках (клиенты агента, прайс-листы, маршруты).
10. Деньги — строкой с 2 знаками (`"1250.00"`), количества — строкой до 3 знаков.

- Флаги из 2.1 в `users/profile/`, `employees`, `roles/custom` (чтение/запись).

### 15.7. Бизнес-правила, которые сервер проверяет сам
1. Агент продаёт только со своего склада, в свою кассу, своим клиентам (по `agent_scope`).
2. Срок долга — из условий клиента; график рассрочки — по настройке клиента.
3. Офлайн-продажа (`offline:true`) никогда не отклоняется из-за цены/лимита/остатка — только флаги и `agent_alert`.
4. Скидка ≤ лимита агента или есть одобрение (`approval`).
5. Номер документа уникален; при занятом номере из пула — 409 `doc_number_taken` (не должно случаться).
6. Сдача выручки закрывает смену агента только после `accepted`.
7. Все действия — в журнал аудита с `device_id`.
8. При отзыве устройства — отзыв refresh-токенов.

1. Профиль агента, флаги, роль-шаблон, `agent_scope`, устройства (нед. 1–2).
2. Новые поля клиента + `agents/me/clients/` + `bootstrap/` (нед. 1–2).
3. Склад типа `agent` и перемещения с приёмом — по [ТЗ-Склад] (нед. 2–4).
4. Расширение `pos/checkout/` (`source:"agent"`, склад, визит, номер, срок по условиям, офлайн-флаги, сравнение тела при повторе) + пул номеров (нед. 2–4).
5. `agents/orders/` со статусами и резервом (нед. 3–5).

7. Маршруты, визиты, медиа (нед. 4–6).

Решение по умолчанию: **режим «Агент» в том же приложении NurMarketMobile** (общие очередь, каталог, печать, PDF, ИИ, 5 языков) — вход по роли: у кого `can_use_agent_app`, открывается оболочка агента. Отдельный APK/ярлык — по решению владельца (вопрос 1).

### 16.2. Модули (`lib/features/agent/…`)

### 16.3. Карта экранов
```
Вход (пароль) → Регистрация устройства → PIN
Мой день ─┬─ Начать день (смена + приём загрузки)
          ├─ Следующая точка → ВИЗИТ: Чек-ин → Фото → [Заказ | Продажа | Оплата долга | Возврат | Задачи | Заметка] → Подпись/Печать → Чек-аут (причина)
          ├─ Маршрут (список / открыть в картах / порядок)
          └─ Конец дня → Пересчёт машины → Сдача выручки → Закрыть смену
Клиенты → Карточка (контакты, карта, долг, лимит, условия, история, «обычно берёт», заметки, задачи) → Новая точка
Каталог (цены клиента или базовые) → Корзина
Машина → Остатки · Загрузки · Возвраты · Списания · Ревизии
Деньги → Касса агента · Оплаты · Долги моих клиентов · Расходы · Сдачи
KPI → День · Месяц · Бонус
Ещё → Синхронизация (очередь, «Не принято»), Настройки (язык, тема, шрифт, слабый телефон, принтер), Нур Советник
Супервайзер → Команда (реальное время) · Отклонения · Одобрения · Маршруты · Рейтинг
```

### 16.5. Очередь
- Новые `kind` (8.2), зависимости через `dependsOn`, переписывание `local_id → server id` после ответа.
- Отправка пачкой через `sync/batch` (до 50), откат на поштучную отправку, если в `capabilities` нет `agents_v1`.
- Медиа отдельно, после записи-владельца; запись не ждёт фото (ссылка добавляется PATCH-ем).
- Экран «Синхронизация»: отправлено/в очереди/«Не принято» с причиной, «Данные от ЧЧ:ММ», кнопка «Отправить сейчас».

### 16.6. Новые зависимости (согласовать с владельцем — правило 4)
`geolocator` (P0), `sqlcipher_flutter_libs` + шифрованный drift (P0/P1), `local_auth` (биометрия, P1), `flutter_map` + тайлы OSM (P1, если нужна карта внутри), `record` (голосовые заметки, P1). Подпись, оптимизация маршрута, PDF, печать — без новых библиотек.

### 16.7. Тесты
- Модульные (на фикстурах, **без боевой базы**): расчёт цены клиента, офлайн-лимит долга, баланс машины (загрузка − продажи − возвраты ± списания), касса агента, очередь (ключи, повтор, `idempotency_conflict`, зависимости, переписывание `local_id`), пул номеров, геозона.
- Виджет-тесты: мастер визита, корзина, сдача выручки.
- Сценарии «конец дня»: 40 визитов офлайн → включить сеть → всё принято, остатки и деньги сходятся.
- Живая проверка — на тестовом аккаунте NBS (агент + супервайзер + кладовщик), слабый телефон 2 ГБ RAM, принтер BT 58 мм.

### 17.2. Критерии приёмки MVP
1. 40 визитов за день **без интернета**: продажи, оплаты, долги, возвраты, накладные, печать работают; при появлении сети всё уходит за ≤ 2 мин, **0 потерь и 0 дублей** (проверка: повторная отправка той же очереди не создаёт новых чеков).
2. Вечером: остаток машины на телефоне = остаток склада агента на сервере = загрузка − продажи − возвраты ± списания; выручка к сдаче = сумма оплат в кассе агента; акт приёма-сдачи подписан и печатается.
3. Агент не видит чужих клиентов и не может продать с чужого склада — **проверено запросами к серверу**, не только интерфейсом.
4. Продажа в долг выше лимита онлайн отклоняется (`debt_limit_exceeded`), офлайн принимается с флагом, супервайзер видит оповещение ≤ 5 с после синхронизации.
5. Чек-ин вне геозоны и поддельный GPS помечаются и видны супервайзеру.
6. Отзыв устройства → на следующем запросе данные стёрты, вход невозможен.
7. Заявка проходит путь «отправлена → принята → собрана → отгружена → доставлена», агент видит статус.
8. Все новые надписи на 5 языках; накладная — ru/ky; тёмная тема и крупный шрифт читаемы (контраст ≥ 4,5:1).
9. На телефоне 2 ГБ RAM: старт ≤ 3 с, заказ на 10 позиций ≤ 90 с, расход батареи за 10 ч ≤ 25 %.

### 17.3. Риски
| Риск | Мера |
|---|---|
| Сервер не успевает к А2–А3 | приоритет 15.8; обходной путь на пилот: склад-машина = отдельный филиал (лимит 3 филиала!) — только для 1–2 агентов; заявки — через `showcase/orders/` |
| Двойные продажи из-за повтора с другим телом | сравнение хэша тела на сервере (15.1 п. 3) — блокер приёмки |
| Расхождение остатков машины после офлайна | один владелец склада (агент), правка остатка машины только через документы, `negative_stock` алерт |
| Юридическая сила накладной/номера | пул номеров от сервера; форма накладной согласовать с бухгалтером клиента (вопрос 5) |
| Слабые телефоны и батарея | режим слабого телефона, GPS только в визитах, `--split-per-abi`, исправления отчёта оптимизации до пилота |
| Утечка ключей ИИ с телефонов агентов | ИИ для агентов — после прокси на сервере (А6) |
| Приватность геоданных | трек выключен по умолчанию, согласие, срок хранения |
| Смешение со складским ТЗ | все складские сущности — только по «ТЗ Склад 10 из 10 (30.10.2026)», здесь только тип `agent` и приём получателем |
| Карты в КР (2GIS популярнее Google) | MVP — открытие внешнего приложения на выбор агента |

## 18. Вопросы к владельцу (топ-10)
1. **Отдельное приложение или режим в NurMarketMobile?** (рекомендуем режим + отдельный ярлык «NurCRM Агент»).
2. **Схема работы**: продажа с машины, заявки на склад или обе? Есть ли водитель-экспедитор отдельно от агента?
3. **Цены**: в MVP хватит «розница/опт + скидка клиента %», или прайс-листы нужны сразу?
4. **Документ при отгрузке**: какая форма накладной/реализации нужна клиентам, нужна ли нумерация «как у бухгалтерии» и ЭСФ из машины?
5. **Долги**: может ли агент продавать в долг сам в пределах лимита, или каждый долг одобряет супервайзер?
6. **Сдача выручки**: кому агент сдаёт деньги (кассир в кассе / бухгалтер / супервайзер), можно ли тратить из выручки (топливо), удерживать ли недостачу из зарплаты?
7. **Карты**: 2GIS, Яндекс или Google; нужна ли карта внутри приложения в MVP?
8. **Геотрек весь день** нужен (с согласием) или хватит координат визитов?
9. **Бонусы агентов**: % от отгрузки, от оплаченного или от маржи; штрафы за просроченную дебиторку?
10. **Пилот**: какой клиент, сколько агентов и машин, какие телефоны и принтеры; разрешаете ли новые библиотеки (GPS, шифрование базы) и ИИ для агентов сверх лимита «2 сотрудника»?
