## 7. Пункт 9: сжатие Brotli и Gzip

**Вердикт: применимо, в основном уже сделано.**

### 7.1. Проверка `app.nurcrm.kg` через curl (05.11, без входа)

- `GET /` → 302 на `https://nurcrm.kg/`. Страница отдаётся с `Content-Encoding: br` (920 байт), с `gzip` (1042 байта) или без сжатия (2370 байт).
- `GET /api/schema/` (404, JSON) с `Accept-Encoding: br, gzip` → **`Content-Encoding: br`**. Значит, ответы API за Cloudflare сжимаются brotli.
- `GET /api/main/products/list/` без токена → 401, 109 байт, без сжатия: слишком маленький ответ, это нормально.
- Во всех ответах `Server: cloudflare`, `cf-cache-status: DYNAMIC`, `alt-svc: h3`.

### 7.2. Наши клиенты

- **Касса, NurCRM:** `SocketsHttpHandler { AutomaticDecompression = DecompressionMethods.All }` (`NurMarketApiClient.cs:84-86`). Клиент сам отправляет `Accept-Encoding: gzip, deflate, br`. Комментарий `:76-77`: страница каталога 155 КБ сжимается до 18 КБ. Второй клиент NurCRM (долги) настроен так же: `Api/ClientDebtsApiService.cs:283`. **Сделано.**
- **Касса, внешние клиенты:** **ни в одном** нет `AutomaticDecompression`: Gemini, Groq, GitHub, OFF, DuckDuckGo, Яндекс, Telegram, миниатюры, реестр ключей. Без этого `Accept-Encoding` не отправляется и ответы приходят несжатыми. Заметно для JSON Gemini (длинные ответы), списков выпусков GitHub (`per_page=30` с вложениями) и HTML DuckDuckGo и Яндекса. Для картинок пользы нет: они уже сжаты.

  **План Н-19 (S, риск низкий):** одна фабрика `ExternalHttp.Create(TimeSpan timeout)` с `SocketsHttpHandler { AutomaticDecompression = All, PooledConnectionLifetime = 15 мин }`. Ей заменить статические клиенты и три `new HttpClient()` из Н-16. `PooledConnectionLifetime` нужен, чтобы долгоживущие клиенты замечали смену DNS.
- **Мобилка:** свой адаптер и `Accept-Encoding` не заданы, поэтому работает обычный `dart:io HttpClient`. У него `autoUncompress = true`, gzip отправляется и распаковывается сам. Brotli `dart:io` не умеет; gzip для нас достаточно. **Сделано.**

### 7.3. Свои серверы

- **NurSupportBot**: HTTP-сервера нет, сжатие ответов **не применимо**. Его исходящие запросы к Telegram и NurCRM без автораспаковки (`TgClient.cs:22`, `NurCrmClient.cs:29`). Ответы маленькие, можно не трогать.
- **NurRemoteSupport**: `ResponseCompression` нет. Через Caddy включено только `encode gzip` (`NurRemoteSupport/deploy/Caddyfile:16`). В nginx-конфиге `deploy/nginx-support.nurcrm.kg.conf` нет директив gzip и brotli. Основной трафик — WebSocket с картинками экрана, которые уже сжаты, так что сжатие HTTP почти ничего не даст. **Почти не применимо.** Если править: Б-5 (S) — `encode zstd gzip` в Caddy и `gzip on; gzip_types application/json;` для `/api` в nginx.

## 10. Вопросы к Умару (для ТЗ)

1. **Каталог `products/list/`**: можно ли поднять потолок страницы со 100 до 500, как у ленты `products/changes/`? Это 31 запрос вместо 155 при полной загрузке. И какой максимум `page_size` у каждого списочного адреса: клиенты, должники, `pos/sales`, закупки?
2. **Итоги на сервере вместо скачивания чеков:** сумма скидок, выручка, число чеков и возвраты за период одним ответом. Сейчас касса качает до 150 000 чеков (`AnalyticsReportData.cs:283-287`).
3. **Лента изменений `updated_since` или курсор с ETag для клиентов и должников**, по образцу `products/changes/`. Тогда касса и мобилка не будут каждый раз перекачивать весь список.
4. **Поиск клиентов** `clients/?search=…&page_size=20`: гарантирован ли поиск по телефону и имени на сервере? Тогда окно выбора клиента не будет грузить всех.
5. **ETag и 304** для `users/company/`, настроек компании (`app-settings`), `company/addons/`, списка касс. Их опрашивают каждые 30 с – 15 мин.
6. **Курсорные страницы для `pos/sales/`** (стабильные при вставках). Сейчас при сдвиге страниц бывают повторы, касса чистит их по id.
7. **Фото товаров:** отдаёт ли Cloudflare медиа из кэша (`Cache-Control`, ожидаемо `cf-cache-status: HIT`) и есть ли уменьшенные миниатюры (`?w=200`)? Касса и мобилка показывают плитки размером около 100–200 px.
8. **Частота запросов:** какое ограничение на пользователя (сколько в секунду или минуту)? Нужно знать, сколько параллельных запросов безопасно (раздел 8.1).
