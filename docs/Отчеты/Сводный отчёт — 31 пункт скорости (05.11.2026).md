## 1. Резюме

**Подходит (10 из 31):** п. 2 (касса), 3, 5, 8, 9, 11, 12, 17, 22, 26. **Частично (16):** 1, 4, 7, 13, 15, 16, 18, 19, 23, 24, 25, 27, 28, 29, 30, 31. **Не подходит (5):** 6, 10, 14, 20, 21. Многое из «веба» у нас уже сделано: сжатие br/gzip, паузы поиска, ETag/304 у ленты каталога, страницы по 50 плиток, кэш фото в мобилке, индикатор «Ждём ответ сервера».

**Главные выгоды (по убыванию пользы к риску):**
1. **Размер установки −80…115 МБ в папке, ≈ −30…45 МБ в Setup** (п. 11, 22): метапакет `NAudio` тянет весь WPF/WinForms (≈87 МБ), плюс Octokit, linq2db+Npgsql, файлы QuestPDF. Это смена зависимостей, нужен ОК.
2. **Миниатюры товаров** (п. 15): кэш хранит оригиналы (195 файлов, 15,2 МБ, до 6022 px), после 320 px WebP — 2,2 МБ (−86 %); декодирование идёт в потоке интерфейса.
3. **Запросы к серверу** (п. 3): список клиентов качается из 10 мест без кэша (до 6000 клиентов при каждом открытии выбора); сводка владельца каждые 30 с (14–16 запросов в минуту, можно ~6–8); каталог без курсора 91–181 с против ~16–19 с лентой по 500.
4. **База** (п. 8, 17): приход 50 строк 41–48 мс → 1,6 мс; избранное 15 мс → 0,014 мс при каждом обновлении каталога; `LoadKnownSaleIds` у большого магазина 3 с → 0,24 с (правка кода, схема не меняется).
5. **Картинки в установщике** (п. 2): WebP ≈ −15 МБ (−8 % Setup, −13 % APK кассы).
6. **Ошибки сроков и безопасность** (п. 12, 6): токен NurCRM уходит на чужие хосты картинок (Н-9); исключение срока ломает ответ Советника (Н-13); дубли `sendMessage` в Telegram (Н-14); ключ активации «сгорает» при таймауте (Н-17).

**Не делать:** Redis, CDN, SSR, OpenTelemetry-пакеты, AVIF, оптимистичное обновление денег и остатков, лишние индексы.
