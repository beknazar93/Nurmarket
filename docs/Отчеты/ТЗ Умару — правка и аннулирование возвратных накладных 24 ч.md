# ТЗ Умару — правка и аннулирование возвратных накладных в течение 24 часов (10.11.2026)

**Статус контракта: ПРЕДЛОЖЕН НАМИ (касса NurCRM), сервером НЕ подтверждён.** Касса уже умеет работать по этому контракту (за признаками сервера, см. п. 1); пока признаков нет — у кассы всё как сегодня. Если вам удобнее другие имена полей/адресов — напишите, поправим кассу; важны смысл и гарантии (пп. 5–8).

Два документа: **«Возврат от клиента»** (сегодня `POST api/main/pos/sales/{id}/return/`, список `GET api/main/pos/returns/`) и **«Возврат поставщику»** (сегодня `POST api/main/suppliers/{id}/returns/`, `GET api/main/suppliers/returns/`, `GET api/main/suppliers/returns/{id}/`). Оба проводятся сразу при создании (черновика нет), поэтому «закрытие документа» = момент проведения.

Главный приоритет — **корректность склада и денег**: никакого двойного списания/поступления, всё в одной транзакции.

## 1. Признаки в `GET api/main/capabilities/`

| Признак | Что включает в кассе |
|---|---|
| `supplier_return_edit_24h` | кнопки «Редактировать», «Удалить», «История» у возврата поставщику |
| `pos_return_edit_24h` | то же у возврата от клиента |

Объявлять признак — только когда для этого типа готовы ВСЕ пункты 2–8 (поля, PIN-токен, PATCH, void, history, PDF-метка не нужна — её рисует касса).

## 2. Поля документа (в строке списка И в карточке)

Добавить к ответам `GET …/returns/` и `GET …/returns/{id}/` (оба типа):

| Поле | Тип | Смысл |
|---|---|---|
| `version` | int ≥ 1 | версия документа; растёт на 1 при каждой правке/аннулировании |
| `status` | `posted` / `voided` | проведён / аннулирован |
| `closed_at` | ISO-8601 с поясом | момент проведения (с него считаются 24 ч) |
| `editable_until` | ISO-8601 | `closed_at + 24 ч` — считает сервер |
| `server_now` | ISO-8601 | время сервера в момент ответа (касса по нему пишет «осталось N ч», решений по часам устройства не принимает) |
| `can_edit` | bool | **для этого пользователя прямо сейчас**: не аннулирован, срок не вышел, нет запрета (см. п. 6) |
| `can_void` | bool | то же для аннулирования |
| `edit_block_reason` | string / null | код, почему нельзя (`edit_window_expired`, `already_voided`, `has_later_documents`, `period_closed`, `permission_denied`) |
| `voided_at`, `voided_by_name`, `void_reason`, `void_approved_by_name` | | у аннулированного |
| `edited_at`, `edited_by_name`, `edit_count` | | последняя правка |

Строки (`items`): обязательно `id` (строка документа), `product_id`, у возврата поставщику — `qty`, `purchase_price`, `discount` (сумма скидки строки), `note`, `line_total`; у возврата от клиента — `sale_item_id`, `quantity`, `price`, `discount`, `note`, `line_total`. Уровень документа: `comment`/`note`, `total_amount`/`amount`.

Аннулированные документы физически не удаляются (soft delete, `status: voided`). **Важно для старых версий кассы у клиентов:** по умолчанию (без параметра) списки `GET …/returns/` отдают только действующие (`posted`) — иначе старые кассы посчитают аннулированные возвраты в итогах смены/«Финансов». Новая касса просит `?status=all` там, где показывает метку «АННУЛИРОВАН»; итоги (`meta.total_amount`) всегда без аннулированных. Карточка `GET …/returns/{id}/` отдаёт документ в любом статусе.

## 3. Подтверждение PIN руководителя — одноразовый токен

Используем уже существующий `POST api/users/auth/pin/verify/` (он у вас есть: `{pin} → {token, expires_in}`, 400 `pin_invalid` + `attempts_left`, 429 `pin_locked` + `retry_after`). Нужно **расширить** тело полями области:

```json
POST api/users/auth/pin/verify/
{ "pin": "1234", "scope": "return_edit",           // или "return_void"
  "object_type": "supplier_return",                // или "pos_return"
  "object_id": "uuid-документа", "version": 3 }
→ 200 { "confirm_token": "…", "expires_in": 120, "scope": "return_edit",
        "object_id": "…", "approved_by_name": "Айбек (владелец)",
        "server_now": "…", "editable_until": "…" }
```

Правила:
- PIN проверяется **только на сервере**; хранить только хэш (bcrypt/argon2, соль), в открытом виде нигде, в журналы не писать.
- Чей PIN: любого активного пользователя компании с ролью `owner`/`admin` (или с правом `can_approve_return_edit`); кто подтвердил — пишется в аудит (`approved_by`).
- Токен **одноразовый** (гасится первым же PATCH/void, даже неуспешным по существу, кроме 5xx), живёт ≤ 120 с, привязан к `user` (кто нажал), `scope`, `object_type`, `object_id`, `version`. Чужой scope/документ/версия → 403 `confirm_invalid`.
- Лимит: 5 неверных PIN подряд на пользователя-компанию → 429 `pin_locked` + `retry_after` (сек) на 15 мин; ответ 400 `pin_invalid` всегда с `attempts_left`.
- Уже при выдаче токена проверить срок и статус: 409 `edit_window_expired` / `already_voided`, 412 `version_conflict` + `current_version` — чтобы не просить PIN зря.
- Нет PIN у руководителя → 400 `pin_not_set`.

## 4. Правка — `PATCH`

```
PATCH api/main/suppliers/returns/{id}/        (возврат поставщику)
PATCH api/main/pos/returns/{id}/              (возврат от клиента)
Заголовки: Idempotency-Key: <uuid>   If-Match: "3"   X-Confirm-Token: <confirm_token>
```

Тело — **полный новый состав** (строки, которых нет, — удалены; строки без `id` — новые, если вы это разрешаете; иначе 400 `new_lines_not_allowed`):

```json
{ "version": 3, "edit_reason": "ошиблись количеством (от 5 до 500 знаков)",
  "comment": "…",
  "items": [ { "id": "line-1", "product_id": "…", "qty": "2", "purchase_price": "150.00",
               "discount": "0.00", "note": "" } ] }
```
У `pos_return` в строке: `id`, `sale_item_id`, `quantity`, `price`, `discount`, `note`. Тип компенсации (`compensation`, касса денег, приход-основание, чек-основание, поставщик/клиент) **в этой версии не меняются** — для этого аннулировать и оформить заново.

Ответ 200 — документ целиком (новая `version`, пересчитанный `total_amount`, `can_edit`…). Повтор тем же `Idempotency-Key` → тот же ответ + `"replayed": true`.

## 5. Аннулирование — `POST …/void/`

```
POST api/main/suppliers/returns/{id}/void/
POST api/main/pos/returns/{id}/void/
Заголовки: Idempotency-Key, If-Match: "3", X-Confirm-Token (scope = return_void)
Тело: { "version": 3, "reason": "от 5 до 500 знаков" }
→ 200 документ со status: voided
```
Физически ничего не удалять (soft delete): `status=voided`, `voided_at`, `voided_by`, `void_approved_by`, `void_reason`.

## 6. Срок 24 часа — только время сервера

- `editable_until = closed_at + 24 ч`. Проверять **на сервере** трижды: при выдаче токена, в начале транзакции PATCH/void (после блокировки строки документа) и не доверять ничему от клиента.
- Истёк → 409 `edit_window_expired` + `editable_until`, `server_now`.
- Дополнительно запрещать (409 с кодом), если: документ `voided` (`already_voided`); закрыт период/смена (`period_closed`, `shift_closed` — если у вас есть закрытие периода); у возврата от клиента — по чеку после этого возврата был следующий возврат/обмен (`has_later_documents`) — чтобы не ломать цепочку «сколько ещё можно вернуть»; у возврата поставщику — `debt_offset` уже частично зачтён оплатой (`debt_already_paid`), если пересчёт долга невозможен.

## 7. Склад и деньги — пересчёт (одна транзакция, `SELECT … FOR UPDATE`)

Принцип: **сторно старых движений + проведение новых** (не «дельта на глаз»), в одной транзакции с изменением документа; движения связаны с документом и версией (`return_id`, `version`), поэтому повтор/гонка не может провести дважды.

| Документ | Правка | Аннулирование |
|---|---|---|
| Возврат от клиента | сторно: −поступление старых строк на склад, −выплата/−уменьшение долга по старой сумме; затем новые: +поступление новых строк, новая выплата/уменьшение долга. Количество по строке ≤ «можно вернуть» по чеку без учёта этого возврата (иначе 409 `exceeds_returnable`). Сумма выплаты ≤ оплачено (409 `refund_exceeds_paid`). | товар снова списывается со склада (отмена поступления), деньги: кассе — сторно выплаты (`cashflow` обратного знака в ту же кассу и смену/период аннулирования), долг клиента — восстанавливается на сумму `debt_adjustment`. Если остатка не хватает — 409 `negative_stock` (или разрешить минус по настройке компании — скажите, как у вас). |
| Возврат поставщику | сторно: +возврат на склад старого количества, сторно компенсации (cash — минус поступление в кассу; debt_offset — долг поставщику обратно +); затем новые: −списание нового количества, новая компенсация. Количество ≤ «можно вернуть» по приходу (`returnable_qty`) без учёта этого возврата; остатка должно хватить на увеличение — иначе 409 `negative_stock` / `exceeds_returnable`. | списанное количество возвращается на склад; компенсация сторнируется (cash — расход из кассы обратно / debt_offset — долг поставщику увеличивается обратно). |

Общее:
- `returned_qty`/`returned_amount` у чека/прихода пересчитываются; статус чека (`partially_returned`/`returned`/`canceled`) — тоже (см. наш вопрос от 06.11 про частичный возврат долгового чека — та же логика должна работать и при правке).
- Себестоимость, отчёты смены и «Финансы» берут актуальную версию; аннулированный документ в суммах = 0.
- Ошибка на любом шаге — откат всего; 5xx не должен оставлять половину движений (у частичного возврата долгового чека 06.11 было именно так — это критично).
- Одновременная правка: `If-Match`/`version` обязательны (нет — 428 `version_required` + `current_version`); устарела — 412 `version_conflict` + `current_version`, ничего не изменено.

## 8. Журнал аудита и история

Таблица аудита (отдельно от документа, только добавление): `id, company, object_type, object_id, number, version_before, version_after, action (created|edited|voided), snapshot_before (JSON всего документа), snapshot_after, diff, reason, created_by, performed_by, approved_by (кто ввёл PIN), device_id/IP, at (время сервера)`.

```
GET api/main/suppliers/returns/{id}/history/
GET api/main/pos/returns/{id}/history/
→ 200 [ { "version": 1, "action": "created", "at": "…", "user_name": "Кассир", "approved_by_name": null,
          "reason": "", "total": "300.00", "snapshot": { …документ v1 целиком… }, "diff": [ … ] },
        { "version": 2, "action": "edited", "at": "…", "user_name": "Кассир", "approved_by_name": "Айбек",
          "reason": "ошиблись количеством", "total": "150.00", "snapshot": { … v2 … },
          "diff": [ { "line_id": "line-1", "field": "qty", "old": "2", "new": "1" } ] },
        { "version": 3, "action": "voided", … } ]
```
Доступ — только `owner`/`admin` (или право `can_view_audit`); остальным 403 `permission_denied`. Первоначальная версия (v1) всегда доступна через `snapshot` — касса показывает её в окне «История».

| HTTP | `code` | Когда | Доп. поля |
|---|---|---|---|
| 400 | `pin_invalid` | неверный PIN | `attempts_left` |
| 400 | `pin_not_set` | у руководителя не задан PIN | |
| 429 | `pin_locked` | лимит неверных PIN | `retry_after` (сек) |
| 428 | `confirm_required` | PATCH/void без `X-Confirm-Token` | |
| 403 | `confirm_invalid` | токен истёк/использован/другой документ/scope/версия | |
| 403 | `permission_denied` | нет прав на действие/историю | |
| 409 | `edit_window_expired` | прошло 24 ч | `editable_until`, `server_now` |

## 10. PDF/Excel

Документы касса строит сама по ответу сервера (актуальная версия). У `status: voided` касса пишет «АННУЛИРОВАН» в заголовке и строку «Статус: аннулирован дата, причина». Если у вас есть свои печатные формы на сайте — та же метка и данные последней версии; первоначальная версия — из `history[].snapshot`.

## 11. Тесты приёмки (на стенде, касса + сервер)

1. Правка в пределах 24 ч: возврат поставщику 2 шт × 150 → правка на 1 шт; остаток товара +1, долг поставщику/касса скорректированы на 150, `version` 1→2, история с v1 и v2.
2. Аннулирование в 24 ч: возврат от клиента 1 шт (наличные 100) → void; остаток −1, в кассе сторно −100 (возврат от клиента) обратно, чек снова «без возврата», `status: voided`, в списке есть с меткой, итоги без него.
3. Блокировка после 24 ч: `closed_at` 25 ч назад (подмена времени сервера на стенде) → `can_edit:false`, PIN-токен 409 `edit_window_expired`, PATCH с ранее выданным токеном 409 (повторная проверка в транзакции). Часы ПК вперёд/назад на результат не влияют.
4. Неверный PIN: 400 `pin_invalid` с `attempts_left` 4…0, затем 429 `pin_locked`; верный PIN во время блокировки — тоже 429.
5. Пересчёт остатков и финансов: сверка остатков, `cashflows`, долга клиента/поставщика до/после правки и аннулирования (полный и частичный возврат, долговой чек, `debt_offset`).
6. Без двойного проведения: повтор PATCH/void тем же `Idempotency-Key` (в т. ч. после обрыва) → `replayed`, движения одни; повтор с новым ключом и старым токеном → 403 `confirm_invalid`; void уже аннулированного → 409 `already_voided`.
7. История: 3 версии, `snapshot` v1 совпадает с исходным документом; кассир без прав → 403.
8. PDF/Excel: после правки — новые цифры; у аннулированного — метка.
9. Одновременное редактирование: два устройства берут v3, первое сохраняет (v4), второе → 412 `version_conflict` + `current_version: 4`, ничего не изменено.
10. Нагрузка: 20 параллельных void одного документа → проведён один, остальные 409/412, остаток изменился один раз.

## 12. Риски для учёта (просим учесть)

- Аннулирование возврата от клиента, когда товар уже продан снова, уводит остаток в минус — нужен ответ `negative_stock` или явная политика.
- Возврат денег клиенту наличными уже ушёл из кассы: аннулирование не вернёт деньги физически — сторно-проводка должна попасть в текущую смену/период как отдельная операция, а не переписывать закрытую смену.
- Правка возврата поставщику с `debt_offset` после частичной оплаты долга — однозначное правило пересчёта или запрет `debt_already_paid`.
- Цепочки: правка возврата, после которого был ещё один возврат по тому же чеку/приходу, — запрещать (`has_later_documents`) либо пересчитывать «можно вернуть» по всей цепочке.
- Частичный возврат долгового чека сейчас уже работает с ошибкой (наш вопрос 06.11) — правка поверх него унаследует ошибку; сначала закрыть тот вопрос.
