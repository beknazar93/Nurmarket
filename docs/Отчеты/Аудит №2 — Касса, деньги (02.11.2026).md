### Расчёт суммы чека против правил сервера (проверено по формулам)

- Правило сервера (сверка контракта, раздел 8): `подытог = FLOOR(Σ весовых, 0,01) + HALF_UP(Σ остальных, 0,01)`; база = подытог − скидки строк; скидка чека % = HALF_UP(база × p / 100); итог = база − скидка.
- `CartTotalsCalculator.Calculate` (`:48-78`): весовые и остальные копятся отдельно в `decimal` без округления строк; `QuantityRules.Subtotal` (`:142-143`); база процента — округлённый подытог минус скидки строк (`:74`); скидка процентом округляется отдельно (`:75`, `:150-151`). Совпадает.

- `CheckoutViewModel.RecalculateTotals` / `ComputeOrderDiscountAmount` (`:1156-1222`): процент от округлённой базы; бонусы уходят одной суммой `order_discount_total` (`:1110-1122`), итог считается от неё же (`:1169-1172`). Сдача — от округлённого итога (`CartTotalsCalculator.cs:93-94`).

## 3. Находки аудита №2

### Средние

**К3-01 · СРЕДНЯЯ (ПЛАУЗИБЛЬНО) · деньги, надёжность файлов. «Файл занят» читается как «пусто», и следующая запись затирает данные — в четырёх хранилищах из перевода на `AtomicFile`.**
- Почему возможно: `AtomicFile.ReadAllText` при «файл занят» (антивирус, индексатор, синхронизация папки `%APPDATA%`) честно бросает `IOException` (`AtomicFile.cs:86-90`). Но эти хранилища ловят исключение целиком, возвращают пустой список, а потом пишут поверх:
  1. **Поправки ящика смены** — `ExchangeCashCorrections.cs:176-189` (`catch { return new List<Entry>(); }`), запись — `:89-98`, `:109-117`, `:138-146`. Сценарий: после возврата долгового чека касса пишет поправку −2,00, а файл в эту секунду держит антивирус. Список прочитан как пустой — в файле остаётся только новая поправка, все прежние поправки смены пропали. «Касса:», X-отчёт и сумма «ожидается» в Z завышены на их сумму, при закрытии — ложная недостача. Пока файл занят, `ForShift` отдаёт 0 (`:39-45`), и шапка, X-отчёт и окно закрытия (`MainWindow.axaml.cs:3867`) в эту секунду считают без поправок.
  2. **Отложенные чеки** — `DeferredCartsStore.cs:26-46` (catch-all), `Add` `:68-76`, `RemoveIds` `:101-106`: пропадают все отложенные чеки, кроме нового.
  3. **Состояние офлайн-смены** — `OfflinePosStateStore.cs:124-139` (catch-all → null), `SaveFromApp` `:54-68`. Вызывается часто: из каждого ответа списка смен (`ShiftStateService.cs:434-448`). При null теряются `OfflineOpeningCash`, `OriginOfflineShiftId` и владелец смены. Тогда офлайн-смену больше не передать серверу автоматически, а при закрытии переданной смены не проверяются её чеки под офлайн-id (они уйдут в следующую смену). Ещё одно: `Write` (`:144-155`) без повторов. Если он бросит исключение в `CloseLocallyAndQueue` (`CashShiftService.cs:915-920`), в файле останется закрытая смена. `RestoreToApp` (`:104-116`) потом вернёт её как текущую, а очередь закрытий (`SyncService`) её пропустит («смена активна»). Получается К2-01 обходным путём.
  4. **«Неясная оплата»** — `PendingUnknownCheckoutStore.cs:77-102`: занятый файл при запуске даёт null. Запись «в полёте» не восстанавливается, и повтор «Оплатить» уйдёт с новым ключом — возможна вторая продажа.
- Правильный образец уже есть в коде: `PendingDebtPrepaymentStore.cs:81-108` (флаг `_readBusy` запрещает запись), `ShiftCashOperationsStore.cs:304-325` (`forWrite`), `SaleReturnLedger.cs:313-346` (`readOk`).
- Как исправить: тот же приём в четырёх местах (занят → не писать и повторить позже; для `PendingUnknownCheckoutStore` — повтор чтения с паузой и запрет новой оплаты, пока запись не прочитана). `OfflinePosStateStore.Write` — `WriteAllTextWithRetry` в try. `RestoreToApp` не должен ставить смену, которая есть в `PendingShiftCloseStore`. ≈ 1 ч.

**К3-02 · СРЕДНЯЯ · деньги, обмен. После К2-03 кассир выдаёт деньги по расчёту кассы, а печатный чек обмена и журнал смены — по цифрам сервера.**
- Где: `ExchangeWindow.cs:518-522` (`PrintExchange(..., returned, newAmount, difference, ...)`, всё от сервера); `:509` (событие смены на сумму сервера `returned`); строки чека — по доле скидки (`UnitRefund`, `:518`).
- Сценарий: чек 100 со скидкой 10 % на весь чек (оплачено 90). Обмен на товар за 50. Кассир по окну выдаёт **40**, а на бумаге: строки на 90, «возвращено 100», «к выдаче 50». У покупателя на руках чек, по которому ему «недодали» 10 — спор на кассе. В Z строка «Возвраты» завышена на 10 (наличные при этом верны — по `cash=`).

Либо, пока сервер не учитывает скидку на чек, не оформлять обмен по таким чекам (возврат + новая продажа). ≈ 30 мин + одна живая проверка на NBS.

### Низкие

- **К3-03 · НИЗКАЯ (ПЛАУЗИБЛЬНО) · возврат.** После ограничения ожидания документа 3 с (К2-12, `ReturnSaleDialog.axaml.cs:1593-1605`) журнал чека записывает возврат без `ServerDocId`. При следующем частичном возврате того же чека `ServerReturnFiguresAsync` (`:1443-1448`) может принять этот прошлый документ за «самый новый, ещё не виденный», если новый сервер ещё не показал. Тогда сумма возврата урезается до старого документа (`:1615-1619`). Сервер назвал выдачу больше — цифра сервера отбрасывается, и кассир выдаёт меньше положенного (с предупреждением «проверьте»). Исправить: брать `refund.id` и `refund.amount` прямо из ответа на возврат (сервер их присылает, проверка бэкенда п. 7.3) и писать id в журнал; документ запрашивать только у старого сервера. Это же ускорит К2-12.
- **К3-04 · НИЗКАЯ (ПЛАУЗИБЛЬНО) · возврат долгового чека.** Если сервер не прислал `debt_adjustment`, выдача по `refund.cash` ограничена только суммой возврата (`ReturnSaleDialog.axaml.cs:1683-1689`), а не тем, что покупатель реально внёс. Сбой сервера `cash = 5` при внесённых 2 → кассир выдаст 5. Исправить: при известном остатке долга (`!local.DebtUnknown`) — `srvCash + srvNon ≤ local.Cash + local.NonCash + 0,01`, иначе расчёт кассы с предупреждением.
- **К3-05 · НИЗКАЯ · хвост Ф-6.** `SyncService.cs:778` пишет «старше 7 суток» для чека 1–7 суток; `:779` ставит `TooOldForServer = true`, и чек становится кандидатом «Провести по PIN» (`SyncService.LateAccept.cs:56`), хотя причина отказа другая. Исправить: `TooOldForServer` — только при возрасте больше 7 суток, текст журнала по возрасту.
- **К3-06 · НИЗКАЯ · скорость смен.** Каждый `RefreshAsync` («Новый чек» — `PosCheckoutService.cs:941`, опрос шапки, перед закрытием) при вчерашней смене в очереди закрытия пытается закрыть её на сервере и ждёт до 6 с (`ShiftStateService.cs:95-101`, `181-203`). Если сервер упорно не закрывает (`Failed`), запись остаётся, и задержка повторяется на каждом чеке. Исправить: не чаще раза в минуту (как `_lastCatchUpUtc`) и без ожидания (в фоне).
- **К3-10 · НИЗКАЯ · бонусы.** Окончательный отказ сервера (400 «Недостаточно бонусов», если баллы потратили на другой кассе) снимает операцию из очереди только с записью WARNING (`ServerLoyalty.cs:173-178`). Скидка бонусами выдана, а баллы не списаны — владелец не узнает. Очередь досылается только при следующей операции с баллами или при входе (`CompanyInfoService.cs:59`), таймера нет. Исправить: запись в «Некорректные чеки» при отказе `redeem`; досылка очереди раз в 1–2 минуты.
