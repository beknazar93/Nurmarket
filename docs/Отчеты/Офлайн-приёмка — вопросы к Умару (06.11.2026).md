# Офлайн-приёмка — вопросы к Умару (06.11.2026)

Задача владельца: приход, принятый без интернета, должен уйти на сервер «со старым временем» — когда его принимали, а не когда появилась связь.

## Что касса делает сегодня
- Время приёма (часы ПК плюс поправка `ServerClock`, запомненная в момент нажатия «Оприходовать») хранится в задаче очереди на диске. Перезапуск его не меняет.
- Сервер сам ставит `created_at` прихода (время получения запроса). Принять дату в `POST suppliers/{id}/receipt/` он пока не умеет: `OPTIONS` не отдаёт схему полей, в ответе Умара от 30.10 принимаются только `document_number` и `document_date` — это номер и дата накладной **поставщика**, а не время приёма. Подставлять туда время приёма нельзя, чтобы не затереть дату настоящей накладной.
- Поэтому касса отправляет приход как есть, а настоящее время кладёт в `comment` документа: «Принято 06.11.2026 14:32, отправлено после восстановления связи 15:10». Пометка считается один раз на ключ повтора, тело повторного запроса не меняется (иначе возможен `409 idempotency_conflict`).
- Локально время приёма пишется в историю закупок товара (`ProductPurchaseHistory.at`), в запись «Закупки» и в изъятие из ящика смены. В списке «Приходы в фоне» видны оба времени: «принят 14:32 · отправлен 15:10».

## Вопросы
1. **Дата прихода.** Какое поле принимает `POST /api/main/suppliers/{id}/receipt/`, чтобы `created_at` (и число в списке «Закупки», отчёты за день) было временем приёма? Предложение — как у офлайн-чека:
   ```json
   POST /api/main/suppliers/<id>/receipt/
   Idempotency-Key: <uuid>
   {
     "items": [{"product": "<id>", "qty": 2, "purchase_price": 10}],
     "payment_type": "debt",
     "idempotency_key": "<uuid>",
     "offline": true,
     "received_at": "2026-11-06T14:32:00+06:00"
   }
   ```
   Нужны: границы (сколько суток назад можно, как у `offline_too_old` — 7 суток?), ответ при закрытом периоде / закрытой смене (какой код, чтобы касса показала «Требует внимания», а не меняла дату на текущую молча), и что делается с долгом поставщику (дата долга = дата прихода?).
2. **Приход без поставщика** (сейчас касса пишет остаток `PATCH products/{id}/` — `quantity`, `purchase_price`, `price`). Есть ли способ записать приход с датой — например, документ прихода без поставщика или акт `stock-adjust` с `occurred_at`? Если нет — дата сохраняется только в локальной истории кассы.
3. **Оплата и расходы.** `payment_type=cash` и `cashbox_role/shift` пишут расход с временем получения запроса. Принять ли `received_at` и для расхода, и в какую смену он попадёт, если смена уже закрыта? Касса сейчас в такой ситуации отказывается писать изъятие из ящика и пишет «Требует внимания».
4. **Долг поставщику / `deals/pay-any/`.** Дата долга — по `created_at` прихода. Нужна дата прихода из п. 1 и в сделке долга.
5. **Журнал идемпотентности.** `GET idempotency/{ключ}/` для прихода от поставщика: отдаёт ли он `state` (`done` / `in_progress` / `failed`) и `receipt_id` в ответе? Касса при неизвестном исходе сверяется по этому ключу и не создаёт второй приход; сейчас без `receipt_id` ей приходится искать приход в списке.
6. **Доп. расходы (`extra_costs`) и себестоимость.** Касса пишет себестоимость отдельным `PATCH products/{id}/`. Принимает ли сервер дату у этого шага? (Если нет — в карточке «Последний приход» будет дата отправки.)

7. **`comment` в POST прихода (живой тест 06.11, Б-11).** Касса кладёт «№ ПР-…; Принято … отправлено после восстановления связи …» в поле `comment` тела `POST suppliers/{id}/receipt/` (тест кассы проверяет тело запроса). На сервере у офлайн-приходов ПР-…78–82 `comment` пустой. Сохраняет ли `POST` это поле вообще (`PATCH suppliers/receipts/{id}/` его принимает, в `GET` оно есть)? Если нет — просим принимать `comment` (или `note`) при создании прихода; пока касса отдельным `PATCH` комментарий не дописывает (нужны `reason`, `version`, `If-Match` — лишний шаг на каждый приход).
   Сторона кассы исправлена 06.11: пустая пометка «Принято…» больше не запоминается после первой неудачной попытки (раньше приход, дошедший через минуты, уходил с пустым комментарием).

Проверка выполнена только чтением (`OPTIONS`, `GET`, вход); записей на сервер не делалось.
