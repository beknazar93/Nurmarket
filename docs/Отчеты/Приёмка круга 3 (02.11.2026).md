## 2. Находки

### 1. Надёжность файлов (К3-01)

Что сделано верно:
- `AtomicFile.TryRead` различает три случая: «файла нет», «прочитан», «не прочитан».
- Если файл не прочитан, поверх него больше не пишется.
- `RestoreToApp` не возвращает текущей смену, которая стоит в очереди закрытия (`OfflinePosStateStore.cs:111`).
- `OfflinePosStateStore.Write` больше не бросает исключение.

**1.1 СРЕДНЯЯ (ПЛАУЗИБЛЬНО). Состояние офлайн-смены и журнал наценок теряют правки, сделанные, пока файл был занят.**
- Где: `OfflinePosStateStore.cs:148-152`, `Purchases/ReceiptMarkupLog.cs:162-164`, `:179-187`.
- Сценарий: кассир открывает смену без связи. В этот момент антивирус держит `offline_pos_state.json`. `RememberOfflineOpening` пишет сумму открытия только в память (`_lastKnown`).
- Через секунду файл свободен. Следующий `TryLoad` (а его вызывает каждый ответ списка смен) берёт из файла СТАРОЕ состояние и затирает им память (`_lastKnown = parsed`).
- Итог: сумма открытия (`OfflineOpeningCash`) и офлайн-id потеряны. Офлайн-смену больше не передать серверу автоматически, её чеки по офлайн-id не проверяются при закрытии.
- В `ReceiptMarkupLog` так же: когда файл снова читается, `_cache` с неотправленной правкой не используется.
- Отчёт исполнителя («уходят в файл при первом удачном чтении, без потери») для этих двух хранилищ не соответствует коду.
- Как исправить: при переходе «не прочитан → прочитан», если в памяти есть незаписанная правка, сначала записать её в файл и только потом брать файл.

**1.2 СРЕДНЯЯ. Записи, отложенные в память, уходят в файл только при следующей записи. При закрытии программы они пропадают.**
- Где: `ExchangeCashCorrections.cs:39-45` (`ForShift` не сбрасывает `_pendingMemory`), `:212-231`; `DeferredCartsStore.cs:61-85`; `RentalReceiptInfoStore`.
- Сценарий: при возврате долгового чека поправка ящика −2,00 попала в память (файл заняли на 200 мс).
- Следующих поправок в смене нет. Вечером кассир закрывает программу — поправка потеряна. «Касса:» и «ожидается» в Z завышены на 2,00, получается ложная недостача.
- Тост обещает «изменения держатся в памяти», но не предупреждает, что при выходе они пропадут.
- Как исправить:
  - сбрасывать отложенное в файл при первом удачном чтении (`ForShift`, `LoadAll`) и по таймеру;
  - при выходе из кассы — последняя попытка записи; не вышло — окно «данные не сохранены».

**1.3 НИЗКАЯ (ПЛАУЗИБЛЬНО). Удаление записи, пока файл занят, не сохраняется: удалённая запись возвращается.**
- Где: `DeferredCartsStore.cs:46-50` вместе с `RemoveIds` (`:127-132`); `ExchangeCashCorrections.cs:205-208` вместе с `RemoveDebtPrepay` (`:154-174`).
- Почему: отложенное в памяти сливается с файлом объединением по id, поэтому удаление пропадает.
- Сценарий: кассир вернул отложенный чек в работу и продал его. Антивирус держал файл при записи. После освобождения файла чек снова виден в «Отложенных» — его можно продать второй раз.
- То же с поправкой `debtprepay:`: она снята в файле, но осталась в копии `.bak`, и при слиянии возвращается.
- Как исправить: хранить в памяти не весь список, а журнал операций (добавить / удалить id) и применять его к файлу.

**1.4 НИЗКАЯ (ПЛАУЗИБЛЬНО). Пока файл занят, `TryRead` усыпляет поток окна кассы.**
- Где: `AtomicFile.cs:176`.
- Почему: в каждой попытке чтения `Thread.Sleep`, а читают и с потока окна:
  - `HasHeldReceipts` — проверка кнопки «Вернуть отложенный» (`BasketPanelViewModel.cs:206`, `:510`);
  - `ReadShiftCashBalance` в `MainWindow`;
  - `ForShift` при обновлении шапки.
- Сколько: до ~0,5 с (отложенные чеки), ~0,26 с (поправки) и ~1,1 с (неясная оплата) на один вызов.
- Плюс: каждая неудачная попытка пишет WARNING дважды (`:88` и `:179`).
- При долгой блокировке (облачная синхронизация `%APPDATA%`) окно подвисает.
- Как исправить: на потоке окна читать без повторов (1 попытка, копия `.bak`), повторы делать в фоне. Строку журнала писать одну на вызов.

**1.5 НИЗКАЯ. Неясная оплата: если файл занят 5 раз подряд при запуске, защита от второй продажи не работает.**
- Где: `PendingUnknownCheckoutStore.cs:77-117`.
- Исполнитель этот остаточный риск признал.
- Сценарий: касса упала посреди оплаты «в долг», а при запуске антивирус держит файл дольше ~1,1 с. Записи «в полёте» нет, следующее «Оплатить» уйдёт с новым ключом.
- Как исправить: «не прочитано, последней записи нет» → признак «проверьте Продажи перед первой оплатой» (вопрос кассиру один раз).

**1.6 НИЗКАЯ. Перемещения: при занятом файле запись теряется.**
- Где: `PendingTransferKeys.cs:39-45`, `:69-78`.
- Почему: при `_readFailed` метод `Data()` каждый раз отдаёт новый пустой словарь, и `Set()` пишет в него, то есть в никуда. Это хранилище в К3-01 не переводили.
- Риск: дубль перемещения (сервер ключ у `branch-transfers` не проверяет).

### 2. Обмен и возврат

Что проверено и верно:
- **К3-02.** Поправка ящика пишется один раз на обмен (ключ `exchange-overcredit:<id>`).
  - Знак проверен на трёх примерах: 100 −10 % → 50 даёт +10; 100 → 120 наличными даёт +10; разница со сменой знака даёт +10.
  - Печать, журнал смены и окно показывают одни цифры (`ours`, `payDifference`), цифра сервера стоит в примечании.
- **К3-04.** Ограничение «выдача не больше внесённого» работает только при известном долге. Иначе остаётся прежний путь с предупреждением.
- **К2-19.** «Вернуть весь чек» при неотправленном офлайн-возврате шлёт `Quantity` строки. Это остаток к возврату (свойство только для чтения), а не количество, выбранное кассиром. Строки без остатка в запрос не попадают.
- **К2-24.** Ключ «брак» отличается от обычного возврата. Ключ обычного возврата прежний, поэтому неясные возвраты прошлой версии повторяются тем же ключом.
- **К3-10.** Очередь бонусов разбирается под замком файла, запись снимается по ключу. Таймер раз в 90 с. Окончательный отказ сервера попадает в «Некорректные чеки».
- **Адрес `GET api/main/idempotency/{key}/` на сервере есть.**
  - Подтверждено проверкой бэкенда 01.11 (п. Б-10): `found:true, state:"done", status_code:200`.
  - Незнакомый ключ: 404 `found:false` (код `idempotency_key_not_found`).
  - Незнакомый адрес: 404 `route_not_found` без `found` → касса считает исход неизвестным и сверяет по чеку. Ложного «не прошёл» на старом сервере нет.

**2.1 СРЕДНЯЯ (ПЛАУЗИБЛЬНО). К2-09: «найден» принимается без проверки исхода операции.**
- Где: `SalesApiService.QuickCheckout.cs:91-94` и `ReturnSaleDialog.axaml.cs:2210-2223`.
- Почему: сервер отдаёт `state` и `status_code`, а касса смотрит только `found:true`.
- Сценарий: возврат получил отказ 409 «больше положенного» (возврат на другой кассе), но ответ не дошёл (обрыв). Ключ записан с исходом 409. Касса покажет «Сервер уже провёл этот возврат» с суммой к выдаче, вернёт товар в остаток и запишет возврат в смену. Кассир выдаст деньги за непроведённый возврат.
- Так же с `state:"in_progress"`.
- Тот же разбор у оплаты (раздел 1, «в полёте») — там это с прошлых кругов.
- Как исправить: `Found` — только при `state=="done"` и `status_code` 2xx. Иначе исход неизвестен → сверка по чеку.

**2.2 НИЗКАЯ (ПЛАУЗИБЛЬНО). К2-09: «не найден» принимается сразу после обрыва.**
- Где: `ReturnSaleDialog.axaml.cs:2205`.
- Почему: у оплаты есть выдержка (`InFlightReconcile`, `age > settle`), у возврата её нет. Медленный сервер может ещё проводить возврат.
- Деньги не теряются: ключ остаётся, повтор тем же ключом не задвоит. Но если кассир изменит количество, ключ будет новым.
- Как исправить: та же выдержка, что у оплаты.

**2.3 НИЗКАЯ (ПЛАУЗИБЛЬНО). К3-03: отсечка «документ не раньше отправки −1 мин» сравнивает часы ПК с часами сервера.**
- Где: `ReturnSaleDialog.axaml.cs:1301`, `:1460`.
- Работает только со старым сервером, где в ответе нет `refund.id`. Текущий сервер `refund.id` присылает.
- Сценарий: часы ПК спешат больше чем на минуту → новый документ отсекается → сумма берётся по расчёту кассы, а не по серверу.
- Как исправить: запас 10 мин или время из заголовка `Date` ответа.

**2.4 НИЗКАЯ (ПЛАУЗИБЛЬНО). К3-03: при `refund.id` в ответе не запрашиваются движения денег сервера (`cashOut = null`).**
- Где: `ReturnSaleDialog.axaml.cs:1607-1627`.
- Когда цифры сервера правдоподобны, это не нужно. Когда неправдоподобны (расчёт кассы, К3-04), пропадает сверка «сервер записал выдачу меньше» (`server_under` для окна закрытия смены).

**2.5 НИЗКАЯ. К3-10: ответы 401, 502, 503, 504 считаются попытками.**
- Где: `ServerLoyalty.cs:191`, `:127`.
- Сценарий: сервер перезапускается 5 минут, чеков с бонусами много. Каждая продажа запускает сброс очереди, поэтому первая операция быстро набирает 20 «ошибок сервера». Её снимают как «не принятую»: баллы не списаны, остаётся ручная правка.
- Тот же путь даёт ложную запись в «Некорректные чеки»: 409 «ещё выполняется» (повтор тем же ключом) попадает в окончательные отказы.
- Как исправить:
  - 502/503/504 считать отсутствием связи;
  - предел — по времени (например, сутки с первой попытки), а не по числу ответов;
  - 409 `idempotency_in_progress` — повторить.

### 4. Округление весовых (К3-07) — ПРИНЯТО

### 7. Память и нагрузка — ПРИНЯТО

- **Обрыв страницы при потоковой загрузке каталог не затирает.** Исключение выходит из `SyncCatalogFullBodyAsync` до `SyncReplaceAllWithDiff` (`AvaloniaCatalogCacheService.cs:786-806`), частичный `newList` выбрасывается. В потоковом режиме после первой переданной страницы запасной адрес не пробуется (`CatalogApiService.cs`: `restart is null && delivered > 0`).
- **Старый риск (не регрессия).** Пустая страница посреди загрузки (200 без товаров) по-прежнему считается концом списка. Так было и до правки.
- **`ApiThrottle.CriticalInFlight`.** Все 5 мест — `using var`, уменьшение счётчика однократное (`_done`). Утечь счётчик может только при «вечном» ожидании внутри критичной операции. Ожидание между страницами ограничено 20 с.
- **Размер страницы.** Потолок 100 определяется только при наличии ссылки `next`. Номера страниц не сдвигаются.
- **НИЗКАЯ (ПЛАУЗИБЛЬНО). Уплотнение кучи.**
  - Где: `AvaloniaCatalogCacheService.cs:739-743`.
  - Блокирующий сбор (если чек пуст) останавливает все потоки, на слабом ПК — до ~1 с. Кассир может как раз начать скан, но ввод сканера буферизуется системой.
  - Если чек открыт, сбор неблокирующий, а режим `CompactOnce` остаётся взведённым. Уплотнение больших объектов произойдёт при следующем полном сборе в случайный момент, например во время оплаты.
  - Как исправить: при открытом чеке не взводить `CompactOnce`, отложить до простоя.
- **Страховка раз в 8 ч.** Обоснована журналом: каждая полная загрузка давала `added=0, changed=0, deleted=0`. Сбои ленты возвращают её к 30 мин.
