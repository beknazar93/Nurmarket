Просьба владельца: «смотри редактирование 24 часа есть, верно? сделай его постоянно открытым, но все изменения записывай!»

## Что было

- Редактор принятой накладной (выпуск 1.17.65+) — это «Б-лайт»: правится только КОЛИЧЕСТВО. PATCH прихода у сервера нет; уменьшение идёт возвратом поставщику, увеличение — доприходом (`ReceiptEditService`, `ReceiptEditPlanner`).

Проверка — `ReceiptEditPolicy.Evaluate` (`Services/Purchases/InvoiceCore.cs`), читалась в `InvoiceDocumentWindow` (кнопка «Изменить», таймер, баннер «Осталось …») и в `ReceiptEditService.ApplyAsync`.

## Что можно править в накладной уже сейчас (без серверного PATCH)

Единственные вызовы сервера, которые есть: возврат поставщику, доприход (`POST suppliers/{id}/receipt/`), `PATCH` товара (`PatchProductFieldsAsync`: `price`, `markup_percent`, `name`, `unit`), `DELETE suppliers/receipts/{id}/` (полное аннулирование прихода). PATCH самого прихода (`suppliers/receipts/{id}/`) у сервера нет, поля документа (поставщик, дата, номер, комментарий, скидка, НДС, цена закупки строки) изменить нечем.

| Поле | Можно сейчас? | Как | Журнал (`fields` в `purchase-edits.jsonl`) |
|---|---|---|---|
| Количество | да | меньше: возврат по строке прихода; больше: доприход «дополнение к ПР-…»; меньше проданного нельзя | `quantity`: было → стало |
| Удалить позицию | да | количество 0 (возврат всей строки) | `quantity`: N → 0 |
| Добавить существующий товар | да | увеличить количество строки (доприход) | `quantity` |
| Добавить НОВУЮ позицию | нет | нужен PATCH прихода; подсказка «Требует серверной поддержки» (Insert) | — |
| Цена продажи товара | да (новое) | шаг `price`: GET товара (читаем «было» с сервера до записи), затем PATCH товара `price`; значение абсолютное, повтор безопасен | `sale_price`: было → стало |
| Наценка | да (новое) | вместе с ценой продажи: `markup_percent` | `markup_percent`: было → стало |
| Единица, название, штрихкод товара | не в этой форме | это карточка товара (меняется в «Товарах»), к документу прихода не относится | — |
| Цена закупки строки | нет | в документе прихода; без PATCH прихода можно только «возврат + доприход по новой цене» (два документа, деньги и долг, ломает трассировку) — не делаем | — |
| Поставщик, дата, номер, комментарий, скидка, НДС | нет | кнопки серые, подсказка «Требует серверной поддержки» | — |
| Итог накладной | как следствие | считается из строк | `total_before` / `total_after` |

Цена продажи и наценка — это поля ТОВАРА в каталоге (в документе прихода цен продажи нет): окно предпросмотра прямо так и пишет и показывает «было → станет». Каждый товар — отдельный шаг со своим статусом (`done` / `unknown` / `failed`), порядок: возвраты, доприходы, цены; при обрыве правка получает статус `partial` / `applying`, «Довести» повторяет только недоведённые шаги. Без связи в очередь встают только количества; изменение цены продажи без связи не сохраняется (подсказка в окне).

Формат записи: к прежним полям добавлен массив `fields`:

```json
"fields":[{"field":"quantity","subject":"Молоко 1 л","product_id":"p-17","before":"100","after":"10","status":"done"},
          {"field":"sale_price","subject":"Молоко 1 л","product_id":"p-17","before":"150","after":"140","status":"done"},
          {"field":"markup_percent","subject":"Молоко 1 л","product_id":"p-17","before":"25","after":"16.67","status":"done"}]
```

## Защита

- Правка суммы накладной: в окне «Проверьте правку» при изменении итога показывается предупреждение (поставщику могли уже заплатить, товар из партии продан, расчёты с поставщиком и прибыль прошлых дней сами не пересчитываются); причина обязательна всегда (не короче 5 знаков), меньше проданного уменьшить нельзя (остаток склада).
- Способ оплаты поставщику сервер не хранит (вопрос 6.8 прежнего ТЗ) — поэтому «после оплаты» определяется по подписи закупки на ПК; предупреждение показывается при любом изменении суммы.
- Правка старше 7 суток от прихода: AUDIT-WARNING + пометка «задним числом» в Telegram владельцу (раз в сутки на накладную) + метка в «Журнале правок» — как раньше.

## Что ждёт сервера (вопрос Умару): контракт `PATCH suppliers/receipts/{id}/`

Заголовок `Idempotency-Key`; тело — любое подмножество (частичное обновление), ответ — обновлённый приход с `version` (если `version` в запросе не совпал — 409 `conflict`):
```json
{ "version": 3, "reason": "Опечатка в цене",
  "supplier_id": "…", "created_at": "2026-10-20T10:00:00", "document_number": "…", "document_date": "…",
  "comment": "…", "discount": {"type":"percent","value":5}, "vat": {"rate":12,"included":true},
  "items": [ {"id":"…","qty":10,"purchase_price":120,"unit":"шт"},   // изменить строку
             {"product_id":"…","qty":5,"purchase_price":100},        // добавить
             {"id":"…","delete":true} ] }                            // удалить
```
Требования: сервер сам пересчитывает остатки, себестоимость партий, долг поставщику / движение денег; пишет СВОЙ журнал изменений документа (кто, когда, `before`/`after` по каждому полю, причина, роль) и отдаёт его `GET suppliers/receipts/{id}/history/`; права — owner и admin; отказ с кодом, если правка сделает остаток отрицательным (проданное из партии). Тогда касса включит серые поля («Требует серверной поддержки») и заменит возвраты/доприходы одним вызовом.
