# Rongta RLS1000: разбор протокола и что касса умеет — 13.11.2026

**Коротко.** Программа RLS1000 говорит с весами своим протоколом по **UDP 5001**, а не командой «!0V» (TCP 4001). **Тип штрихкода — байт 42 карточки PLU** (64 байта), записан двоичным числом (17 → 0x11). В «!0V» такого поля нет совсем, поэтому madv4 и не помогал. Касса теперь после «!0V» записывает тип в весовые карточки «родной» командой весов «обновить PLU», как RLS1000.

**Как получено.** Установленную программу `C:\Program Files (x86)\RLS1000` (V1.129, сборка 2018.05, без подписи) **не меняли**. Её скопировали в `C:\Users\User\NurMarket-tools\RLS1000-copy` и в копии поставили адрес весов 127.0.0.1. Рядом работала своя ловушка на 127.0.0.1:5001. Как ловушке отвечать «как весы», выяснили по RLS1000.exe (Delphi 7). Нужные функции: 0x6d4afc «подключиться», 0x6d50fc «пакет → ответ», 0x6d44d8 «разбор ответа». Ответ 0x02 значит «принято», 0x55 — «отказ». После этого RLS1000 отдала всё, что умеет. **На реальные весы 192.168.1.87 ничего не отправлялось.** Журналы и пакеты лежат в `C:\Users\User\NurMarket-tools\rls-trap-logs`, снимки окон — в `...\rls-shots`. Эталоны для тестов — `NurMarketKassa.Tests/Hardware/RongtaUdpFixtures.cs`.

**Что у владельца в установленной программе.** Только заводские файлы 2015–2018 годов. Своих соединений и PLU-файлов нет. В списке весов строка «test» с IP 192.168.1.87: это заводской адрес по умолчанию, он просто совпал с адресом весов. В заводском `rtPLU_EN.TXP` у всех товаров тип штрихкода 2, отдел 21. Этикетка `rtlabel_en.scr` (D0, 56×40 мм) содержит элемент штрихкода EAN-13: какие цифры в него попадут, решает тип у товара. В «установить функцию» (F6) стоят заводские значения: тип штрихкода 0, тип этикетки 6, точность цены 2, «автоматически обновлять время» включено.

## 1. Пакет
| Байты | Что |
|---|---|
| 0 | команда |
| 1–2 | параметр (младший байт первым) |
| 3–258 | данные, 256 байт |
| 259–260 | сумма байтов 0–258, младший байт первым |

Пакет всегда 261 байт. Весы отвечают одним байтом: 0x02 — принято, 0x55 — отказ. Ответ на чтение — пакет от 301 байта (его точный вид без весов не проверить). Если ответа нет, RLS1000 ждёт около 1 с и повторяет.

| Команда | Параметр | Что делает | Данные |
|---|---|---|---|
| 0E | 0001 | подключиться | номер весов (4) + дата-время ПК BCD: гг мм дд чч мм сс |
| 0E | 0002 | отключиться | номер весов |
| 0E | 0003 | прочитать страницу памяти | номер страницы (2); FFF — сведения о весах (ёмкость PLU) |
| 0E | 0004 | подготовить область перед полной загрузкой | от–до (PLU: 0200–02FF) |
| 0E | 0006 | обновить цену (F7) | записи по 7 байт: LF (BCD 3) + цена (BCD 4), до 36 штук |
| 0E | 0010 / 0014 | системные параметры: чтение / запись | 256 байт настроек (п. 3) |
| 0E | 0016 | выгрузить продажи | ответ — данные (формат без весов не виден) |
| 01 | 0200+ | «Скачать plu» (F9): страница памяти PLU | 4 карточки по 64 байта; позиция = порядковый номер |
| 0B | 0000 | «обновить plu» (F8): поиск по LF-коду | до 4 карточек по 64 байта |
| 02 | 01FD, 00FD | горячие клавиши | LF-коды по 3 байта BCD, 84 на страницу |
| 09 / 00 | 00FB / 0300+ | этикетка: список элементов / фон | раскладка .scr |
| 62, 07, 08 | — | шрифты и служебные области (китайский шрифт) | касса не трогает |

**Номер весов** — это IP-адрес как одно число, последние 8 цифр в BCD, младшая пара первой: 127.0.0.1 → `33 64 70 30`, 192.168.1.87 → `63 58 23 32`.

## 2. Карточка PLU (64 байта)
| Байты | Поле | Формат | Колонка RTPLU |
|---|---|---|---|
| 0–35 | Название | 36 байт, хвост — пробелы 0x20 | Название |
| 36–38 | LF-код | BCD 6 цифр | LF код |
| 39 | Таблица скидок | двоичный | Таблица скидок |
| 40 | Учётная запись | двоичный | Учётная запись |
| 41 | Отдел (DD) | BCD 2 | Отдел |
| **42** | **Тип штрихкода** | **двоичный 0–99** | **Тип штрихкода** |
| 43–46 | Цена | BCD 8 (сом × 10^знаков) | Цена единицы |
| 47 | Единица (младшие 4 бита: 1 г, 2 10 г, 3 100 г, 4 кг, 5 oz, 6 lb, 9 шт.) + 4 старших бита (0–15, 19-я колонка TXP) | двоичный | Вес единицы |
| 48–49 | Срок годности, дни | двоичный, младший байт первым | Срок годности |
| 50 / 51 | Сообщение 1 / 2 | двоичный | Сообщение 1/2 |
| 52–54 | Тара, г | BCD 6 | Тара |
| 55 | Тип упаковки (биты 6–7) + допуск % (биты 0–5) | двоичный | Тип упаковки, Ошибка(%) |
| 56–58 | Вес упаковки (PT), г | BCD 6 | Вес PT |
| 59–63 | Код (Art. No.) — печатается в штрихкоде | BCD 10 | Код |

Чем подтверждено: две серии по 20 карточек, в каждой менялось одно поле, и 3 товара с типами 02, 07, 17. Тесты `RongtaUdpProtocolTests` собирают эти пакеты кодом кассы и совпадают с RLS1000 байт в байт.

## 3. Системные параметры (0E/0014, блок 256 байт)
Байты 0–4 — дата и время (BCD дд мм гг чч мм). Байт 26 — тип штрихкода по умолчанию. Байт 93 — «тип для всех весовых». Байт 105 — признак «включить тип для всех». Байт 106 — «тип для всех штучных». Байт 52 связан с «автоматически обновлять время».

**Касса этот блок не отправляет.** RLS1000 не читает настройки с весов, а пишет блок целиком из своего SYSTEM.CFG. Значит, такая запись переписывает **все** настройки весов: знаки цены, формат этикетки, пароли. Безопасно так сделать нельзя, не зная текущих значений на весах. Тип «для всех» и знаки цены ставят на самих весах ([SETTING]).

## 4. Что сделано в кассе
- `Services/Hardware/RongtaUdpProtocol.cs` — пакеты, номер весов, карточка 64 байта, «подключиться», «обновить PLU», «отключиться».
- `Services/Hardware/RongtaUdpScaleService.cs` — отправка по UDP 5001 с повторами. Каждый обмен пишется в `Logs\rongta-udp-exchange.log`.
- `Services/RongtaBarcodeTypeWriter.cs` и одна вставка в `ScalesPluWindow` — после «Отправить на весы» (Rongta напрямую) весовые товары получают выбранный тип. Карточка: LF = номер PLU (ячейка), Code = «Код в ШК», остальное — как в «!0V». Пишется **только если в «Настройках весов Rongta» выбрана структура** (кнопка «Исправить: тип 07» или выбор в списке). По умолчанию ничего не меняется.
- Окно «Настройки весов Rongta» теперь из четырёх вкладок: «Подключение / Загрузка товаров / Штрих-код / Дата и параметры».
  - Крупно показан текущий тип и пример этикетки «1,150 кг × 1100 = 1265,00 → штрихкода НЕТ / 20 00005 01150 C».
  - При типе по сумме — предупреждение и кнопка «Исправить: тип 07».
  - Кнопки: «Записать тип во все товары на весах…» (с подтверждением), «Не записывать тип», «Записать дату и время на весы» (это «подключиться» + «отключиться», как «Проверка порта» в RLS1000).
  - Поле «TCP-порт для проверки» убрано: RLS1000 говорит с весами по UDP 5001, проверка TCP-порта ничего не показывала.
- Не проверено на весах: (1) примут ли весы команду 0B от кассы без чтения сведений (RLS1000 перед ней читает страницу FFF и служебные страницы шрифта). (2) Что LF-код карточки, созданной «!0V», равен номеру PLU. Если он равен «Код в ШК», это неважно, пока номер и код совпадают; по умолчанию так и есть. (3) Ставят ли весы часы по пакету «подключиться».

## 5. Что проверить владельцу (безопасный порядок)
1. «Настройки весов Rongta» → «Штрих-код» → **«Исправить: тип 07»**.
2. В окне «Весы» отметьте **один** весовой товар, у которого «Код в ШК» пуст или совпадает с PLU, и нажмите «Отправить на весы». В строке итога должно быть «Тип штрихкода 07 записан…».
3. На весах зажмите [PLU] → «single item edit» → номер PLU → [PRN/ENTER]. «Bar Code Type» должен быть 07.
4. Положите товар дороже 1000 сом и напечатайте этикетку. Штрихкод `20 0000N 0WWWW C` должен быть. Отсканируйте его кассой: сумма должна совпасть.
5. Если всё верно — «Записать тип во все товары на весах…». Если весы не ответили на порту 5001, пришлите `%LOCALAPPDATA%\NurMarketKassa\Logs\rongta-udp-exchange.log`, а тип пока поставьте на весах: [SETTING] → «barcode type: set all barcodes' type» → 07.
6. «Дата и параметры» → «Записать дату и время на весы», затем проверьте часы весов.

Старые этикетки (тип 02, сумма) после смены типа не сканируйте: касса прочтёт сумму как вес.

## 6. Сценарии на будущее (пакеты с оценкой)
| Сценарий | Как у весов | Касса сейчас | Что добавить | Оценка |
|---|---|---|---|---|
| Тип штрихкода по товару | байт 42, команда 0B | пишет после «!0V» (весовые) | штучным — свой тип (на весах «ALL PCS Barcode Type») | 0,5 дня |
| Быстрое обновление цены | 0E/0006: LF + цена, 36 в пакете | цена уходит полной записью «!0V» | «обновить цены» одной командой: секунды вместо минуты | 0,5–1 день + проверка на весах |
| Полная запись без «!0V» | 0B по LF или 01 по страницам | «!0V» + 0B | писать только 0B (имя 36 байт, тара, упаковка, сообщения) — одна запись вместо двух | 1–2 дня + проверка |
| Дата и время | дата в пакете «подключиться»; полная запись — в блоке 0E/0014 | кнопка «Записать дату и время» | автоматически при каждой отправке товаров | 1 час (после проверки) |
| Своя этикетка | 09/00FB — элементы, 00/0300+ — фон .scr (70 страниц) | нет (RTLabel) | загрузка готового .scr из RTLabel кнопкой кассы; редактор — нет | 2–3 дня, риск «пустой этикетки» (D0/D1) |
| Тип 99 «свой штрихкод» | раскладка в системном блоке (Dept + LFCode + Total по умолчанию) | нет | только через весы/RLS1000 — блок переписывает всё | не советуем |
| Горячие клавиши | 02/01FD, 00FD: LF-коды по 3 байта | «!0L» (весы принимают, раскладка не меняется) | клавиши «родной» командой — может, это и починит раскладку | 0,5 дня + проверка |
| Скидки по времени | таблица скидок (байт 39, «RebateBtn», файлы .REB) | нет | разбор формата таблицы — ещё одна ловушка | 1–2 дня |
| Продажи с весов | 0E/0016 → данные (ответ на ловушке не получен) | нет | нужен 1 сеанс записи обмена RLS1000 ↔ реальные весы (pktmon) | 1–2 дня после записи |
| Сообщения (состав, ингредиенты) | область 0x0138–0x01FC (команда 62), номер в байтах 50–51 | нет | тексты до 197 сообщений | 1–2 дня |
