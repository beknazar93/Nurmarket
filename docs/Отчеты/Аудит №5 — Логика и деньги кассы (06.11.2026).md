## 3. Новые находки (Л5)

### ВЫСОКИЙ

**Л5-01 · ВЫСОКИЙ · Признаки сервера (capabilities) пропадают при любом сбое обновления — денежные правила «мигают».**
- Где:
  - `Infrastructure/Services/Api/ServerCapabilities.cs:117-123`: при ошибке запроса кэш **заменяется** пустым списком с `Ok=false`, даже если для этого аккаунта уже был хороший список;
  - `:84-85`: при `Ok=false` `Cached()` даёт `null`;
  - `:40-46`: тогда `Has()` даёт `false` для всех признаков. Обновление идёт раз в 10 мин, после сбоя — раз в минуту. Без связи признаки «выключены» всё время.
- Что зависит от `Has()`:
  1. **`checkout_branch`.** `DeviceIdentity.ApplyTo` (`QuickCheckoutBody.cs:177`) добавляет `device_key`, `device_name`, `branch` в тело чека. Это тело и есть отпечаток, по которому касса повторяет оплату тем же ключом (`PosCheckoutService.Quick.cs:118-137`; восстановление «неясной оплаты» — только при `QuickBody == fingerprint`, `:126-128`).
     - Сценарий: оплата «в долг» или смешанная, ответ сервера не дошёл (сеть плохая). Фоновое обновление признаков в это же время тоже падает, и `checkout_branch` становится `false`. Кассир жмёт «Оплатить» ещё раз: тело без `device_key`, отпечаток другой, ключ **новый**.
     - Если сверка по ключу (`ReconcileInFlightAsync`) не дошла (та же сеть) и кассира уже предупредили, вторая продажа уйдёт новым ключом. Если первая прошла — **двойной долг или двойная продажа**.
     - Сбой связи и «мигание» признака происходят одновременно, то есть именно тогда, когда исход оплаты неизвестен.
  2. **`weight_line_total_floor`** (`QuantityRules.cs:147, 163-170`). При «выключенном» признаке касса считает итог по старому правилу (вниз от суммы весовых), а сервер — по новому (каждая строка вниз). Чек с несколькими весовыми строками расходится на 0,01 × (n−1). Офлайн-чеки за время без связи все посчитаны по старому правилу.
  3. **`debt_return_drawer_cash`.** Безопасно: поправка пишется только при точном совпадении расхождения. Но окно возврата долгового чека ждёт остаток 6,5 с вместо 2,5 с.
- Совет:
  - при сбое обновления **оставлять прежний хороший список** этого аккаунта, только помечать его устаревшим; пустой список ставить, только если хорошего не было;
  - отпечаток быстрой оплаты считать **без** `device_key`/`device_name`/`branch`: добавлять их после расчёта отпечатка, при отправке;
  - для денежных признаков (`weight_line_total_floor`, `debt_return_drawer_cash`) хранить последнее известное значение на диске по аккаунту.
- Трудоёмкость: S. **Подтверждено кодом** (механизм). Насколько часто это бывает — нужна проверка вживую: стенд «сбои сервера», оплата в долг при обрыве.

**Л5-02 · ВЫСОКИЙ · Шаг округления весовых строк берётся из единицы суммы, выбранной на кассе, а не из настройки сервера.**
- Где: `Infrastructure/Services/Pos/QuantityRules.cs:150-151`: `WeightStep = EffectiveScaleAmountUnit == "som" ? 1 : 0,01`. `EffectiveScaleAmountUnit` = локальная ?? серверная (`UserPreferences.cs:807-808`).
- Локальный выбор (`ScaleBarcodeAmountUnitLocal`, 05.11) сделан для **разбора штрихкода** у клиента с весами TM-30F. У компании этого клиента на сервере, скорее всего, `som`, а на кассе выбрано «тыйыны». Сервер по ответу Умара считает `line_total` = FLOOR(цена × вес) **до шага весов**, то есть по своей настройке.
- Сценарий (TM-30F, у компании `som`, на кассе «тыйыны»): 3,840 кг × 200,10 = 768,384.
  - Касса: шаг 0,01 → 768,38.
  - Сервер (если шаг — 1 сом): 768,00.
  - Кассир берёт с покупателя на 0,38 больше, чем записал сервер. За смену набегают сомы «излишка».
  - Обратная пара (на сервере `tiyin`, на кассе «сомы») даёт недобор.
- Вдобавок `CartTotalsCalculator.ShownRounding` (`:119-123`) прячет строку «Округление весовых», если разница больше 0,01 на строку. Строки чека тогда не сходятся с итогом без объяснения.
- Совет:
  - шаг брать только из серверной `ScaleBarcodeAmountUnit` (её и применяет сервер), а локальный выбор оставить для разбора штрихкода;
  - после оплаты сверять итог ответа сервера с итогом кассы и писать расхождение в журнал.
- Трудоёмкость: S. Механизм **подтверждён кодом**. **Нужна проверка вживую** на NBS: чек с весовой строкой при `scale_barcode_amount_unit = som` — что сервер пишет в `line_total` и `total`.
