## Высокая серьёзность

### В-1. Неясный исход печати записывается как «точно не напечатан» → дубль без пометки

**Где:** `PhoneSalePrintWatcher.cs:474`
```csharp
_journal.Finish(entry.SaleId, PhonePrintStatus.Failed, error, maybePrinted || timedOut);
```
`timedOut` становится true только по своему тайм-ауту 40 с (`:445`). Но 40 с не наступают никогда:
- `ReceiptHistoryService.PrintAsync` → `LptReceiptPrinterService.PrintWithTimeoutAsync` сам отдаёт `false` через **8 с** (`LptReceiptPrinterService.cs:45`). Получается текст «Принтер не ответил…», а задача печати **продолжает работать**.
- `PrinterPortService.SendRawBytes` ждёт порт до **15 с** (`PortWaitLimit`, `PrinterPortService.cs:88, 118`), потом пишет.

**Как ломается (обычный час пик):**
1. Касса печатает свой чек.
2. В это время приходит чек телефона. Порт занят, через 8 с — `Failed`, `MaybePrinted=false`.
3. Ещё через несколько секунд порт освобождается, и чек телефона выходит на бумагу.
4. В меню «Не напечатаны» висит этот чек. Кассир жмёт «Напечатать» — второй экземпляр **без** «ПОВТОРНАЯ ПЕЧАТЬ».

Это нарушает ТЗ («ПОВТОРНАЯ ПЕЧАТЬ» — при неизвестном исходе) и даёт двойную бумагу.

Тот же случай: графический чек (до 60 с `WriteTimeout`), зависший USB.

**Правка** (минимальная, только К-П1). «Точно не ушло» — только когда касса отказала до отправки: печать выключена или принтер не выбран. Всё остальное — «исход неизвестен».

В `PhonePrintEnv`:

### С-2. Свои продажи кассы могут посчитаться «чужими»

**Где:** `PhoneSalePrintWatcher.cs:318-323`.

`CurrentShiftId()` берёт `PosApp.ActiveShiftId`. Когда смена открыта без связи, там стоит `"offline-shift-<guid>"` (`CashShiftService.cs:143, 211`). Чеки такой смены при досылке уходят без `shift_id`, и смену выбирает сервер: «по времени sold_at или открытую на момент выгрузки» (`SyncService.cs:465-478`). То же при автозакрытии смены сервером в 23:00 (`offline-closed-…`).

У такой продажи на сервере смена не совпадает с `currentShift` и может не быть в `OwnShifts`. `OwnShifts` пополняется только при удачном опросе — а при офлайн-смене удачного опроса не было.

Итог:
- если сервер ставит `paid_at` = время выгрузки — свой чек печатается второй раз с «Продажа с телефона»;
- если `paid_at` = `sold_at` — свой чек засоряет «Не напечатаны», и кассир может его «допечатать».

### С-4. Нагрузка на сервер

**Сейчас:**
- одна назначенная касса — 12 запросов списка в минуту + 0,5 на назначение + 1 на каждый чек телефона;
- страница 20 строк × ~35 полей `SaleList` ≈ 15–25 КБ без сжатия, то есть ~0,2–0,3 МБ в минуту и ~100–180 МБ за 10-часовой день на одну кассу;
- у N касс компании (по одной на `cashbox`) — N×12 в минуту;
- сервер ограничивает частоту **на пользователя** (`ApiThrottle.cs:6`). Опрос тратит тот же запас, что оплата кассира. Если все кассы под одним логином — запас общий.

**Слабые места:**
- интервал ровно 5 с без разброса (`:86, :171`) — кассы бьют в сервер синхронно;
- после 429 пауза — только `Retry-After` (обычно 5–15 с), потом снова 5 с;
- запрос назначения при сбое повторяется каждые 5 с: `RoutingFetchedUtc` не двигается, `_errorStreak` не растёт (`PhonePrintSettings.cs:207-218, 243-250`);
- `RefreshRoutingAsync` идёт **до** проверки `ThrottleLeft` (`:216` и `:230`), то есть и во время паузы, которую сервер просил у всей кассы.

**Безопасное предложение** (задержка остаётся ≤ 10 с, как в В-8):

| Что | Значение |
|---|---|
| Интервал | **8 с ± 1 с** случайно (`Random.Shared`) |
| Страница | **10** строк (`PageSize = 10`; минимум в `PosSalesListAsync` — 5) |
| 429 | пауза = max(`Retry-After`, 30 с), каждый следующий 429 подряд — ×2, до **5 мин**; сброс после удачного опроса |
| Чужой 429 в кассе | если `ApiThrottle.LastThrottledUtc` моложе 60 с — опрос пропускаем (печать телефона — самый неважный трафик) |
| Ошибки сети | как сейчас, 10→20→40→60 с |
| Назначение | не чаще раза в 2 мин; после ошибки — не раньше чем через 30 с (`_routingRetryUtc`); проверку `ThrottleLeft`/`_pauseUntil` — до `RefreshRoutingAsync` |
| Без сессии | нет `AccessToken` — опрос не идёт (сейчас локальный 401 → пауза до 60 с: нагрузки нет, но лишняя работа) |

Итог — ~7,5 лёгких запросов в минуту на кассу, ~40–60 МБ в день. После Б-68 (`created_after`, `ETag`/304) — почти ноль.

Код паузы в `catch (ApiException ex) when (ex.StatusCode == 429)` (`:249`):
```csharp
// 2026-10-27, ревью К-П1: 429 — печать телефона уступает сервер кассе: не меньше 30 с, подряд — вдвое, до 5 мин.
_throttleStreak++;
var floor = TimeSpan.FromSeconds(Math.Min(300, 30 * Math.Pow(2, _throttleStreak - 1)));
var wait = _env.ThrottleLeft();
if (wait < floor) wait = floor;
_pauseUntil = now + wait;
```

## Низкая серьёзность

- **Н-1. Фильтр сотрудников по подстроке** (`PhoneSalePrintWatcher.cs:327-328`): `IndexOf` — «Бек» совпадает с «Айбек». Сравнивать целиком без учёта регистра: `staffFilter.Any(f => string.Equals(f, staff, StringComparison.OrdinalIgnoreCase))`.
- **Н-2. Строка на чеке** (`:529-534`): остальной чек всегда по-русски (`SaleReceiptTextBuilder` без `Tr.T`), а эта строка — на языке интерфейса. Казахские и кыргызские ө, ү, ң в cp866/1251 выйдут «?». Длинное имя (> 32 знаков на 58 мм) не переносится. Предложение: строку на бумаге — всегда «Продажа с телефона: …», переносить по ширине (`ReceiptLineLayout`); на экране — `Tr.T`. *Решение владельца: язык чека.*
- **Н-3. Повтор не проверяет статус** (`:493-506`): «Напечатать» у старого `Skipped` печатает и продажу, которую уже отменили или вернули целиком. Перед печатью проверить `status` в `detail`: не `paid/debt/partially_returned` — отказ «Продажа отменена на сервере» (5 языков).
- **Н-4. Таймер 40 с** (`:445`): `Task.Delay(PrintTimeout)` без отмены висит 40 с после каждой печати. Мелочь — `using var cts = new CancellationTokenSource(); … Task.Delay(PrintTimeout, cts.Token); cts.Cancel();`.
- **Н-5. «Не напечатаны» копятся 7 дней**, кнопки «Скрыть» нет. `Prune` — только при запуске (`:141`): касса, работающая неделями, держит записи дольше. Добавить «Скрыть» (статус `hidden`) в К-П3, `Prune` — раз в сутки в цикле.
- **Н-6. Событие `Changed` приходит из фонового потока** (`:177-181`, `PhonePrintSettings.cs:348-354`). Сейчас подписчиков нет. В К-П3 подписываться только через `Dispatcher.UIThread.Post`.
- **Н-7. Наблюдатель не останавливается никогда.** Нет `Stop()` ни при выходе, ни при выходе из учётной записи. Вреда нет: без токена — локальный 401 и пауза; процесс закрывается вместе с ним; «printing» при закрытии превращается в «неясный исход». Для порядка — `Stop()` в обработчике закрытия главного окна при выходе из программы.
- **Н-8. «Проверить сервер сейчас» видят все** (`MainWindow.PhoneLink.cs:132-151`). Частые нажатия — лишние запросы, ответа на экране нет. Не чаще раза в 10 с и короткий тост с итогом.
- **Н-9. Журнал занят антивирусом** — `Load` считает его повреждённым (`PhoneSalePrintJournal.cs:93-100`) и начинает новый. Двойной печати не будет («нулевой» опрос), но пропадает список «Не напечатаны». Отличать `IOException` (повторить позже) от `JsonException` (отложить файл).
- **Н-10. Один id ПК на двух компьютерах.** `LanDeviceId` хранится в `user-settings.json`. Если перенести настройки на другой ПК копированием `%APPDATA%`, у двух ПК будет одно назначение, и оба печатают. Описать в К-П3 («после переноса настроек — заново назначить кассу»). Можно добавить к id имя компьютера.
- **Н-11. Android/Linux.** Код общий (оба проекта берут `**\*.cs`). Windows-только вызовов и `#if` нет, `File.Replace` работает и в Unix. На Android `MainWindow` тоже создаётся (`AndroidDesktopLifetime`), поэтому наблюдатель стартует и там — выключенный. Ctrl+Shift+F9 на планшете недоступен. Сборку Portable и Android в этом ревью **не запускал**: Windows-сборка подтверждается стендом (dll 01:23). Перед выпуском — обычная сборка `NurMarketKassa.Portable` и `NurMarketKassa.Android` по `build-locked.ps1`.

Ещё мелочь: строка состояния говорит «чеки печатает другая касса» без имени ПК. ТЗ просит «Печатает касса “ПК-2”». Имя можно взять из `LanSyncService.Instance.Peers` по id или писать рядом с id в назначение. Это К-П3.
