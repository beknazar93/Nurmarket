### Если делать — как включить (Gemini)
- **Адрес**: `POST /v1beta/models/{model}:streamGenerateContent?alt=sse`, тело то же. Ответ — `text/event-stream`, строки `data: {…GenerateContentResponse…}`.
- **Текст** — `candidates[0].content.parts[].text` каждого куска. Части с `"thought": true` пропускать, как сейчас. В последнем куске — `finishReason` и `usageMetadata`; источники поиска Google — в последних кусках.

- **Flutter**: `Options(responseType: ResponseType.stream)` + `CancelToken`, `utf8.decoder` + `LineSplitter`.
- **Отмена**. Кнопка «Стоп» отменяет токен, соединение закрывается, пришедший текст остаётся с пометкой «остановлено». Считать, что запрос всё равно засчитан в лимит ключа.
- **Ошибка до первого куска** (HTTP 429/400/503, ключ) — как сейчас: перебор ключей и моделей остаётся без изменений.
- **Ошибка посреди потока** (обрыв, `finishReason` SAFETY/MAX_TOKENS, объект `error`):
  - показать пришедшее и плашку «Ответ оборвался — Повторить»;
  - запасную модель автоматически **не** запускать;
  - срок ждать до первого куска (сейчас 7–20 с на попытку), дальше — «тишина между кусками не дольше 10 с» вместо общего срока.
- **Служебные строки.**
  - Во время потока показывать «черновик» — только строки без служебных префиксов (ТОВАР, БОТ, СЦЕНАРИЙ, ПОСТАВЩИК, ИТОГ НАКЛАДНОЙ, напоминания).

  - В конце заменить черновик готовым ответом через нынешний разбор: карточки действий, таблицы.

### Где выгоднее всего

## 15. Ленивая загрузка картинок и размеры — ЧАСТИЧНО (одна серьёзная находка)

### Что уже хорошо
- **Каталог кассы — страницы по 50 плиток**: `CatalogPanelViewModel.cs:23`, `:1016-1023`; телефон ставит меньше. - **Кэш расшифрованных миниатюр** ограничен 160 штуками; есть подсказка сборщику мусора (`AssetPathToBitmapConverter.cs:79-139`).

  - дисковый кэш `CachedPhoto` (`photo_cache.dart:96-108`);

  - фиксированный `SizedBox` и буквы названия, пока фото нет (`ui.dart:227-242`);
  - ленивые `ListView.builder` / `SliverGrid.builder` с заданной высотой (`sale_screen.dart:569-576`, `stock_screens.dart:134`).
  Прыжков нет.

### Находки
1. **Миниатюры хранятся оригиналами с сайта** — главное. `ProductThumbService.cs:89-93` пишет на диск байты как есть. Замер кэша программы владельца на этом ПК:
   - 195 файлов, **15,2 МБ**;
   - ширина: медиана **900 px**, максимум **6022 px**;
   - уменьшенные до 320 px WebP q80 занимают **2,2 МБ (−86 %)**.
   Показываются они в 36–180 px, а расшифровываются в **потоке интерфейса**: конвертер вызывает `Bitmap.DecodeToWidth` синхронно (`AssetPathToBitmapConverter.cs:161-166`), каждый раз как плитке приходит путь. Полное чтение одного такого файла заняло в среднем **49 мс** (замер Pillow на этом ПК; Skia с масштабированием быстрее, но файл всё равно разбирается целиком). Страница из 50 плиток при первом показе может держать интерфейс порядка секунды на слабом ПК. Это оценка, Skia в кассе не замерялась.
2. **Внутренний прыжок в плитке**. Строка фото в карточке видна только когда путь уже есть (`IsVisible` по `ProductImagePath`, `CatalogPanelView.axaml:576-585`, `MaxHeight=64`, без резерва). Путь приходит через `Dispatcher.InvokeAsync` после проверки кэша (`ProductThumbService.cs:49`). Фото появляется чуть позже плитки, и название внутри неё съезжает вниз. Коробка плитки та же, соседи не двигаются. Заметно при первом показе страницы и, вероятно, после пересборки плиток при синхронизации каталога (`AssetPathToBitmapConverter.cs:27-29`) — **проверить вживую**.
3. **Выбор ссылки на фото штрафует WebP**: `ProductImageUrl.cs:142-143`, `score -= 50`. Если сервер отдаёт и JPG, и WebP, касса возьмёт более тяжёлый JPG. Сейчас в кэше только `.webp`, то есть сервер отдаёт одну ссылку. Мелочь, но правило устарело.

### План
- **(а) Пересжатие при скачивании** — M. В `ProductThumbService.DownloadToCacheAsync` после скачивания уменьшить до 320 px по ширине и сохранить WebP (SkiaSharp уже есть в проекте, используется в `KnowledgeBaseWindow.axaml.cs:421`).
  - Имя — `<sha>.t320.webp`, чтобы не путать со старыми файлами. Старые файлы пересжать по одному при первом обращении или просто стереть.
  - **Важно:** тот же кэш берёт экран покупателя (`CustomerDisplayViewModel.cs:834`, `TryGetCachedPath`). Проверить, в каком размере он показывает фото позиции. Если крупнее 320 px — хранить 480 px или держать отдельный размер для него.
  - 320 px выбраны не случайно: это ширина декодирования для экрана с масштабом 200 % (`AssetPathToBitmapConverter.cs:84-85`).
- **(б) Декодирование вне потока интерфейса** — S–M. В `SetThumbAsync` (фоновый поток) сразу расшифровать `Bitmap.DecodeToWidth` и положить в кэш конвертера, а потом выставить `ProductImagePath`. Конвертер тогда возьмёт готовое из кэша. Для этого нужен внутренний метод `AssetPathToBitmapConverter.Prewarm(path)` с тем же ключом кэша `path|thumb`.
- **(в) Резерв места под фото** — S. `IsVisible` строки фото считать по `ImageUrl` (фото будет), а не по `ProductImagePath` (фото уже на диске), с подложкой `BrushPanelSoft`, как на складе. Учитывать настройку `ShowCatalogPhotos` (`ShowProductPhotoConverter.cs:13-14`). То же в макетах `CardsLayoutView.axaml:171`, `MinimalLayoutView.axaml:158`, `ProLayoutView.axaml:309`.
- **(г)** Убрать штраф `.webp` в `ProductImageUrl.cs:142-143` — S, после проверки на реальном JSON товара.

**Риски.**

- (б) Avalonia 11 разрешает создавать `Bitmap` вне потока интерфейса. Но если перестраховаться, это всё равно то же поведение, что сейчас, плюс прогретый кэш.
