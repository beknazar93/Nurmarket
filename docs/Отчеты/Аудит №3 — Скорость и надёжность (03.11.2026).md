### Р3-02. ВЫСОКИЙ — закрытие «извне» и выключение Windows упираются в модальный вопрос без срока

- **Что держало выход вчера (ответ на вопрос задания).** Журнал кассы, 18:35:05.887: «Модалка открыта: ShiftNotClosedDialog». Закрытия этой модалки в журнале нет, а в 18:35:26 уже «Application started» нового процесса. Закрытия тоже нет, новый старт — в 18:35:35. `tools/qa/deploy_both.ps1:13-16` шлёт `CloseMainWindow()`, ждёт 15 с и делает `Stop-Process -Force`.
- **Живой опыт 03.11, 22:35.** `WM_CLOSE` главному окну кассы по hwnd (то же, что `CloseMainWindow`): через 0,25 с окно «Смена не закрыта». Через 5, 10, 15 и 20 с процесс жив, окно висит. Сама касса отвечает (пинг 0 мс): это не зависание потока, а ожидание человека. После «Отмена» касса работает. После «Выйти без закрытия смены» процесс завершается за 0,15 с: `SyncService` и `Dispose` выход больше не держат, С-14 работает.
- **Где.** `K/MainWindow.axaml.cs:2616-2626` (`OnClosing`) → `:2639-2669` (`HandleCloseRequestAsync` → `ShiftNotClosedDialog.Prompt`, вложенный цикл `PosDialogHost.Show`, `D/PosDialogHost.cs:82-127`, без срока). Причина закрытия (`WindowClosingEventArgs.CloseReason`) не проверяется. Владелец: `M/OwnerShellWindow.axaml.cs:298-325` (`ConfirmLeaveAsync`, тоже без проверки причины).
- **Выключение Windows (по коду, вживую не проверялось — нельзя на рабочем ПК).**
  1. В Avalonia 11.2.5 есть `IPlatformLifetimeEventsImpl.ShutdownRequested` (WM_QUERYENDSESSION) и `WindowCloseReason.OSShutdown`: строки найдены в `Avalonia.Win32.dll` и `Avalonia.Controls.dll` установленной кассы.

  3. Windows ответит «Приложение препятствует завершению работы». Если нажать «Всё равно завершить», процесс убивается (`TerminateProcess`).
  4. Тогда `ProcessExit` не выполнится: отложенные записи `AtomicFile` (Р3-04) и последний чекпоинт WAL не сделаются. Сама база SQLite (`synchronous=FULL`) переживёт.

- **Что сделать.**
  1. В `OnClosing` при `CloseReason is OSShutdown or ApplicationShutdown` (и при флаге «закрывает установщик») вопрос не показывать: сохранить состояние (`SaveApplicationState`) и выйти; смена остаётся открытой, как при «Выйти без закрытия смены».
  2. Для установщика — сигнал «закройся тихо» через существующий канал «покажись» (`Program.cs`, `StartShowRequestListener`) или ключ командной строки.
  3. Вопрос владельца — тоже только для `WindowClosing`.

### Р3-04. СРЕДНИЙ — запасные файлы `*.pending` восстанавливаются без слияния, при убийстве процесса не пишутся

- **Где.** `I/Services/AtomicFile.cs:286-314` (`RecoverPending`):
  - запасной файл новее рабочего становится `DeferredWrite(..., merge: null)` и записывается поверх файла целиком, без функции слияния хранилища (`MergeEntries`, `MergeState`, `MergeInfos`);
  - если рабочий файл новее, запасной **удаляется** — изменения, которые были только в памяти закрытого процесса, пропадают.
- `:272-283` `WritePending` пишет через `File.WriteAllText`, без сброса на диск.
- `:229` запись идёт только из `ProcessExit`, а при `Stop-Process -Force`, «Всё равно завершить» Windows или установщике через 15 с (Р3-02) он не срабатывает.
- **Хранилища.** `exchange_cash_fix.json` (поправки «ожидаемо в кассе»), `offline_pos_state.json`, `deferred_carts.json`, `pending-unknown-checkout.json`, `rental-receipts.json`, `receipt-markups.json`.
- **Сценарий.** Антивирус держит `offline_pos_state.json`, касса откладывает запись. Установщик или выключение убивает процесс — состояние смены, отложенное в памяти, потеряно. Второй сценарий: файл освободился, его записал другой процесс (новее) — `*.pending` молча удаляется.
- **Что сделать.** В `RecoverPending` передавать функцию слияния хранилища: хранить имя хранилища → `merge` в реестре или регистрировать её при первом `TryRead`. Удалять `*.pending` только после слияния. В `WritePending` — `Flush(true)`. Вместе с Р3-02 сократить случаи убийства.
