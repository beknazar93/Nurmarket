# ТЗ Умару: доступы сотрудников и маркетплейс — синхронизация (11.11.2026)

От: команда кассы NurCRM. Решение владельца магазина: «доступы даются из сайта и из программы владельца — синхронизацию с сайтом, и маркетплейс тоже».

## Что касса уже сделала без вас (ничего ломать не нужно)

- Касса и программа владельца перечитывают **`GET api/users/profile/`** и **`GET api/users/company/addons/`** раз в ~90 с, а также при возврате в окно и при открытии «Маркетплейса»/«Сотрудников».
  - Изменения применяются без перезапуска.
  - `GET api/users/company/` (тариф, `features`) и `GET api/main/marketplace/themes/` — раз в 10 минут.
- Доступы сотрудников программа владельца пишет уже существующим **`PATCH api/users/employees/{id}/`** (только изменённые `can_*`).
- Функция открыта, если её включил сервер (`addons`, `active:true`) **или** действует ключ активации на этом компьютере.

Ниже — что нужно от сервера, чтобы опрос стал почти бесплатным, а синхронизация — полной в обе стороны. Контракт — предложение, поправьте под себя и напишите нам итог.

## 1. Дешёвая проверка «изменились ли доступы» (приоритет 1)

**Проблема.** Каждые 90 с касса скачивает весь профиль. Касс в магазине несколько, магазинов — сотни.

**Просим (один из вариантов):**

- **А.** `ETag` в ответе `GET api/users/profile/` и `GET api/users/company/addons/`, плюс поддержка `If-None-Match` → `304 Not Modified`. Касса это уже умеет: так работает опрос `app-settings` и ленты товаров.
- **Б.** Поле `access_version` (целое, растёт при любом изменении доступов пользователя, его роли или addons компании) в профиле и лёгкий метод:

```
GET api/users/access-version/
→ 200 {"user_access_version": 1234, "company_addons_version": 56, "plan_version": 7}
```

Касса перечитывает профиль, addons или компанию только если версия выросла.

**Когда растёт версия:** `PATCH employees/{id}/` (любой `can_*`, роль, `is_active`), правка роли `roles/custom/{id}/`, включение или выключение addon, смена тарифа.

## 2. События вместо опроса (приоритет 2, по желанию)

Если есть лента событий компании (как `products/changes`), добавьте типы:

```
GET api/main/events/?after=<cursor>
→ {"results":[{"id":..,"kind":"access","user_id":"..","at":".."},{"kind":"addons"},{"kind":"plan"},{"kind":"themes"}],"next_cursor":".."}
```

- Касса уже опрашивает ленту каждые 3–8 с, поэтому событие `access` для её пользователя доставит изменение за секунды.
- Без данных: только тип и id. Права касса прочитает из профиля.

## 3. Ключи активации — на сервер (приоритет 2)

**Проблема.** Функции, открытые ключом (LicenseKeys на компьютере), сервер не знает: отключить, продлить или отозвать их с сайта нельзя. У постоянных ключей нет срока.

**Просим:**

```
POST api/users/company/addons/activate-key/
body: {"key": "NMK-...."}
→ 200 {"code": "kassa-labeleditor", "active": true, "until": "2027-11-11", "source": "key"}
→ 400 {"code": "invalid_key"} | 409 {"code": "key_used", "company": "<другая>"}
```

- После этого функция приходит в `GET users/company/addons/` с полем **`source`**: `"purchase" | "key" | "trial" | "support"`.
- Касса перестанет держать ключ «вечно локально». Отзыв на сайте закроет и ключевую функцию.
- Пакеты тарифа уже идут через `POST api/users/company/features/activate/`. Можно объединить оба метода в один.
- Хэши ключей пакетов в кассе есть. Список ключей функций передадим отдельно (не в этот документ, он секретный).

## 4. Покупка или подключение из программы (приоритет 3)

Сейчас из программы уходит только заявка `POST api/support/addon-requests/`. Оплату принимает поддержка.

**Если планируется онлайн-оплата:**

```
POST api/users/company/addons/{code}/checkout/
→ 200 {"payment_url": "https://...", "order_id": "..."}
GET  api/users/company/addons/orders/{order_id}/
→ 200 {"status": "pending|paid|failed", "addon": {"code":"kassa-..","active":true,"until":".."}}
```

- То же для тем: `POST api/main/marketplace/themes/{id}/checkout/`.
- Касса откроет `payment_url` в браузере и будет опрашивать заказ раз в 10 с не дольше 15 минут.

## 5. Доступы сотрудника из программы владельца

Метод `PATCH api/users/employees/{id}/` уже есть, и касса им пользуется. Просим подтвердить и, если нужно, добавить:

1. **Ответ после PATCH** — полная карточка сотрудника со всеми `can_*`, чтобы программа сразу показала итог (сейчас перечитывает список).
2. **Отказ** — единый формат `403 {"code":"permission_denied","required":"can_view_products"}` (было в ТЗ 26.10). Касса покажет в подсказке точное имя галочки.
3. **Защита:** себе права менять нельзя; права администратора выдаёт только владелец (`employee_rights_guard`, сервер ceba67c) — оставить.
4. **Конфликт:** последний записавший побеждает. Просим отдавать `updated_at` у сотрудника и принимать необязательный заголовок `If-Unmodified-Since`. Если запись старше — `409`, и программа предложит перечитать.
5. **Отключённый сотрудник** (`is_active:false`): `GET users/profile/` с его токеном → `401` или `403 {"code":"user_inactive"}`. Касса тогда выведет его из смены.

## 6. Права и безопасность

- Все методы — с токеном пользователя.
- Методы записи (п. 3–5) — только владелец или администратор компании.
- Метод из п. 1 доступен любому сотруднику. Он не раскрывает права других сотрудников, только версии.
- Без ПДн в событиях: id и тип.

## 7. Что касса сделает, когда метод появится

| Пункт | Что поменяется в кассе |
|---|---|
| 1 (ETag или версия) | Опрос профиля и addons станет условным: 304 или та же версия → без разбора. Такт можно будет сократить до 30 с без роста нагрузки |
| 2 (события) | `access` / `addons` / `plan` / `themes` будят нужную проверку сразу |
| 3 (ключи) | Ввод ключа отправляет его на сервер; ключевые функции приходят из addons с `source:"key"` и отзываются с сайта |
| 4 (оплата) | Кнопка «Купить» в «Маркетплейсе» вместо заявки |
| 5 (сотрудники) | Итог правки без перечитывания, точный текст отказа, предупреждение о конфликте |
