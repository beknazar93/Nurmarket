# Возвраты: правка и аннулирование в течение 24 ч — анализ и план (10–11.11.2026)

ТЗ владельца: «NurCRM Market — редактирование и удаление возвратных накладных в течение 24 часов» (возврат от клиента и возврат поставщику; PIN руководителя; срок 24 ч по серверу; склад и деньги пересчитываются транзакционно; журнал аудита; PDF/Excel с меткой «АННУЛИРОВАН»).
ТЗ серверу: **docs/Отчеты/ТЗ Умару — правка и аннулирование возвратных накладных 24 ч.md**. Контракт **предложен нами, сервером не подтверждён**.

## 1. Как сейчас (факты из кода)

| | Возврат от клиента | Возврат поставщику |
|---|---|---|
| Создание | `POST api/main/pos/sales/{id}/return/` (`idempotency_key`, `cashbox_role: pos_main`, `items[{sale_item_id, quantity}]`, `reason`); весь чек — без `items`. `SalesApiService.PosReturnSaleAsync / PosReturnWholeSaleAsync` | `POST api/main/suppliers/{id}/returns/` (Idempotency-Key; `reason, comment, compensation cash/debt_offset/none, cashbox_id, receipt_id, items[product_id, qty, purchase_price, receipt_item_id]`). `SupplierApiService.PostReturnAsync`, окно `SupplierReturnDialog` |
| Чтение | `GET api/main/pos/returns/?sale&date_from&date_to` → `id, sale, sale_number, amount, is_full, cashier, shift, created_at, items(qty,name), reason` (`NurCrmReportsApi.ListReturnsAsync`) | `GET suppliers/returns/`, `GET suppliers/returns/{id}/` → `id, supplier_*, receipt_id, created_at, reason, compensation, total_amount, created_by_name, comment, items(product_name, qty, unit, purchase_price, line_total, article, barcode), number_display, warehouse` |
| Версия / статус / closed_at / can_edit / история | **нет** | **нет** |
| Правка / удаление | нет (сервер не умеет) | нет |
| Где в окнах | `ReturnSaleDialog*` (оформление), `ReceiptHistoryWindow` (чек → возвраты), `FinanceWindow.Charts` (вкладка «Возвраты»), `ShiftDrillDownDialog`; мобилка `ops_repository.dart`, `shift_repository.dart` | `SupplierReturnsWindow` (раздел владельца), `PurchasesWindow` вкладка «Возвраты» (`ReturnRow`, `ShowReturnAsync`), `SupplierCardView.ReturnCard` |
| PDF/Excel | — | `SupplierReturnDocUi` + `SupplierReturnDocuments` / `…Renderer` (PDF, печать) / `…Office` (Word, Excel), строятся по ответу сервера |

- «Закрытие документа»: черновиков нет, оба возврата проводятся при создании → `closed_at` = момент проведения (просим сервер отдавать явно).
- **Образец «за признаком»**: удаление/правка прихода — `receipt_delete` / `receipt_edit` в `GET api/main/capabilities/` (`ServerCapabilities`), `DELETE/PATCH suppliers/receipts/{id}/` с Idempotency-Key + If-Match (428 `version_required`, 412 → `ReceiptChangedException`, повтор только после нового подтверждения), `GET …/history/`; права — `PermissionService.CanDeletePurchaseDocuments` (owner или `can_unpost_documents`).
- **PIN**: на сервере уже есть `POST api/users/auth/pin/verify/ {pin} → {token, expires_in}`; 400 `pin_invalid` + `attempts_left`; 429 `pin_locked` + `retry_after` (5 ошибок → 15 мин); токен идёт заголовком `X-Confirm-Token` (поздний чек: `SalesApiService.LateAccept`, `SyncService.VerifyOwnerPinForLateAsync`, `ExpiredSaleGuard.AskOwnerPinAsync`, `ActionGuard`). PIN нигде не хранится; `SensitiveDataRedactor` вычищает `pin`/`token` из журнала. Локальный PIN при запуске программы владельца (`OwnerStartupGate`, `AccountView.OwnerPin`) — локальный, для этой задачи **не годится** (проверка должна быть на сервере).
- Роли: `owner`/`admin` (`PermissionService.IsOwnerOrAdmin`), флаги `can_unpost_documents`, `can_edit_purchase_documents`.
- Время: `ServerClock` (сдвиг по заголовку Date) — для этой задачи только подсказка; решает сервер.

## 2. Главные решения

1. **Всё за признаками сервера** `supplier_return_edit_24h` и `pos_return_edit_24h` + разрешение в самом документе (`can_edit` / `can_void`). Нет признака или полей → кнопок нет, всё как сегодня.
2. **Срок 24 ч решает только сервер** (поля `editable_until`, `server_now`, `can_edit`; проверка при выдаче токена и ещё раз в транзакции PATCH/void). Касса показывает только подсказку «можно изменить ещё N ч» = `editable_until − server_now − время с ответа`; часы устройства в расчёт не входят. Перед PIN касса ещё раз читает карточку (свежие версия и срок).
3. **PIN** — расширение уже существующего `users/auth/pin/verify/`: `{pin, scope: return_edit|return_void, object_type, object_id, version}` → одноразовый `confirm_token` (≤120 с) для ОДНОГО действия над ОДНИМ документом и версией; заголовок `X-Confirm-Token`. Лимит попыток и блокировка — сервер; касса во время блокировки (429 + `retry_after`) запросов не шлёт, окно показывает отсчёт.
4. **Одновременная правка** — `If-Match: "version"` + `version` в теле; 412 `version_conflict` → «документ изменён другим сотрудником — обновите», ничего не повторяется молча (как Л5-13 у приходов).
5. **Без двойного проведения** — Idempotency-Key (`PendingIdempotencyKey`: тот же состав после обрыва — тот же ключ), сервер — сторно старых движений + новые в одной транзакции, движения привязаны к документу и версии.
6. **Soft delete** — `POST …/void/` с причиной; документ остаётся (`status: voided`). Старые кассы у клиентов не должны увидеть аннулированные в итогах → по умолчанию списки сервера без них, новая касса просит `?status=all`.
7. **Журнал аудита** — на сервере (snapshot до/после, кто создал/правил/подтвердил PIN, причина, время сервера); касса показывает `GET …/history/` только руководителю (сервер всё равно отвечает 403 остальным); первоначальная версия — `snapshot` v1.
8. PDF/Word/Excel строятся по актуальной версии; у аннулированного — «— АННУЛИРОВАН» в заголовке и строка «Статус: дата, причина».

## 4. Куда повесить кнопки «Возврата от клиента» (другому исполнителю)

Общие части готовы; кнопки в окнах клиента НЕ трогал. Подключение — одна строка там, где показан возврат (нужен `PosReturn` из `NurCrmReportsApi.ListReturnsAsync` — у него уже есть `Edit`):

```csharp
var doc = new ReturnDocRef(ReturnDocKind.Customer, r.Id, "№ " + r.SaleNumber, (double)r.Amount, r.Edit ?? ReturnEditState.None);
panel.Children.Add(ReturnEditFlows.Bar(this, doc, edit: null, reload: ReloadAsync));   // «Удалить» + «История» + подсказка срока
if (ReturnEditFlows.VoidedPill(this, doc.State) is { } pill) header.Children.Add(pill);   // «АННУЛИРОВАН»
```
Места: `ReceiptHistoryWindow.axaml.cs` (≈стр. 1050, блок «возвраты по чеку»), `ReturnSaleDialog.Outcome.cs` (≈стр. 37, итог после возврата), `FinanceWindow.Charts.cs` (вкладка «Возвраты», ≈стр. 49), `SalesWindow.Returns.cs` (новый файл другого исполнителя). Окно правки строк возврата от клиента (`edit`) — по образцу `SupplierReturnEditDialog`: поля `sale_item_id, quantity, price, discount, note`, PATCH `api/main/pos/returns/{id}/` через `ReturnEditApi.PatchAsync(ReturnDocKind.Customer, …)`. Списки `pos/returns/` для показа аннулированных — с `status=all` и итогами без `IsVoided` (иначе по умолчанию сервер их не отдаёт).

## 5. Риски

- Контракт не подтверждён: имена полей/адресов могут измениться — правки только в `ReturnDocEdit.cs`/`SupplierReturnEdit.cs`.
- Учёт: аннулирование возврата от клиента может увести остаток в минус (товар уже перепродан); наличные клиенту уже выданы — сторно должно идти текущим периодом; `debt_offset` после частичной оплаты долга; цепочки возвратов по одному чеку/приходу; известная ошибка частичного возврата долгового чека (06.11) — сначала закрыть её.
- Список «Закупки → Возвраты» и карточка поставщика запрашивают без `status=all` — аннулированные там не видны (сделано намеренно, чтобы итоги не задвоились); видны в разделе «Возвраты поставщикам».
- Мобилка: возврата поставщику нет; правка возврата от клиента в мобилке не делалась (только касса/владелец).

## 7. Не проверено вживую

Сервер этого не умеет: ни одной живой правки/аннулирования не было. Не проверены живые форматы ответов, PIN руководителя с областью действия, пересчёт склада и денег на сервере, PDF/Excel на реальном аннулированном документе, кнопки в настоящем окне на реальном аккаунте.

## 8. 11.11.2026 — сервер Умара готов (боевой app.nurcrm.kg): сверка с реальным контрактом

- Тела: возврат от клиента `PATCH pos/returns/{id}/ {version, edit_reason, items:[{sale_item_id, quantity}]}` (без цен/скидок); поставщику `items:[{id, qty, purchase_price}]` — скидка и примечание строки убраны из окна правки и из тела (сервер их не хранит), строка без id не отправляется (`new_lines_not_allowed`). Idempotency-Key + If-Match + X-Confirm-Token на PATCH/void; `replayed:true` — успех.
- `edit_block_reason` → пояснение на 5 языках под строкой возврата (кнопок нет): legacy / чек в долг / агент / после был другой возврат / смена закрыта / 24 ч / уже аннулирован / нет прав (`ReturnEditErrors.BlockReasonText`, `ReturnEditGate.BlockHint`).
- Коды: 428 confirm_required / version_required, 403 confirm_invalid, 412 version_conflict (+current_version), 400 validation_error / idempotency_key_required / new_lines_not_allowed, 409 negative_stock / exceeds_returnable / debt_already_paid / period_closed, PIN: pin_invalid (+attempts_left), pin_not_set, pin_locked (+retry_after) — свои тексты.
- `?status=all` при признаке: «Закупки → Возвраты», карточка поставщика, «Возвраты поставщикам», возвраты чека (окно возврата, история чеков, покупки клиента), «Финансы → Возвраты»; итоги и ленты — без аннулированных.
- Новое окно `CustomerReturnEditDialog` (строки, «можно до N» = returnable_qty чека + количество в этом возврате, «Убрать», причина, сумма ≈, PIN → PATCH); окно «Возвраты по чеку» (`ReturnEditFlows.ShowCustomerReturnsAsync`) и кнопка «Правка возвратов» (`CustomerReturnsEntry`) в «Истории чеков» и «Покупках клиента»; кнопка «Правка» в строке «Финансы → Возвраты»; в окне возврата по чеку — «Редактировать / Удалить / История». После правки/аннулирования — перечитывание чека/списка и остатков товаров (`StockSyncService.ScheduleStockReread`).
- Тесты: `ReturnEdit24hContractTests` (WireMock), `ReturnEdit24hUiTests` (окна клиента и поставщика, PIN, плашка долга; 1024×600 / 1366×768, ru/ky).
- Живьём на NBS ещё не проверено: PIN владельца, правка и аннулирование возврата не-долгового чека за сегодня, перечитывание остатков.
