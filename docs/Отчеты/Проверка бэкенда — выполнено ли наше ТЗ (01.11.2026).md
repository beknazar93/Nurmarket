## 6. Что исправить в КАССЕ, раз сервер уже сделал

1. **Проведение старых чеков по PIN не найдёт токен.**
   - Описание `POST api/users/auth/pin/verify/` (OPTIONS): ответ `{token, expires_in}`.
   - Касса ищет только `confirm_token`, `confirmation_token`, `x_confirm_token`: `NurMarketKassa.Infrastructure/Services/Api/SalesApiService.LateAccept.cs:30`.
   - Итог: подтверждение PIN всегда вернёт `no_token_field`, и чеки старше 7 суток по PIN не проведутся.
   - Что сделать: принимать `token`, когда рядом есть `expires_in` и нет `access`/`refresh`.
   - Сервер на чек старше 7 суток отвечает `400 offline_too_old` с `data {max_days, late_max_days, accept_late}`.
2. **Бонусы без ключа повтора.** `Services/ServerLoyalty.cs:146`: `POST clients/{id}/bonus/` уходит без `Idempotency-Key`. Сервер ключ понимает: повтор → 200, бонус не удваивается. Добавить заголовок и `idempotency_key` в теле.
3. **Возврат чека: ключ только в теле.** Это `SalesApiService.cs:854, 894` и `SalesApiService.Exchange.cs:99`. Сервер это понимает: повтор даёт тот же `refund.id`. Можно сделать надёжнее:
   - добавить и заголовок;
   - после обрыва узнавать исход через `GET api/main/idempotency/{key}/` (`found, state, status_code`) — как уже сделано для checkout (`SalesApiService.QuickCheckout.cs:89`).
4. **Архив товара вместо удаления.** В коде нет `/archive/` и `product_has_history`. На `DELETE` товара с историей сервер отвечает `409 product_has_history` с `data {receipts, sales, transfers, supplier_returns, purchase_orders}`. Предложить «Отправить в архив»: `POST products/{id}/archive/` и `unarchive/`, по признаку `product_archive`. Учесть:
   - архивный товар по `GET products/{id}/` даёт **404**;
   - в списке он виден только с `?include_archived=1`.
5. **Закупочная цена — 4 знака.** Сервер хранит 4 знака, касса режет:
   - до 2 знаков: `CatalogApiService.cs:876` (`"0.##"`), `BulkImport/BulkCardsLoader.cs:344`, `PurchaseReceivingService.cs:1014` (комментарий «не больше 2 знаков» устарел);
   - до 3 знаков: `PurchaseReceivingService.cs:745`, `Purchases/ReceiptEditService.cs:405, 811, 912`.

   Это и есть причина расхождения с бумажной накладной (сводное п. 19).
6. **«Продажи и финансы» — позиции пачкой.** `GET api/main/pos/sales/items/?date_from&date_to` (`count, limit, offset, results`) вместо ≈230 запросов по чеку. Сейчас касса этим адресом не пользуется. Определение выручки — в `definition` (`sales_total_minus_returns_v1`).
7. **Номера документов.** Сервер отдаёт:
   - `number_display` («ПР-2026-000073» / «ВП-2026-000010»), `series`, `year`, `sequence`;
   - рабочие фильтры `?number=` и `?document_number=`.

   Касса их не читает (`SupplierApiService.cs` `ParseReceipt`).
8. **Возврат сверх оплаченного.** В `409 refund_exceeds_paid` теперь есть `max_quantity`, `max_amount`, `requested_quantity`. Показывать кассиру «можно вернуть не больше …».
9. **Лента изменений.** `main/changes/` отдаёт `supplier_debt_changed`, `bonus_changed`, `stock_changed`, `sale_returned`. По ним можно обновлять долг поставщику и бонусы без перечитывания.
10. **Swagger работает** (2 578 путей) — сверять контракт можно по нему, а не наугад.
11. **Из Сверки 01.11 (ещё в силе):**
    - `return_status:"full"` (`CartDisplayHelper.cs:196`);
    - процент скидки от округлённого подытога;
    - весовая строка — вниз;
    - `stock[]` в ответе checkout;
    - `available:false` у помощника.
12. **Ссылка-корзина и события витрины** (`cart-link`, `showcase/events/`) готовы на сервере. Для бота кассы (Т3, метки `c_`/`w_`) серверная часть есть, касса её ещё не использует.
