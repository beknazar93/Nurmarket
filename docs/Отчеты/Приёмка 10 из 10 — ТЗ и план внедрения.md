## 1. Критерии «10 из 10» — измеримая матрица

### 1.0. Правила подсчёта

- **Оценка измерения** = ⌊10 × выполнено / всего⌋. **10 — только когда выполнены все пункты.** Итог приёмки — минимум по семи измерениям (не среднее).
- **Действие** (для подсчёта в UI-тестах) — одно законченное усилие человека. Это одно из:
  - скан (серия символов сканера с Enter);
  - одно нажатие клавиши или сочетания (Enter, F9, Ctrl+Enter, Esc, цифра 1–5);
  - набор значения в поле, закончившийся Enter или Tab (считается одним действием, как в аудите);
  - один щелчок мышью или касание.
  
  Перемещение курсора программой — не действие.
- **Время без живого человека** — модель KLM (Keystroke-Level Model): символ 0,28 с, Enter/клавиша 0,28 с, скан 1,0 с, наведение мышью 1,1 с, перенос руки клавиатура↔мышь 0,4 с, «подумать» перед полем 1,2 с. К этому прибавляется измеренная задержка программы на каждом шаге. Сценарий из теста переводится в секунды функцией `KlmEstimate(script)` — она лежит в стенде `UiTests/Harness/ReceivingDriver.cs`, её делает пакет H. Живая проверка: секундомер, NBS, медиана 5 попыток.
- **Стенд**:
  - Avalonia.Headless, сервер — `UiFake`/WireMock (`FakeNurCrmServer`);
  - тесты — только `tools/qa/test-safe.ps1` (`-Phase unit|ui`, `-Filter "FullyQualifiedName~Receiving"`);
  - снимки — `%TEMP%\nurmarket-tests\ui-actual\rcv10\…`; эталоны обновляются сознательно (`-UpdateSnapshots`), с визуальным разбором.
- **Размеры**:
  - окна: 1024×600, 1280×720, 1366×768, 1920×1080;
  - масштаб 100/125/150 % (в Headless — `RenderScaling`);
  - темы: светлая, тёмная, «Сенсорная»;
  - языки: ru, ky, en, tr, uz.

  Все сочетания — только для снимков ключевых состояний (таблица в 1.5). Остальные проверки — ru/ky на 1024×600 и 1366×768.
- **Каталог для замеров**: генератор `CatalogFixture.Make(n)` (пакет H) — 15 000 и 50 000 товаров с настоящими формами кодов из разбора «470»: EAN-13 470…/46…/487…, EAN-8, UPC-A, 9-значные «200…», дубли, неверные контрольные цифры.

### 2.5. Событийная модель

Всё в потоке UI. Сессия — обычный объект с событиями C#: без статических событий наружу, без MediatR.

| Событие | Когда | Кто слушает |
|---|---|---|
| `LinesChanged(NotifyCollectionChangedEventArgs)` | добавление, удаление, порядок | таблица (через `ObservableCollection`), черновик, итоги |
| `LineEdited(ReceivingLineVm, string property)` | `PropertyChanged` строки (сессия подписывается сама и отписывается при удалении) | итоги (на каждый символ, С-10), проблемы, черновик (`Touch`) |
| `ScanFinished(ScanOutcome)` | конец обработки скана | карточка «последний», вспышка, звук, фокус, карточка нового (`New`) |
| `ScanStarted(code)` / `ScanPending(code)` | скан ушёл на сервер | индикатор «Ищу на сервере…» |
| `IssuesChanged(IReadOnlyList<ReceivingIssue>)` | пересчёт проблем (debounce 150 мс) | флажки внизу, причина на кнопке, рамки полей |
| `SupplierChanged`, `PaymentChanged` | шапка | закупки по истории (Д-12), шаги, подсказка |
| `PostStateChanged(Idle / Reviewing / Queued / Waiting / Done / Background / Failed)` | проведение | кнопка, полоса итога, состояние экрана |
| `DraftSaved(DateTime)` / `DraftRestored(n, stockChanged)` | черновик | подпись «Черновик сохранён 10:42» |

Правила:
1. Асинхронные команды сессии возвращают исход (`Task<ScanOutcome>`), а не `void`. После каждого `await` проверяется `IsDisposed`/«та же сессия» (сейчас это `_receive != s` в 20 местах).
2. Повторный вход в `ScanAsync`, пока предыдущий скан ждёт сервер, допустим: коды обрабатываются по порядку, вторая копия того же кода — «гонка» (`raced`, как в `WarehouseViewModel:952`).
3. `Dispose()` снимает все подписки: `ReceivingMarkupSettingsStore.Changed`, `BackgroundReceivingQueue.JobFinished`, язык, тема.

### 2.6. Порядок поиска при скане (`ReceivingScanResolver`)

```
код ← ProductCodeLookup.Normalize(ввод)            // мусор сканера, пробелы, русская раскладка
0. Повтор: RepeatGuard.Check(код)==Repeat и строка с кодом есть → AskRepeat (окно «Сколько?»)
1. Строка уже в приёме (штрихкод или товар) → Bumped (+1 в единицах колонки, ReceivingRepeatScan.AddTo), строка наверх
2. Не похоже на код (буквы, < 4 цифр) → поиск по названию (ReceivingNameSearch: память → база кассы → умное);
   точное → Added; умное → Suggestions (без добавления); каталога нет → NotFoundByName (новый не предлагать)
3. База кассы: ProductCodeLookup.FindLocal(код, allowWeightLabel:false) — основной, доп. коды, размеры, артикул/код целиком → Added
4. Нет связи (BackgroundReceivingQueue.NoConnectionNow) → сразу к шагу 7 (сеть не ждём)
5. Склад сервера: warehouse-barcode/{код}/?branch=<филиал>, ответ только при ServerAnswerHasCode(requireField:true).
   Параллельно (до ответа Умара о доп. кодах): products/list/?search=код с точной сверкой (ResolveServerResultsAsync).
   Общий бюджет 3 с; оба точных → берём warehouse-barcode. AmbiguousBarcodeException → Ambiguous
6. Общая база NurCRM: локальная копия GlobalProductCatalog.Find, затем global-barcode/{код}/ (+BarcodeForms.Alternate),
   ответ — только при ServerAnswerHasCode(requireField:false) → New(Source=GlobalBase, название подставлено)
7. Весовая этикетка: только если ProductCodeLookup.ScalePrefixConfigured и FindWeightLabel нашла товар → Added/Bumped на вес
8. 13 цифр и неверная контрольная цифра → CheckDigitHint («отсканируйте ещё раз», «Это …?» при соседе в каталоге, «Всё равно добавить»)
9. Иначе → New(Source=Unknown) — открывается карточка нового товара
Каждый исход: PurchaseReceivingService.LogScan(код, путь, результат) + длительность в мс.
```

Что меняется по сравнению с сейчас:
- оба входа идут одним порядком;
- шаг 5 делает оба запроса параллельно (раньше в «Закупках» последовательно, в «Складе» без `list?search`);
- шаг 8 новый (рекомендация из разбора «470», п. 6.3);
- шаг 6 сначала смотрит встроенную копию общей базы (быстро и без сети).

Логика `LookupAsync` и `FindLocal` не переписывается — resolver их вызывает.

### 2.7. Ввод в ячейки без «эха» — `EchoGuard`

Корень регрессии 1.17.82–84: в Avalonia 11.2 `TextChanged` приходит через Dispatcher, позже, чем снят флаг `Syncing`. Поэтому текст, который поставила сама программа, разбирался как ввод кассира (`PurchasesWindow.Receive.Render.cs:329–342`).

Правило для нового кода (обязательно, проверяет ревью Q1):
1. **Поля строки таблицы и карточки — только `Binding` TwoWay к `*Text`-свойствам `ReceivingLineVm`**: `QtyInputText`, `PurchaseInputText`, `SalePriceText`, `MarkupText`, `ProductName`, `PackCountText`, `PiecesText`, `PackPriceText`. Свойства уже хранят сырой ввод во время правки, а `CommitText()` нормализует его по уходу из поля. Движок привязок не возвращает в источник значение, которое сам поставил, — эха нет по построению. Так уже работает таблица Склада.
2. **Запрещено**: `TextChanged` → запись в VM в файлах `Receiving*`. Тест-сканер исходников это ловит.
3. Где запись в поле руками всё-таки нужна (поле скана, поиск «Каталога», PLU, № накладной), есть `EchoGuard`:
   ```csharp
   public sealed class EchoGuard
   {
       public void Put(TextBox box, string text);   // запомнить «это поставила программа» и поставить текст
       public bool IsEcho(TextBox box);             // true — этот TextChanged от Put; запись снимается при первом отличии
       public void Forget(TextBox box);
   }
   ```
   Алгоритм тот же, что в `Render.cs:333–342` (словарь «поле → поставленный текст»), но в одном месте и с тестами.
4. Переиспользование строк при прокрутке (виртуализация) меняет только `DataContext`: привязки переключаются без записи в источник. Тест Д-7 (`Echo_Recycle_NoMutation`) обязателен.
5. Уход из поля (`LostFocus`, Enter, Tab) → `line.CommitText()`; Esc → `CancelCellEdit()` (снимок `BeginCellEdit` при входе в поле).

### 2.8. Таблица и виртуализация

### 3.6. Шапка

- **«← Закупки»** (вход «Закупки») или ничего (вход «Склад» — вкладка). Esc на пустом экране — назад; с работой — черновик сохраняется, назад без вопроса (черновик потом предлагается).
- **Шаги ①②③ нажимаются**: ① → открыть выбор поставщика (F4); ② → поле скана (F2); ③ → «Проверка и оплата» (F9). Готовый шаг — `BrushSuccess` с ✓, текущий — `BrushAccentSoft` + полужирный, будущий — `BrushTextMuted` (не `TextSoft`, AA). Подсказка «что дальше» под шагами по состоянию:

| Состояние | Подсказка |
|---|---|
| пусто, без поставщика | «Сканируйте товары — поставщика можно выбрать позже» |
| пусто, с поставщиком | «Сканируйте товары или откройте «Каталог» поставщика» |
| есть строки, есть проблемы | «Исправьте отмеченные строки: N ▸» |
| есть строки, нет поставщика | «Выберите поставщика или проведите без него» |
| всё готово | «Проверьте итог и нажмите «Провести приход» (F9)» |
| нет связи | «Нет связи — приход сохранится и уйдёт сам» |

- **Поставщик**: поиск по названию, телефону, ИНН (`PurchasesSupplierPicker` переносится как есть); «+» — новый поставщик. После выбора закупки строк подставляются по истории этого поставщика (Д-12).
- **Оплата**: сегменты «Сразу · Частично · В долг до [дд.мм ▾]», срок по умолчанию 30 дней (настройка магазина). Последний выбор запоминается на ПК. Без поставщика сегменты неактивны с подписью «без поставщика — без долга и оплаты». Сумма частичной оплаты и источник «Сразу» (касса расходов / ящик смены) задаются в окне проверки.
- **№ накладной**: поле 140 px (`MinWidth`), подпись-водяной знак «№ накладной» (в ky — короткий вариант «Накл. №», полный — в подсказке).
- **«Накладная ▾»**: «Загрузить файл / фото» (существующий `InvoiceImportFlow`), «Повторить прошлый приход», «По заказу поставщику».
- **«⋯»**: «Наценка для всех…», «Доп. расходы…», «Обнулить количество», «Очистить список», «Настройки приёмки».

### 3.7. Поле скана и «последний товар»

- Поле 56 px (52 на 1024), шрифт 16, значок `IconBarcode` слева, водяной знак «Штрихкод или название — F2». При фокусе — рамка `BrushFocusRing`.
- Пока идёт поиск на сервере, справа в поле — «Ищу на сервере…» с крутилкой; можно сканировать дальше.
- **«Последний товар»** — карточка 40–96 px, держится до следующего скана:
  - строка 1: значок исхода (✓ добавлен, +1 повтор, ★ новый, ⚠ не принят) + название крупно (15 полужирный, 2 строки);
  - строка 2: значок источника + текст («Склад», «База NurCRM», «Неизвестно», «Из интернета»), «было 4 → станет 16 шт» (в единицах колонки, Б-4);
  - строка 3: «[−] 12 [+]» — шаг 1 или 0,5 для дробных; клавиши «+»/«−» на цифровом блоке, когда фокус в скане и поле пустое. Закупка мелко.
  - Диктор: живой регион, читает «Добавлено: Масло…, 16 штук».
- **Вспышка**: фон карточки и строки — 150 мс появление, 1,2 с затухание. Склад — `BrushSuccessSoft`, база NurCRM — `BrushAccentSoft`, новый — `BrushWarningSoft`, ошибка — `BrushDangerSoft` на поле скана. При «без анимаций» (`RenderModeSettings`) — без затухания. Раскладка не сдвигается.
- **Звук**: по умолчанию **выключен** (решение владельца). Настройка «Настройки → Приёмка → Звук при скане». Три коротких сигнала: успех, новый, ошибка. Только Windows (winmm), на Linux/Android переключатель скрыт.

- текущая — фон `BrushAccentSoft`;

| Штрихкод | 7 | отсканированный код | без кода (вход Ins) — выбор «Сгенерировать» (`BarcodeGenerator.GenerateForReceivingLine`: не «0», не «2», не «470», без дублей) / «Без штрихкода» |
| PLU | 8 (только «кг») | следующий свободный (локальный максимум + 1, сверка с `GetWeightProductCountAsync`) | уходит при создании (`ProductEditRequest.Plu`); занят на сервере (400) → следующий и запись в журнал |
| «Найти в интернете» | кнопка | — | **только по нажатию** (`ReceivingInternetLookup`), результат помечается «Из интернета» |

- **Enter-цепочка типового случая**: Название ⏎ → Закупка ⏎ → «Готово» ⏎ = 3 действия (С-4). Пропущенные поля берут умолчания.
- «Готово» → карточка сворачивается, строка становится обычной «новой», **фокус в поле скана**.
- **Esc** → свернуть: введённое остаётся в строке, пустое название — красная пометка в строке. Повторный Esc в скане — назад.
- **Новый скан при открытой карточке**: она сворачивается в строку без потерь, обрабатывается новый код (если тоже новый — открывается его карточка).
- Повторный скан того же неизвестного кода → «Сколько?», а не вторая карточка.
- Товар на сервере создаётся **только при проведении** (как сейчас).
- Вход без скана: «＋ Новый товар» / Ins → та же карточка без штрихкода.

### 3.10. Нижняя панель

- Слева — флажки проблем по видам, только если они есть: «⚠ без названия: 1 ▸», «⚠ без закупки: 1 ▸», «⚠ без цены продажи: 2 ▸», «⚠ ниже закупки: 1 ▸», «▲ подорожало: 2 ▸» (последний ведёт к «Обновить цены продажи»). Нажатие — к первой строке вида, повтор — к следующей.
- Справа — «Итого приход» подписью 12 и суммой 22–24 полужирно, `BrushAccentText`, `num` (как Ф0). Под суммой мелко — «Прибыль +4 539,00» (видна кассиру).
- Кнопки: «Очистить» (в «⋯» на 1024), «Этикетки (N)» (N — строк с количеством; печать «Этикетки на приход», существующая), **«Провести приход F9»**.
- **Причина неактивности** — текстом слева от кнопки, не только подсказкой: «Добавьте товар» / «Нужно исправить: 2 ▸» / «Идёт проведение…». Без поставщика кнопка активна, в подсказке: «без поставщика — без долга и оплаты».

### 3.15. Touch-вариант

Тема «Сенсорная» → ресурсы `NurFieldHeight` 52, `NurTouchTarget` 52, `NurRowHeight` 56, шрифт 16:

- «−/+» карточки 52×52;

### 3.16. Доступность
