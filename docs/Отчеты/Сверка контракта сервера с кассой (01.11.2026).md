Модель сервера, которая сходится со всеми 7 чеками:
1. Обычные строки: `qty × price` без округления; весовая строка — **вниз** до 0,01 (22,638 → 22,63).
2. `subtotal = HALF_UP(Σ строк, 0,01)`.
3. Скидка чека процентом = `HALF_UP(subtotal_ОКРУГЛЁННЫЙ × p / 100, 0,01)` — от округлённого подытога (чек 1977: 1,43 × 50 % = 0,715 → 0,72; от точного 1,425 было бы 0,71).
4. `total = subtotal − скидка` (уже два знака).

Ответы на вопросы координатора: (а) 0,345 × 45 со скидкой 10 % → **13,98** (`subtotal 15.53`, `discount_total 1.55`); весовой товар по API с ценой 45 сервер не продал (`price_below_cost`, закупка 50,60), поэтому проверен настоящим весовым товаром по 66,00 — строка округляется вниз; (б) 17,00 − 2,5 % → **16,57**, 5,00 − 2,5 % → **4,87**; (в) процент — **от округлённого** подытога (чек 1977); (г) 0,375 × 3,80 дважды → **2,85**.

Скидки строк вместе со скидкой чека не проверялись (база процента «подытог − скидки строк» — предположение).

## 5. Ошибки сервера (Умару)

1. Возврат долгового чека: `expected_cash`/`drawer_expected_cash`/`ledger_expected_cash` смены не уменьшаются на `refund.cash` (чек 1973: выдано 2,00, ожидаемая осталась +2), хотя `cashbox.balance` уменьшен верно.
2. Долговой чек после полного возврата: `remaining_debt "2.00"`, `debt_remaining "3.00"`, `debt_amount "3.00"` при `debt_adjustment.remaining_debt 0.00` и закрытой сделке.
3. Весовая строка: `line_total` строки 22,64 (половина вверх), а `subtotal` 22,63 (вниз) — сумма строк на чеке не равна подытогу.
4. `shift_totals.cashbox.name` в ответе checkout — сломанная кодировка.
5. PATCH прихода без `version` и без `If-Match` принимается без проверки версии (касса так не делает, но сайт/телефон могут затереть чужую правку).
6. В теле checkout нет поля примечания — тестовые чеки нельзя пометить «АУДИТ 01.11» (пометка есть только в названиях доп. услуг чеков 1974–1978).

## 8. Правило округления весовых (по опытам)

Опыты 01.11, вечер: смена `19fefe82`, наличные, каждый чек сразу возвращён целиком. Скрипты `contract-check\w_round.py`, `w_round2.py`, проверка правила — `v_rule.py`; ответы сервера — `out\W*.json`, `out\weight_results.jsonl`.

Опыт (е) для x,xx4 не ставил: вниз и половина вверх дают там одно и то же число. Опыт (г) с 0,345 × 45 тоже ничего не различает (38,163 → 38,16 при любом правиле), поэтому взята доп. услуга 0,344 × 13 = 4,472.

Что из опытов следует:
- Вниз округляется **сумма всех весовых строк чека** (не каждая строка): 1981 — 4,875 + 22,638 = 27,513 → 27,51 (если каждую строку вниз — вышло бы 27,50).
- Невесовые строки (штучные и «Доп. услуга», даже с дробным количеством) складываются точно и округляются половиной вверх **отдельно**, а не вместе с весовыми: 1985 — 22,63 + 4,472 = 27,102 → 27,10 (если весь подытог вниз — вышло бы 27,11; если половиной вверх — 27,11).
- «Весовая» = у товара `is_weight: true`. Ни единица «кг», ни дробное количество тут ни при чём: «Алма» (`dee7b768`, кг, `is_weight: false`) в чеках 1854–1856 — 2,295 × 45 = 103,275 → **103,28** (половина вверх).
- Скидка чека в процентах считается от уже округлённой базы: 1986 — (22,63 − 0,07) × 15 % = 3,384 → 3,38; итог 19,18 (если от точной базы 22,568 — вышло бы 3,39 и 19,17). `discount_total` = скидки строк + скидка чека.
- `line_total` / `amount` у весовой строки сервер показывает половиной вверх (22,64), поэтому сумма строк на чеке не равна `subtotal` (22,63). Это нестыковка на сервере.

**Формула сервера** (сходится со всеми 18 чеками 1971–1988 и с 66 из 69 весовых чеков дампа `round-1031\sales-detail.jsonl`):
```
W = Σ qty × price по строкам, где product.is_weight = true            (точно)
N = Σ qty × price по остальным строкам (штучные, «Доп. услуга»)       (точно)
subtotal       = FLOOR(W, 0.01) + HALF_UP(N, 0.01)
base           = subtotal − Σ скидок строк
order_discount = HALF_UP(base × p / 100, 0.01)      (скидка суммой — как есть, не больше base)
discount_total = Σ скидок строк + order_discount
total          = subtotal − discount_total
```
Три чека дампа, где формула не сошлась (195, 202, 203 от 24.08.2026), — по удалённым товарам (404), флаг `is_weight` у них не узнать. С допущением «весовой» они сходятся (867,475 → 867,47; 29,325 → 29,32; 15,525 → 15,52).

Что поправить в кассе:
- Округлять вниз не каждую весовую строку, а сумму весовых строк: `CartTotalsCalculator.cs:52-62` (накопить отдельно весовые и остальные, затем `FLOOR(W) + HALF_UP(N)`), а также `QuickCheckoutBody.cs:275-286` (`ComputeTotal`).
- Признак «весовая» брать из `is_weight` товара: проверить, что `CartDisplayHelper.LineMustWeigh` смотрит именно на него, а не на единицу «кг» или дробное количество.
- База процента — округлённый `subtotal − скидки строк` (как в разделе 3).
- Две строки одного весового товара по одной цене сервер не принимает (500). Касса сливает их в одну позицию (`QuickCheckoutBody.cs:70-93`) — это слияние нельзя убирать.

Следы опытов: чеки 1984–1988 (27,63; 27,10; 19,18; 22,50; 32,07) — все возвращены наличными, остатки W 0,500 кг и Маски 10 шт — как были.
