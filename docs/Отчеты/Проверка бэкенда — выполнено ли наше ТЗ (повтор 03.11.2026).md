3. **Не склеивать в один запрос две одинаковые весовые строки** — сейчас касса и так шлёт одну (Сверка 01.11). Причина: сервер отвечает 500. И итог чека брать из `subtotal` / `total` сервера, а не из суммы `line_total` строк — у весовой строки они расходятся на копейку.
4. **«Касса:» после возврата долгового чека.** Сервер не вычитает `refund.cash` из ожидаемой наличности смены. Пока Умар не исправит, касса должна сама вычитать `refund.cash` из ожидаемой суммы. Если уже вычитает, проверить, что поправка не задвоится, когда сервер исправит; ориентир — `debt_adjustment.cash_refund_due`.
5. **Долговой чек после возврата:** не верить `remaining_debt`, `debt_remaining`, `debt_amount` чека — они устаревшие. Брать `status:"canceled"` или `return_status:"full"` и `debt_adjustment` из ответа возврата.
6. **PIN.** Касса уже принимает поле `token` и знает `pin_not_set` (`SalesApiService.LateAccept.cs:31`). На NBS PIN не задан — для живой проверки «старых чеков по PIN» владельцу нужно задать PIN.
7. **Поиск исхода по ключу.**
   - Журнал хранится 7 дней; в ответе есть полный `response`: из него можно сразу взять `refund` или `id` прихода, без второго запроса.
   - Бонусы в этот журнал не попадают: для бонуса исход по ключу так не узнать — сверять по балансу или истории.
8. **Новые признаки, которыми можно пользоваться:**
   - `returns_search` — работает `pos/returns/?search=2014` → 1;
   - `receipts_filters` — `suppliers/receipts/?supplier=&date_from=` работает;
   - `shifts_date_filter` — `shifts/?date_from&date_to` работает;
   - `products_has_promotion` — `products/list/?has_promotion=true` → 5;
   - `debt_pay_idempotency` — касса ключ уже шлёт.

   Касса сейчас фильтрует эти списки сама.
9. **Правка накладной.** Сервер принимает PATCH без версии, но касса версию шлёт всегда — менять ничего не нужно. А сайт и телефон могут затереть правку кассы: это вопрос к Умару.
