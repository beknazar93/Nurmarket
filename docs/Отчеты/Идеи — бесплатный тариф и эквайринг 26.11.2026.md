## Часть А. Вечный бесплатный тариф

### А1. Что делают другие

| Kaspi Касса (КЗ) | бесплатно целиком (касса, подключение, ОФД) — зарабатывает на платежах | — | [П21] |

**Вывод [О]:** все делают одно и то же — бесплатный *вход* с границами, который закрывается ростом (товары/точки/сотрудники) и платными функциями; платят за результат платежи, подписки на рост, а не сам вход.

### А2. Что у нас уже есть [К]

- Планы приходят с сервера в `capabilities.plan`: `limits{max_staff, max_devices, max_cashboxes}`, `allowed_clients[]` (для «Мини» — только `mobile`), `upgrade_plan`; блок `plan_limit` и диалог «перейти на Старт, не теряя чек» (`PlanBlockMonitor`) уже работают.
- Пробные периоды на сервере: Мини 14 дней при регистрации, Старт/Стандарт 10 дней, модуль 7 дней (старая инструкция, раздел 4).
- **Нет** лимитов по числу товаров, чеков в месяц, истории продаж — этих полей в `capabilities` нет. Это главное, что нужно просить у Умара.

### А3. Предлагаемый вариант «Старт-Free» (рекомендация)

Основная идея: бесплатный тариф не «урезанная касса навсегда», а **бесплатная касса для малого и одного человека**, которая честно подводит к Мини/Старту, когда магазин растёт.

| Параметр | Предложение (допущения [Доп]) | Почему |
|---|---|---|
| Срок | без срока | это и есть «вечный» |
| Точки / кассы / сотрудники | 1 точка, 1 касса, 1 сотрудник (владелец=кассир) | не конкурирует с Мини/Стартом для магазина с кассирами |
| Устройства | 1 устройство на выбор: Windows/Linux/Android **или** телефон | иначе клиент будет «одним телефоном» вести 3 точки |
| Товары | до 300 | как у Telemedia (по [П21]); 2–3 страницы прилавка |
| Чеки | до 300 чеков в месяц [Доп] | магазин «у дома» делает больше → естественный рост |
| История продаж | 60 дней | для отчётов за год нужна подписка (как у Loyverse) |
| eKassa / фискализация | **без** (или eKassa платно отдельно 650 сом у Telemedia — как есть) | фискальная часть стоит нам и Telemedia; кому нужен чек ФД — идёт на Мини/Старт |
| Модули Маркетплейса | только 7-дневные пробы; постоянные — платные | сохраняем платные модули 100–300 сом |
| Сферы | любая; «Базар» и «Автозапчасти» открыты (витрина сфер) | показываем глубину, не продаём железо |
| Весы/ККМ-периферия | без (скан, чековый принтер — да) | весы и этикетки — модуль 200 сом |
| ИИ-накладная, Нур Советник, Telegram-отчёты | нет (пакеты), 3 пробы ИИ в месяц [Доп] | дорогой расход (ИИ) |
| Водяной знак на чеке | да: строка «Касса NurCRM — nurcrm.kg» на печатном чеке и на экране; снимается на любом платном тарифе | реклама + мотив платить; **юридически** для фискальных чеков нельзя менять обязательные реквизиты — делаем нижнюю строку, не меняя фискальную часть |
| Поддержка | база знаний и бот; чат WhatsApp — платным | экономия |
| Перенос данных | 1 раз, до 300 товаров | |
| Реклама в кассе | нет (портит доверие) | |

### А4. Как не убить платные тарифы

1. **Мини (500) остаётся «базарной кассой с поддержкой»**: бесплатный не даёт eKassa, сотрудников, ИИ, 2-е устройство. Граница по возможностям, а не только по объёму.
2. **Жёсткий потолок по чекам/товарам** с плавным апселлом: на 80 % — подсказка «Осталось 60 чеков», на 100 % — касса не блокирует продажу, а **предлагает Мини/Старт за одно нажатие** (как уже умеет PlanBlockMonitor), 3 «забытых» продажи в месяц разрешены.
3. **Один бесплатный на человека/ИНН/телефон**: защита от фермы бесплатных аккаунтов (номер телефона + устройство; по ИНН при регистрации юрлица [Доп]).
4. **Нельзя на бесплатном:** eKassa, филиалы, ИИ, Telegram-отчёты, права кассиров, API. Это то, за что платят компании (Старт = 1 300).
5. **Конверсионный бюджет вместо «бесплатно навсегда» для всех:** на сайте «бесплатно до 300 товаров и 300 чеков».
6. **Пилот, не запуск:** сначала только мобилка + 1 Windows, 3 месяца; смотреть конверсию в Мини/Старт.

### А5. Модель дохода (все числа — допущения [Доп], не прогноз)

Допустим, за 6 месяцев приходит 1 000 регистраций на «Старт-Free». Если 8 % переходят на Мини/Старт (средняя 800 сом/мес) — 80 клиентов × 800 = 64 000 сом/мес. Стоимость бесплатных: хранение, сервер, поддержка ~ 15–30 сом на аккаунт/мес (допущение) = 15–30 тыс. сом/мес. При конверсии 3 % — 24 000 сом/мес, это ниже порога. **Ключевое — стоимость на бесплатного: нужны лимиты на ИИ, фото, историю.** Если конверсия <3 %, программу сворачиваем или сужаем (лимит 150 товаров).

### А6. Что просить у Умара (сервер)

1. План `free` в `capabilities.plan` с `limits`: добавить поля `max_products`, `max_sales_per_month` (+ окно «месяц» по календарю компании), `history_days`.
2. Флаги: `fiscal_allowed=false`, `receipt_watermark=true` (касса печатает нижнюю строку), `ai_quota` (число распознаваний накладных в месяц).
3. Анти-абьюз: уникальность по номеру телефона и устройству; 1 `free` на ИНН.
4. Апселл-API: `GET billing/upsell` → ближайший платный тариф и цена, чтобы касса показывала «Мини за 500» без зашивания цен.
5. Блокировка при превышении: код `plan_limit` уже понимается кассой; добавить подкод `products|sales|history`.
6. Срок хранения данных при неактивности (напр. 12 месяцев) — политика, чтобы не копить мёртвые аккаунты.
7. Метрики: сколько free-аккаунтов, дошли до лимита, перешли на платный.

Размер работ [О]: сервер M (лимиты + флаги + антиабьюз), касса S–M (сообщения лимита, водяной знак, 5 языков, чек-лист и тесты).

### А7. Риски

- Каннибализация Мини: решается границей по возможностям (п. А4).
- Нагрузка поддержки: бесплатным — только бот и база знаний.
- Юридические: реклама «бесплатно» — указать условия лимитов; водяной знак не трогает фискальные реквизиты.
- Репутация: «зависшие» лимиты, потеря данных — обязателен экспорт Excel при сворачивании.

**Рекомендация:** делать «Старт-Free» (А3) как пилот с лимитом 300 товаров / 300 чеков, без eKassa, с водяным знаком; запуск после ответа Умара по полям из А6; в рекламе — «Бесплатно для маленькой точки».

## Часть Б. Банковский эквайринг и QR-оплата в кассе

### Б1. Что уже есть в коде [К]

| Что | Где | Статус |
|---|---|---|
| Загрузка картинки **статического QR банка** (Настройки → Операции) и показ покупателю (экран покупателя / окно оплаты, на одном экране крупно) | `CustomerDisplayViewModel`, `CheckoutViewModel.PaymentQr` | работает; подтверждает кассир вручную |

| Выбор банка при безналичной и смешанной оплате, сумма безнала в смешанной | `CheckoutViewModel` | работает |
| **Оплата подписки через ELQR (Элдик Банк)**: счёт, QR, опрос статуса, продление | `SubscriptionWindow`, `BillingApi`, `AccountView.Subscription.cs` | боевая оплата не проверена [Д] |
| Договор Элдик Банка подписан (NBS Холдинг, Nur CRM): комиссия **30 сом с транзакции**, платит клиент (строка «Комиссия банка») | ТЗ сервер — Оплата подписки ELQR, раздел 8 [Д] | на подписку, не на оплату товара магазином |
| Покупатель-ссылки и deep link в банковские приложения | в ТЗ предусмотрено `psType`: eldik, mbank, bakai, ab, odengi, demir, optima, kicb, kompanion, megapay, namba, simba, balance [Д] | для подписки |

Следовательно: **договор у NurCRM — на приём подписок. Для оплаты в магазине получатель — магазин, не NurCRM.** Это ключевое отличие: если деньги магазина идут через наш ключ, мы становимся платёжным агентом (нужна лицензия/регуляторика — [О] риск, требуется юрист/НБКР).

### Б2. Варианты

| # | Вариант | Как работает | Усилия [О] | Риск | Доход NurCRM | Плюсы / минусы |
|---|---|---|---|---|---|---|
| 1 | **Статический QR (есть)** | покупатель вводит сумму, кассир подтверждает | 0 | кассир может ошибиться | 0 | работает у всех банков; нет авто-проверки |
| 2 | **QR с суммой (есть, включить и проверить)** | как п.1, но сумма в QR | S: проверка на 3–5 банках, включить для MBank | другие банки отвергнут QR | 0 | экономит секунды, снижает ошибки суммы |
| 3 | **Свой динамический ELQR на каждый чек + проверка оплаты (каждый магазин — со своим банком)** | магазин даёт свой ключ банка (или подключает по OAuth/мастеру), касса/сервер создаёт Dynamic QR с `id`, ждёт callback/state | L: интеграции с 2–3 банками, секреты хранить только на сервере | ключи магазинов на нашем сервере — уязвимость; нужна изоляция | подписка на модуль «Приём QR» 100–300 сом [Доп] | авто-проверка, магазин получает деньги на счёт сам; сложные договоры у каждого магазина |
| 4 | **Агрегатор (FreedomPay и подобные) как единая точка** | один договор у NurCRM с агрегатором, магазин подключается как под-мерчант | L–XL: договор, KYC магазинов, возвраты | регулятор, комиссии, ответственность за споры | доля комиссии (допущение 0,2–0,5 %) | «подключил за день»; зависимость от агрегатора |
| 5 | **Банковский POS-терминал + интеграция** (О!Касса/О!Bank Smart POS, MBANK Smart POS, терминал PAX 910S у Telemedia) | касса шлёт сумму на терминал, получает «одобрено» | L: драйверы под каждый терминал | зависимость от банка | комиссия банка делится [Доп] | карты + QR; сильнее для магазинов с картой; нужен SDK |
| 6 | **Свой «Платёжный ключ магазина»**: касса показывает «ELQR магазина» (статический QR точки) и сервер узнаёт об оплате через **выписку/уведомление банка** (SMS-парсер, e-mail, webhook банка бизнеса) | подтверждение приходит как событие, касса отмечает чек оплаченным | M: разбор уведомлений, привязка к чеку по сумме+времени | ложные срабатывания, конфиденциальность SMS | модуль 100–200 сом [Доп] | дёшево, без договоров, но хрупко и не для всех банков |

Банки, которые **дают кассовую часть бесплатно** (MKassa/MBANK, О!Касса, Bakai Kassa [П21]), забирают рынок «ККМ + QR» у малой точки; наша сила — учёт + сферы, поэтому цель не «быть банком», а **быть удобным слоем поверх банков**.

### Б3. Рекомендация и этапы

**Этап 0 (1–2 недели, без Умара):** проверить и включить «QR с суммой» на тестовых магазинах; для каждого банка в списке (MBank, Optima, Bakai, О!Деньги, Элдик) сфотографировать результат сканирования; выдать владельцу чек-лист «какой банк принимает QR с суммой» и показывать в настройке только проверенные. Усилия S. Доход 0, но закрывает «нет эквайринга» в рекламе формулой «QR на сумму чека».

**Этап 1 (MVP, 1–2 месяца, с Умаром):** вариант 6 + подтверждение вручную: «Оплата получена?» с таймером; автоотметка по уведомлению банка бизнеса там, где оно есть (Bakai Business, MBusiness). Логирование, сверка «оплаты без чека» в программе владельца. Усилия M.

**Этап 2 (3–6 месяцев):** вариант 3 для банков, у которых есть открытый merchant API с callback (Элдик/ELQR — наш контакт уже есть; затем MBANK/Optima по договорённости); магазин подключает свой банк в мастере «Приём оплаты по QR»; сервер хранит ключи в изолированном хранилище, касса получает статус по опросу (как в оплате подписки, интервал 3 с). Модуль «Приём QR» 100–300 сом [Доп]. Усилия L.

**Этап 3 (6–12 месяцев):** варианты 4–5 по результатам спроса: агрегатор и интеграция с терминалами. Комиссию платит магазин (банк берёт ~1 % QR / 1,5 % карты по примеру О!Кассы [П21]), NurCRM берёт долю, если договор позволяет.

**Фискальная часть:** каждая оплата по QR — обычная «безналичная» оплата в чеке eKassa (поле способа оплаты в чеке сервера); для возврата по QR нужен Refund API банка (в договоре Элдик — check/create/execute/state [Д]) либо ручной возврат; в MVP возврат ручной.

**Кто платит комиссию:** банк берёт с магазина (как у О!Кассы 1 %/1,5 % [П21]) либо с покупателя — нельзя навязать покупателю по закону о платежах [О, юрист]. Для подписки решено: 30 сом с транзакции платит клиент [Д].

### Б4. Что просить / подтверждать

- **Умар:** webhook банка в кассовый поток (status по `invoice_id`), хранение ключей магазина (шифрование, роль «только сервер»), события `payment_confirmed` в чеке.
- **Банки (Элдик/МПЦ, MBANK, Optima, Bakai):** есть ли открытый API динамических QR, webhooks, песочница; можно ли магазину выдать ключ на нашу программу; условия агрегатора. В открытых источниках документации API МПЦ для кассовых программ не найдено [П: поиск 26.11] — запрашивать напрямую; ELQR, по данным прессы, превысил 1 трлн сом операций (24.kg) — рынок большой.
- **Юрист:** статус NurCRM при передаче платежей магазинов (агент/нет), договор с магазином, возвраты.
- **Владелец:** какие банки в приоритете; хочет ли получать долю с платежей или только брать плату за модуль.

### Б5. Риски

- Чужие деньги: сегодня деньги магазина не проходят через NurCRM; до этапа 4 так и оставить.
- Ложная оплата: подтверждать только по статусу банка, не по картинке в телефоне покупателя.
- Единая точка отказа: при обрыве связи у кассы остаётся ручное подтверждение + офлайн-очередь.
- Секреты: ключи банков не хранятся в клиентах (касса/мобилка/сайт) — как в договоре.

## Три главные идеи

1. **«Старт-Free»:** 1 точка, 1 касса, до 300 товаров и 300 чеков в месяц, без eKassa/ИИ/модулей, водяной знак на чеке, один на телефон/ИНН; пилот 3 месяца; сервер добавляет `max_products`, `max_sales_per_month`, `receipt_watermark`.
2. **«QR на сумму чека» — сразу:** включить и проверить уже готовый QR с суммой на 3–5 банках; в рекламе формулировать как «QR на сумму чека», а не «эквайринг».
3. **Авто-оплата QR поэтапно:** этап 1 — подтверждение по уведомлению банка бизнеса; этап 2 — merchant-API ELQR для магазинов со своим банком; агрегатор и терминалы — после замера спроса. Договор Элдик Банка пока только на подписку.
