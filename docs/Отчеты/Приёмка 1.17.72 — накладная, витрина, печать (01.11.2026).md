## 1. Накладная через серверный PATCH

### Н-1. БЛОКЕР — отказы сервера с кодом 409/423 считаются «ответ не дошёл», правка зависает
- Где: `NurMarketKassa.Infrastructure/Services/Purchases/ReceiptEditService.cs:704` (фильтр `catch (ApiException ex) when (step.Kind == "patch" && !PendingIdempotencyKey.IsOutcomeUnknown(ex))`) и `:713–716`; причина — `NurMarketKassa.Infrastructure/Services/PendingIdempotencyKey.cs:78–80`: любой 409 (кроме «цена изменилась» и «сумма возврата больше») и 423 там считаются «исход неизвестен».
- Что не так: по ТЗ 3.2 и ответу Умара (c8958b4) коды `negative_stock`, `has_returns`, `debt_already_paid`, `version_conflict` (без If-Match или если сервер ответит 409), `idempotency_conflict`, `receipt_fully_returned` приходят с **409**, а `period_closed` — с **423**. Ни один из них не попадает в ветку с понятным текстом `PatchErrorText`; срабатывает общий `catch`: шаг `unknown`, правка `applying`, `conflict = false`.
- Сценарий: накладная в долг, долг частично оплачен → уменьшить сумму → сервер 409 `debt_already_paid` → касса пишет «Ответ сервера не дошёл… Закройте накладную… довести правку: повтор пойдёт тем же ключом, ничего не задвоится» → «Довести» снова получает 409 → правка висит, новую сделать нельзя («Прошлая правка не доведена»), выйти можно только через «Отказаться» → пароль → «Проверил вручную». Для `version_conflict` с кодом 409 окно не закрывается и не перечитывается (чек-лист п. 5 не пройдёт), для `negative_stock`/`has_returns` (п. 7) — тот же «зависший» сценарий.
- Денег не задваивает (повтор с тем же ключом и той же версией), но это главный путь ошибок новой функции, а признак `receipt_patch` на сервере уже включён.
- Как исправить: в фильтре для шага `patch` сначала смотреть код: `when (step.Kind == "patch" && (SupplierApiService.ErrorCode(ex) is "version_conflict" or "negative_stock" or "has_returns" or "debt_already_paid" or "period_closed" or "receipt_fully_returned" or "permission_denied" or "reason_required" or "validation_error" or "fractional_not_allowed" or "edit_window_expired" || !PendingIdempotencyKey.IsOutcomeUnknown(ex)))`. `idempotency_conflict` и 409 без кода оставить «неизвестно». Код `period_closed` добавить в `PatchErrorText` (сейчас — общий текст).

### Н-2. СРЕДНЯЯ — «Реквизиты»: комментарий с закреплённым номером «№ ПР-…» редактируется целиком
- Где: `Views.axaml/Main/InvoiceHeaderDialog.cs:63` (в поле весь `r.Comment`), `:115`, `:125` (сравнение после `Trim()`).
- Что не так: номер закупки «ПР-…» закрепляется за документом текстом в комментарии (`DocumentNumberingCore.cs:9, 75`). Владелец, переписав или очистив комментарий, теряет закреплённый номер (на других ПК номер станет другим). Кроме того, если у исходного комментария есть пробел/перевод строки в конце, `comment.Trim() != _r.Comment` → в PATCH уходит «изменённый» комментарий, которого никто не трогал, и в журнал пишется ложное «комментарий: было → стало».
- Как исправить: служебную часть «№ ПР-…» показывать отдельно (только чтение) и дописывать обратно при отправке; сравнивать с `_r.Comment.Trim()`.

### Н-3. СРЕДНЯЯ — отметки «✎ кто и когда» путают позиции с одинаковым товаром
- Где: `Infrastructure/Services/Purchases/ReceiptEditLineHistory.cs:20` (`lineId == … || productId == …`).
- Сценарий: в накладной две строки одного товара (разные цены/партии), правится строка А → отметка и «История позиции» появляются и у строки Б; если у Б количество 0, `InvoiceDocumentWindow.cs` (`row.IsRemoved = effective <= 0 && …"removed"`) покажет её серой «удалил(а)…».
- Как исправить: сравнивать по `LineId`, а по `ProductId` — только для `new:…` и для полей цены продажи/наценки (они относятся к товару).

## 3. Печать, Р-3, Р-6, верхние кнопки

### П-1. СРЕДНЯЯ — запоминание переводов работает на всю программу и может не выключаться часами
- Где: `Infrastructure/Services/Tr.cs:23, 44` (`Track` на каждом `Tr.T` во всём приложении, пока открыт хоть один экземпляр настроек), `PosSettingsWindow.axaml.cs:34, 242` (выключается только по `Closed`).
- Что не так: (а) пока окно настроек открыто (оно немодальное — касса продаёт), каждый `Tr.T` где угодно (в т.ч. строки с подставленными суммами и именами) выделяет массив и делает до 5 вставок; словарь растёт до 40 000 записей (~десятки МБ в худшем случае). (б) После предела каждый `Tr.T` вызывает `ConcurrentDictionary.Count`, которая берёт все блокировки словаря, — на списках с тысячами строк это заметная нагрузка на UI-поток. (в) В программе владельца раздел «Настройки» — скрытое окно оболочки: `Closed` приходит только при вытеснении/закрытии, то есть захват может идти весь день. Утечки «навсегда» нет (лимит и `Clear` при последнем `Dispose`).
- Как исправить: счётчик записей через `Interlocked` вместо `Count`; захватывать только на время построения окна/страниц (или выключать на `Deactivated`/при скрытии раздела), а не на всё время жизни окна.

### П-2. НИЗКАЯ / ПЛАУЗИБЛЬНО — Retranslate ставит локальное значение поверх привязок
- `PosSettingsWindow.axaml.cs` `RetranslateCodeTexts`/`Fix`: `TextBlock.Text`, `ContentControl.Content`, `ToolTip`, `AutomationProperties.Name` задаются локально. Если у элемента была привязка (`{DynamicResource}`/`{Binding}`) и его текст совпал с захваченной строкой, Avalonia 11 снимает привязку — дальнейшие смены языка через ресурс перестанут работать для этого элемента. У `ComboBoxItem` меняется только контейнер, выбранное значение в поле — нет. Поля ввода (`TextBox.Text`) не трогаются — пользовательский ввод не затирается. Исправить: пропускать элементы с активной привязкой на свойстве (`IsSet`/`GetBindingObservable`) или менять только элементы, помеченные при создании.
