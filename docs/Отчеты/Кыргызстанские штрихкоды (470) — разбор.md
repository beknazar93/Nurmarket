## 2. Как касса обрабатывает код «470…» при скане

Кратко: **везде точное совпадение**. Подстрочного/«содержит»/«хвост»/«без последней цифры» поиска в сканировании нет.

| Место | Что делает | Вывод для «470…» |
|---|---|---|
| `ProductCodeLookup.Normalize` (ProductCodeLookup.cs:39) | убирает управляющие символы (в т. ч. GS, перевод строки), пробелы по краям и внутри цифрового кода | мусор сканера безопасен |
| `ProductCodeLookup.Candidates` (:320) и `BarcodeForms.Alternate` (BarcodeForms.cs:10) | вид кода «как пришёл»; 12 цифр → «0»+код; 13 цифр с нулём → без нуля; 14 цифр с нулём → 13; русская раскладка | для «470…» (13 цифр не с нуля) остаётся ровно один вариант — сам код; укорочений нет |
| `FindExact` → `LocalProductRepository.TryGetTileByBarcode` (LocalProductRepository.cs:352) | словарь `_barcodeCache` (без учёта регистра), если кэш не прогрет — запрос `barcode = $value` по индексу | точное совпадение; пробелов/регистра не касается |
| `ProductCodeLookup.FindInCatalog` (:402) | каталог памяти: основной штрихкод → доп. штрихкод → артикул/код товара (равенство, длина ≥3) | артикул учитывается только при полном равенстве; в базе таких совпадений нет |
| `VariantBarcodeIndex.Find` | словарь по точному коду (штрихкоды размеров одежды) | не затрагивает |
| Весовая этикетка (`WeightBarcodeParser.TryParse`, WeightBarcodeParser.cs:207) | только код из 13 цифр на «2» с верной контрольной цифрой | «47…» не проходит ни при каких настроенных префиксах 20–29 (проверено тестом); в приёмке этикетка разбирается ещё и только при настроенном префиксе (`ScalePrefixConfigured`, :365) |
| Сервер, касса (`TryFindProductOnServerAsync`, BasketPanelViewModel.cs:1764) и приёмка (`FindOnServerAsync`, ProductCodeLookup.cs:158) | `products/list/?search=код`, дальше `ResolveServerResultsAsync` (:211): берётся товар, у которого основной штрихкод **равен** одной из форм кода; иначе читаются до 2 карточек и ищется точный доп. штрихкод | «ближайшие» из поиска отбрасываются |
| Приёмка `PurchaseReceivingService.LookupAsync` (:547) | локально → `warehouse-barcode/{код}/?branch=` → `global-barcode/{код}/`; ответ принимается, только если штрихкод в ответе равен коду (`ServerAnswerHasCode`, :663) | чужой/соседний ответ сервера отбрасывается (проверено тестом) |
| Общая база: `GlobalProductCatalog.Find` (GlobalProducts/GlobalProductCatalog.cs:112) | встроенная копия, поиск по первичному ключу, варианты: сам код, 12↔13, 14→13 | точное совпадение |
| Мобилка (`barcode_lookup.dart`, `code_lookup.dart`) | те же правила (`barcodeVariants`), сравнение с карточкой сервера точное; для кодов с ведущими нулями — терпимее (`canonicalCode`) | «470…» не затрагивается; есть то, чего нет в кассе: `findCheckDigitTypo` (receive_lookup.dart:88) — «в магазине код записан с ошибкой контрольной цифры» |

Прямой причины «огурцы → вафли» в коде сканирования для кода «470…» **не найдено**: ни один из путей не умеет вернуть чужой товар по такому коду, кроме двух мест, закрытых 11.11 (п. 4). Версия 1.17.84 (у клиента) дополнительно разбирала любой код «20…29» как весовую этикетку до поиска — это уже исправлено в рабочей копии и к «470…» не относится.

Заметные факты из видео: в строке приёмки показывается **штрихкод найденного товара** (`FromTile` берёт `tile.Barcode`), а не отсканированный код; «Вафли Енсо вес» с кодом 5739… и «Рола Макарон» с кодом 4243… — это коды самих карточек. Чтобы строка получила такую карточку, поиск обязан был вернуть её **как найденную** — значит, либо скан пришёл не как «4700004710078», либо ответ сервера принят без сверки (путь, закрытый 11.11). Журнал клиента (`Приёмка: скан 47*********78 → …`, добавлен 11.11) это покажет — без него причину доказать нельзя.

## 3. Контрольная цифра и проверка кодов

- Расчёт и проверка контрольной цифры есть в: `WeightBarcodeParser` (только EAN-13, для весовых этикеток), `BarcodeGenerator.HasValidCheckDigit`, `InvoiceModels.HasValidCheckDigit` (импорт накладной), `BarcodeLabelService.HasValidGtinCheckDigit` (печать этикеток). EAN-8 нигде не проверяется.
- **Что видит кассир при неверной цифре.** «Штрихкод прочитан неверно, отсканируйте ещё раз» показывается только для этикеток весов своей раскладки (РС-200: `IsCustomLabelWithBadCheckDigit`, BasketPanelViewModel.cs:1651). Обычный код «470…» с неверной цифрой (сканер прочитал с ошибкой) идёт как незнакомый: запрос на сервер → «Добавить товар» с неверным кодом в карточке. Жёстко отвергать нельзя: в каталоге 99 законных-по-факту кодов с «неверной» цифрой (поставщики пишут как есть, EAN-8 — 60).
- Реальный риск скан-ошибки — не «подмена чужим», а «найден сосед в одну цифру». Тест показал: сосед ищется только точно, значит чужой товар не подставится, пока такого кода нет в каталоге; в каталоге соседи есть (серия `47000047100xx`), и только контрольная цифра отличает прочитанный с ошибкой код от настоящего соседа. Скан с одной ошибочной цифрой почти всегда даёт неверную контрольную цифру — поэтому мягкая подсказка полезна (п. 6).

5. Для кодов «470…»: есть ли у сервера отдельная логика для префиксов 20–29 (весовые) в `warehouse-barcode` — именно этим мог объясняться ответ «весовым товаром» на код «20…».

## 8. Что не проверено

- Живой скан на кассе/в приёмке клиента (журнала клиента нет); поведение настольного сканера клиента (какой код он реально отдаёт: полный, без контрольной цифры, с префиксом AIM `]E0`).
- Поведение настоящего сервера NurCRM на соседние/несуществующие коды (только заглушки WireMock — вопросы 1–5).
- Мобильное приложение — только чтение кода, тесты Flutter не запускались.
- Полный прогон всех тестов проекта — не запускался (проверены новые и соседние наборы: каталог, приёмка, генератор).
