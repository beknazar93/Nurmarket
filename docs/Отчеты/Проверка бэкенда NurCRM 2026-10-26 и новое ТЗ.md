### 1.4. Попутные находки (важно для кассы)

1. **404 в JSON у старого сервера.** На любой несуществующий адрес боевой сервер уже сейчас отвечает 404 `{"detail":"…","code":"not_found"}` в JSON.
   - Поэтому правило ТЗ адаптации 1.1.2 («404 с JSON `{"code":"not_found"…}` → новый API, 404 HTML → старый») **даст ложное «новое»**. Признак нового API — только ключ **`found: false`** (его нет) или отдельный адрес возможностей (Н2-01).
   - То же с правилом 1.1.3 «404 без JSON — адреса нет»: на этом сервере все 404 приходят в JSON. Нынешнее `ClientDebtsApiService.IsEndpointMissing` (`404` и `Payload: null`) на боевом сервере не срабатывает никогда. Для оплаты долга это безопасно: касса не уходит на старый путь, а показывает отказ. Но на «нет адреса = старый сервер» полагаться нельзя.
   - **Исправить в ТЗ адаптации (пакет П1) до начала работ.**
2. **`subscription_plan.code` уже есть:** `standard`, рядом `subscription.plan.{code, period, currency}`, `is_trial`, `days_left`. Пункт «Н-тариф-2» из ТЗ логотипы/сферы на сервере **уже сделан**, осталось подтвердить список кодов (`start`, `standard`, `custom`).
3. **Компания:** есть `industry {name:"Магазины", sectors[]}`, `sector {name:"Магазин"}`, `market_spheres` (список), `limits {employees, branches, warehouses, products}`. Поля `logo` у компании **нет**. В публичном дизайне витрины `company` = `{id, name, slug}`, без логотипа. `header.logo` NBS пуст.
4. **Витрина:** у фото товара в публичном списке есть поле `alt` (51 фото, ни одного `nurmarket-ref`). Фронт витрины мог бы скрывать эталоны сам, но надёжнее на сервере (Н2-11).
5. **Дизайн витрины:** `cart` = `checkout_button_text, delivery, fields, min_order_total, order_channel, payment_text, phone_country, style, success_text, whatsapp_phone`. `order_channel` NBS — `server`. Telegram есть только в `footer.socials.telegram` (пусто). Ключей `cart.telegram.*` нет.
6. **Карточка товара по штрихкоду** уже отдаёт `expiry_batches` и `shelf_life_days`. Партии и сроки на сервере есть, это пригодится для профиля «Аптека» (Н2-06).
7. **WebSocket поддержки за Cloudflare:** Cloudflare закрывает простаивающий WebSocket примерно через 100 с. Касса держит `ClientWebSocket` с интервалом поддержки по умолчанию (30 с) и отвечает на `ping` сервера, так что запас есть. При проверке «Получить код» с настоящей кассы стоит посмотреть, не рвётся ли сеанс через 1–2 минуты простоя.

**Проблема.** Касса должна работать и со старым, и с новым сервером. Сегодня их не различить: старый сервер на несуществующий адрес уже отвечает 404 `{"detail":…,"code":"not_found"}` в JSON (`main/changes/`, `main/idempotency/<uuid>/` и любой выдуманный путь).

**Нужно.**
1. `GET api/main/capabilities/` (любой вошедший сотрудник) →
   ```json
   {"api": "2026-10", "server_version": "b7f3d41",
    "features": ["shift_report_v2","cashbox_drawer_cash","idempotency_lookup","price_stable","negative_custom_rejected",
                 "client_documents","bot_owner_server","salary_payouts","supplier_pay_debt","access_codes","changes_feed",
                 "receipt_create_deal","rentals_paged","strict_permissions"],
    "company_flags": {"api_strict_2026_10": false}}
   ```
   Список — по функциям ветки. `company_flags` — состояние флага из Н2-02 для этой компании.
2. Заголовок `X-NurCRM-API: 2026-10` во **всех** ответах API.
3. `GET main/idempotency/{key}/` для неизвестного ключа: 404 `{"detail":"…","code":"idempotency_key_not_found","found":false}`. Код **отличается** от общего `not_found`.
4. Неизвестный адрес: 404 `{"detail":"…","code":"route_not_found"}`. «Объект не найден» оставить `not_found`. Тогда касса отличит «адреса нет» от «записи нет».

**Приёмка.** Старый сервер: `capabilities/` → 404 `route_not_found` (после шага 1 2.3). Новый: 200 со списком. Заголовок есть в ответе `products/catalog-version/`.

**Касса сейчас.** Пробует `idempotency/<uuid>` и решает по JSON. Как показала проверка, это даст ложное «новое» (исправляем в ТЗ адаптации, П1). **После.** Читает `capabilities/` раз в 6 ч.

### Н2-03 (P1). Заказы с сайта и из бота → Telegram (серверный бот), `source` у заказа

**Проблема.** Владелец жалуется: заказы с сайта в Telegram **не приходят вовсе**. Бот (и серверный, и в кассе) сообщает только о заказах, которые сам создал. Заказ из бота кассы создаётся публичным `POST public/companies/{slug}/orders/` без источника, поэтому сайт пишет «Источник: Сайт» (проверено 20.10; 26.10 у заказа `source: "showcase"`).

**Нужно.**
1. `POST api/main/public/companies/{slug}/orders/` принимает `source` ∈ `showcase` (по умолчанию), `telegram_bot`, `voice_ai`, `whatsapp`. Для `telegram_bot` — ещё `telegram_chat_id` покупателя. Отдавать `source` в `showcase/orders/` и фильтр `?source=`.
2. Серверный бот (`mode=server`) при **любом новом заказе** (`showcase/orders`, `status=new`, любой `source`) шлёт сообщение получателям по настройке `orders_recipients` (Н2-04; пока группы нет — владельцу):
   - номер, время, способ получения, строки (название, размер/цвет, количество);
   - сумма — если `orders_show_amount`;
   - телефон — если `orders_show_phone` (по умолчанию `true`);
   - кнопки «Принять» / «Отменить» / «Открыть на сайте» (`callback_data` с id заказа; «Принять» → `PATCH status=accepted`, только владельцу или сотруднику с `can_view_showcase`).
3. Дедупликация — не больше одного уведомления на заказ, журнал `telegram-bot/audit/` (`event: order_notified`, `order_id`, `chat_id`, `ok`, `error`).
4. Ошибка отправки (бот удалён из чата, 403 от Telegram) → `orders_last_error`, повтор через 1, 5, 30 мин, затем отметка «не доставлено».

**Приёмка.**
- Заказ с витрины NBS → сообщение владельцу ≤ 5 с.
- Повторное сохранение заказа (`PATCH comment`) нового сообщения не даёт.
- `source=telegram_bot` виден в `showcase/orders/`.
- При `orders_show_amount=false` суммы в тексте нет.

**Касса сейчас.**
- Программа владельца только опрашивает `showcase/orders/` ради значка (`OwnerShellWindow.PollSiteOrdersAsync`).
- Пакет Г3 (локальный бот) ждёт ответа владельца В-10/В-11.
- В серверном режиме слать может только сервер.

**После правки.** Касса передаёт `source: telegram_bot` и ничего не дублирует, когда бот серверный.

### Н2-04 (P2). «Группа заказов» в серверном боте (Г2)

**Сейчас.**
- В кассе группа заказов уже работает в локальном режиме (Г1): `TelegramOrdersChatId`, `TelegramOrdersTarget = owner|group|both`, `TelegramOrdersShowAmount`, команды `/group <код>` и `/groupoff`, `my_chat_member`, `migrate_to_chat_id` (`TelegramBotOwner.Group.cs`).
- В `telegram-bot/settings/` 26.10 полей `orders_*` нет. Окно настройки бота в серверном режиме пишет «Сервер пока не умеет группу заказов».

**Нужно.**
1. Поля `GET/PATCH api/main/telegram-bot/settings/` (запись — владелец или админ):
   - `orders_chat_id` — только чтение, ставится привязкой;
   - `orders_chat_title`, `orders_chat_bound_at`;
   - `orders_recipients`: `owner|group|both`, по умолчанию `owner`;
   - `orders_show_amount` (bool, `false`), `orders_show_phone` (bool, `true`);
   - `orders_last_error`.
2. `POST api/main/telegram-bot/orders-group-code/` → `{code: "6 цифр", expires_at}` (10 мин, одноразовый, повторный запрос отменяет прежний).
3. Вебхук:
   - `/group <code>` в `group`/`supergroup` от подтверждённого владельца (`from.id` = владелец компании) → привязать и ответить в группе «Группа заказов подключена». Чужому → «Команда только для владельца». Неверный или просроченный код → «Код неверный или устарел»;
   - `/groupoff` от владельца → отвязать;
   - `my_chat_member` со статусом `left`/`kicked` → `orders_chat_id=null` и сообщение владельцу в личку;
   - `migrate_to_chat_id` → заменить id;
   - в группе заказов бот молчит, кроме ответов владельцу на `/group`, `/groupoff`, `/help`.
4. `POST telegram-bot/move-to-server/` (перенос бота из кассы) принимает `orders_chat_id`, `orders_recipients`, `orders_show_amount`, `orders_show_phone` и проверяет `getChat`: бот должен быть в группе.

**Приёмка.**
- Привязка кодом → поля заполнены.
- Заказ (Н2-03) → сообщение в группе ≤ 5 с.
- Удалить бота из группы → `orders_chat_id=null`, владелец получил сообщение.
- `/group` от не-владельца — отказ.

**Касса после.** Пакет Г2: в серверном режиме читает и пишет `orders_*`, локальную привязку переносит при «Перенести на сервер».
