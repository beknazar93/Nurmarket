### 2.3. ETag: 304 на ленте не срабатывает из-за `W/`
- Сервер NurCRM отдаёт сильный ETag. Cloudflare, сжимая ответ, делает его слабым: `W/"0aeda318…"`.
- Касса сохраняет и отправляет назад `W/"…"` (`catalog_feed_cursor.json`: `"ETag":"W/\"b5160ba6…\""`, `NurMarketApiClient.Feed.cs:34`).
- Проверка: `If-None-Match: W/"…"` → **200**; тот же ETag без `W/` → **304** (два раза). Значит, у ленты кассы 304 не бывает никогда.
- `app-settings/nurmarket-kassa/` (`W/"31"`): и с `W/`, и без → 200. 304 для настроек сервер не поддерживает.
- Выгода от 304 на пустой ленте по байтам мала (~200 байт тела), но сервер не собирает ответ.

## 4. Как добиться «мгновенно» без Б-102

Принцип: **сервер — источник данных, а «пора перечитать» приходит самым быстрым доступным путём.** Пути: подсказка по локальной сети → длинный запрос → короткий опрос как страховка.

Подсказки несут только тип и id, без данных. Получатель всё равно берёт данные с NurCRM, поэтому права и правильность не страдают.

### 4.1. Что делаем у себя (без Умара)
1. **Касса — локальный центр событий.**
   - Журнал `LanJournal` уже есть (продажа, отправка продажи, оплата долга), программа владельца забирает его раз в 4 с (`LanSyncService.cs:48`).
   - Добавить виды событий: `price_changed` / `stock_changed` / `product_changed` (при применении ленты и при своей правке), `shift_changed`, `settings_changed`, `staff_changed`.
   - Опрос раз в 4 с заменить длинным запросом: касса держит запрос до 25 с и отвечает сразу при событии. На одном ПК или в одной сети это ≤ 0,1–0,3 с.
   - Программа владельца по событию `sale` сразу обновляет «Сводку», «Продажи» и остаток. Сейчас она берёт из локальной сети только неотправленные продажи (`OwnerShellWindow.axaml.cs:1453`).
2. **PhoneLink для мобилки** (протокол v1 → v1.1).
   - Новый `op:"events"` с `since=<seq>`: длинный запрос к кассе, те же HMAC и одна строка JSON. Мобилка в той же Wi-Fi узнаёт о продаже, цене, смене за ≤ 0,5 с и перечитывает только нужное.
   - Новый `op:"hint"` от мобилки после её `PATCH`, прихода или нового товара: касса **сразу** делает такт ленты. Задержка «цена в мобилке → касса» станет ~1–1,5 с вместо 6 с (0,4 с сервер + 0,3 с лента).
   - Работает, пока мобилка на экране. В фоне Android ограничивает сеть, и на это нужен FCM (4.2).
3. **Подсказка после своей правки.** Касса или владелец сами что-то записали (цена, товар, настройки, смена) → событие в локальную сеть сразу после ответа сервера. Другие кассы и владелец читают ленту или документ немедленно. Настройки: 3–38 с → ~1 с, смена 0–30 с → ~1 с.
4. **Адаптивный опрос как страховка** (интервалы — в `SyncCenter`):
   - лента 3 с, пока у кассира есть чек или открыта оплата, и 10 с после любой подсказки;
   - 8 с в обычном режиме;
   - 30–60 с при свёрнутом окне или простое больше 10 мин;
   - пульс продаж у владельца 5 с при активной «Сводке» или «Продажах», 60 с в свёрнутом окне;
   - смена 10 с при открытом окне смены.
   - В среднем запросов станет не больше, чем сейчас: активные периоды короткие, простой длинный.
5. **Мобилка — лента вместо полной загрузки.**
   - `products/changes/?since=` раз в 8–15 с только на экранах «Продажа», «Склад», «Приёмка». Полная загрузка — раз в сутки или по кнопке.
   - Пауза всех таймеров при уходе в фон, один `runOnce` при возврате.
   - Исправить 3.1 и 3.2.
   - Задержка «касса → мобилка» по остатку и цене: 5 мин → ~5 с без локальной сети, ≤ 0,5 с с PhoneLink. Трафик и батарея — в десятки раз меньше.
6. **Убрать полную перезагрузку каталога после чужой продажи** (`AvaloniaCatalogCacheService.cs:58-66`). Остаток уже приходит лентой. Экономия на большом каталоге — до ~30 тяжёлых запросов в минуту на каждое приложение.
7. **ETag без `W/`.** Отправлять `If-None-Match` без префикса `W/`, пока Умар не сделает слабое сравнение. 304 на ленте сразу заработает.
8. **Соединения.**
   - Касса: `HttpRequestMessage.Version = 2.0` с `RequestVersionOrLower`; `SocketsHttpHandler` с `PooledConnectionIdleTimeout` ≥ 90 с. Параллельные страницы и опросы пойдут по одному соединению.
   - Мобилка: `HttpClient.idleTimeout` ≥ 60 с, чтобы не делать TLS-рукопожатие на каждый такт.
   - Выигрыш ~0,1–0,2 с на запрос и меньше расход батареи.
9. **Оптимистичные обновления и предзагрузка.**
   - Мобилка показывает новую цену сразу и откатывает при ошибке. Сейчас ждёт `PATCH`: 0,5–6 с.
   - Касса грузит список клиентов при первом товаре в чеке (сейчас — при открытии оплаты).
   - Мобилка перечитывает профиль и права при возврате в приложение.
10. **Свой ретранслятор подсказок (по решению владельца).**
    - Сервер помощи `NurRemoteSupport` (`wss://support.nurcrm.kg`) уже есть. Он может разносить подсказки между устройствами в разных сетях. Наши приложения публикуют `{type, ids}` после своих записей, подписчики перечитывают NurCRM.
    - Покрывает изменения из наших программ, но не правки на сайте NurCRM: для них остаётся лента.
    - Это новая обязанность сервера помощи. Нужен ответ владельца.

### 4.2. Что нужно от Умара (контракты)
Полный поток событий описан в ТЗ Умару (Б-102, `ТЗ Умару — что осталось сделать на сервере (29.10.2026).md`, разделы 5 и 7). Ниже — шаги, которые дешевле SSE и дают ≤ 1–2 с.

**У-1. Длинный запрос на ленте товаров** (главное, дешевле SSE).
```
GET /api/main/products/changes/?since=<cursor>&limit=500&wait=25
```
- Есть изменения после `since` → ответ сразу, тело как сейчас.
- Изменений нет → сервер держит запрос до `wait` секунд (максимум 25, меньше тайм-аута Cloudflare 100 с). Изменение появилось → ответ в течение ≤ 0,5 с. Не появилось → `200 {cursor:<тот же>, changes:[], deleted:[], has_more:false}`.
- Заголовок ответа `X-Poll-Wait-Max: 25`.
- Такие запросы не считать в лимит 429. Одно ожидание на устройство; второе с того же устройства отменяет первое.
- Без параметра `wait` — как сейчас (старые кассы не ломаются).

**У-2. Тот же `wait` на событийной ленте** `GET /api/main/changes/?since=&types=&wait=25` (контракт Б-46 п. 2).
- Типы: `sale_created`, `sale_refunded`, `shift_changed` (открыта, закрыта, внесение, изъятие), `settings_changed` (`app`), `staff_changed`, `client_changed` (в том числе бонусы и долг), `debt_paid`.
- Сейчас адреса нет (404).

**У-3. ETag и 304.**
- `If-None-Match` сравнивать слабо (RFC 9110, для GET): `W/"x"` равно `"x"`. Сейчас `W/"…"` → 200, хотя Cloudflare сам ставит `W/`.
- 304 для `app-settings/{app}/`: ETag `W/"31"` есть, 304 нет. То же для `users/company/`, `users/employees/`, `users/roles/`, `products/catalog-version/`.

**У-4. FCM для мобилки (когда приложение не на экране).**
```
POST   /api/users/devices/        {platform:"android"|"ios", app:"nurmarket-mobile", fcm_token, branch_id?}
DELETE /api/users/devices/{token}/
```
- Сервер шлёт data-сообщение (без уведомления на экране): `{type, ids[], at, branch}` на те же события, что в У-2. `collapse_key` по типу, `priority: high` только для `sale_created` и `shift_changed`.
- Права — как у ленты: кассир не получает `staff_changed` и владельческие ключи.
- Со своей стороны: проект Firebase и пакет `firebase_messaging`. Это новая зависимость, нужно согласие владельца.

**У-5. Каталог.**
- Указать в документации максимум `page_size` (сейчас молча 100) или разрешить 500.
- Облегчённый вид для сверки остатков: `GET products/list/?fields=id,price,quantity,updated_at&page_size=500` или `GET products/stock/?since=`. Сейчас 0,5 с работы сервера на 100 товаров.

**У-6. «Сводка»:** `analytics/market/` пересчитывать или сбрасывать кэш при продаже. Сейчас 10–60 с после чека.

**У-7.** Гарантировать порядок `-created_at` по умолчанию в `pos/sales/` (на нём держится пульс продаж).
