# Исправления — Индекс чеков в базе (Н-04, 01.11.2026)

Владелец дал «да» на изменение схемы локальной базы (только индекс). Коммит не делался.

## Причина

Строки проданных товаров лежат в таблице `SoldLineItems` (колонка `sale_id` — номер чека). Чек читают запросом
`WHERE sale_id = $id` (отчёт смены, история чеков, экспорт в Excel, удаление чека при сверке, `DatabaseService.cs` ~1618 и ~2290).
Индекса по `sale_id` в базе фактически не было.

Код создавал `idx_sold_line_items_sale` только внутри `AddSoldLineItemsSaleIdColumn`, сразу после `ALTER TABLE … ADD COLUMN sale_id`.
Но колонка `sale_id` давно входит в `CREATE TABLE`, поэтому `ALTER` всегда падает с «duplicate column», и до `CREATE INDEX` дело не доходит.
Индекс не создавался никогда (кроме совсем старых баз, где колонку добавляли впервые).

## Что сделано

Один индекс: `idx_sold_line_items_sale ON SoldLineItems(sale_id)` (имя то же, что в старом коде).
Второй индекс (товар, дата) не добавлялся: `idx_sold_line_items_product`, `_sold_at`, `_company_sold`, `_company_name` уже есть.
Запрос по `sale_id` с условием `company_id` берёт новый индекс; лишние составные индексы только замедляли бы запись чеков.

Файл: `NurMarketKassa.Avalonia/NurMarketKassa.Infrastructure/Services/DatabaseService.cs`
- `EnsureSoldLineItemsSaleIndex(SqliteConnection)` вызывается в `EnsureSchema()` СИНХРОННО, сразу после `AddCompanyHistoryIndexes`, до миграций и до запуска остальных писателей и окон;
- сначала проверка `sqlite_master`: индекс есть, значит выход (повторный запуск идемпотентен, ~0 мс);
- иначе считается число строк, в журнал пишется INFO «Создаётся индекс … по N строкам (разово)», затем `CREATE INDEX IF NOT EXISTS` с таймаутом команды 120 с и INFO «создан за N мс»;
- любая ошибка (в том числе таймаут на очень большой таблице, > 3 млн строк) ловится, пишется WARNING, запуск не падает, касса работает без индекса.

Почему синхронно, а не в фоне (исправлено по ревью): первая версия строила индекс в фоне под `_dbLock` класса.
Но другие писатели той же `pos_local.db` (LocalProductRepository, LocalAccountsManager и др.) работают на своих соединениях без этого замка.
`CREATE INDEX` держит блокировку записи SQLite секунды, и они ждали бы `busy_timeout` и падали с «database is locked». В `EnsureSchema` в базу пока никто, кроме нас, не пишет.
Цена: один раз на базу запуск дольше на время построения (~2,3 с на 1 млн строк, на обычной базе мгновенно).
Фоновая задача и комментарий про «замок покрывает всех писателей» удалены.

Windows-специфики нет (Linux/Android берут файл глобом). Запросы менять не пришлось.

## Замер (копия, не боевая база)

Синтетическая база в `C:\Users\User\NurMarket-test\stands\audit-index\bench.db` (скрипт `bench.py` рядом): 1 000 000 строк, ~250 тыс. чеков, один `company_id`, те же 4 индекса, WAL, 296 МБ.
Запрос: `SELECT product_name, quantity, unit_price FROM SoldLineItems WHERE sale_id = ? AND company_id = 'comp1'` (как в кассе).

| | До | После |
|---|---|---|
| План | `SEARCH … USING INDEX idx_sold_line_items_company_name (company_id=?)` — перебор всех строк компании | `SEARCH … USING INDEX idx_sold_line_items_sale (sale_id=?)` |
| Чтение одного чека | ~8 000 мс (холодный кэш, 20 чеков подряд) | ~0,05 мс |
| `DELETE … WHERE sale_id = ?` | тот же перебор | тот же индекс |
| Построение индекса | — | 2,3 с на 1 млн строк |
| Повторный `CREATE INDEX IF NOT EXISTS` | — | ~0,03 мс |

Цифра «до» у меня выше, чем в аудите (167–233 мс): в синтетической базе все строки одной компании, планировщик выбирает `company_name` и перебирает весь миллион.
Вывод тот же: без индекса чек читается долго, с индексом мгновенно. Размер базы растёт примерно на 20–30 МБ на миллион строк (текстовый ключ).

## Риски и откат

- Один раз на базе без индекса запуск кассы дольше на время построения (секунды на миллионе строк; на > 3 млн строк команда оборвётся через 120 с с WARNING, индекса не будет, касса работает как раньше).
- Рост файла базы на несколько десятков МБ; ежедневная копия `VACUUM INTO` станет чуть больше.
- Откат: `DROP INDEX IF EXISTS idx_sold_line_items_sale;` (данные не затрагиваются). Чтобы индекс не создавался снова, убрать вызов `EnsureSoldLineItemsSaleIndex(connection)` из `EnsureSchema`.
- Оставшееся из Н-04 (запрос пачкой вместо цикла по чекам, чистка старой истории) — отдельные задачи.
