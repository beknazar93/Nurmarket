## 0. Коротко

**Вывод.** С 29.10 у нас построен хороший «скелет»: лента товаров (`products/changes`), общая лента компании (`main/changes`) для 5 типов, адаптивный опрос, подсказки по локальной сети, PhoneLink-события на стороне кассы. Но это **не организм**, а набор отдельных циклов опроса, и у каждого клиента свой набор:

- касса слушает 5 типов событий из ~20 возможных (то, что сервер уже отдаёт, мы не используем);
- мобилка слушает только ленту товаров раз в минуту, права и настройки видит при запуске;
- целый класс данных вообще живёт в локальных JSON и **не уходит с компьютера** (заказы под клиента, сметы, признаки автозапчастей, ремонт, trade-in, прокат, отметки табеля, журнал серийников, шаблоны ценников…);
- «мгновенности» между сетями нет: серверного push нет, только опрос (≈16 запросов в минуту на простаивающую кассу, ≈90 за 5 минут на клиента).

**Топ-5 дыр:**

1. **Локальные данные сфер не синхронизируются** (ДЫРА). Заказ под клиента с предоплатой, смета, мета автозапчастей (гарантия, «электрика», «установленные не принимаются»), ремонт, trade-in, прокат, табель отметок, серийный журнал, шаблоны ценников — на втором компьютере, в мобилке и на сайте их нет. Две кассы автозапчастей = два разных набора заказов. При смене ПК данные теряются (файл остаётся на старом ПК).
2. **Мобилка не «живая»** (ДЫРА). Нет push и нет событийной ленты: продажа с кассы в мобилке не появляется сама; права и тариф обновляются при запуске; PhoneLink `events/hint` реализован на кассе, но в мобилке не вызывается (в `lib` нет) [код].
3. **Опрос вместо событий** (ЧАСТИЧНО). Каждый клиент по отдельности опрашивает ленту товаров (3–60 с), пульс продаж (5–20 с), смену (30 с), настройки (30 с), права (45–90 с), события (10 с). Задержки 3–38 с, нагрузка на сервер растёт с каждым устройством. Сервер уже отдаёт `main/changes` с типами `client_changed`, `bonus_changed`, `debt_paid`, `cash_moved`, `receipt_changed`, `pos_request_changed`, `rental_*`, а касса их не просит [код+док].
4. **Остатки и «приход в пути»** (ЧАСТИЧНО). Остаток из ленты применяется по товарам с защитой `FeedStockGuard`; при долгом приходе (>30 мин) и при перезапуске защита слабеет (Fable Л-1, Л-6 [док]); признак сервера `stock_balance` (`stock/balance/`) есть с 19.11, а касса его не использует [код: поиска `stock_balance` в коде нет]. Правило «для остатков — только операции, не значения» нигде не записано как норма.
5. **Конфликты правок «последний выиграл» без предупреждения** (ДЫРА). Настройки: PATCH по ключам без версии и `If-Match`. Карточка товара: PATCH без проверки версии (приходы — с `version`, 428 `version_required`). Два устройства правят одну карточку или один настроечный ключ — второе молча перезаписывает первое. Исключение — документы КП/счета (`updatedAt` + «надгробие»), там слияние по записи.

**Целевая модель (3 строки):** (1) сервер — единственный источник правды, клиент — кэш плюс единая офлайн-очередь операций с `Idempotency-Key`; (2) одна лента `main/changes` на ВСЕ сущности (курсор, версия сущности, надгробия) + push-«подсказка» (WebSocket → фоллбэк long-poll → фоллбэк опрос с ETag), данные клиент всегда берёт через REST под своими правами; (3) остатки меняются только операциями, настройки и карточки — по версии с `If-Match`, документы сфер — серверные коллекции (`customer-orders`, смета, `attributes`).

**Мини** — отдельная компания на том же сервере, клиент только `mobile`, без LAN, PhoneLink, ПК-клиентов; апгрейд на «Старт» подхватывает данные без дублей (§5).

## 1. Аудит существующей синхронизации

Условные сокращения: «К» касса (Windows/Linux/Android-касса, тот же код), «В» программа владельца (`--owner`, свои папки данных `NurMarketOwner`), «М» мобилка, «Сайт» market.nurcrm.kg / app.nurcrm.kg, «Бот» Telegram.

### 1.0. Общая схема сейчас

| Канал | Что передаёт | Кто использует |
|---|---|---|
| REST к `app.nurcrm.kg` (Cloudflare, h2) | всё | К, В, М, Сайт |
| Опрос с ETag/304 (адаптивный, `SyncCenter`) | лента товаров, события компании, права, настройки, пульс продаж, смена | К, В (М — только ленту товаров) |
| Подсказки по локальной сети (UDP-обнаружение + HMAC-HTTP, порты 47810–47819, `LanJournal`) | `sale`, `sale_uploaded`, `debt_paid` как события журнала; подсказки `product/stock/price/settings/access` без данных | К ↔ К ↔ В в одной сети магазина (при общем «коде магазина»), В+К на одном ПК через реестр |
| PhoneLink v1 (HMAC по QR) | `scan`, печать, корзина; `events` (long-poll до 12 с) и `hint` | К ↔ М в одной Wi-Fi; на кассе готово, в мобилке `events/hint` не вызываются [код] |
| Серверный WebSocket | есть у сайта («имя события как в WebSocket» [док: Ответы Умара 13.11]); `ws/main/events/` (`stock_changed`, `price_changed` за 0,4 с) в отчёте «Склад» 30.10 помечен «не подключён» | клиентами кассы/мобилки **не используется** [код+док] |
| Push (FCM/APNs) | каркас `PushService` без ключей; в `pubspec` нет `firebase_*` | никто |
| Telegram | бот в кассе (`getUpdates`, работает, пока касса включена) или серверный режим (`telegram-bot/settings`, режим `server`) | К, В, Бот |

Лента товаров, события и опрос идут **от каждого клиента отдельно**: серверу всё равно, сколько у компании устройств, а нагрузка растёт линейно.

### 1.3. Настройки (SettingsCloudSync, user-settings)

**Механизм** [код: `SettingsCloudSync.cs`]: два облачных документа:
- личные — `api/users/app-settings/{app}/` (`nurmarket-kassa` или `nurmarket-owner`; секреты ИИ — поле `secrets`), читаются **один раз за вход** (`PullOnce`), без фонового опроса — личные настройки с другого устройства не прилетают, пока человек не перелогинится;
- общие — `api/main/app-settings/{app}/`, фоновый опрос `CompanyEventsFeed`-подсказка `app_settings_changed` + собственный такт 30 с (120 с в тихом режиме), 3 с отложенная отправка своих правок; ETag сервер даёт `W/"31"`, но 304 на настройках не поддержан [док 29.10]. Мобилка использует свой документ `nurmarket-mobile` (AiAccess, CamAliases, «quotes») и читает `nurmarket-kassa` для режима сферы (`shop_mode.dart`).

**Правила (П1–П4)**: пока область (личная/общая) не получена успешно в этом запуске — она не отправляется («Настройки с сервера: личные получены, общие получены» в журнале — это разрешение отправлять); грязные ключи (изменённые на кассе с последнего получения) не затираются облаком и отправляются; смена пользователя сбрасывает всё; повтор не чаще раза в 60 с. Сервер главнее; если на сервере пусто — первое устройство заполняет (кроме личных и ключей `NoAutoFillKeys`).

**Конфликт:** PATCH меняет только изменённые ключи, **версии и `If-Match` нет** — на ключ «побеждает последний», отдельные ключи двух устройств не конфликтуют (хорошо), один и тот же ключ — перезапись (ДЫРА, но редкая). Строковые JSON-ключи (`SphereSettingsJson`, `AdvisorCapabilitiesJson`, `ClientPriceGroupsJson`, правила весов) — это один «ключ», а внутри несколько полей: два владельца правят разные поля одного такого ключа → побеждает последний целиком.

**Задержка:** общие 3–38 с (замер 29.10); при открытом окне настроек применение откладывается (`HasUnsavedEdits`); личные — только при входе.

**Офлайн:** при нет связи в запуске область не «получена» — отправки нет, правка остаётся «грязной» и уходит позже; кроме того на Android ключи вида кассы (`MainLayoutMode`, `CatalogViewMode`, `ShowCatalogPhotos`, `CatalogTileScalePercent`) в облако не уходят.

### 1.10. LAN-обмен между кассами (NurMarketLan)

- [код] Каждая программа слушает порт 47810–47819, соседей находит по UDP (47809) при одинаковом «коде магазина» либо через реестр `%LOCALAPPDATA%\NurMarketLan` на одном ПК; запрос подписан HMAC; журнал `LanJournal` (`sale`, `sale_uploaded`, `debt_paid`) забирается соседями раз в 4 с; подсказки `product/stock/price/settings/access` без данных; Телефоны получают события по PhoneLink `events`.
- Задержка: ≤0,3–4 с в одной сети; вне магазина (дом, второй магазин) — **нет**.
- Конфликты: данные не переносятся (кроме журнала продаж соседа для вычитания остатка); сервер главнее.
- **Дыры:** (а) работает только в одной сети и при совпадающем «коде магазина» (настройка владельцем); (б) М не слушает событий; (в) типов событий нет для `shift`, `client`, `staff`, цены/остаток идут общей подсказкой; (г) LAN не заменяет сервер — для «организма в разных сетях» нужен серверный push.

### 1.11. События и уведомления (company-events, Telegram)

- `CompanyEventsFeed`: `GET main/changes/?since&types&limit` каждые 10 с (ETag/304; курсор «заморожен» до 30 мин на пустых страницах; `cursor_expired`/`invalid_cursor` → заново + полное перечитывание). Запрашиваются только 5 типов: `features_changed`, `staff_changed`, `app_settings_changed`, `product_changed`, `stock_changed`. Данные событий не читаются — реакция «толкнуть» существующий цикл (честный минимум). Хранение событий 7 дней.

- **Дыры:** вне магазина (владелец дома) уведомления и сводка получаются только в Telegram при серверном режиме; в М нет push; сайт и бот не связаны с лентой событий кассы.

### 1.13. Версии клиентов и совместимость

- [код] Единственный механизм — признаки `GET main/capabilities/` (кэш 10 мин, привязан к аккаунту) и «клиент работает за признаком — нет признака, всё как раньше». Кэш 14 дней в М.

### 1.15. Сайт (market.nurcrm.kg / app.nurcrm.kg), витрина

## 3. Целевая модель «единый организм» (Старт, Стандарт, Своё)

### 3.1. Принципы

1. **Сервер — единственный источник правды.** Клиент хранит кэш и очередь операций; кэш можно стереть без потери данных, очередь — единственное, что может потеряться (поэтому очередь видна на сервере как «ожидается устройство X», см. 3.6).
2. **Три класса данных, три правила записи:**
   - *Операции* (продажа, возврат, приход, списание, внесение, оплата долга, бонус, резерв, предоплата) — append-only, на сервер уходят с `Idempotency-Key`, порядок — по серверному времени и возрастающему `op_seq` устройства; **значение остатка/баланса клиент не пишет** (только «приход +N», «списание −N», «ревизия: разница, считал с версии V»);
   - *Справочники* (карточка товара, клиент, поставщик, сотрудник, категория) — версия записи (`version`/`updated_at`), PATCH только изменённых полей, `If-Match` → 412 `version_conflict` с текущим состоянием;
   - *Настройки и документы* (настройки сферы, КП, смета, заказ под клиента, шаблоны) — серверная коллекция с версией записи, `updated_at`, `updated_by`, надгробием; слияние по записи, а внутри записи — по полям, где есть смысл.
3. **Единая лента.** Всё изменение любой сущности порождает событие в `main/changes` (курсор, тип, id, версия, актор, филиал). Клиент хранит курсор и никогда не «спрашивает всё».
4. **Push как подсказка, данные — через REST.** По WebSocket/long-poll/FCM сервер шлёт не данные, а «после курсора N что-то изменилось, типы…». Клиент читает ленту под своими правами. Это сохраняет проверку прав и позволяет упасть на опрос без потери логики.
5. **Фоллбэк на каждом уровне:** WebSocket → long-poll (`wait=25`) → опрос с ETag (как сейчас) → ручная кнопка «Обновить». LAN-подсказки остаются для скорости внутри магазина и работают при отсутствии интернета.
6. **Версия клиента не должна ломать данные:** запись только по `If-Match`/версии; события с `schema_version`; `min_client_version` в `capabilities`.

### 3.2. Что должно жить на сервере вместо локальных JSON

| Данные | Куда | Как (реалистично) |
|---|---|---|
| Мета автозапчастей (гарантия, «электрика», «установленные не принимаются», состояние) | `attributes[]` товара (выложено 19.11) | ключи `warranty_days`, `electrical`, `no_return_installed`, `condition`; ячейка — `storage_location`; аналоги — `related_input`; **не `alternate_barcodes`** |
| Заказы под клиента | `customer-orders/` (Б-60, 200/пусто) + резервы `reservations/` | статусы: черновик → предоплата → в пути → пришло → продан/отменён; предоплата — **операция «получено», не значение**; связка с `deferred_carts` через `source_id` резерва |
| Сметы | новая коллекция `estimates` (или документ `app-settings` по образцу `quotes` для первой версии) | версия записи, `updated_at`, надгробие |
| Прокат (условия для чека) | поля у `rentals/` (срок, цена/сутки, залог, штраф) | нужен контракт у Умара |
| Ремонт, trade-in | коллекции `repair-orders`, `trade-in` (серверно отложены) | до решения — документ `app-settings` с шифрованием паспортных данных? **Нет:** паспортные данные в общем документе опасны → ждать серверной коллекции с правами |
| Настройки сферы | общий ключ `main/app-settings/nurmarket-kassa` → разделить по ключам и снабдить версией ключа | per-key version, `If-Match` |
| Шаблоны ценников/этикеток, правила скидок | `app-settings` (ключ-документ, версия, `updated_at`) | небольшие JSON; большие — коллекции |
| Отметки табеля | `main/staff/timesheet/marks/` (новое) или документ | то же |

**Практический путь без больших серверных работ (С3–С4):** документ-ключи в `app-settings/nurmarket-kassa/` по образцу КП (`updatedAt` + надгробия + слияние, 90 дней). Ограничения: размер документа и частота PATCH (спросить лимит), нет серверной валидации, нет прав по записям — поэтому для денег (предоплата заказов) и персональных данных (trade-in) — только серверные коллекции.

| Тип `deleted` = событие-надгробие с хранением ≥ 30 дней (не 7) | чтобы касса, не выходившая в сеть неделю, не воскресила удалённое |

### 3.4. Правила конфликтов и порядок операций

| Класс | Правило | Что видит человек |
|---|---|---|
| Остаток, баланс клиента, касса смены | **только операции** (дельты); сервер пересчитывает; клиент показывает «серверный остаток + свои неотправленные дельты» | никогда «моя правка потеряна» |
| Ревизия | операция `revision(product, counted, base_version)`: если за время счёта были движения — сервер считает разницу от версии, а не заменяет значение | «разница 3, учтена с поправкой» |
| Карточка товара/клиента | `version` + `If-Match`; PATCH только изменённых полей; при 412 — окно «Изменено другим (Айдар, 14:32): оставить мою / взять чужую / по полям»; по умолчанию слияние неконфликтующих полей | не теряется чужая правка тихо |
| Настройки | per-key version; общие — последний выигрывает **по ключу** с уведомлением «изменил Айдар»; JSON-ключи разбиваются на поля или версионируются целиком | «настройка изменена с другого устройства» |
| Документы (заказ, смета, КП) | запись + `updated_at`; слияние по записи; статусы — конечный автомат (нельзя «вернуть» из «продан»); поля денег меняются только операциями | история изменений |
| Права/тариф | только сервер, клиент не пишет | применяется на лету |
| Удаление | надгробие; побеждает более поздний `updated_at`, но «удаление против правки» — на подтверждение владельца | не воскресает |

**Идемпотентность и порядок.** Каждая операция имеет `op_id` (UUID, он же `Idempotency-Key`); повтор с тем же ключом возвращает прежний результат (`GET idempotency/{ключ}/`); операции одной сущности отправляются по порядку; время события — серверное, часы устройства — только как «создано на устройстве» (поправка `ServerClock` у кассы есть); `offline_too_old` и `accept_late` остаются единым правилом для К и М.

### 3.5. Push-канал — что реалистично

Бэкенд — Django-подобный (по поведению: `?page=`, DRF-ответы, ETag, `W/` ETag) [не проверено; стек и сервер ASGI/WSGI — вопрос Умару]; Cloudflare перед сервером, WebSocket у сайта уже есть.

| Вариант | Реалистичность | Клиенты | Замечание |
|---|---|---|---|
| **WebSocket-подсказка** `ws/company/` (токен первым сообщением, подписка на типы, ping 30 с из-за 100 с простоя Cloudflare) | **высокая**: на сервере WS уже есть для сайта; дешёвое сообщение `{cursor, types}` | К, В, Android-касса: `ClientWebSocket` (уже используется для Gemini Live и поддержки); М: пакет `web_socket_channel` (новая зависимость — согласие владельца) | в фоне Android/iOS соединение живёт недолго → FCM |
| **Long-poll** `main/changes/?wait=25` и `products/changes/?wait=25` | **средняя**: на WSGI с синхронными воркерами каждый ожидающий клиент блокирует воркер; нужен async-воркер/Channels или отдельный лёгкий сервис | все | хороший фоллбэк, если WS не пройдёт через прокси |
| **SSE** | средняя: HTTP/1.1 keep-alive, те же проблемы с воркерами | К, В; в М нет стандартного | не выбираем |
| **FCM** (мобилка в фоне) | **средняя**: нужны Firebase-проект, `firebase_messaging` и серверная отправка по событиям | М (Android/iOS) | зависимость и ключи — решение владельца; каркас `PushService` готов |
| **Опрос с ETag** (как сейчас) | уже работает | все | остаётся страховкой с мягким интервалом (30–60 с) |

**Рекомендация:** WS-подсказка + long-poll как запас + опрос; FCM для М при согласии. Сообщение WS — только `{cursor, types[], at}`; клиент делает `GET main/changes/?since=…`. Серверная нагрузка: опрос ≈16 запросов/мин на касса → ≈1 пинг/30 с и редкая страховка.

**Ретранслятор подсказок на нашем `NurRemoteSupport`** (`wss://support.nurcrm.kg`, идея из отчёта 29.10, п. 4.1.10) — только как временная мера, если Умар не сделает WS: подсказки наших приложений без данных; не покрывает правки с сайта; новая обязанность сервера помощи — решение владельца.

### 3.6. Офлайн-очередь единая для всех клиентов

Не единый код (К на C#, М на Dart), а **единый контракт**: запись `{op_id, type, payload, created_at, device_id, base_version?, attempts, state}`, одинаковые коды ошибок и исходов (`done|in_progress|failed|unknown → GET idempotency/{key}/`), одинаковое правило «7 суток / `accept_late` + PIN», одинаковое поведение при 5xx (нарастающая пауза), одинаковая видимость на сервере: устройство при каждой связи шлёт «в очереди N, самая старая 2 ч» (лёгкий `POST devices/{key}/queue-status/`) — владелец видит это на сайте/в В/в М («Требует внимания»). Для Мини контракт тот же.

### 3.7. Мобилка читает те же события

М подключает `main/changes` (типы как у кассы + `sale_*`, `shift_*`, `customer_order_changed`) и PhoneLink `events/hint` внутри магазина; WS при открытом приложении, FCM в фоне; при возврате в приложение — одно «обновить права, тариф, настройки, ленту» (`runOnce`). Кэш каталога — лента, как сейчас.

## 4. Согласованность версий клиентов

- `capabilities` расширить объектом `client_policy {min_version{kassa,owner,mobile,android-pos}, recommended, deprecated_features}`; клиент ниже `min_version` получает 426-подобный ответ `upgrade_required` и показывает «Обновите программу» (запись разрешена только по `If-Match`).
- События и сущности с `schema_version`; неизвестные поля клиент сохраняет «как есть» (как КП в мобилке «незнакомые поля»).
- Серверное правило PATCH: пишутся только присланные поля (подтвердить у Умара) — старая касса не затирает `attributes`.
- В `capabilities` — признак `events_ws`, `events_longpoll`, `fcm` для согласования канала.

## 5. «Мини»: независимый контур

Опираюсь на `ТЗ Мини-тариф 500 сом (20.11.2026)`; здесь — только про синхронизацию.

### 5.1. Что такое «раздельно, независимо»

- **Хранилище:** тот же сервер, но **одна отдельная компания** (`company_id`) со своим тарифом `mini` (код `subscription_plan.code = "mini"`, лимиты `max_staff=1`, `max_devices=1`, `max_cashboxes=1`, `allowed_clients=["mobile"]`).
- **Клиент:** только мобилка (`X-NurMarket-Client: mobile/…`). Сервер жёстко (на выдаче токена и в каждом запросе) отвечает 403 `plan_client_not_allowed` для `kassa/owner/android-pos`; сайт — только просмотр владельцу (вопрос 4 в ТЗ Мини).
- **Без LAN и PhoneLink:** у «Мини» нет кассы на ПК → нет соседей, нет сопряжения; мобилка в режиме «Мини» не ищет кассу в подсети (экономия батареи — см. отчёт 29.10: перебор подсети 2 540 TCP-попыток).
- **Без ПК-ленты:** WebSocket/long-poll можно держать (одно устройство), но опрос лёгкий; события для одного клиента не нужны, **главная синхронизация — очередь + кэш**.
- **Свой набор настроек:** `nurmarket-mobile` (мини-настройки) — в серверном документе; ключи кассы не нужны.
- **Не влияет на организм других компаний:** данные разделены по `company_id` (изоляция сервера); кэш-ключи клиента привязаны к аккаунту (`LastDataAccountKey`, `AccountDataIsolation`); лимит нагрузки Мини — отдельные квоты (rate limit по компании); один «Мини» не расходует слоты чужой компании.
- **Офлайн для рынка:** вход 7 суток от пароля и 7 суток для офлайн-чека — главный риск (Б-М8): просить 30 суток/14 суток без PIN (единственный сотрудник).

### 5.2. Апгрейд Мини → Старт (данные уже на сервере)

1. Оплата → `plan_changed` (`features_changed`) → мобилка **сначала допускает очередь** (`runQueue`), затем обновляет режим без перелогина; предупреждение «не отправлено N» блокирует апгрейд-кнопку, пока очередь не пуста.
2. Меняются `plan` и `allowed_clients=["mobile","desktop_pos","desktop_owner","android_pos"]`, `max_staff=3`; слот телефона остаётся; сервер включает флаги (`allow_multi_*` — по плану).
3. Касса и владелец при первом входе: `PullOnce` личных и общих настроек, полная загрузка каталога, лента с нуля; **данные уже на сервере** — дублей нет: товары, клиенты, смены, продажи общие.
4. **Риск «первого устройства заполняет облако».** По правилам SettingsCloudSync пустой общий документ `nurmarket-kassa` заполняется настройками первой кассы (имя магазина, чек, сфера). Если Мини уже хранил сферу/название у сервера — касса должна **сначала прочитать** серверные значения (`market_sphere`, название компании), а не писать свои значения по умолчанию. Нужен тест «апгрейд Мини → Старт: настройки Мини не затёрты».
5. **Локальные данные мобилки:** КП/счета — серверные (ОК); черновики карточек товара и очередь — досылаются до апгрейда; фото (если локальные) загружаются на сервер; настройки камеры/ИИ — серверный документ.
6. **Дубли товаров:** создание товара на Мини без штрихкода → при импорте на кассе (весы, прайс, Excel) возможен дубль по названию; правило — первичный ключ по штрихкоду/артикулу, предупреждение «похожий товар уже есть» при создании.
7. **Нумерация чеков/«Касса»:** у сервера общая; смена и касса уже есть; автосмена Мини остаётся.

### 5.3. Даунгрейд Старт → Мини

- Данные **не удаляются**, функции скрываются (`allowed_clients=["mobile"]`): касса и владелец получают 403 `plan_client_not_allowed` при следующем запросе/входе; их очередь **должна успеть отправиться до отключения** (льготный период и предупреждение в кассе: «Через N дней касса отключится. Отправьте очередь»).
- Лишние сотрудники — `suspended` (не удалены); купленные пакеты — скрыты, не удалены.
- Локальные документы сфер (заказы, сметы…), которые **ещё не на сервере**, при даунгрейде остаются только на ПК и становятся недоступны — **ещё одна причина** перенести их на сервер (С3–С4) до выхода Мини.

### 5.4. Что нужно от синхронизации для Мини (минимум)

Событийная лента не обязательна; нужны: единая очередь (3.6), `plan_changed`, возврат в приложение = «обновить», правило срока офлайна, быстрые карточки без штрихкода. Всё остальное «организма» для Мини не включается.

### Риски

- **Двойной учёт:** LAN-вычитание продажи соседа + лента + пульс могут вычесть остаток дважды (уже была ловушка «Касса:» двойное вычитание, 1.17.76). Решение: один источник — серверный остаток + свои неотправленные дельты (`LanStockAdjuster` уже так считает; новые каналы не должны добавлять поправки).
- **Конфликты:** без `If-Match` на сервере (С10) диалоги слияния (С7) — только по `updated_at`, возможны гонки.
- **Потеря данных при миграции локальных JSON на сервер:** обязательно «копия + хэши до/после», миграция по ключу записи, флаг «перенесено», откат на файл; нельзя удалять локальный файл до подтверждения; хук против тестов на реальных данных уже есть.
- **Нагрузка:** WS/long-poll — соединение на устройство (≈ N устройств компании × число компаний); долгий запрос на WSGI блокирует воркеры (С9 требует ASGI/Channels); опрос остаётся страховкой, поэтому интервалы не снижаем до 1 с.
- **Cloudflare:** простой WS ≈100 с → ping 30 с; `X-Poll-Wait-Max: 25`.
- **FCM:** новая зависимость и ключи → решение владельца.
- **Старые клиенты:** нет `min_client_version` — старая касса не получает новых типов, но и не должна ломать поля; без С10 риск затирания.
- **Мини:** без Б-М3 владелец «Мини» запустит кассу на ПК бесплатно (касса принимает неизвестный план за «Стандарт»); нужен разбор `plan.code` в кассе до выпуска Мини.

## 7. Критерии приёмки (сценарии) и метрики

### 7.1. Сценарии (два устройства/клиента, живая проверка на тестовом аккаунте NBS; не на боевом)

| № | Сценарий | Критерий |
|---|---|---|

| 2 | Изменил цену на сайте/в мобилке → касса и владелец | ≤3 с; цена в окне оплаты не старее 3 с |
| 3 | Остаток после продажи на другой кассе | касса/владелец/мобилка ≤3 с, без двойного вычитания; сверка `stock_balance` — расхождение 0 |

| 6 | Заказ под клиента создан на кассе 1 → виден на кассе 2, в мобилке и на сайте | ≤5 с, предоплата одна, в смену не задваивается |

| 9 | Смена открыта на кассе 1 → касса 2 «смена открыта» | ≤3 с |
| 10 | Настройка (чек, сфера) изменена владельцем → все кассы | ≤3 с; открытое окно настроек применяет по закрытию |
| 11 | Старая версия клиента (ниже `min_version`) | предложение обновиться, данные не затёрты |
| 12 | **Мини независим:** вход в кассу с логином Мини → отказ `plan_client_not_allowed`; Мини не влияет на соседнюю компанию (нет событий, слотов, ключей); даунгрейд Старт→Мини не удаляет данные; апгрейд Мини→Старт — касса подхватила данные без дублей и без перезаписи настроек | все 4 проверки зелёные |

### 7.2. Метрики

- **Задержка доставки:** p50/p95 «событие на сервере → применено на клиенте» (логировать `SYNC_LAG` = `at` события − момент применения), цель p95 ≤ 5 с при WS, ≤ 12 с при опросе.
- **Нагрузка:** запросов в минуту на устройство в простое (строка `STATS` кассы раз в 5 минут): сейчас ≈16, цель ≤3; доля устройств на WS ≥ 90 %.
- **Дубли:** число «чеков с одним Idempotency-Key» = 0; число расхождений «остаток кассы vs `stock_balance`» в сверке; число «воскресших» удалённых товаров = 0.
- **Очередь:** возраст самой старой записи, число «Не принято», время «после связи до пустой очереди».
- **Конфликты:** число 412 `version_conflict`, доля разрешённых без потери; число потерянных правок (по журналу изменений) = 0.
- **Миграция:** локальных записей перенесено = записей на сервере; расхождение 0.
- **Качество:** жалобы «касса и сайт не совпадают» — по обращениям.

## 9. 8 вопросов владельцу (с рекомендацией)

1. **Что болит сильнее всего?** Остатки (приход в пути, «не совпадает»), настройки, права, скорость, сайт↔касса, потеря заказов при смене ПК? **Рекомендую порядок:** остатки и приход (С4) → локальные данные сфер на сервер (С5–С6) → скорость/push (С8–С9) → права в мобилке (С2). Назовите, что поставить первым.
2. **Можно ли хранить локальные данные автозапчастей, заказов, смет на сервере** — в `attributes` товара, в `customer-orders/` и в документах `app-settings` (смета, шаблоны)? Для персональных данных (trade-in: паспорт) — только после серверной коллекции с правами. **Рекомендую: да**, начать с автозапчастей (`attributes` готовы) и заказов (`customer-orders/`).
3. **Push-канал:** согласны на серверный WebSocket (Умар) как основу, long-poll запасом, а опрос оставить страховкой? **Рекомендую: да.**
