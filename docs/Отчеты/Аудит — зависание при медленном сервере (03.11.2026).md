# Аудит — зависание при медленном сервере (03.11.2026)

Жалоба владельца (дословно): «если сервер зависает, то зависает и наша программа! исправь!»

Аудитор — Opus. Код не правился. `dotnet test` не запускался. Установленная касса не запускалась и не трогалась: хэши её настроек, базы и `auth.dat` до и после замеров совпали.

## 0. Коротко для владельца

- **Касса не «падает» и не замирает целиком.** На пути к серверу UI-поток почти нигде не ждёт синхронно. Окно Windows «Не отвечает» из-за сервера в рабочих сценариях не появляется; единственное подозрительное место — закрытие программы (С-14).
- **Зависает окно или кнопка.** Когда сервер отвечает медленно (5–55 с) или принял соединение и молчит, окно ждёт ответа до 55 секунд. Это срок `HttpClient.Timeout`. Часто запросов в цепочке 2–3, и ожидание доходит до 110–165 с. Кнопки «Отмена» нет, надписи «сервер медлит» нет. Для кассира это и есть «программа зависла».
- **Медленный ответ кассе не виден.** Ответ через 20 с считается успехом. Авария («Автономно») не объявляется, поэтому каждый следующий шаг снова ждёт полный срок. Защита от «сервер недоступен» сделана хорошо (оплата 5 с, автовход 3 с, окна возврата и долга 5 с), но от «сервер жив, но тормозит» её нет.
- **Фон мешает переднему плану.** У запросов одна общая очередь на 12 мест. Фоновые загрузки (каталог, сводка владельца, обновление токена) занимают все места, и любой клик кассира ждёт свободного места ещё до отправки запроса.
- **Исправление** — один общий приём на передний план: не дольше 8 с без ответа, затем надпись «Сервер отвечает медленно…» с кнопкой «Отменить ожидание». Отдельная «быстрая полоса» в очереди запросов для действий кассира. Денежные операции продолжаются в фоне с тем же ключом идемпотентности. Ниже — ТЗ из 24 пунктов (С-01…С-24).

Выводы:
- **UI-поток живой (пульс 0–14 мс), но окно ждёт ровно столько, сколько медлит сервер, и до 55 с.** Это и есть жалоба. Синхронное ожидание дало бы 8 с замороженного интерфейса — такого на пути к сети не найдено.
- **Медленный ответ (8, 20, 50 с) оставляет связь в состоянии «Online».** Каждый следующий шаг снова ждёт полный срок.
- **Один «молчащий» запрос даёт только «Degraded».** Аварию объявляют 3 сбоя подряд, то есть 3×55 с.
- **Фон и обновление токена занимают очередь.** Тогда даже мгновенно отвечающий запрос кассира ждёт 54–55 с.

Время «зависания» в сценариях из задания (запуск, смена, оплата, возврат, склад и т. д.) складывается из этих вызовов. Ожидание = число последовательных вызовов без своего срока × задержка сервера (до 55 с каждый); см. столбец «Сейчас» в разделе 4. Живой замер окон — раздел 8.

### С-01. Общий помощник «серверный вызов переднего плана» (основа, делать первым)

Где:
- `I/Services/ServerAnswerWait.cs` — расширить, новый класс не плодить;
- `D/ModalShell.cs` — индикатор.

Что сделать:
1. Константа `ServerAnswerWait.ForegroundBudget = 8 с`.
2. Новый метод `ServerAnswerWait.ForegroundAsync<T>(string context, Func<CancellationToken, Task<T>> op, CancellationToken userCancel, Action<bool>? onSlow = null)`:
   - внутри `RunAsync(op, ForegroundBudget, userCancel)`: срок отсчитывается с последнего ответа сервера, `BeginResponseWatch` уже есть;
   - через 3 с без ответа — `onSlow(true)`, это показ «Ждём сервер…»;
   - по ответу — `onSlow(false)`;
   - по истечении 8 с без ответа — `ServerNotAnsweringException`. Аварию НЕ объявлять: это «медленно», а не «недоступен». Только `ServerOutageMonitor.ReportSlow(context)` (С-02);
   - отмена пользователем — `OperationCanceledException`, сбоем сервера не считается.
3. Вариант для записи — `ForegroundWriteAsync`. Через 8 с он НЕ отменяет запрос: возвращает управление окну с признаком «ещё идёт» (`Task<ForegroundResult<T>>` с `Pending = true` и `Completion` — той же задачей). Окно пишет «Сервер отвечает медленно — операция продолжается, результат появится сам» и разрешает закрыться. Нужно для денег и записей, см. С-08/С-09.
4. В `ModalShell`:
   - метод `RunServerAsync(Func<CancellationToken, Task> action)`: как `RunBusyAsync`, но создаёт `CancellationTokenSource` окна;
   - через 3 с ожидания показывает в подвале строку «Ждём ответ сервера NurCRM… N с» и кнопку «Отменить ожидание», которая отменяет токен;
   - пока идёт ожидание, ✕ и Esc работают как «Отменить ожидание»;
   - закрытие окна отменяет токен.
5. Для кнопок вне `ModalShell` (главное окно, склад, владелец) — маленький помощник `A/Services/ServerWaitIndicator.cs`: та же строка и кнопка в `CartMessage`/строке статуса окна. Таймер — `DispatcherTimer`, UI не блокировать.

Приёмка:
- стенд `delay 20` вокруг любого вызова через `ForegroundAsync`: управление возвращается за 8,0–8,5 с, текст «Сервер отвечает медленно» на 5 языках, `ServerOutageMonitor.State` остаётся `Online`/`Degraded`, но не `Outage`;

## 7. Риски

- **Двойная запись денег.** Денежный запрос, отданный в фон, нельзя повторять без того же ключа идемпотентности. Если ключа нет — сначала добавить. Отмена токена денежного запроса запрещена: только «перестать ждать в окне». Проверять журналом стенда (`out\server.log`): один POST или повтор с тем же ключом.
- **Ложная авария.** «Медленно» не должно объявлять `Outage`: иначе оплаты уйдут в очередь при живом сервере. `ReportSlow` — только журнал и значок.
- **Чужой аккаунт при «Продолжить без ожидания»** (С-03 п. 4). Без подтверждённой компании открывать кассу только с кэшем ТОЙ ЖЕ компании.
- **Быстрая полоса под нагрузкой.** 4 + 8 мест — не больше нынешних 12 соединений. HTTP/2 мультиплексирует, лишних соединений не будет. Следить за 429: щит `ApiThrottle` общий и не меняется.
- **Потоки.** Таймеры индикатора — `DispatcherTimer` (UI). Продолжения фоновых задач, трогающие окна, — через `Dispatcher.UIThread.Post`, и только если окно не закрыто (ловушки — AI_HANDOFF раздел 10).
- **Устаревший ответ в закрытом окне.** Всем фоновым продолжениям проверять `IsClosed`/токен окна.
- **Порядок «добавить товар в чек» до прихода** (С-07) не должен ломать запрет продажи в минус. Если запрет включён, поведение согласовать с владельцем.
