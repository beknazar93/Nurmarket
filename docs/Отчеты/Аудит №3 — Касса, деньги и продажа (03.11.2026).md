**Д3-01 · СРЕДНИЙ · недоделано (С-08/С-09 аудита зависаний). Денежные окна на медленном сервере по-прежнему ждут до 55 с без «Отменить ожидание», хотя выпуск обещает «касса не ждёт медленный сервер».**
- Где:
  - `ServerAnswerWait.ForegroundWriteAsync` (`ServerAnswerWait.cs:153`) вызывается только в пополнении (`MainWindow.Dialogs.cs:1196`) и в карточке товара (`ProductEditDialog.axaml.cs:2274`). В возврате, обмене, оплате долга, «в долг», зарплате, прокате его нет (Grep по снимку выпуска).
  - Возврат: `SalesApiService.Exchange.cs:117-122` — `RequestAsync` без срока (55 с HttpClient). Обмен: `:75-81` — 30 с. «В долг»/смешанная: `PosCheckoutService.cs:396-397` — срок ответа ставится только для `queueable` (наличные, безнал).
  - Отчёт исполнителя сам пишет: «С-08 НЕ сделано», «С-09 НЕ сделано» («Аудит — зависание при медленном сервере», раздел 10).
- Сценарий: сервер отвечает 20–50 с. Кассир жмёт «Вернуть» → окно занято до 55 с, отмены нет. Покупатель ждёт; кассир может закрыть программу через диспетчер задач.
- Деньги не теряются: ключ возврата и долга сохраняется, повтор тем же ключом. Поэтому не ВЫСОКИЙ.
- Противоречие поведения: оплата наличными через 5 с объявляет **аварию** («касса работает автономно»), а окна чтения через 8 с — лишь «сервер медлит». Это Д-4 из живой проверки 03.11, в выпуске осталось.
- Как исправить: ТЗ С-08/С-09 уже написано (раздел 5 того же отчёта). Отдельная задача Opus/Sonnet с `/code-review` для денег.

**Д3-02 · СРЕДНИЙ · НОВОЕ. Быстрая полоса очереди не охватывает возврат, обмен, внесения/изъятия и проведение старых чеков по PIN — они ждут место в фоновой очереди за каталогом.**
- Где: `NurMarketApiClient.cs:59-64` — полоса выбирается по `IsForeground` = `ForegroundFlag || ApiThrottle.IsCritical`. Критичными помечены только оплата (`PosCheckoutService.cs:322`), открытие/закрытие и сверка смены (`CashShiftService.cs:109`, `:477`; `ShiftStateService.cs:62`; `MainWindow.axaml.cs:3277`). Возврат (`SalesApiService.Exchange.cs:117`), обмен (`:75`), внесение/изъятие (`ShiftApiService.cs:438`), проведение по PIN (`SalesApiService.LateAccept.cs:99`) идут без `Foreground()` и без `BeginCritical` → в фоновую полосу (8 мест).
- Комментарий исправления ревью В-1 (`NurMarketApiClient.Headers.cs:43`: «проведение старых чеков, перемещения идут в быструю полосу») для этих вызовов неверен.
- Сценарий: сервер медлит, 8 фоновых запросов (страницы каталога, лента, остатки) висят до 55 с → «Вернуть» сначала ждёт свободное место, потом свой ответ. До 110 с.
- Как исправить: обернуть отправку возврата, обмена, внесения/изъятия и проведения по PIN в `ApiThrottle.BeginCritical()` (как оплата) — одна строка в каждом месте.

**Д3-03 · СРЕДНИЙ · недоделано (Ж-05 от 01.11). X-отчёт: обычные возвраты превращаются в «Корректировку по данным сервера», а плитки «Продажи 0 / Наличные 0,00» при трёх продажах смены.**

X-отчёт: «Продажи 0», «Наличные 0,00 сом», «Безналичные 0,00», «Возвраты 15,60»; в раскладке «Наличные продажи +0,00 / Возвраты наличными −7,60 / Корректировка по данным сервера +7,60 / = 9 450,00».
- Итог верен, но раскладка врёт по слагаемым: сервер убирает возвращённые продажи из «продаж», касса вычитает возвраты ещё раз и подгоняет разницу «Корректировкой» (`DrawerBreakdownBuilder.cs:45-56`). Подсказка этой строки говорит «Ящик под эту строку не подгоняйте» — а здесь она возникает в самом обычном дне с возвратами. Владелец/кассир не может сверить ящик по строкам.

Либо подпись «Наличные продажи (за вычетом возвращённых)» и не вычитать возвраты по этим чекам второй раз.

**Д3-04 · СРЕДНИЙ · недоделано (П-2 повторной проверки 03.11). «История чеков» без ответа сервера: номера «№1…№N», способ оплаты «—», сумма без скидки на чек.**
- Где: `ReceiptHistoryService.cs:193-207` (`NumberAndSort` → «№» + порядковый), `:214-247` (`LoadCashSoldSales`: сумма = Σ qty × price, без скидок строк и чека, без округления весовых).
- Живая проверка 03.11 (П-2) это показала после сборки 18:35 — в выпуск исправление не вошло. Чек со скидкой 10 % (как 002031: 3,60) в такой истории показан как 4,00; кассир по бумажному чеку его не найдёт (поиск «002031» → пусто).
- Как исправить: хранить номер чека, итог и способ оплаты из ответа оплаты (`PAY quick OK number=…`) рядом с `SoldLineItems` и показывать их.

**Д3-05 · СРЕДНИЙ (ПЛАУЗИБЛЬНО) · недоделано (2.2 приёмки круга 3). Неясный возврат: «ключ не найден» принимается сразу, без выдержки — на медленном сервере возможна вторая выдача.**
- Где: `ReturnSaleDialog.axaml.cs:2205-2209`. У оплаты выдержка есть (`InFlightReconcile`), у возврата нет.
- Сценарий: сервер медленный, запрос возврата ещё не дошёл до записи ключа → «не найден» → касса говорит «не прошёл, повторите». Если кассир повторит тем же составом — тот же ключ, задвоения нет. Если изменит количество (новый ключ) — сервер проведёт оба возврата (в пределах количества чека): в CRM вернётся больше, чем отдал покупатель, «ожидается в ящике» уменьшится на сумму первого (ложный излишек при закрытии), остаток товара завысится.
