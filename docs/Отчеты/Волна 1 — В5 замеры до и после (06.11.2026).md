# Волна 1 — В5 «Скорость — SQLite и замеры»: замеры до и после (06.11.2026)

**Как мерили.** BenchmarkDotNet (`tools/bench/NurMarketKassa.Bench`, файл `Wave5SqliteBench.cs`, короткий прогон `ShortRun`: 3 прогрева + 3 замера, поэтому у быстрых операций «разброс» большой — смотрите порядок величины, а не третью цифру). ПК: i7-7700, .NET 8.0.28.

**На чём.** Копия базы «большой магазин» `C:\Users\User\NurMarket-test\perf-db-copy\pos_scaled.db` (176 МБ): 15 461 товар, 301 тыс. строк продаж (≈100 тыс. чеков), 99 тыс. строк истории закупок, 20 тыс. списаний, 30 тыс. событий смены. Копия сделана из копии настоящей базы NBS через sqlite3 backup API (`make_scaled.py`); на каждый запуск замеров она ещё раз копируется через `SqliteConnection.BackupDatabase` во временную папку данных (`NURMARKET_DATA_ROOT`), **настоящая база кассы не читалась и не менялась** (хэши `pos_local.db` и `user-settings.json` до и после совпали, см. `test-safe.ps1`). «Текущая компания» в замерах выставлена на компанию копии, иначе условие по компании не применялось бы.

**«До»** снято на коде без правок В5 (одноразовый прогон, `bench-before`), **«после»** — на коде с правками; «после» для схемы — на копии, которую кассa открыла впервые (индексы построились при открытии).

## Что и где изменено

- **Шаг 3.** `DatabaseService.LoadSoldLinesBySaleIds` — пачки по 500 номеров одним `IN (…)` и `+company_id` (К-1); `LoadKnownSaleIds` — `+company_id` (К-2); `PurchaseReceivingService.AppendHistoryBatch` — вся история прихода одной транзакцией и одной подготовленной командой, при сбое пачки строки пишутся по одной (Л-4); `LoadLocalHistoryMany` — история закупок многих товаров одним запросом (Л-3), применено в `RestockSuggestionsWindow` и `InvoiceDocumentWindow`.
  - **К-2: `LoadKnownSaleIdsBetween` в `SalesHistoryBackfill` не подключён сознательно.** Офлайн-чек пишется в историю со временем продажи (до трёх суток назад), а сервер ставит `created_at` в момент выгрузки; окно по дате пропустило бы такой чек, и его строки записались бы второй раз. Кроме того, время в `sold_at` хранится строкой «o» то в UTC, то в местном поясе, и сравнение строк на границе окна ненадёжно. Полный список со знаком «+» даёт тот же результат за 150 мс. Файл `SalesHistoryBackfill.cs` не менялся.
- **Шаг 19 (25.3, 25.4).** `busy_timeout` каталога 3000 → 5000 (теперь один срок у обоих «хозяев» `pos_local.db`). Новый `DatabaseService.WithReadConnection` — чтение без замка записи класса: база в WAL, читатель видит целый снимок и не мешает писателю; если WAL выключен, берётся общий замок чтения. `LoadLocalHistory` и `LoadLocalHistoryMany` читают через него; таблица истории создаётся один раз под замком записи.
- **Шаг 18 (24.1, 24.2).** `LoadOfflineSalesExceptStatus`, `CountOfflineSalesByStatus` + фасады `OfflinePendingSalesStore.LoadAllUnsynced()` и `SyncedCount` через `COUNT(*)`. `SyncReplaceAllWithDiff` читает отпечатки потоком (`LoadAllFingerprints`).
- **Шаг 24 (18.3, PerfSummary).** Новый `Infrastructure/Services/PerfSummary.cs`: времена запросов к API (из `ApiPathStats.Record`) и к SQLite складываются в кольцо по 400 значений на ключ; раз в календарный день (по таймеру после суток работы или при закрытии программы после 30+ минут) в журнал уходит ОДНА строка раздела `PERF`: p50/p95/max по самым частым путям и по операциям SQLite. Запрос SQLite дольше 200 мс сразу пишется строкой `SQLITE SLOW` (имя операции и миллисекунды, без текста запроса; не чаще раза в 30 с на операцию). Без логинов, имён, сумм, идентификаторов. Подключено к 16 методам `DatabaseService` и к `WithConnection`/`WithReadConnection`.
- **Шаг 30 (схема, «да» владельца).** `DatabaseService.EnsurePerfIndexes` при открытии базы: 4 индекса `CREATE INDEX IF NOT EXISTS` (`idx_products_favorite_name` частичный, `idx_writeoff_company_created`, `idx_writeoff_company_name`, `idx_products_barcode_nocase`) и версия схемы `PRAGMA user_version = 1` — только если построены все; данные не затрагиваются. Откат: `DROP INDEX …; PRAGMA user_version = 0;`.
- **Б-5.** Компания в условиях «только свои строки» передаётся параметром `$ownCompany` команды (20 мест `DatabaseService` + `PurchaseReceivingService`), а не литералом в тексте запроса. Публичный `OwnRowsClauseFor()` без команды оставлен для `StockTransferService` (файл чужой волны).
- **Шаг 25.** `tools/qa/weak-run.ps1` (слабый ПК: 2 ядра, BelowNormal, прокси `tools/qa/slow_server.py` с профилями fast/slownet/badnet/serverdown/slowbytes, отдельная папка данных, закрывает только свою кассу) и `tools/qa/weak-android.ps1` (AVD 2 ядра/2 ГБ/umts-hsdpa, холодный старт ×N, gfxinfo, meminfo). Оба имеют `-Check` (проверка условий без запуска). `slow_server_v.py` перенесён из стенда в `tools/qa/slow_server.py` (секретов нет).

## Что не дало эффекта (честно)

- **24.1 — без выигрыша.** Потоковое чтение отпечатков без `ORDER BY name` время и объём выделенной памяти не изменило (172 → 174–185 мс). Настоящая экономия (кэш плиток без `description` и `bundle_items_json`) требует, чтобы карточка товара, печать этикеток и редактирование читали описание по требованию: `Description` берётся из плитки в `ProductDetailsWindow`, `ProductEditDialog`, `BarcodePrintCatalog`, `CatalogFeedSync` — это чужие файлы. Кэш не тронут.
- **К-1 и Л-3 — выигрыш скромнее обещанного в аудите** (×1,5 и ×1,4 вместо ×3 и ×8): аудит мерил чистый SQL в Python, а на кассе основное время — создание объектов из строк (2 780 записей истории и 900 строк чеков). Зато в 300 раз меньше захватов блокировки и соединений.
