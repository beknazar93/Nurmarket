## 2. Слабости (по убыванию серьёзности)

### 2.1. Блокеры денег и данных

**С-01. Правка карточки товара перезаписывает остаток (и цену), изменённые в другом месте.** [код]
- Где: `Views.axaml/Dialogs/ProductEditDialog.axaml.cs:2106` (`Quantity = quantityValue ?? 0`), `NurMarketKassa.Infrastructure/Services/Api/ICatalogApiService.cs:174` (`SendQuantity` по умолчанию `true`), `CatalogApiService.cs:926–930` (поле `quantity` убирается только при `SendQuantity = false`). В окне правки `SendQuantity` нигде не ставится.
- Что ломается: окно всегда шлёт PATCH со всеми полями, в том числе остатком, прочитанным при открытии. Кассир открыл товар (остаток 20), за это время другая касса продала 5 (на сервере 15), кассир поменял только название → «Сохранить» → на сервере снова 20. То же с ценой, которую за это время поменяли на сайте или в программе владельца. Два окна одного товара (касса + программа владельца): прав последний. Версии/ETag нет.
- Чем грозит: «лишний» товар на складе, расхождение при ревизии, недостача без следа (через PATCH, не документом).
- Исправление (минимальный дифф): в `SaveAsync` — `SendQuantity = _existing is null || Math.Abs((quantityValue ?? 0) - _existing.Quantity) > 0.0005`. Цену/закупку слать только при изменении — по тому же образцу (флаги `Send*` в запросе уже есть). Трудоёмкость: 15 мин (остаток), ~1 ч (цены).

**С-02. Приход от поставщика с дробным количеством (весовые, новое в 1.17.70) — сервер хранит количество прихода целым.** [код + предп.]
- Где: `PurchaseReceivingService.cs:731` (`["qty"] = Math.Round(l.Quantity, 6)` — уходит 2,5), комментарий `:729` «сервер принимает не больше 3 знаков» не подтверждён документом. Против: «Ответ Умара c8958b4» п.3 — «Количество в строке прихода — пока целое»; «Склад — функции и данные» 3.6 — swagger `qty: integer`, все 109 строк приходов NBS целые.
- Что может сломаться (зависит от сервера): (а) 400 — весь приход (все позиции накладной) не проводится, задача очереди «отклонена»; (б) сервер молча усекает 2,5 → 2 — остаток и сумма долга на сервере меньше, чем в кассе, а сверка `FindPostedReceiptAsync` (`:286–313`, сравнивает «товар:кол-во:цена») никогда не совпадёт → после обрыва связи приход может уйти второй раз (если сервер не смотрит ключ в теле, см. С-07).
- Стенд: `Validate` пропускает строку «Сахар 2,5 кг, с поставщиком» без замечаний [запуск].
- Исправление: до подтверждения Умара — для приходов **с поставщиком** не проводить строку с дробным количеством, если `capabilities` не говорит о дробном `qty` (понятный текст: «сервер принимает целое количество; примите без поставщика или округлите»), путь «без поставщика» оставить. Живая проверка: приход 0,5 кг тестового товара на NBS — пишет на сервер, решает владелец. Трудоёмкость: 30 мин + проверка.

**С-03. Создание товара: после 4 секунд без ответа товар создаётся второй раз в фоне.** [код; дубль на сервере — предп.]
- Где: `ProductEditDialog.axaml.cs:40` (`FastCreateTimeout = 4 с`), `:2176–2190` (отмена по таймауту → локальная запись + `CreateOnServerInBackgroundAsync`), `:2196–2220` (повторный `CreateProductAsync` без проверки).
- Что ломается: первый POST мог дойти до сервера (по комментарию в `CatalogApiService.cs:717` сервер отвечает и по 40–60 с), а фон шлёт второй — два товара с одним штрихкодом (остаток делится на две карточки; такие дубли уже есть на NBS — «Патроны» 1140 + 1211). Если второй POST получил 400 — «сохранён только локально», повтора нет, а на сервере товар есть.
- Исправление: перед фоновым повтором — `FindWarehouseProductByBarcodeAsync(штрихкод)`; нашёлся — взять его id. Ключ идемпотентности в заголовке, если сервер его поддерживает для `products`. Трудоёмкость: 1–2 ч.

**С-04. Скан сканером в окне правки подменяет основной штрихкод существующего товара.** [код]
- Где: `ProductEditDialog.axaml.cs:470–483` (`OnBarcodeScanned` → `Barcode = barcode` и для `_existing != null`).
- Что ломается: кассир правит цену товара A, сканирует товар B «посмотреть» → «Сохранить» → у A штрихкод B, свой код потерян, два товара с одним кодом, касса пробивает не тот.
- Исправление: при `_existing != null` скан не принимать (или спросить «Заменить штрихкод?»). 15 мин.

**С-05. Перемещение между филиалами без ключа повтора: после обрыва — двойное перемещение.** [код]
- Где: `Views.axaml/Dialogs/StockTransferDialog.Branches.cs:245` (`POST api/main/branch-transfers/` без `Idempotency-Key`, таймаут 45 с), `:253–258` (любая ошибка → «Перемещение не проведено на сервере»).
- Что ломается: ответ потерялся (таймаут/обрыв) — перемещение на сервере проведено, кассир видит «не проведено» и жмёт «Отправить» ещё раз — товар уходит дважды.
- Исправление: заголовок `Idempotency-Key` = id документа кассы (тот же при повторе); при «исход неизвестен» — сначала найти перемещение на сервере по комментарию «документ {номер}» и не слать второй раз. Сообщение «Связь прервалась — проверяем, прошло ли перемещение». 1 ч.

**С-06. Массовая загрузка: повтор поправленного файла удваивает приход.** [код, отчёт помощника]
- Где: `Services/BulkImport/BulkImportJournal.cs:51` (журнал по хэшу всех ячеек), `Views.axaml/Main/BulkImportWizardWindow.cs:1366–1393`.
- Что ломается: загрузили приход 3 000 строк, исправили одну цену в файле, загрузили снова — хэш другой, журнал новый, все 3 000 строк приходуются второй раз. Защита «уже загружен» — только для байт-в-байт того же файла.
- Исправление: при открытии искать свежие (до 7 дней) журналы той же компании/имени файла; совпадает больше половины пар «штрихкод+количество» — спросить «Загрузить только новые строки / Всё заново». 1–2 ч.

**С-07. Ключ повтора прихода уходит только в теле, а сервер c8958b4 смотрит заголовок `Idempotency-Key`.** [код]
- Где: `CatalogApiService.cs:791–793` (`CreateSupplierReceiptAsync` без заголовков); тело — `PurchaseReceivingService.cs:202, 755`. Возврат поставщику уже шлёт и заголовок, и тело (`SupplierApiService.cs:422–430`).
- Чем грозит: в очереди приходов от дубля спасает сверка по списку (`FindPostedReceiptAsync`), но она бессильна в случае С-02(б) и если первая отправка была > 3 страниц назад. С заголовком сервер сам ответит `replayed: true` (Ответ Умара, п.3 «Прочее»).
- Исправление: передать `headers: {Idempotency-Key: ключ}` в `CreateSupplierReceiptAsync` (как у возврата). 10 мин.

**С-08. Excel: наценка в процентном формате «25 %» читается как 0,25 %.** [код, помощник]
- Где: `Services/BulkImport/ProductFileReader.cs:378–407` (`CellText` не смотрит стиль ячейки), `BulkImportPlan.cs:676`. Цена продажи ≈ закупке — продажа почти без наценки по всему файлу.
- Исправление: формат ячейки 9/10 или с «%» → ×100; или все значения столбца ≤ 1 — ×100 с предупреждением. 30–60 мин.

### 2.2. Важные

**С-09. Карточка, открытая из кэша (сервер ответил 5xx/429), при сохранении стирает скидку, наценку, страну, вес.** [код, помощник] `WarehouseWindow.axaml.cs:1393–1407`, `CatalogApiService.cs:855–859`; в кэше этих полей нет (`LocalProductRepository.ToTileVm`, ~1964–1987). Исправление: признак «открыто из кэша» → не слать эти поля (флаги `Send*`) или предупреждать. ~1 ч.

**С-10. «Услуга» при сохранении становится «Товаром».** [код, помощник] `ProductEditDialog.axaml.cs:206–212` читает только `IsBundle`, `existing.Kind` игнорируется; `CatalogApiService.cs:847` шлёт `kind = "product"`. Услуга начинает списываться со склада. 1 строка.

**С-11. Мастер массовой загрузки не предупреждает «цена продажи ниже закупки», а заголовок «Цена» всегда считается ценой продажи.** [код, помощник] `BulkImportPlan.Check` (776–845). В накладной поставщика «Цена» — это закупка: закупка 50, в файле «Цена 48» → цена продажи молча 48. Ручная приёмка спрашивает (`WarehouseWindow.ReceivingScan.cs:593`). Исправление: плитка «ниже закупки» + подтверждение; при наличии столбца «Сумма» понижать уверенность «Цена». 1 ч.

**С-12. Обрезка списка ошибок пачки → неудачные строки помечаются «записанными» и больше не загружаются.** [код, помощник] `BulkReceivingFeeder.cs:505–506`, `BulkImportJournal.cs:156–171`: >2000 ошибок на пачку — тексты очищаются; пачку убрали из «Приходов в фоне» или прошло 7 дней — `FoldReceipt(null)` отмечает записанными все строки. Исправление: хранить штрихкоды неудачных строк без лимита; неполный список — части не «done» не переносить. 1 ч.

**С-13. NaN в расчётах приёмки не отсекается.** [запуск] Помощник по коду предположил, что «NaN»/«Infinity» из файла проходят в мастер (`BulkImportPlan.TryNumber`, 670–702). **Запуском это не подтвердилось:** на 5 000 строках с мусором «Infinity» в закупке даёт «закупка: слишком большое число», строки с «NaN» в приход не попали (0 из 3 421 строк `Lines`). Но в самих расчётах защиты нет: `ReceivingPricing.SaleFromMarkup(100, NaN)` в режиме «вверх до целого» возвращает **NaN** (ветка `WholeUp`, `ReceivingPricing.cs:63–64`, проверки стоят только во второй ветке), `ReceivingLineVm.QuantityTooPrecise(NaN)` = false, а `Validate` проверяет `Quantity <= 0` — NaN это пропускает. Из окна ввода NaN не попадёт (разбор `CheckoutValidation`), риск — новые пути ввода (ИИ, файл, мобилка). Исправление: в `SaleFromMarkup`/`RoundSaleUp` и в `Validate` — `double.IsFinite`. 10 мин.

**С-14. Архив товаров (сервер c8958b4) не поддержан: архивные товары остаются в кассе и продаются.** [код] Поле `is_archived` нигде не читается (Grep по решению — 0 совпадений), кнопки «В архив» нет (`WarehouseWindow.axaml.cs:1486–1501` предлагает «спишите остаток»). Если владелец заархивирует товар на сайте, касса продолжит его показывать и пробивать. Исправление: при синхронизации каталога пропускать `is_archived = true`; в окне «нельзя удалить» — кнопка «В архив» (`POST products/{id}/archive/`) при признаке `product_archive`. 1–2 ч.

**С-15. Опт и мин. остаток с пробелом между разрядами уходят нулём; скидка не проверяется.** [код, помощник] Проверка (`ProductEditDialog.axaml.cs:1989–1990`) принимает «1 500», а в запрос идёт `TryParseNumber` (`:2113–2114`, `:2254`), который на пробеле даёт 0. **С-16. ## 5. Что хорошо

1. **Приход в фоне — образцово для денег:** ключ прихода пишется на диск до отправки, после обрыва сначала ищется уже проведённый приход, создание товара не повторяется вслепую (`WasCreateAttempted` → поиск по штрихкоду), три исхода «прибавилось/нет/непонятно» для PATCH остатка без поставщика с честным текстом кассиру (`PurchaseReceivingService.cs:979–995`).
2. **Цена продажи не меняется сама при подорожании закупки** (Б-06): чтение цены «до», возврат только при `price_changed`, PATCH с ценой «как на сервере сейчас», а не из кэша ПК (`:892–901`).
3. **Наценка и округление считаются в decimal**, сумма строки округляется по итогу (3 × 12,333 = 37,00), «вверх до целого» без шума double; «Не округляй» — лишние знаки не проводятся молча.
4. **Долг поставщику** — журнал меток, поиск уже созданной сделки, ни одного вслепую повторённого денежного POST.
5. **Массовая загрузка**: кодировки (BOM/UTF-16/cp1251), заголовок не в первой строке, научная запись Excel — понятная ошибка, план строится в фоне за словарями без O(n²), 429 с Retry-After.
6. **Переводы**: 2002 вызова `Tr.T`, все на 5 языках; тёмная тема без жёстких цветов.
7. **Генератор штрихкода** криптослучайный, без 0/2 в начале и без повторов; общий каталог товаров (128 тыс.) — SQLite по ключу, слияние новой выгрузки в фоне на отдельном соединении.
