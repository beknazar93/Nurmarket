## 0. Как проверял (важно для повторения)

- **Пароль из задания сервер не принял** (`401 no_active_account`). Поэтому:
  - касса вошла сама по сохранённой сессии (автовход);
  - у программы владельца сохранённая сессия **истекла сама** (refresh-токен выдан 30.10, срок 7 суток, кончился 06.11 в 10:53). Программа при запуске молча удалила `auth.dat` и показала экран входа.   - сверка «на сервере через API» шла не прямыми GET-запросами (без пароля их не сделать), а через окна, которые читают сервер: «Закупки» (список приходов NurCRM), «Долги клиентов» владельца («по данным NurCRM»), лента товаров кассы `products/changes` (товар пришёл в кассу с сервера).
- **Обрыв интернета без прав администратора:** кассу и владельца запускал с `HTTPS_PROXY=http://127.0.0.1:18778` (процессу через WMI, в среду Windows ничего не записано). Свой CONNECT-прокси `cproxy.py` по команде `__mode?m=reset` рвёт туннели к `*.nurcrm.kg` (RST), содержимое TLS не трогает. Адрес API остаётся боевым, поэтому папка данных и ключ аккаунта прежние (через `DESKTOP_MARKET_API_URL` касса ушла бы в папку стенда и сочла бы аккаунт другим).
- **Потеря сессии (C):** отдельный стенд — копия данных кассы/владельца в `live-0611\standC` (`NURMARKET_DATA_ROOT`), `DESKTOP_MARKET_API_URL=http://127.0.0.1:18777`, прокси `proxy.py` (на базе `tools/qa/slow_server.py`) **ничего не пересылает на сервер**: отвечает 401 на всё, 200 на «/». Настоящие токены не использовались.
- UI — только UIA (Invoke/ValuePattern) и PostMessage по hwnd; снимки — PrintWindow. Фокус и передний план не трогались.

## 2. Баги

### Высокая серьёзность (деньги / данные)

**Б-1. Возврат по долговому чеку, сделанный без связи, при автоматической досылке отклоняется сервером.**
Шаги: продажа 2 × 15 сом в долг клиенту «ТЕСТ-ЖИВОЙ-0611 Клиент» (чек 2056) → обрыв → Меню → «Возврат» (окно «Возврат без связи») → чек 2056, 1 шт, причина → «Оформить возврат» (касса показала «К возврату 15,00 · выдать 0,00 · долг уменьшится на 15,00») → связь вернуть.
Факт: `13:56:43 [WARNING] OFFLINE ops: refund 02fd337a… — требует проверки: method: Долг нельзя указывать в строках оплаты.` В «Неотправленном» запись «Ошибка · требует проверки» (A74). Ручное «Повторить» в 13:57:31 прошло («возврат … проведён на сервере»). Без человека возврат так и висел бы, а кнопка «Убрать из очереди» рядом может привести к его потере.
Ещё: в журнале у операции «клиент —», хотя чек долговой и на клиенте.

**Б-2. Частичный возврат долгового чека онлайн: касса показывает ошибку, а сервер возврат проводит. Остаток долга пропадает.**
Шаги: продажа 2 × 15 в долг (чек 2057, долг клиента 30) → Меню → «Возврат» → чек 2057 → 1 шт → «Вернуть выбранные» → причина → «Вернуть».
Факт: окно «Возврат» с текстом `method: Долг нельзя указывать в строках оплаты.` (D38). В журнале ошибки нет, только открытие `PosAlertDialog`. При этом в «Истории чеков» у 2057 статус «Частичный возврат», строка 1 × 15 (D39): сервер возврат провёл. Кассир видит ошибку и может вернуть повторно.
Долг после возвратов: «Оплата долга» в кассе показывает у клиента 0,00 (ожидалось 15 + 15 = 30). «Долги клиентов» владельца (данные NurCRM) клиента вообще не показывали (D41). После новой продажи в долг на 7 и её погашения касса записала `остаток 30.00`, окно обещало «Останется долг: 0,00», а владелец показывает «7,00 сом, чеков: 1» (D64, D65). Три разных числа долга одного клиента.
Чек 2056 после частичного возврата помечен «Возврат / отменён» (как полностью отменённый), чек 2057 — «Частичный возврат». Одинаковая операция, разные статусы.
Закрытие смены: «Возвраты в счёт долга 17,00» учитывает только возврат по 2056; возврат по 2057, который сервер провёл, не учтён (на наличные не влияет).
Нужен разбор с Умаром: что сервер ждёт в строках оплаты возврата по долговому чеку, и куда девается оставшийся долг при частичном возврате.

**Б-3. Номер прихода: в списке «Закупок» один, в окне документа другой (+1).**
Шаги: 3 офлайн-прихода → после досылки «Закупки» показывают ПР-2026-000077/78/79 (95/190/285 сом). Открыть строку ПР-…77 → заголовок окна «Приход ПР-2026-000078» при содержимом прихода 77 (1 шт × 95). 78 → «…79», 79 → «…80» (такого номера нет). Старый ПР-…76 открывается правильно. (B22, B23-open-78/79)
Причина по коду: список берёт номер, который касса присвоила сама (`DocumentNumbering`, «№ …» в комментарии), а окно `InvoiceDocumentWindow` — серверный `number_display` (`DocumentNumbering.ReceiptText(r)`). Нумерации кассы и сервера разошлись на единицу. Печать и PDF из окна документа, видимо, выйдут с серверным номером, отличным от списка.

### Средняя серьёзность

**Б-4. «Требует внимания» владельца не видит неотправленное.** Строка «Не отправлено на сервер» считает только `OfflinePendingSalesStore.PendingCount` — очередь продаж СВОЕЙ базы (`NurMarketOwner`). Не учитываются ни фоновые приходы и новые товары (3 прихода в очереди — строки нет, «Загрузка…», A30), ни очередь кассы на том же ПК (офлайн-чек 2055 в кассе — у владельца пусто, A72), хотя текст строки обещает «ждут отправки в кассе этого компьютера». Ещё: без связи блок «Требует внимания» долго висит на «Загрузка…».

**Б-5. Приём без интернета невозможен, если окно «Закупки» открыто уже без связи.** Выпадающий список поставщиков: «Поставщиков пока нет — нажмите «＋»» (B36), хотя файл `suppliers-cache.json` (13 поставщиков) записан в 13:46:39, ещё до обрыва. В журнале: `Закупки: поставщики не загружены (Сервер недоступен: чтение временно приостановлено (предохранитель).)`. Похоже, отказ «предохранителя» происходит раньше, чем код берёт сохранённый список; ещё в кэше `"CompanyId":""`. Обойти можно только «Оприходовать без поставщика» (без долга поставщику и без накладной). Первый офлайн-приход прошёл лишь потому, что окно открыли онлайн.

**Б-6. Масштаб 125/150 %: значок «Неотправленных приходов: N» налезает на шапку «Сводки».** При 125 % закрывает дату «Пятница, 6 ноября 2026» (A30), при 150 % — конец слова «Сводка» и дату (A40). С двумя видами («… · Неотправленных новых товаров: 1») значок ещё длиннее.

**Б-7. Пустой фильтр в «Неотправленном» говорит неправду.** При 3 ждущих приходах фильтр «Чек продажи» или «Ошибка» показывает «Неотправленного нет — всё на сервере.» (A23). Нужно «По этому фильтру ничего нет».

**Б-8. Владелец при потерянной сессии не говорит «Войдите снова».** После «Позже» у владельца нет «🔑 Войдите снова». Шапка «Сводки» пишет «Сервер недоступен · по данным касс в локальной сети», хотя сервер отвечает 401 (C14). Ещё на стенде владельца поверх «Сессия истекла» одновременно открылся анонс «Просрочка при продаже» — две модалки сразу (C10).

**Б-9. Полный каталог после каждого запуска и без продолжения после обрыва.** При старте пишется «тёплый старт … весь каталог не качаем», но через ~2 мин идёт `CATALOG full` — 155 страниц по 100 товаров, 113 с (касса), 82 с (владелец). Обрыв на странице 151 из 155 → в следующий раз всё сначала (13:34:44, 13:46:55). За час касса сделала 341 запрос `products/list` (`PERF … p50 581 p95 1126`). Сервер отдаёт по 100 товаров вместо запрошенных 300.

**Б-10. Новая сборка один раз сбросила общую наценку приёмки владельца.** `receiving-markup.json`: было `AutoEnabled: true, DefaultPercent: 20`, стало `false / 0`. Сообщение только в журнале (`WARNING Наценка приёмки: общая наценка сброшена один раз при обновлении (была включена, 20 %)`). Само значение 20 % потеряно, вернуть можно из копии (`live-0611\backup\NurMarketOwner\receiving-markup.json`). Если сброс задуман, владельцу клиента нужно сказать об этом на экране, а не только в журнале.
