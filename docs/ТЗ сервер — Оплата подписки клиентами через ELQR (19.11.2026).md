# Оплата подписки NurCRM клиентами через ELQR (Элдик Банк / RSK) — разбор и ТЗ

Источники: договор «о приеме платежей посредством ELQR» (шаблон Элдик Банка, docx) и документация API (Google Doc: Dynamic QR v1.2/1.3, Static QR, Refund API для Dynamic QR, Acquiring API карточных платежей RSK Tech). Ключи API в документы и в чат не вставлять.

## 1. Что это
- **Мерчант (Клиент по договору) — компания NurCRM** (юрлицо или ИП). Плательщики — магазины, оплачивающие подписку. Деньги приходят на расчётный счёт NurCRM единой суммой за день, не позднее следующего рабочего дня после 15:00 (Бишкек).
- **Dynamic QR** — QR на конкретный счёт: уникальный `id` (UUID), сумма, срок `ttl` (по умолчанию 180 с, `0` — бессрочный). Подходит для «Оплатить тариф».
- **Static QR** — один QR на торговую точку (`account`, до 32 знаков), сумма вводится плательщиком; банк вызывает `callbackCheck` (проверка точки, можно вернуть имя получателя и сумму) и `callbackSuccess` (платёж проведён). Подходит как «наклейка» для пополнения.
- **Refund API** — возврат по Dynamic QR (check → create → execute → state). Банк сам успешные платежи не возвращает (п. 5.2 договора); споры плательщик ↔ мерчант решаются между ними.
- **Acquiring API (карты)** — создание платежа, ссылка на страницу оплаты, webhook `CHARGED`. Для карты; про рекуррентные платежи (автопродление) упомянут только `paymentType: RECURRENT`, методов в документе нет.

## 2. Как встроить (рекомендация)
Ключ `x-api-key` живёт **только на сервере NurCRM** (Умар). Касса, программа владельца, мобилка и сайт ходят на сервер NurCRM, сервер — в банк.

1. Владелец открывает «Аккаунт → Подписка» (касса/программа владельца/сайт): тариф, срок «до …», кнопка «Продлить».
2. Выбор тарифа и срока (1 / 3 / 6 / 12 мес.), сервер создаёт **счёт** (invoice) и Dynamic QR: `id` = id счёта, `amount` в сомах, `name` = «NurCRM · <магазин>», `ttl` 900–1800 с (для «оплатить позже» — выставить счёт со ссылкой и `ttl=0`, но один счёт = один QR).
3. Клиент показывает `qrImage` (base64) и ссылку `qrLink`; на Android — кнопка «Открыть в приложении банка» (`psType`: eldik, mbank, bakai, ab, odengi, demir, optima, kicb, kompanion, megapay, namba, simba, balance).
4. Касса опрашивает свой сервер каждые 3 с (`GET billing/invoices/{id}`), сервер — банк (`GET /api/v1/qr/state/{id}`) или получает callback. Статусы банка: QR → CREATED → PROCESSING → SUCCESS / ERROR / CANCELLED.
5. По `SUCCESS` сервер **один раз** продлевает подписку (идемпотентно по `id`), пишет в журнал платежей, шлёт владельцу чек/уведомление; касса показывает «Оплачено ✓, тариф до …».
6. Резервная сверка: раз в час и ночью — `POST /api/v1/qr/completed-transactions` за последние сутки; недостающие платежи зачисляются (и ловит потерянные callback'и).

Static QR: по желанию — «QR компании» для пополнения баланса/оплаты без кассы: `account` = код компании NurCRM; `callbackCheck` возвращает `available`, `recipient` (имя магазина — плательщик видит, кому платит), `amount` (если тариф фиксирован); `callbackSuccess` зачисляет.

## 3. Что нужно от сервера (ТЗ Умару)
- `POST billing/invoices/` {plan_code, months} → {invoice_id, amount, qr_image, qr_link, expires_at}. Сумму считает сервер (прайс/скидки/акции, лимиты тарифа — как в Б-39), не клиент.
- `GET billing/invoices/{id}/` → {status: pending|processing|paid|expired|cancelled|error, paid_at, plan, valid_until}.
- `GET billing/invoices/` — история платежей компании (для экрана «Платежи» и актов).
- `POST billing/eldik/callback/` — приём callback банка: проверка `x-request-signature` (HMAC-SHA256 тела **как получено**, ключ = api-key; проверку включить, хотя банк называет её необязательной), идемпотентность, ответ 200 быстро, продление асинхронно. Ограничить по IP банка (уточнить адреса).
- Обработка ошибок банка: **все ошибки, кроме неверного ключа (401), приходят со статусом 200 и телом `{"err": {"err_code", "error"}}`** — обязательно разбирать поле `err`, а не только HTTP-код.
- Суммы в Dynamic/Static QR — числа в сомах (`5.11`), не в тыйынах; у Acquiring (карта) — в минимальных единицах. Не смешивать.
- Ежемесячный акт сверки по Приложению 5 (по сервисам: «Мобильное приложение Элдик Банк / сторонних банков», количество, сумма, ставка, вознаграждение) — отчёт в админке NurCRM из `completed-transactions`.
- Возвраты подписки — вручную через бухгалтерию; Refund API использовать по решению владельца (справочник `type` отличается от `psType`: aiyl, eldik, bakai, obank, optima, simba, mbank, kicb, kompanion).
- Права: оплату и просмотр платежей — владелец и админ; кассир видит только статус «подписка активна до».
- Лимиты тарифа и блокировка при просрочке — как сейчас (на сервере).

## 4. Что сделает касса (после сервера)
- Экран «Подписка» в Настройках → Аккаунт и в программе владельца: тариф, срок, цена, «Продлить», выбор срока, QR с таймером и счётчиком обновления статуса, «Открыть в приложении банка» (Android), история платежей, «Отправить счёт в WhatsApp/Telegram».
- Предупреждение за 7/3/1 день до конца подписки; при отсутствии связи — понятное «нужен интернет».
- Тексты на 5 языках; тесты (статусы, таймаут QR, повторное нажатие, потеря связи после оплаты → опрос по `invoice_id`).

## 5. Вопросы банку (до подписания договора)
1. Ставка комиссии (Приложение 3 пустое), вариант I (банк удерживает) или II (счёт раз в месяц) — что выгоднее и что принято у вас.
2. Тестовая среда (sandbox) и тестовый ключ; можно ли на старте без договора.
3. Максимальный `ttl`; смысл «бессрочного» QR и его уникальность; лимиты запросов.
4. Повторы callback при ошибке (сколько, с каким интервалом), IP для белого списка, таймаут ответа.
5. Формат подписи: что именно «JSON без пробелов» — сырое тело или каноническая форма.
6. Есть ли рекуррентные списания (автопродление картой) и как подключаются (в доке только значение `RECURRENT`).
7. Пагинация и лимит `completed-transactions`.
8. Часовой пояс дат (предположительно Бишкек, UTC+6) и формат всех дат.
9. Версия 1.3 (`psType`) — доступна ли на старте; ссылка deeplink для каждого банка.
10. Возврат по успешным платежам: порядок, срок, комиссия при возврате.

## 6. Что решает владелец (бизнес/юридическое)
- Кто подписывает договор: юрлицо или ИП NurCRM (реквизиты, счёт зачисления, ответственное лицо по расчётам, Приложение 1 — перечень услуг и коды платежей: «Подписка NurCRM»).
- Кто платит комиссию банка (заложить в цену или принять на себя).
- Политика возвратов за подписку (банк успешные платежи не возвращает; споры — на NurCRM, п. 5.3–5.4).
- Пени за просрочку расчётов с банком 0,1 %/день (до 20 %) — оплачивать счета/акты вовремя; договор на 12 месяцев с автопродлением, расторжение за 30 дней.

## 7. Риски
- Один неверный разбор `err` (ответ 200) = «оплачено» без оплаты или потерянный платёж → ставить продление только по `SUCCESS` и сверке.
- Потерянный callback → почасовая сверка по `completed-transactions`.
- Двойное зачисление → идемпотентность по `id`.
- Просроченный QR → создавать новый счёт, не переиспользовать `id`.
- Ключ API в клиентах кассы/мобилки запрещён.
