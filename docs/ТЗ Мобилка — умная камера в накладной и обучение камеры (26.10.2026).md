# ТЗ: Мобилка — умная камера в накладной и обучение камеры (26.10.2026)

**Требование владельца (26.10.2026, дословно):** «умную камеру в мобилке тоже добавь в добавление нового товара из накладных!! обучение камере тоже».

**Кто что делает:** ТЗ и приёмка — Opus; код — Sonnet (пакеты в разделе 6); макеты — Fable (раздел 5). Код продукта при подготовке ТЗ не менялся.
К боевому серверу был один GET: схема API `https://app.nurcrm.kg/swagger/?format=openapi`. Из неё взяты адреса фото товара и поле `alt`.

---

## 0. Коротко (итог расследования)

- **Сценарий «накладная → товары» в мобилке уже есть, но сырой.** Склад → «Умная камера» → сегмент «Накладная» (`SmartCameraScreen`, `lib/features/scan/smart_camera.dart:485–857`). Каждый снимок отдельно идёт в Gemini, получается список «есть в базе / новые» с полями «название, закупка, цена, количество». Дальше два пути: «Загрузить N товаров на склад» (без поставщика, остаток пишется прямо в товар) или «В приёмку с поставщиком» (`/admin/receive`).
- **Чего нет (сама просьба владельца):**
  - у позиции накладной нет поля штрихкода. Штрихкод нового товара берётся только тот, что ИИ «прочитал» с накладной, и только с верной контрольной цифрой (`smart_camera.dart:554`);
  - нет умной камеры в позиции: ни скана штрихкода, ни «узнать по виду»;
  - нет обучения камеры из позиции;
  - нет экрана обученных товаров (эталонов): ни списка, ни удаления, ни проверки.
- **Найдены ошибки на этом пути, одна из них про деньги и остатки (Б1):** «Загрузить на склад» при каждом нажатии строит строки заново. Повтор после частичной ошибки снова прибавляет остаток уже проведённым строкам и может создать товар второй раз. Чинить отдельным срочным пакетом П0.
- **Расхождение с кассой (Б2):** касса проводит накладную только закупкой у поставщика (`ProductActionPlan.cs:578`, `:731–735`). Мобилка позволяет «прямо на склад» без поставщика. К тому же для этого хватает права «Склад», без «Закупок» (`session_store.dart:85, 93`).
- **Предложение:** отдельный экран «Накладная» (`/admin/invoice`). Шаги: страницы (камера, галерея или PDF) → одно распознавание всех страниц → шапка (поставщик, номер, сумма) → карточка на каждую позицию с полем штрихкода и кнопкой «Умная камера» → «Научить камеру» прямо из позиции → проведение только существующим `AdminReceiveRepository.post` (ключ повтора и защита от двойного прибавления уже есть).
- **Схема базы (drift v6) не меняется.** Эталоны уже хранятся файлами плюс настройкой `refs.index` в таблице `Settings`. Черновик накладной и сведения об эталонах — туда же, отдельными ключами настроек.
- **Выпуск после реализации — 1.18.5+6** (сейчас `pubspec.yaml:19` = `1.18.4+5`).

### 1.2. Как сейчас идёт накладная (по коду)

1. Склад → «Умная камера» → сегмент «Накладная» → большая кнопка-видоискатель → `LiveShotPage.open` (кадр `veryHigh`) → «Узнаю товар…».
2. `VisionService.recognize(jpeg, mode: 'invoice')`. Из ответа берутся `name`, `count`, `label_price`; `barcode` в задаче для накладной **не просится**.
3. `match()`: штрихкод (если ИИ его дал и контрольная цифра верна) — 0,9, иначе похожесть слов. Строка с совпадением ≥ 0,75 — «есть в базе», иначе «новый» с подсказками «Это «…»?» (`smart_camera.dart:497, 690–705`).
4. Следующий снимок (вторая страница) **добавляется** к списку. Известные товары складываются по `product.id` (`:522–528`), а новые с одинаковым названием не складываются и задваиваются.
5. «Загрузить на склад» → `_lines()` создаёт **новые** `ReceiveLine` (`:535–560`) → `post(lines, null, false)`: без поставщика, остаток `PATCH`-ем. Или «В приёмку с поставщиком» → `AdminReceiveScreen(initialLines)`.
6. Цена новых: «+30 % к закупке, до 5 сом» (`_autoPrice` `:533`, надпись `smartPriceRule`).

### 1.4. Камера: как вызывается

- **`CameraGate`** (`live_shot.dart:19–90`): камера одна на приложение (CameraX). Следующий экран открывает её только после `release` прежнего (`idle()` ждёт до 3 с). Перед `BarcodeBindPage` после фото вызывается `await CameraGate.idle()` (`smart_camera.dart:283`). На экране нового товара встроенный сканер останавливают перед обучением (`new_item.dart:997–1004`).
- **`LiveShotPage`**: `open` — один кадр («Сканировать» кнопкой, без автоснимка), `openMany` — обучение («Фото 2 из 5», «Переснять», «Готово» с 1 снимка), `openLive` — продажа «По виду» (кадр за кадром, панель результата).
- **`BarcodeBindPage`** — сканер `mobile_scanner` с ITF-14 и автозумом. Владельца кода ищет через `CodeLookup.find(..., allowWeightLabel: false)`.
- **`CodeLookup`** — образец поиска «как на ПК» (`ProductCodeLookup` кассы): телефон, потом сервер. «Сервер не ответил» ≠ «не найден».
- **Связь с накладными:** в накладной сейчас камера одна — снимок страницы. Ни скана штрихкода по позиции, ни «по виду», ни эталонов в этом сценарии нет.

## 2. Целевой сценарий «Накладная → товары»

### 2.1. Вход и права

- Новый экран **«Накладная»**, маршрут `/admin/invoice`, файл `lib/features/admin/invoice_intake.dart`.
- Входы:
  - Склад → ряд кнопок (`stock_screens.dart:228–241`): четвёртая плитка «Накладная» или замена «Умной камеры» меню из двух пунктов — решит Fable;
  - на экране «Умная камера» сегмент «Накладная» открывает новый экран (`context.pushReplacement('/admin/invoice')`) вместо старого списка;
  - меню администратора (`admin_screens.dart:116`).
- Права: `routePermission('/admin/invoice') = viewProducts` и маршрут в `_procureRoutes` (нужен `canProcure`). Обучение камеры из позиции — как сейчас, при `canRoute('/admin/new-product')`.

### 2.2. Шаги пользователя

**Ш1. Страницы накладной.** Экран пустой, три крупные кнопки:
- «Снять страницу» — `LiveShotPage.open(preset: veryHigh)`, подсказка `liveHintInvoice`;
- «Из галереи» — `ImagePicker().pickMultiImage(maxWidth: 2000, imageQuality: 85)` (есть в `image_picker 1.1.2`, без новых зависимостей);
- «PDF» — `FilePicker.pickFiles(type: custom, allowedExtensions: ['pdf'], withData: true)` (`file_picker` уже в проекте), до 15 МБ.

Страницы — лента миниатюр «1, 2, 3 …» с ✕ и «+ Ещё страница». До 10 страниц, всего до 15 МБ (больше — сообщение «слишком большой файл, снимите страницы камерой»). Кнопка **«Распознать (N стр.)»**.

**Ш2. Распознаю.** Один запрос к Gemini со **всеми** страницами. PDF уходит как `inline_data` `application/pdf`: Gemini читает PDF сам, растр не нужен. Подпись «Распознаю накладную… 1–2 мин на большой накладной», «Отмена». Ответ: шапка (поставщик, номер, дата, итог) и строки (№, название, штрихкод или артикул, ед., кол-во, цена закупки, сумма).

**Ш3. Проверка: шапка и позиции.**
- **Шапка.** «Поставщик» — выпадающий список `suppliers()`, заранее выбран поставщик с похожим названием (`VisionService.nameScore` ≥ 0,75). Не нашёлся — пусто, «Провести» не активна, подсказка «Выберите поставщика» (В1 — нужен ли путь без поставщика). Ниже — № и дата накладной (только для показа и журнала `Audit`; на сервер не уходят, у `receipt/` таких полей нет), «В долг / Оплачено наличными» (как `AdminReceiveScreen` `:1000–1008`).
- **Сверка итога.** «Сумма строк 2 460 сом · в накладной 2 460 ✓». Расхождение > 1 сом — жёлтая строка «Сумма не сходится на N сом — проверьте количество и цены» (проведение не блокирует).
- **Позиции** — карточка на каждую строку в порядке накладной (см. 2.3). Сверху счётчики «Позиций N · новых K · приход к складу M · штрихкоды введено X из Y».
- **Добавить строку вручную**: «+ Позиция» (поиск по складу через `pickProduct` или новый товар по названию).

**Ш4. «Умная камера» в позиции** (кнопка у поля штрихкода, иконка `qr_code_scanner` + подпись).
1. Открывается сканер штрихкода (`BarcodeBindPage` с новыми параметрами: заголовок «Отсканируйте штрихкод: «{название}»», шаги не показываются, кнопки «Не читается — по виду», «Ввести вручную», «Отмена»).
2. **Код прочитан** → `CodeLookup.find(..., allowWeightLabel: false)` → разбор по таблице 2.3 и 2.4.
3. **«Не читается — по виду»** → `await CameraGate.idle()` → `LiveShotPage.open(preset: high)`, подсказка «Наведите на товар — узнаю по обученным фото и прочитаю штрихкод с упаковки». Одновременно:
   - `exactMatches(ref, jpeg, кандидаты)`: обученные эталоны телефона и фото NurCRM для кандидатов этой позиции (`match()` по названию строки) — как в продаже;
   - `recognize(jpeg, mode: 'sale')` — бренд, название, объём и цифры штрихкода с упаковки (`validEan`).

   Нижняя панель результата:
   - «✓ Точно: «Сок Да-Да 1 л» (на складе 12 шт)» → «Да, это он» превращает строку в «приход к товару»;
   - «Штрихкод с упаковки: 4870…, сверьте» → «Вставить» (поле в мягком цвете «прочитано камерой — сверьте»);
   - «Не узнал» → «Ввести вручную» / «Научить камеру» (Ш5) / «Пропустить».
4. Повторное «По виду» — новый кадр. Каждый кадр — запрос к ИИ, поэтому без непрерывного режима (как в продаже, `live_shot.dart:103–104`).

**Ш5. «Научить камеру» из позиции** (меню «⋯» карточки и кнопка в панели «Не узнал»). Подробно — раздел 3.

**Ш6. Провести.**
1. Проверки до окна итога (блокируют): поставщик выбран; нет повторов штрихкода (2.4); у новых есть название и цена продажи > 0; кол-во > 0 (строки с 0 не проводятся и показаны серыми).
2. Окно итога, как `postSummary` (`admin_receive.dart:779–789`), плюс строки: «штрихкодов: X из Y (без штрихкода — K, их можно поставить позже в карточке)», «научено камере: T», «цены продажи изменятся: P».
3. Проведение (порядок важен, всё существующими методами):
   1. `AdminReceiveRepository.post(lines, supplierId, paidNow, l10n:)`. Те же объекты `ReceiveLine` при повторе — ключ повтора и `createUnknown` работают.
   2. Для проведённых известных товаров без штрихкода с введённым кодом — `PATCH api/main/products/{id}/ {barcode}` (как `teachExistingProduct` `:317–320` и `set_barcode` кассы после закупки). Если у товара уже есть **другой** основной штрихкод — не менять (В4).
   3. Эталоны: для новых — `ProductRefs.save(id, shots)` + `shareTeachShots` после создания (как `new_item.dart:268–277`); для известных они сохранены сразу при обучении (Ш5).
   4. `catalogRepo.sync()`, `Audit.log('receive', 'Накладная №… от …: N поз.', amount: сумма)`.
4. Проведённые строки уходят из списка, непринятые остаются с причиной. Всё проведено — экран закрывается, черновик стирается.

**Ш7. Черновик.** После распознавания и при каждой правке черновик (шапка, строки, пути снимков обучения) пишется в настройку `invoice.draft` (JSON). Страницы — файлы `{документы}/invoice_draft/`. Снимки обучения новых товаров до создания — файлы `{документы}/invoice_draft/teach_{n}_{i}.jpg`. При входе на экран есть черновик — вопрос «Продолжить накладную от {дата} (N поз.)? / Начать новую». Черновик живёт 7 дней. Схема БД не меняется.

### 2.3. Позиция: «известный товар» и «новый товар»

| Состояние строки | Как определяется | Поле штрихкода | Карточка |
|---|---|---|---|
| **Приход к товару склада, у товара есть штрихкод** | Штрихкод с накладной или камеры нашёлся (`CodeLookup`), или совпадение ≥ 0,75 / ✓ эталон и подтверждено | Подставлен, **только чтение**, серый, «уже у товара» | Миниатюра, «На складе: 12 шт · цена 85», «+ кол-во», закупка (было → стало), цена продажи |
| **Приход к товару склада без штрихкода** | То же, у товара `barcode` пуст | Пустое, правится, «Умная камера» | То же + «штрихкод поставим товару после проведения» |
| **Выберите: это «…»?** | Совпадение 0,5–0,75 (`_CamItem` `:497`) | Пустое, правится | Подсказки-кнопки «Это «…»?» (как `:690–705`) и «Нет, новый товар». Пока не выбрано — строка считается **новой** |
| **Новый товар, штрихкода нет** | Ничего не нашлось | Пустое, правится, «Умная камера» | Плашка «новый», название, ед. (шт/кг/л/упак), закупка, продажа (подсказка по правилу), кол-во |
| **Новый товар, штрихкод с накладной или камеры** | ИИ дал код с верной контрольной цифрой, кода нет на складе | Подставлен, правится, мягкая подпись «прочитано с накладной (камерой) — сверьте» | — |
| **Введённый код у другого товара склада** (для «нового») | `CodeLookup` нашёл товар | Как ввели | Вопрос «Штрихкод уже у «X». Это тот же товар? — **Да, приход к «X»** (строка становится известной, название из накладной остаётся подсказкой) / **Нет, другой код**» (поле очищается) |
| **Код не проверен** | `CodeLookup` → `unavailable` | Как ввели, значок ⚠ «не проверен — нет связи» | Перед проведением — повторная проверка. Не прошла по связи — проведение не начинается («Нет связи с сервером») |
| **Весовая этикетка** | `parseWeightLabel` (как `admin_receive.dart:554–557`) | Не принимается, тост `pAWeightLabel` | — |
| **Проведена** | `posted` | — | Уходит из списка |
| **Ошибка проведения** | `errors` | — | Красная подпись с причиной, остаётся |

Для «приход к товару» закупку **со склада** подтягивать как `AdminReceiveScreen._addProduct` (`GET products/{id}/` → `purchase_price`, `:490–495`) — показать «было → стало».

### 2.4. Один штрихкод в двух позициях — блок

- Сравнение по `barcodeVariants(normalizeCode(code))` (те же написания, что у `CodeLookup`), среди **всех** строк, включая серые (штрихкоды известных товаров).
- Обе строки с красной рамкой и подписью «Этот штрихкод уже у строки N». «Провести» не активна, над кнопкой — «Повтор штрихкода в строках N и M — исправьте».
- Две строки накладной — один и тот же известный товар (разные страницы) → не блок: подсказка «Строки N и M — один товар. Объединить?» → «Объединить» (кол-во складывается, закупка — средневзвешенная, показать).
- Код, у которого товар есть только как **доп. штрихкод упаковки** (`hit.qty` = N штук) → строка известная, подпись «штрихкод упаковки ×N — количество в штуках = кол-во × N?» с выбором (как у кассы штрихкод упаковки).

### 2.5. Защита денег и остатков

1. Своей логики остатков и денег не писать. Только `AdminReceiveRepository.post` (приход поставщику с `idempotency_key` и подписью состава, `createUnknown` → `findCreated`) и `PATCH` штрихкода после проведения.
2. Объекты `ReceiveLine` создаются **один раз** на строку и живут до успеха (урок Б1). Правка строки после неудачной попытки меняет поля того же объекта. Подпись ключа повтора поменяется сама (`receiptSignature` включает qty и закупку), значит это будет новый приход, и это правильно.
3. Двойное нажатие «Провести» — флаг `_posting`, как `admin_receive.dart:763–772`.
4. Новых денежных операций в очереди (outbox) не делать: приход с поставщиком — только при связи (как сейчас). Без связи — «Нет связи — накладная сохранена черновиком, проведите, когда появится интернет».
5. Цена продажи известного товара по приходу **не снижается** сама (как касса 15.10): предложенная ниже текущей показывается «предлагается 79 (сейчас 85) — не меняем», менять — только руками.
6. Цена нового товара — правило из В2. По умолчанию: минимальная наценка 20 % с округлением вверх (`MinMarkupPrice` кассы: до сома, от 1000 — до 10 сом).
7. Создание товара шлёт `barcode` только после проверок 2.4. Ответ 400 по штрихкоду — строка с ошибкой «штрихкод уже занят», остальные строки идут дальше (как сейчас).
8. Ключ ИИ и снимки накладной в журнал и тосты не печатать.

### 2.6. Ошибки и офлайн

| Ситуация | Что видит пользователь | Поведение |

## 3. Обучение камеры

### 3.1. UX

**Из позиции накладной** («⋯» → «Научить камеру», или «Не узнал» → «Научить камеру»):
1. `teachCamera(context, askBarcode: поле штрихкода пусто, productName: название строки, productId: id известного товара или null)` — та же страница `openMany` (3–5 ракурсов: справа, слева, сверху, этикетка спереди, сзади) и шаг «Штрихкод».
2. Результат:
   - **Известный товар** — `ProductRefs.save` сразу, `RefCache.forget`, отправка в NurCRM (`shareTeachShots`). Штрихкод из шага — в поле строки. В товар он записывается **после проведения** (2.2 Ш6), а не сразу, как в `teachExistingProduct`: чтобы отмена накладной не меняла товар. «Заменить» (`takenFrom`) в накладной не предлагать (`productId` передавать, но `canReplace` выключить параметром): чужой код → вопрос 2.3.
   - **Новый товар** — снимки в черновик (файлы), сохраняются эталоном и уходят в NurCRM после создания товара. Главное фото товара — `teachPhoto(shots)`, если другого нет (как `new_item.dart:274`).
3. На карточке значок «📷 3 фото» (повторное нажатие — «Переобучить / Удалить снимки»).

**Экран «Обученные товары»** (новый, `/admin/refs`, файл `lib/features/scan/refs_screen.dart`). Вход: «Умная камера» → значок в заголовке и карточка товара (`product_edit.dart` рядом с «Научить камеру» — «Проверить камеру»).
- Список: миниатюра первого снимка, название, «3 фото · 26.10 · на этом телефоне ✓ · в NurCRM ✓/—», размер. Сверху: «Обучено 42 товара · 9,8 МБ». Поиск по названию.
- Действия у строки:
  - **«Проверить»** — `LiveShotPage.open(preset: high)` → `identify(кадр, [(name, эталоны этого товара)])` → «Узнал ✓ (×N)» или «Не узнал — переобучите при хорошем свете».
  - **«Переобучить»** — `teachExistingProduct`.
  - **«Удалить»** — «Удалить снимки на этом телефоне / и в NurCRM (на всех телефонах)» (В6).
- Пусто: «Камера ещё не обучена. Научите её на товаре — в складе или прямо из накладной».

### 3.2. Объём

- Снимать 3–5, хранить 3 (`maxPerProduct`), JPEG 640×480 ≈ 40–80 КБ, то есть ≈ 120–240 КБ на товар. 500 товаров ≈ 60–120 МБ.
- На экране — общий размер. Больше 300 МБ — предупреждение «Много места — удалите эталоны товаров, которых нет в продаже» (без автоудаления).
- Проверка качества снимка (на подсказках, без нового ML): тёмный кадр (средняя яркость по миниатюре) — подсказка «Темно — включите свет». Только подсказка, сохранить можно.

### 3.3. Хранение (без изменения схемы)

- Файлы — как сейчас (`refs/`). Список — `refs.index` (формат не менять: его читают `RefCache` и старые версии).
- **Новая** настройка `refs.meta`: JSON `{productId: {"at": ISO-дата, "remote": [imageId…], "name": "…"}}`. Её пишут `ProductRefs.save` и `shareTeachShots`, читает экран «Обученные товары». Её отсутствие не ошибка: дата берётся из `File.lastModified`.
- Новые методы в `ProductRefs`: `list(db)` → `[(id, paths, at, remoteIds)]`, `delete(db, id)` (файлы + оба индекса), `sizeBytes(db)`.

### 3.4. Синхронизация между телефонами через NurCRM

- Механизм уже есть (аудит У-8): снимки обучения — доп. фото товара (`images/`, `is_primary=false`), другие телефоны берут их в `RefCache.remote`. **Переиспользуем.**
- Доработка: при загрузке снимка обучения добавлять поле формы `alt = "nurmarket-ref"` (поле есть в `ProductImage`, до 255 знаков). `uploadImage(..., alt:)` — необязательный параметр, по умолчанию как сейчас. Из ответа `POST` брать `id` фото в `refs.meta.remote`.
- `RefCache.remote`: сначала фото с `alt == "nurmarket-ref"`, потом главное (если их меньше 3). Ответ `GET products/{id}/` пока не всегда даёт `alt` — тогда как сейчас (`imageUrls`). Можно дополнительно `GET products/{id}/images/` (есть в схеме), но не больше одного запроса на товар и только для кандидатов.
- Удаление «и в NurCRM» → `DELETE api/main/products/{id}/images/{imageId}/` по `refs.meta.remote`; 404 — считать удалённым.
- На кассе (Avalonia) эталонов нет: касса ими не пользуется и не мешает.

### 3.5. Приватность

- Подсказка на странице обучения (новая строка под `teachHint`): «Снимайте только товар — без людей, лиц и документов в кадре».
- Снимки уходят двум получателям: Google Gemini (уже так при каждом скане «По виду») и NurCRM (фото товара). Это сказать в первом показе экрана «Обученные товары» одной строкой.
- Снимки накладной (страницы) в NurCRM **не** отправлять. Они идут только в Gemini и лежат в черновике на телефоне до проведения или 7 дней.
- Снимки обучения с `alt = nurmarket-ref` сейчас **видны на витрине и сайте** как обычные фото товара (В3).

### 3.6. Размер запросов к ИИ

- Сверка в позиции — как в продаже: до 6 товаров, до 2,5 МБ (`exactMatches`). Кандидаты — по названию строки, обученные первыми.
- Накладная: до 10 страниц, до 15 МБ (Gemini принимает до ~20 МБ в одном запросе с `inline_data`). Фото из галереи — `maxWidth: 2000, imageQuality: 85` (≈ 300–600 КБ на страницу).
