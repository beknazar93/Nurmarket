## Общие правила для всех частей

Эти правила касаются **всех** новых и изменяемых эндпоинтов ниже. Если правило противоречит текущему поведению — новое поведение
вводить так, чтобы старые клиенты не сломались (только добавлять поля, не переименовывать и не удалять).

### О1. Формат ошибки

Любой ответ 4xx/5xx — JSON (никогда HTML), с машинным кодом:

```json
{
  "code": "amount_exceeds_debt",
  "detail": "Сумма больше долга клиента. Максимум: 190.00",
  "field": "amount",
  "data": { "max": "190.00", "debt_remaining": "190.00" }
}
```

- `code` — короткий английский код (список кодов — в каждой части). Касса принимает решения **только по `code`**, текст
  `detail` показывает человеку как есть.
- `field` — имя поля тела, к которому относится ошибка (или `null`).
- `data` — числа и id, нужные клиенту (максимум, доступный остаток, текущая версия и т. п.).
- Для ошибок по строкам (позиции чека, строки прихода) — массив `errors`:
  `"errors": [{"index": 6, "field": "variant", "code": "variant_required", "detail": "…", "product": "<uuid>"}]`.
- Прежний формат DRF (`{"amount": ["…"]}`, `{"detail": "…"}`) можно отдавать **дополнительно** в тех же ответах для сайта.
- **404 «адреса нет» и 404 «объект не найден» должны различаться.** Касса считает «адрес не существует (старая версия сервера)»
  только 404/405 **без JSON** (как у неизвестного маршрута Django) и тогда уходит на старый путь
  (`ClientDebtsApiService.IsEndpointMissing`). 404 с JSON (`{"code": "not_found"}`) — «сервер адрес знает, объекта нет».
  Пожалуйста, не отдавайте HTML-404 на существующих маршрутах.
- 5xx — только при настоящем сбое. Проверки бизнес-правил (лимит скидки, повтор, «нет долга») — 4xx с кодом.
  Живой пример: 22.09 скидка суммой у кассира с потолком `max_discount_percent` давала 500 (у владельца — 200)
  [по коду кассы, `StagingCartService.ApplyOrderDiscountFromSnapshotAsync`] — исправлено ли, подтвердите.

### О2. Идемпотентность денежных операций

Все запросы, которые двигают деньги или склад (продажа, оплата долга, приход, возврат, выплата, расход, прокат, оплата поставщику),
принимают ключ повтора:

1. Заголовок `Idempotency-Key: <16–64 символа [A-Za-z0-9_-]>` (касса шлёт 32 hex). Для совместимости — то же значение в теле
   `idempotency_key` (так касса уже шлёт в приходе поставщика и в оплате взноса сделки). Если пришли оба и не совпали —
   400 `idempotency_key_mismatch`.
2. Область ключа — компания + эндпоинт. Хранить **не меньше 7 суток** (не 24 ч: офлайн-чек может пролежать в очереди кассы
   выходные). Минимум, на который мы согласны, — 24 ч, но тогда напишите это явно.
3. **Ключ проверяется ДО любых проверок** (права, смена закрыта, долга нет, остатка нет, сумма больше долга). Если операция с этим
   ключом уже прошла — вернуть **тот же ответ** со статусом 200 и `"replayed": true`, даже если сейчас проверка уже не прошла бы
   (долг погашен этой же оплатой, смена закрыта и т. п.).
4. Тот же ключ с **другим телом** — 422 `idempotency_key_reused` (с `data.original_created_at`). Сейчас `pos/checkout/` тело при
   повторе не сравнивает и молча возвращает прежнюю продажу [проверено на NBS 28.09].
5. Тот же ключ, пока первая операция ещё выполняется, — 409 `idempotency_in_progress` + заголовок `Retry-After` (секунды).
   Касса на 409/423/425 повторяет тем же ключом и **не** уходит на другой путь [по коду кассы, `PosCheckoutService.IsQuickTransientStatus`].
6. Отказ по существу (4xx, кроме 409/423/425/429) означает «ничего не создано» — ключ после этого можно использовать заново
   с тем же телом (повтор даст тот же отказ или успех, если причина ушла).
7. Узнать исход по ключу без повтора: `GET api/main/idempotency/{key}/` — см. часть 17, п. 17.3 (один эндпоинт на все операции).

### О3. Пагинация и списки

- Ответ списка: `{"count": N, "next": "<url>|null", "previous": "<url>|null", "results": [...]}`; параметры `page`, `page_size`
  (до 500; по умолчанию — как сейчас).
- Страница за последней — 404 с JSON `{"code": "page_out_of_range"}` или пустой `results`, **не 500**. 06.10 `pos/sales/?page=3` при
  65 чеках отвечал 500 [проверено на NBS 06.10], касса обходит это отдельным запросом `count`.
- Порядок — стабильный (вторичная сортировка по `id`), иначе при подкачке страниц строки дублируются/теряются.
- Фильтры дат `date_from`, `date_to` — **включительно**, в часовом поясе компании.

### О4. Время

- Все даты-время — ISO 8601 со смещением: `2026-10-20T13:10:48+06:00` (часовой пояс Бишкека; журнал кассы ведётся в +06:00).
- Даты без времени — `YYYY-MM-DD`, считаются в часовом поясе компании.
- Сервер сам закрывает смены в 01:00 — всё «за день» (лимиты, отчёты) — с 00:00 до 23:59:59 по +06:00, если не оговорено иначе.

### О5. Деньги и количества

- В ответах деньги — **строкой с 2 знаками**: `"387378.89"`. Количество — строкой до 3 знаков: `"1.250"` / `"2"`.
- В запросах принимать и строку, и число; точка как разделитель. Округление — до копейки, «половина вверх».
- Валюта — сом (KGS), отдельное поле не нужно, пока мультивалютности нет.

### О6. Права

- Каждое API проверяет права пользователя из токена (`can_view_*` и роль) **на сервере**; ответ без права — 403
  `{"code": "permission_denied", "data": {"permission": "can_view_products"}}`. Скрытие пункта меню на сайте — не защита (часть 21).
- Денежные операции сохраняют автора (пользователь из токена) и отдают его в истории (`created_by: {id, name}`).

### О7. Совместимость

- Новые поля — только добавлением. Переименование (`method` → `payment_method`) — через приём обоих имён (часть 17, п. 17.5).
- Касса проверяет наличие нового адреса так: 404/405 без JSON → «нет на этом сервере» → старый путь. Поэтому новые адреса можно
  выкатывать по одному, без одновременного выпуска кассы.

## Часть 17. Оплата долга клиента без смены и идемпотентность

**Приоритет: П1.** Деньги. Источник: ТЗ 18.10 п. 1, живые проверки 19.10.

### Зачем
Владелец принимает оплату долга у себя (наличные «в руки», перевод) в программе владельца — кассовой смены у него нет, и деньги
в ящик кассира не попадают (решение владельца 18.10). Кассир принимает оплату в своей смене. В обоих случаях при обрыве связи
касса должна точно узнать, прошла ли оплата, — иначе либо двойная оплата, либо клиент «заблокирован» до ручной проверки.

### Что есть сейчас
| Запрос | Тело | Ответ | Пометка |
|---|---|---|---|
| `POST api/main/clients/{id}/pay-debt/` + `Idempotency-Key` | `{"amount": "30.00", "method": "cash", "shift": "<uuid>"?}` | `{"paid", "left", "applied": [...], "cashflows", "replayed"}`; гасит от старых долгов к новым | [проверено на NBS 28.09 и 19.10], код — `ClientDebtsApiService.PayDebtAsync` |

### Что нужно

   с ролью `owner` («Владелец / вне смены»).

   выручка и не `other_income` (иначе задвоение дохода — см. ч.8 §2).
5. При `shift` — как сейчас: наличные — в `debt_payments_cash` и `expected_cash` смены; `transfer` — только в безнал смены, **не** в

Сейчас мы не знаем, так ли это, — касса на всякий случай после обрыва закрывает поля и даёт только «Повторить тем же ключом».

**17.3. Узнать исход по ключу.** Один эндпоинт для всех денежных операций с ключом:

## Часть 18. Долги в списках и общий на компанию дневной лимит долга

**Приоритет: П1** (поля списка), **П2** (должники с чеками, дневной лимит). Источник: ТЗ 18.10 п. 2, проверки 19.10, «Передача
работы 16–18.10» п. 10.

### Зачем
Касса и программа владельца показывают «Вам должны …», карточку должника и «одной суммой» (какие чеки закроет оплата). Для этого
нужен **точный** остаток по каждому чеку.

### Что есть сейчас
- `GET api/main/pos/sales/?status=debt` — `debt_remaining` приходит не всегда, `debt_amount` не учитывает оплаты через сделку
  (`clients/{c}/deals/{d}/pay/`). Поэтому касса на каждый чек делает ещё 2 запроса: `GET pos/sales/{id}/` → `GET clients/{c}/deals/{d}/`
  (`remaining_debt`). У должника с 50 чеками — 100 лишних запросов и отказы 429 [по коду кассы, `PayDebtDialog.LoadDebtRowsAsync`].
- Живой случай 19.10 [проверено на NBS]: чек продажи в долг при каждой загрузке был «точный остаток не получен», и «одной суммой» у
  клиента была закрыта навсегда. Причина — у продажи нет сделки (`deal_id` пуст), а касса ждала сделку. Касса теперь считает такую
  продажу точной по `debt_remaining`/`debt_amount` — но правило «у продажи без сделки остаток = `debt_remaining`» должен подтвердить сервер.
- `GET api/main/clients/debtors/` — есть [проверено на NBS 20.10]: `client, full_name, phone, telegram_chat_id, debt_total, sales_count,
  oldest_debt_at`; только долги по продажам; касса шлёт `min_amount` и `ordering=-debt_total` (соблюдаются ли — подтвердите).
- Долги «без продажи» (`clients/{id}/debts/`, ручные сделки) в `pos/sales/?status=debt` не видны — итог у кассы может быть меньше
  серверного, а «одной суммой» сервер может гасить и их [по коду кассы, риск записан 18.10].
- Лимит «чеков/сом в долг за день» ведёт **каждая касса и каждый телефон сам** — у магазина с тремя кассами лимит фактически в 3 раза
  больше заданного [по коду кассы, «Передача работы 16–18.10», п. 10].

### Что нужно

**18.1. Поля долга в списке продаж (П1).** В `GET api/main/pos/sales/` (любой `status`, всегда, даже 0) и в `GET pos/sales/{id}/`:
```json
{
  "id": "<uuid>", "number": 505, "status": "debt", "total": "200.00",
  "debt_amount": "200.00",
  "debt_paid": "10.00",
  "debt_remaining": "190.00",
  "prepayment": "0.00",
  "deal_id": "<uuid>|null",
  "due_date": "2026-11-01|null",
  "client": "<uuid>", "client_name": "Клиент А", "client_phone": "+996 *** ** ** 12"
}
```
- `debt_remaining` = долг продажи минус **все** оплаты: через `pay-debt`, через взносы сделки, предоплата.
- `deal_id: null` — у продажи нет сделки, и `debt_remaining` — окончательный остаток.
- Фильтр `?status=debt&has_remaining=true` — только с остатком > 0 (П2).

**18.2. Должники одним запросом (П2).** Расширить `GET api/main/clients/debtors/`:
- `?include=sales` — в каждой строке `sales: [{sale, number, created_at, total, debt_remaining, due_date, deal_id}]` от старых к новым
  (в том порядке, в каком их гасит `pay-debt`);
- `manual_debts_total` — ручные долги без продажи (сделки клиента `kind=debt` без `sale`), `debt_total` = продажи + ручные;
- `overdue_amount`, `last_payment_at`;
- `type=clients` по умолчанию — **без поставщиков** (см. часть 26, п. 26.5);
- пагинация по О3 (сейчас массив целиком; касса умеет оба вида).

**18.3. Общий на компанию дневной лимит долга (П2).** Предложение [предположение — подтвердите, как удобнее вам]:
1. Настройка компании: `GET/PATCH api/main/debt-limits/` →
   `{"max_sales_per_day": 10, "max_amount_per_day": "20000.00", "max_debt_per_client": "5000.00", "applies_to": ["cashier"]}`
   (`null` — без лимита; менять — только владелец/админ).
2. Счётчик: `GET api/main/debt-limits/usage/?date=2026-10-20` →
   `{"date": "2026-10-20", "sales_count": 7, "amount": "14250.00", "limits": {...}, "left": {"sales": 3, "amount": "5750.00"}}`.
3. Проверка при продаже в долг (`pos/checkout/`, `pos/sales/{id}/checkout/` с `method: "debt"`) — на сервере, в той же транзакции:
   превышение → 400 `debt_daily_limit_exceeded` (`data: {"limit": "20000.00", "used": "19800.00", "requested": "500.00"}`) или
   `debt_client_limit_exceeded`. Владелец/админ — без лимита, если `applies_to` их не включает.
4. Офлайн-досылка (`sold_at` в прошлом) лимитом **не** отклоняется: деньги/товар уже отданы; вернуть предупреждение

### Как проверить
1. Продажа в долг 200, оплата 10 через `pay-debt` и 20 через взнос сделки → в списке `debt_paid 30`, `debt_remaining 170` без

3. `clients/debtors/?include=sales` — чеки в порядке погашения; поставщиков нет.

   - `custom` с отрицательной ценой — **подтвердите**, допустимо ли это на старом пути; если нет — одинаковый отказ на обоих.
4. **Одинаковые правила на обоих путях.** Товар с размерами/цветами без выбранного варианта: сейчас `add-item` принимает,
   `pos/checkout/` — отклоняет. Нужно одно правило (наше предложение — в п. 19.6 для досылки и в части 27, п. 27.3 для онлайна).

**19.2. Сверка итога на сервере (П1).** Новое поле тела `expected_total` (итог, который кассир назвал покупателю). Сервер считает итог
сам (цены, акции, скидки); расхождение больше 0,01 → **продажа не создаётся**, 409:
```json
{
  "code": "total_mismatch",
  "detail": "Итог сервера 42.50 не совпадает с итогом кассы 50.00",
  "data": {
    "server_total": "42.50", "expected_total": "50.00",
    "lines": [{"index": 0, "product": "<uuid>", "server_price": "42.50", "sent_price": "50.00", "reason": "promotion"}]
  }
}
```
Живой случай: продажа №1136 (28.09) — окно оплаты 50,00, кассир взял 50, сервер провёл 42,50 (акция товара, которой касса не
видела). Сейчас касса сверяет итог сама до отправки и после ответа — на сервере это надёжнее.

**19.3. Коды отказов чекаута (П1).** Формат — О1, ошибки строк — в `errors[]` с `index` (номер позиции в `items`, с 0):
| code | Где | Когда | `data` / поля строки |
|---|---|---|---|
| `variant_required` | строка | у товара есть размеры/цвета, `variant` не передан | `product`, `product_name` |
| `variant_not_found` | строка | `variant` не принадлежит товару | `variant` |
| `insufficient_stock` | строка | остатка мало и продажа в минус запрещена | `available`, `requested` |
| `product_not_found` | строка | товар удалён/не из компании | `product` |
| `price_below_cost` | строка | цена ниже закупки, а кассиру нельзя | `min_price` |
| `discount_limit_exceeded` | чек/строка | скидка выше `max_discount_percent` для роли | `max_percent`, `requested_percent` |
| `cash_less_than_total` | чек | `payment.received` < итога (наличные) | `total`, `cash_received` |
| `mixed_sum_mismatch` | чек | `cash_amount + card_amount` ≠ итог | `total`, `cash_amount`, `card_amount` |
| `total_mismatch` | чек | см. 19.2 | см. 19.2 |
| `shift_closed` / `shift_required` | чек | смены нет/закрыта (онлайн-продажа без `sold_at`) | `shift` |
| `debt_daily_limit_exceeded` | чек | см. часть 18 | см. часть 18 |
| `too_many_items` | чек | > 1000 позиций | `max` |

Сейчас «Товар «Nike» имеет размеры/цвета…» приходит как `{"items": {"6": "…"}}` (индекс — строкой-ключом), «Сумма, полученная
наличными, меньше суммы продажи» — только текстом [проверено на NBS 20.10].

**19.4. Ответ чекаута — всегда с номером (П1).** Во всех ответах продажи (`pos/checkout/`, `pos/checkout/batch/` в каждом `results[]`,
`pos/sales/{id}/checkout/`, повтор `replayed: true`):
```json
{
  "id": "<uuid>", "number": 1833, "status": "paid", "total": "209.00",
  "sold_at": "2026-10-20T13:14:56+06:00", "shift": "<uuid>", "cashbox": "<uuid>",
  "payment_method": "cash", "cash_received": "300.00", "change": "91.00",
  "replayed": false, "warnings": []
}
```
- Без `number` касса после досылки ищет «свой» чек в истории по сумме и времени (`ReceiptHistoryWindow`, 20.10) — это ненадёжно.
- **Постоянный номер чека.** Сейчас номер на сайте — место чека в общем списке компании (новые первыми), номер старого чека растёт с
  каждой продажей; касса нумерует так же (с 1.17.22). Нужен постоянный `number`, выдаваемый при создании и не меняющийся
  (по компании или по кассе — решите сами, напишите правило). Это понадобится и для фискализации. **[подтвердите, что `number`
  в ответе `pos/checkout/` уже постоянный]** — касса его печатает.

**19.5. Ключ повтора продажи (П1).** По О2: хранить ≥ 7 суток; тот же ключ с другим телом → 422 `idempotency_key_reused`
(сейчас молча возвращается прежняя продажа [проверено на NBS 28.09]); 409 `idempotency_in_progress`, пока первая обработка идёт.
Если обработка большого чека идёт дольше, чем клиент ждёт (касса ждёт `min(60, 15 + 0,1 × позиций)` с), сервер **доводит** продажу
до конца и хранит результат под ключом — касса узнает исход повтором или через `GET api/main/idempotency/{key}/`.

**19.6. Досылка офлайн-продаж (П1).** Офлайн-продажа — деньги уже у кассира, товар у покупателя. Отказ сервера при досылке оставляет
продажу «висеть» в очереди кассы. Предложение [предположение — подтвердите]:
1. Флаг тела `"offline": true` (вместе с `sold_at`). Для таких продаж сервер **не отклоняет** из-за того, что изменилось после
   продажи: цена/акция (проводить по присланным ценам), остаток (продажа в минус, `warnings: [{"code": "negative_stock", "index": 3}]`),
   размер/цвет не выбран (списать с товара, строка с пометкой `variant_missing: true`, предупреждение `variant_required`),
   дневной лимит долга (предупреждение).
2. Отклонять только то, что провести нельзя: товар удалён (`product_not_found` с `index` — касса превратит строку в «Доп. услугу»),
   итог не сходится с оплатой (`cash_less_than_total`, `mixed_sum_mismatch` — с суммами), неверный ключ.
3. Ответ — как 19.4 + `warnings[]`; касса покажет предупреждения владельцу в «Некорректных чеках».

**19.7. Старый путь — быстрее (П2, если 19.1 займёт время).**
- `POST api/main/pos/sales/{id}/items/bulk/` `{"items": [ {как add-item}, ... ]}` → корзина целиком; ошибки строк — `errors[]` с `index`;
  ничего не добавлено, если есть ошибка (одна транзакция).
- `POST api/main/pos/carts/{id}/clear/` — очистить корзину одним запросом (позиции **и** скидки чека: 22.09 скидка прошлого чека
  оставалась на переиспользованной корзине и применялась к следующему [проверено на NBS 22.09]). Сейчас касса удаляет позиции по одной
  (274 запроса в случае выше).

**19.8. Мелкое (П3).**
- Выгрузка «Все продажи» с товарами: `GET api/main/pos/sales/?include=items&date_from=&date_to=` — сейчас запрос на каждый чек
  (≈5 чеков/с из-за ограничения частоты) [по коду кассы, «Передача работы» п. 19].
- Весовой товар, несколько взвешиваний: сервер сливает строки одного товара, и порог акции считается от общей суммы, а касса —
  по строке; нужно правило (сливать/не сливать) и одинаковый расчёт [по коду кассы, «Передача работы» п. 9].

**19.9. Возврат: доля скидки чека, потолок = оплачено (П1, деньги).** [проверено на NBS 20.10] `POST api/main/pos/sales/{id}/return/`
(касса шлёт только `idempotency_key`, `cashbox_role` и, при частичном возврате, `items: [{sale_item_id, quantity}]` — сумму считает сервер).
- **Случай 001837** (безнал): «Aos» 50,00 + «1» 2 × 15,00 = 80,00, скидка на чек 5,00 → **оплачено 75,00**. Возврат строки «1» — документ
  возврата **30,00** (без доли скидки; положено 30 × 75/80 = 28,13). После него сервер **убрал скидку из продажи** (total 50,00, в чеке
  «Aos 50,00, Итого 50,00»), и «Вернуть весь чек» по остатку дал **50,00** (положено 46,87). Всего возвращено **80,00 из 75,00**; в отчёте
  смены «Возвраты 231,40» при продажах 226,40. Тот же сервер при полном возврате сразу всего чека считает верно (№1348, 04.10).
- **Случай 001836** (наличные, без скидки на чек): после частичного возврата сервер пропорционально пересчитал у продажи
  `cash_received`/`change` (70,59 / 20,19 вместо 100,00 / 28,60) и убрал возвращённую строку из `items` — история и копия чека лгут.
- **Нужно:** (1) сумма возврата строки = её сумма после скидки на позицию × (итог продажи / сумма строк до скидки на чек), округление до
  копейки; последний возврат чека — ровно остаток; (2) **сумма всех возвратов по продаже ≤ оплачено** (итог продажи с учётом долга: у
  продажи «в долг» сначала уменьшается долг, деньги — только в пределах внесённого); при превышении — 409 `refund_exceeds_paid`
  с `paid`, `refunded`, `requested`; (3) продажа после частичного возврата хранит **исходные** `total`, `discount_total`,
  `cash_received`, `change` и все строки (у строки — `quantity_refunded`); остаток к оплате/возврату — отдельными полями
  (`refunded_total`, `refundable_total`); (4) в ответе возврата — `amount`, разбивка `cash`/`noncash`/`debt_reduced` и `id` документа;
  (5) у смешанной оплаты — хранить разбивку нал/безнал (сейчас `cash_received=0`, `payments` одной строкой `mixed`).
- **Касса (правки 20.10, со следующего выпуска):** считает сумму сама (журнал `sale-returns.json`: продажа как заплатили + возвраты этой кассы), кассиру
  показывает свою сумму и разбивку («наличными · на карту/перевод», «долг уменьшен на …»), а если сервер записал больше — пишет WARNING
  и строку «Возврат больше положенного» в «Некорректные чеки». Деньги в отчётах сервера при этом остаются завышенными, пока не исправлен п. 19.9.
- **Приёмка:** чек 80 − 5 = 75 → возврат строки 30 → документ 28,13; «вернуть весь чек» → 46,87; всего 75,00; третий возврат → 409.
  Продажа «в долг» 15,00 без предоплаты → возврат: `cash 0`, `debt_reduced 15`. Смешанная 40 + 25 → возврат: `cash 40`, `noncash 25`.

### Как проверить (приёмка части 19)
1. Чек 300 позиций (разные товары, 2 варианта одежды, 1 «Доп. услуга», 1 поштучно из пачки, скидка на чек) одним `pos/checkout/` —
   ≤ 3 с, итог = `expected_total`, остатки списаны, в ответе `number`.
2. Тот же ключ → 200 `replayed: true`, тот же `number`; тот же ключ с другим `qty` → 422.
3. Товар с размерами без `variant` онлайн → 400 `errors[0].code = variant_required`, `index` верный; тот же чек с `offline: true` и
   `sold_at` вчера → 201, `warnings` с `variant_required`.
4. `payment.received` меньше итога → 400 `cash_less_than_total` с `total` и `cash_received`.
5. Акция на товар, касса прислала цену без акции и `expected_total` без акции → 409 `total_mismatch`, продажи нет.
6. `pos/sales/{id}/checkout/` старого пути — в ответе `number`.

## Часть 20. События изменений для касс

**Приоритет: П2.** Источник: ТЗ 18.10 п. 3, AI_HANDOFF (версия каталога).

### Зачем
Касса узнаёт, что владелец погасил долг, поменял общие настройки, цену товара или принял возврат проката, только при открытии окна,
при входе, раз в 2 мин опросом настроек или по локальной сети магазина (если устройства в одной сети; события `sale`, `sale_uploaded`,
`debt_paid` [по коду кассы, `LanJournal`]). Владелец из дома — касса видит изменения с задержкой, кассир может принять оплату уже
погашенного долга (сервер тогда ответит `no_debt` — хорошо, но кассиру неудобно).

Версия каталога: адреса `products/catalog-meta/`, `products/meta/`, `catalog/version/`, `products/version/` отвечают 404/405
[проверено на NBS 04.10]; касса считает «версию» сама по списку товаров (количество | последнее изменение | id) и раз в 2 мин
проверяет её. При этом `PATCH products/{id}/` с новой ценой версию не меняет [по коду кассы, 06.10] — после правки цены ИИ-советником
касса вынуждена делать полную загрузку каталога.

### Что нужно (вариант А обязателен, Б — желательно)

**А. Лента событий опросом.**
```
GET api/main/changes/?since=<cursor>&types=debt_paid,product_changed&limit=500
```
```json
{
  "cursor": "c_000000000123457",
  "has_more": false,
  "events": [
    {
      "id": "c_000000000123456",
      "type": "debt_paid",
      "at": "2026-10-20T14:05:11+06:00",
      "branch": null,
      "actor": {"id": "<uuid>", "name": "Сотрудник 1", "app": "nurmarket-owner"},
      "entity": "client", "entity_id": "<uuid>",
      "data": {"amount": "10.00", "left": "190.00", "sales": ["<uuid>"]}
    }
  ]
}
```
- `since` не передан → пустой `events` и текущий `cursor` (точка отсчёта).
- `cursor` непрозрачный, растёт монотонно; хранить события ≥ 7 суток; старый курсор → 410 `{"code": "cursor_expired"}` (касса
  делает полную синхронизацию и берёт новый курсор).
- `has_more: true` → касса сразу запрашивает следующую порцию.
- Фильтр по филиалу — как у остальных запросов кассы (`?branch=`); события, на которые у пользователя нет прав (зарплата для кассира),
  не отдаются.
- Нагрузка: 15 000 компаний × 2 программы × опрос раз в 30–60 с ≈ 500–1000 запросов/с, почти все с пустым ответом — запрос должен
  быть дешёвым (индекс `company, id`; ответ без событий ≤ 20 мс). Допустимо `Cache-Control`/`ETag` + 304.

**Типы событий:**
| type | entity | data (минимум) |
|---|---|---|
| `sale_created`, `sale_returned`, `sale_canceled` | sale | `number`, `total`, `cashbox`, `shift`, `status` |
| `debt_paid` | client | `amount`, `left`, `sales[]`, `method`, `shift|null` |
| `debt_created` | client | `sale`, `amount` |
| `app_settings_changed` | app_settings | `app` (`nurmarket-kassa`/`nurmarket-owner`), `keys[]`, `versions{}` (часть 21) |
| `product_changed` | product | `ids[]`, `fields[]` (`price`, `quantity`, `variants`, `promo`, `barcode`, `deleted`) |
| `stock_changed` | product | `ids[]` (приход, списание, ревизия, продажа на другой кассе) |
| `rental_created`, `rental_returned`, `rental_extended` | rental | `number`, `status`, `date_to` |
| `supplier_debt_changed` | supplier | `debt_total`, `reason` (`receipt`/`payment`/`return`) |
| `cashflow_created` | cashflow | `type`, `amount`, `cashbox`, `shift|null`, `source_kind` |
| `shift_opened`, `shift_closed` | shift | `cashbox`, `cashier` |
| `features_changed` | company | `features[]` (часть 28) |
| `pos_request_created`, `pos_request_resolved` | pos_request | часть 22 |

**Версия каталога (часть А, отдельно, П2):** `GET api/main/products/version/` → `{"version": 1834, "updated_at": "…", "count": 330}`;
`version` растёт при **любом** изменении товара/цены/остатка/варианта/акции. Если лента событий сделана — достаточно `product_changed`.

**Б. WebSocket.** `wss://app.nurcrm.kg/ws/company/` — те же события тем же JSON. Токен — первым сообщением
(`{"type": "auth", "token": "…"}`), а не в адресе (адреса пишутся в журналы прокси). Ping/pong раз в 30 с; при разрыве касса
досинхронизируется лентой А по последнему `id`.

### Как проверить
1. Касса держит курсор → владелец гасит долг в программе владельца → в ленте `debt_paid` с клиентом и остатком ≤ 1 с после ответа оплаты.
2. Правка цены на сайте → `product_changed` с `fields: ["price"]`; `products/version/` вырос.
3. Курсор 8-дневной давности → 410 `cursor_expired`.
4. Кассир не получает `cashflow_created` по зарплате.

### 21.4. Общие настройки компании: версия, права, секреты (П2)

**Что есть:** `GET/PATCH api/main/app-settings/{app}/` (общие на компанию) и `api/users/app-settings/{app}/` (личные); `app` —
`nurmarket-kassa`, `nurmarket-owner`. PATCH сливает ключи верхнего уровня [по коду кассы, `SettingsCloudSync`]. Касса хранит там:
вид чека, общие настройки «Оплата долга» (`DebtPaymentOptions`: какие способы разрешены кассе/владельцу, нужен ли код сотрудника),
коды сотрудников (только хэши, с 18.10), темы и виды кассы магазина.
**Проблемы:**
1. Две кассы, записавшие одновременно, затирают друг друга (последний PATCH побеждает).
2. Права записи неясны: по коду кассы кассиру на запись приходит 403 и касса пишет «меняют только владелец и администратор»; в
   проверке 18.10 читал любой сотрудник, включая хэши кодов. **[подтвердите текущие правила: кто читает, кто пишет]**.

**Нужно:**
1. Версии. В ответе GET — служебное поле (старые клиенты его игнорируют):
   ```json
   {
     "DebtPaymentOptions": {"KassaCash": true, "KassaTransfer": false, "OwnerCash": true, "OwnerTransfer": true, "RequireEmployeeCode": false},
     "_meta": {
       "version": 42,
       "keys": {"DebtPaymentOptions": {"version": 7, "updated_at": "2026-10-19T16:20:00+06:00", "updated_by": {"id": "<uuid>", "name": "Сотрудник 1"}}}
     }
   }
   ```
   и заголовок `ETag: "42"`.
2. PATCH с условием: заголовок `If-Match: "42"` (весь документ) **или** в теле `"_expected": {"DebtPaymentOptions": 7}` (по ключам).
   Не совпало → 409 `{"code": "version_conflict", "data": {"current": {…значения и версии изменившихся ключей…}}}` — касса перечитает
   и повторит. PATCH без условия — как сейчас (для совместимости).
3. Права: запись общих настроек — только владелец/админ (403 `permission_denied` остальным). Чтение — всем сотрудникам компании, кроме
   **секретных ключей**: ключи с префиксом `secret_` (или список, который мы согласуем) отдаются только владельцу/админу.
4. Лимит размера: 256 КБ на приложение, 64 КБ на ключ → 413 `{"code": "too_large"}`.
5. Событие `app_settings_changed` (часть 20).

### 21.5. Коды доступа сотрудников — проверка на сервере (П2)
Сейчас личные коды сотрудников (на действия «удалить строку/чек», «удалить со склада», «изменить/добавить товар», «принять оплату долга»
— коды действий кассы `cartDelete`, `warehouseDelete`, `productEdit`, `productAdd`, `debtPayment`) хранятся хэшами в общих настройках
и проверяются кассой. Это значит, что хэши читает каждое устройство. Нужно:
- `PUT api/users/employees/{id}/access-codes/{action}/` `{"code": "1234"}` — задать (хэш делает сервер, код назад не отдаётся);
  `DELETE` — снять; только владелец/админ.
- `POST api/users/access-codes/verify/` `{"action": "debtPayment", "code": "1234"}` →
  `{"ok": true, "employee": {"id": "<uuid>", "name": "Сотрудник 2"}}` или 400 `{"code": "code_invalid"}`;
  ограничение — 5 попыток в минуту на пользователя/устройство, затем 429.
- `GET api/users/employees/{id}/access-codes/` → `[{"action": "debtPayment", "set": true, "updated_at": "…"}]` (без кодов).
После готовности касса перестанет хранить хэши в общих настройках.

### Как проверить
1. Две кассы читают версию 42, первая PATCH с `If-Match: "42"` → 200, версия 43; вторая с `If-Match: "42"` → 409 с текущими значениями.
2. Кассир PATCH → 403; кассир GET → без `secret_*` ключей.
3. `verify` с неверным кодом 6 раз за минуту → 429.

## Часть 22. Запросы «на кассу» (`pos/requests`)

**Приоритет: П3.** Источник: ТЗ 18.10 п. 5, макеты владельца.

### Зачем
По макетам владелец может оформить операцию с наличными (приём долга, выплату зарплаты, оплату поставщику, оплату проката), а
кассир подтверждает её в своей смене — деньги реально в ящике, Z-отчёт сходится. Сейчас владелец принимает деньги только «в руки»,
вне смены (часть 17).

### Что нужно
```
POST api/main/pos/requests/            + Idempotency-Key
```
```json
{
  "type": "debt_payment",
  "cashbox": "<uuid>",
  "amount": "500.00",
  "method": "cash",
  "payload": {"client": "<uuid>"},
  "comment": "Клиент А занесёт после обеда",
  "expires_at": "2026-10-20T23:59:59+06:00"
}
```
- `type`: `debt_payment` (`payload.client` или `payload.sale`), `salary_payout` (`payload` — как в части 24), `supplier_payment`
  (как в части 25), `rental_payment` (`payload.rental`), `cash_out` (изъятие с назначением).
- Ответ: `{"id", "status": "pending", "created_by", "created_at", …}`. Создают — владелец/админ.

```
GET  api/main/pos/requests/?status=pending&cashbox=<uuid>      — касса видит свои запросы
POST api/main/pos/requests/{id}/accept/   {"shift": "<uuid>"}  — кассир выполняет
POST api/main/pos/requests/{id}/decline/  {"reason": "…"}
POST api/main/pos/requests/{id}/cancel/                        — владелец отзывает
```
- `accept` выполняет операцию **атомарно** в смене кассира (как `pay-debt` со `shift` и т. п.), ключ повтора операции = id запроса
  (повторный `accept` → 200 с тем же результатом, `replayed: true`). Ответ — результат операции + `status: "accepted"`.
- Статусы: `pending` → `accepted` | `declined` | `canceled` | `expired` (по `expires_at`, по умолчанию 24 ч).
- Ошибки: `request_not_pending` (409), `shift_closed`, `shift_not_owned`, плюс коды самой операции (часть 17/24/25).
- События `pos_request_created` / `pos_request_resolved` (часть 20) — касса покажет плашку без опроса.

### Как проверить
Владелец создаёт `debt_payment` 500 на кассу 1 → касса 1 видит его ≤ 60 с → `accept` со сменой → долг −500, `expected_cash` +500;
повтор `accept` → `replayed: true`, второго списания нет; запрос на кассу 2 касса 1 не видит.

## Часть 25. Поставщики: долг, оплата, создание

**Приоритет: П1.** Деньги. Источник: «Поставщики и долги поставщикам в NurCRM — исследование 2026-10-20» (разделы 2, 3, 6;
вопросы 6.1, 6.3, 6.4, 6.5, 6.8, 6.12), «Поставщик в карточке товара» (20.10).

### Как устроено сейчас (кратко)
Отдельной сущности «долг поставщику» в секторе «Магазин» нет: долг — это **сделка** (`deal`, `kind=debt`) у контрагента с
`type="suppliers"`, та же модель, что долг клиента (`installments`, `payments`, `remaining_debt`). Итог — `GET main/clients/{id}/kpis/` →
`debt.amount` = **наш долг поставщику** [проверено на NBS 20.10: у поставщика «Поставщик А» `debt 1299.00 / 1`].

Закупку «в долг» на сайте делает **фронтенд** тремя-четырьмя отдельными запросами, не атомарно [по коду сайта, `SupplierReceiptPage`]:
`POST suppliers/{id}/receipt/ {items, payment_type}` → (тариф «Старт») `POST main/debts/` → `POST clients/{id}/deals/`
(`title: "Долги {имя}"`, `kind: debt`, вся сумма, срок, `auto_schedule: true`) → при частичной оплате `POST construction/cashflows/`
(«Закупка: {имя}»). Каждому приходу «в долг» на NBS соответствует сделка, созданная в ту же секунду с «сайтовым» названием —
**значит, сервер сам сделку-долг, скорее всего, не создаёт** [проверено на NBS 20.10, чтением; окончательно — только тестовым приходом].

Касса при приёмке шлёт только приход [по коду кассы, `PurchaseReceivingService`]:
```json
POST api/main/suppliers/{id}/receipt/
{
  "items": [{"product": "<uuid>", "qty": 10, "purchase_price": 45.5}],
  "payment_type": "cash|debt",
  "cashbox_role": "expense_variable",
  "idempotency_key": "<ключ>"
}
```
Если сервер сделку не создаёт, **долг, принятый кассой, не виден** ни в карточке поставщика на сайте, ни в `kpis`, и погасить его нельзя.

### Что нужно

**25.1. Приход в долг — атомарно на сервере (П1).** `POST api/main/suppliers/{id}/receipt/` + `Idempotency-Key` (и `idempotency_key` в теле):
```json
{
  "items": [{"product": "<uuid>", "qty": "10", "purchase_price": "45.50"}],
  "payment_type": "cash|debt|prepayment",
  "paid_amount": "200.00",
  "cashbox": "<uuid>?", "cashbox_role": "expense_variable?", "shift": "<uuid>?",
  "debt_days": 30, "debt_months": null, "first_due_date": "2026-11-20",
  "comment": "накладная №123"
}
```
- `cash` — всё оплачено: склад + **один** расход (`source_kind: procurement_receipt`) из `cashbox`/`cashbox_role`/`shift`.
- `debt` — склад + сделка-долг на всю сумму (`kind: debt`, срок из `debt_days`/`debt_months`, `first_due_date`), без расхода.
- `prepayment` — склад + расход на `paid_amount` + сделка-долг на остаток (или сделка `kind: prepayment` — как вам правильнее, но
  остаток долга должен быть виден в `kpis.debt`).
- Всё в **одной транзакции**: либо приход, расход и сделка, либо ничего.
- Ответ:
  ```json
  {
    "id": "<uuid приход>", "total_amount": "455.00", "payment_type": "debt",
    "paid_amount": "0.00", "debt_amount": "455.00",
    "deal_id": "<uuid>", "cashflow_id": null,
    "supplier_debt_total": "1754.00", "replayed": false
  }
  ```
- Повтор тем же ключом — тот же ответ, вторая сделка и второй расход **не** создаются.
- После выката сервера сайт должен перестать создавать сделку/расход сам (иначе будет двойной долг) — **согласуйте дату** с фронтендом.
- Ошибки: `supplier_not_found`, `items_empty`, `payment_type_invalid`, `paid_amount_exceeds_total`, `cashbox_not_found`, `shift_closed`;
  ошибки строк — `errors[]` с `index` (О1).
- **[проверено на NBS 20.10]:** сервер сделку-долг при `payment_type: "debt"` **сам не создаёт** — два тестовых прихода по 1 сом
  (поставщик «Поставщик А»): сделки не появилось ни через 1 мин, ни позже. С 20.10 касса создаёт её сама (как сайт) — после выката 25.1
  перейдёт на `deal_id` из ответа.
- **[проверено на NBS 20.10]:** `POST clients/{id}/deals/` с `debt_days: 30` создаёт **30 ежедневных взносов** (1 сом → 30 × 0,03), а не один
  платёж через 30 дней; один взнос на `first_due_date` даёт `debt_months: 1`. Опишите письменно, как сервер строит график из
  `debt_days` / `debt_months` / `first_due_date` / `auto_schedule`.
- **[проверено на NBS 20.10] — опасно для цен:** приход с новой ценой закупки (1 сом вместо 11) молча меняет `markup_percent` товара
  (36,36 % → 1400 %), а следующий `PATCH products/{id}/ {"purchase_price": "11.00"}` пересчитывает **цену продажи** по этой наценке
  (15 → 165 сом). Нужно: приход не меняет цену продажи и наценку без явного флага (`update_markup: true`); `PATCH` цены закупки не меняет
  цену продажи, если `price` не передан (или вернуть в ответе `price_changed: true`, чтобы касса предупредила).

**25.2. Долг в списке поставщиков (П1).** В `GET api/main/clients/?type=suppliers` (и в карточке) — поля, чтобы не запрашивать `kpis` на
каждого (N запросов: у NBS 10, у крупного магазина — сотни):
`debt_total` (мы должны), `prepayment_total` (мы предоплатили), `overdue_amount`, `next_due_date`, `last_receipt_at`, `receipts_count`.
Или отдельный отчёт `GET api/main/suppliers/debts/?overdue=true&ordering=-debt_total` с теми же полями и пагинацией.

**25.3. Оплата поставщику одной суммой (П1).**
```
POST api/main/clients/{id}/pay-supplier-debt/        + Idempotency-Key
```
```json
{"amount": "1299.00", "method": "cash|transfer", "cashbox": "<uuid>?", "shift": "<uuid>?", "date": "2026-10-20", "comment": "…"}
```
- Гасит сделки-долги поставщика от старых взносов к новым (как `pay-debt` клиентов), сам пишет **один** расход на каждую погашенную
  сделку (`source_kind: supplier_debt_payment`, касса — `cashbox` или из смены `shift`).
- Ответ: `{"paid", "left", "applied": [{"deal", "installment", "amount"}], "cashflows": [{"id", "cashbox", "shift", "amount"}],
  "paid_by": {"id", "name"}, "replayed"}` (`paid_by` — пользователь из токена, как `received_by` в части 17).
- Ошибки: `no_debt`, `amount_exceeds_debt` (`data.max`), `cashbox_not_found`, `shift_closed`, `insufficient_cashbox_balance` (если есть).

**25.4. Когда сервер пишет расход при оплате сделки поставщика (П1, ответ письменно).** На NBS в `deal.cashflows` есть расходы

1. Описать, какие поля принимает `deals/{deal}/pay/`: `cashbox`, `cashbox_role`, `payment_method`, `shift`, `amount`, `date`, `note`.

3. Ключ повтора — проверять до остальных проверок (О2).
4. Частичная `amount` — см. часть 17, п. 17.8.

**25.5. Приходы — способ оплаты и долг (П2).** В `GET api/main/suppliers/receipts/` и `…/{id}/` добавить `payment_type`, `deal_id`,
`paid_amount`, `debt_remaining`; фильтр `payment_type` (сейчас способа оплаты в списке приходов нет [проверено на NBS 20.10], он есть

**25.6. Кто оплатил (П2).** В `payments[]` сделки — `created_by_name`, `cashbox`, `cashbox_name`, `payment_method` (сейчас `created_by` —

**25.7. Создание поставщика — обязательные поля (П2).** Касса (окно товара и приёмка, с 20.10) создаёт поставщика минимальным телом

Сайт шлёт ещё пустые `email, date, status, llc, inn, okpo, score, bik, address` [по коду сайта]. **[подтвердите]**: принимается ли
минимальное тело (вживую ещё не проверяли). Нужно: обязательны только `type` и `full_name`; `phone` — необязателен (у поставщика

## Часть 26. Поставщики: исправление ошибок сервера и сайта

**Приоритет: П1** (26.1–26.4), **П2** (26.5), **П3** (26.6). Источник: исследование 20.10, раздел 3 и вопросы 6.2, 6.6, 6.7, 6.9, 6.10, 6.11.
Все случаи — [проверено на NBS 20.10] чтением; имена поставщиков заменены.

**26.1. Двойной расход при оплаченной закупке (П1, деньги).** При приходе «оплачено сразу» сервер сам пишет расход
`source_kind: "procurement_receipt"` («Приход поставщика: {имя}», `source_id` = id прихода; найдено 38), а сайт поверх этого шлёт свой
`POST construction/cashflows/` «Закупка: {имя}» (`source_business_operation_id: "Закупки"`; найдено 9). Деньги списываются **дважды**:
01.09 «Поставщик В» 3 996 + 3 996, 02.09 «Поставщик Г» 8 250 + 8 250 — в одну секунду.
**Нужно:** убрать расход «Закупка: …» на сайте (сервер уже пишет свой); подтвердить, каким полем выбирается касса оплаты прихода
(`cashbox_role: "expense_variable"`, `cashbox`). Дать скрипт/админку для поиска уже задвоенных пар у компаний (одинаковая сумма,
один поставщик, разница ≤ 5 с) — владельцы сами решат, удалять ли.
**Как проверить:** приход 100 «оплачено» с сайта → у прихода ровно один расход 100.

**26.2. Возврат поставщику «в счёт долга» не уменьшает долг (П1).** `POST main/suppliers/{id}/returns/` с `compensation: "debt_offset"`
проводится (статус `posted`), но сделка-долг не меняется: «Поставщик А», возврат 4 сом 19.10 — долг 1300 − оплата 1 = остаток 1299, как
и до возврата. **Нужно:** `debt_offset` уменьшает долг поставщику (гасит взносы его сделок от старых к новым, как оплата, но без движения
денег; если долга меньше суммы возврата — остаток становится предоплатой/долгом поставщика нам). В ответе возврата —
`debt_offset: {"amount": "4.00", "applied": [{"deal", "installment", "amount"}], "left": "1295.00"}`. Если сервер хранит зачёт
отдельно — **[подтвердите, где]**, и пусть `kpis.debt` и `remaining_debt` его учитывают.

**26.3. Акт сверки для поставщиков — неверный знак (П1).** `GET main/clients/{id}/reconciliation/json/` для поставщика: все сделки (включая
оплаченные закупки `kind: sale`) идут в дебет «компании», итог `debt: {"debtor": "Поставщик А", "creditor": "NBS", "amount": 1305}` —
будто поставщик должен нам, хотя мы должны ему 1299. Приходы (`receipts`), возвраты и движения денег в акт не входят. У «Поставщика Д»
акт показывает 19,4 млн «долга поставщика». **Нужно:** для `type: suppliers` — правильное направление (мы — должник по закупкам);
строки: приходы (кредит поставщика), оплаты сразу и оплаты долга, возвраты (`cash` и `debt_offset`) — дебет; сделки `kind: sale` у
поставщика (это оплаченные закупки, которые создаёт карточка товара сайта) **не** считать долгом. `entries[].ref_type` — добавить
`receipt`, `supplier_return`, `cashflow`. PDF `reconciliation/` — то же. Пока не исправлено, наша программа владельца считает акт сама и
серверный не показывает.

**26.4. Защита от дублей сделок (П1).** «Поставщик Д»: две одинаковые сделки «Долг …» 11 700 с разницей 36 секунд (двойное нажатие) —
`kpis.debt` = 23 400. **Нужно:** `POST main/clients/{id}/deals/` принимает `Idempotency-Key` / `idempotency_key` (О2); после 25.1 —
одна сделка на приход (связь `deal.receipt`, повторная сделка на тот же приход → 409 `deal_exists` с id).

**26.5. `clients/with-debts/` смешивает клиентов и поставщиков (П2).** На NBS 16 строк, из них 3 поставщика; суммы и направления долга
нет — вкладка «Должники» сайта показывает поставщиков как должников. **Нужно:** фильтр `?type=clients|suppliers` (по умолчанию —
`clients`) и в строке `debt_total` + `direction: "they_owe" | "we_owe"`.

**26.6. Единый реестр взаиморасчётов (П3).** Для «Магазина» — как у «Строительства» (`building/debts/ledger/`, `building/debts/summary/{type}/{id}/`)
или «Склада» (`warehouse/crud/counterparties/{id}/debts|payments/`, `warehouse/counterparties/balance-summary/` — магазину отвечает 400
[проверено на NBS 20.10]): одна лента «начислено / оплачено / зачтено / списано» по контрагенту. Тогда 26.2–26.3 решаются в одном месте.

**Для фронтенда сайта (передайте, пожалуйста):** окно сделки у поставщика называется «Долг клиента» — нужно «Наш долг поставщику»;

- Если сервер ключ не принял или нет связи — касса **сама** проверяет ключ (локальная проверка). В коде кассы есть общий «мастер-ключ»
  функций (значение здесь не приводим) — его можно извлечь из exe. Решение владельца — перевыпустить ключ и проверять только на сервере.
- Темы, виды кассы, экран покупателя, шаблоны чека/ценника — **данные** (JSON + картинки), не код. Каталог тем касса сначала будет
  читать из публичного файла в GitHub (сервер не нужен).

### Что нужно

**28.1. Ключи — только на сервере (П2).**
1. Ключ — одноразовый, привязывается к компании при первой активации; на сервере хранится хэш. Повторная активация той же
   компанией → 200 (тот же `code`, `replayed: true`); другой компанией → 409 `key_already_used`.
2. Ответ: `{"code": "<функция>", "features": ["…полный список…"], "expires_at": "…|null"}`.
3. Ограничение подбора: не больше 10 неверных ключей в час на компанию → 429 `too_many_attempts`.
4. Пробный доступ без мастер-ключа: `POST api/users/company/features/trial/ {"code": "<функция>"}` → `{"code", "expires_at"}` (например,
   7 дней, один раз на функцию на компанию). Это заменит локальный «тестовый доступ» кассы.
5. `GET api/users/company/features/` → `[{"code", "source": "tariff|key|trial|support", "expires_at", "activated_at", "activated_by"}]`.
6. Отключение/перенос — только поддержка NurCRM (админка), событие `features_changed` (часть 20).
7. Ошибки: `key_invalid` (400), `key_already_used` (409), `key_expired` (400), `too_many_attempts` (429).
Когда сервер будет надёжно отвечать — касса уберёт локальную проверку ключей и мастер-ключ (после выпуска с серверной проверкой).

**28.2. Темы как функции (П3).** `features/activate` принимает ключи платных тем/видов: `code` вида `theme:<id>` / `layout:<id>`; в
`features` они видны как остальные функции. Установка темы — копия её данных в общие настройки магазина (часть 21) — делает касса.

**28.3. Каталог тем на сервере (П3, позже).** `GET api/marketplace/themes/?kind=theme|layout|customer_display|receipt` →
`[{"id", "kind", "title", "author": {"id","name"}, "price": "0.00", "version", "preview_url", "file_url", "sha256", "min_app_version"}]`;
файлы — через медиа (27.4). Счёт продаж по автору — отчёт для владельца NurCRM (`GET api/marketplace/sales/?author=`). Публикует
только владелец NurCRM (админка), не дизайнер.

### Что НЕ требуется от бэкенда
- Программа для дизайнеров («NurMarket Студия», `--designer`) работает без входа в NurCRM, на тестовых данных.
- Новые «функции» от дизайнеров — это макеты и описания; код пишет команда кассы. Чужой код в кассу не загружается.
- Публичный каталог тем на первом этапе — файл в GitHub (только чтение для касс), сервер не нужен.
- Отправка электронного чека в WhatsApp через `wa.me` и QR — делает касса (27.5, п. 4).
- Своя экранная клавиатура, печать, денежный ящик, весы, сканер — всё на стороне кассы.
- Фискальные данные чека (ККМ/ФД/ФП) — не нужны: чек нефискальный.
- Локальная сеть магазина (обмен событиями между кассами) — остаётся у кассы как запасной канал к части 20.

### 31.1. API варианта для витрины (бэкенд, П1)

1. Модель варианта: + `color_hex` (`#RRGGBB`, необязательно; без него витрина рисует кнопку с названием цвета), + `sort_order`
   (целое, необязательно). Без `sort_order` сервер сортирует размеры сам: XXS…XXXL, 4XL, 5XL; затем числа по возрастанию (42 … 60,
   35 … 46, 86 … 164); затем W26…W36; затем по алфавиту. Касса пишет те же размеры из готовых сеток.
2. Фото по цвету: у фото товара (`products/{id}/images/`) — необязательное поле `color` (строка, как у варианта). Загрузка — тем же
   multipart с полем `color`; в ответах `images[].color`. Фото без цвета — общие для всех цветов.
3. Публичная карточка `showcase/{id}/`: в каждом варианте + `color_hex`, `sort_order`; варианты уже отсортированы; + `colors: [{name,
   hex, images: [url…]}]` и `sizes: [..]` по порядку; `images[].color`. Неактивные (`is_active=false`) не отдавать.
4. Наличие — **по филиалу витрины** (настройка компании `showcase_branch`, по умолчанию главный склад) и **за вычетом резервов**
   заказов витрины: `in_stock`, `low_stock` (порог как у товара), `available` — число, только если ≤ 5 («Осталось 2»), иначе `null`.
   Точный остаток больше 5 покупателю не раскрывать.
5. Цена варианта: `price` (своя или цена товара), `final_price` с акцией, `old_price` (зачёркнутая — если `final_price` ниже цены
   товара или действует акция), `discount_percent`. Сейчас `old_price` всегда `null`, даже когда размер дешевле товара — **[подтвердите правило]**.
6. Список `showcase/`: + `colors: [{name, hex}]` (до 8, только в наличии) и `sizes_in_stock: [..]` — для кружков и строки «S M L» на
   карточке; `in_stock` товара с вариантами = есть хоть один активный вариант с остатком; `price_range` — по вариантам в наличии.
7. Масштаб: варианты в списке — одним запросом (`prefetch_related`), без запроса на каждый товар; кеш публичного списка 30–60 с, сброс
   при продаже, приходе, возврате и правке варианта.

### 31.2. Карточка товара на витрине (фронтенд, П1) — см. макет

1. Цвета — кружками-образцами (`color_hex`; под кружками «Цвет: Белый»); нет кода — кнопка с названием цвета.
2. Размеры — сеткой кнопок в порядке сервера. Размер, которого нет в выбранном цвете, — серый, зачёркнутый, в корзину не кладётся
   (но его можно выбрать для «Сообщить о поступлении», 31.6). Один цвет или один размер — выбран сразу.
3. Выбор цвета меняет фото (`colors[].images`, иначе общие); выбор размера и цвета — цену, старую цену, «−N%» и подпись наличия
   («В наличии» / «Осталось 2» — по настройке `card.show.stock`).
4. «В корзину» неактивна, пока не выбраны размер и цвет; подсказка «Выберите размер». Ничего нет в наличии — «Нет в наличии» серым.
5. Ссылка «Таблица размеров» (31.7), если таблица есть у товара или категории.
6. Ссылка на вариант: `?variant=<uuid>` открывает карточку с выбранным размером и цветом (для рекламы и бота).

### 31.4. Корзина и заказ с вариантом (П1, главное)

1. Корзина — по ключу «товар + вариант»: «Nike — 46, Белый» и «Nike — 48, Белый» — разные строки; фото строки — фото цвета.
2. «Оформить» **создаёт заказ на сервере**: `POST public/companies/{slug}/orders/` `{"customer": {name, phone}, "items": [{"product",
   "variant", "qty"}], "delivery": {...}, "comment"}` → номер заказа; затем (по настройке) WhatsApp с текстом и номером заказа. Сейчас
   заказ уходит только текстом в WhatsApp — касса и «Заказы с сайта» его не видят, остаток не резервируется.
3. Проверки сервера (формат О1): товар с активными вариантами без `variant` → 400 `variant_required` (с `index` строки); вариант чужого

   и даёт исправить корзину. `cart/quote` — те же правила и цены вариантов (без создания заказа).
4. Идемпотентность (О2): заголовок `Idempotency-Key` — повторное нажатие «Оформить» не создаёт второй заказ.
5. В заказе (`showcase/orders/`) у строки — `variant`, `variant_size`, `variant_color`, `product_name` «Nike — 46, Белый» (у бота уже так);

### 31.5. Резерв варианта (П2)

1. Создание заказа резервирует **вариант и товар** (как `stock_reserved` сейчас у товара); `canceled` возвращает оба; `done` без продажи
   кассы — окончательное списание; продажа кассы с `variant` по заказу (`sale`) — без двойного списания.
2. Резерв виден у варианта (`reserved`) и вычитается из `available` витрины (31.1.4).
3. Остаток товара с вариантами = сумма остатков активных вариантов, сервер пересчитывает сам (ч.10 п.3.5, вариант А). Сейчас на NBS
   расходится (53 и 89). Касса показывает предупреждение, но правильно выровнять может только сервер.

### 31.6. «Сообщить о поступлении» (П2)

2. Остаток варианта стал > 0 (приход, возврат, правка) — сообщение покупателю через WhatsApp/Telegram компании (если подключены) и запись
   владельцу; подписка закрывается.
3. Владельцу: `GET api/main/showcase/stock-requests/?status=open` — кто ждёт какой размер (касса покажет в «Заказах с сайта» и в «Что заказать»).

2. В `charts.payment_methods` способ «Смешанная» раскладывается по долям: `cash`, `noncash` (по банкам/способам), `debt`. Сейчас сводка не знает, куда его отнести.
3. Возвраты вычитаются из выручки того же периода одним правилом (см. 33.4).

### 33.3. Поля отчёта смены `GET api/construction/shifts/{id}/report/`
Добавить (имена как в кассе, числа строками «0.00»):
- `revenue_excl_debt` — выручка без долга (нал + безнал + предоплаты по долговым чекам − возвраты, если возвраты учитываются в выручке — указать явно в ответе полем `revenue_excl_debt_includes_returns`);
- `credit_sales_total` — выдано в долг за смену (долговая часть чеков: в примере 3,00);
- `debt_repaid_total` — оплачено долгов за смену (в примере 3,00 нал.), с разбивкой `debt_repaid_cash` / `debt_repaid_noncash`;
- `prepayment_total` — предоплаты по долговым чекам (в примере 1,00, нал.).
Пример (круг 6): `sales_total` 6.00, `returns_cash` 1.00, `closing_cash` 46.00, `expected` 46.00, `cash_diff` 0.00; ожидаемые: `revenue_excl_debt` 3.00, `credit_sales_total` 3.00, `debt_repaid_total` 3.00, `prepayment_total` 1.00. Сумма в ящике: 41 (открытие) + нал 2 + оплата долгов 3 + возврат(−1) … — касса не может свести строки Z-отчёта (получается 45 при 46 «по системе»), потому что возвращённая продажа 001879 не входит в «Наличными», а возврат вычитается: нужно, чтобы отчёт отдавал `cash_in_drawer_breakdown` (открытие, продажи нал., предоплаты, оплата долгов, возвраты нал., расходы/внесения, итог).

### 33.4. Возвраты: `returns_total` = 0 из-за пустого `shift`
Возвраты (круги 5–6) создаются с пустым полем `shift`, поэтому в отчёте смены `returns_total = 0`, хотя `returns_cash` = 1.00 (сервер при закрытии считает возврат наличными отдельно). Нужно: у возврата `shift` = смена, в которой он оформлен (по кассе и времени), и `returns_total`/`returns_cash`/`returns_noncash` в отчёте считаются по ней; возврат долгового чека с безналом не должен превращаться в «Наличные» (см. ч.30.4).

### 33.5. Остаток кассы при закрытой смене
Окно «Открыть смену» не получает «Остаток по системе»: касса берёт его из списка **открытых** смен (`ShiftBalanceHelper.FindOpenShiftBalance`), а при закрытой смене её нет; в журнале «Не удалось определить остаток кассы из ответа API». На сервере у последней закрытой смены `closing_cash` 41.00 / 46.00. Нужно: `GET api/construction/cashbox/balance/?cashbox={id}` (или поле `last_closing_cash` в ответе списка касс) — текущий остаток денег в кассе независимо от того, открыта смена или нет.

### 1.1. Требования к масштабу (15 000 ботов)

Владелец: расчёт на 15 000 клиентов. У каждого клиента свой бот, то есть один сервер держит до 15 000 вебхуков.

1. **Вебхук только принимает и сразу отвечает 200** (≤ 100 мс): проверить секрет, записать `update_id` и поставить задачу в очередь. ИИ, запросы к базе и отправку ответа делать **только в воркере**. Иначе Telegram при медленном ответе повторяет обновление, и получаются дубли.
2. **Дубли:** уникальный индекс `(bot_id, update_id)`. Повторно доставленное обновление не обрабатывать.
3. **Воркеры масштабируются горизонтально** (несколько процессов или машин), очередь общая. Нужен мониторинг: длина очереди, возраст самой старой задачи, ошибки. **Тревога, если задача ждёт больше 30 с.**
4. **Ответ владельцу — не позже 5 с** после сообщения (без ИИ ≤ 2 с, с ИИ ≤ 10 с при сравнении периодов). Подтверждение — замер на нагрузочном тесте (п. 9 ниже).
5. **Лимиты Telegram:** не больше ~30 сообщений в секунду на одного бота и 1 в секунду в один чат. Рассылки (сводка смены, утренние отчёты) — через очередь с ограничением скорости, **распределённые во времени**: не все 15 000 сводок в 09:00:00, а с разбросом.
6. **Лимиты ИИ:** очередь вызовов ИИ с ограничением на компанию (`customer_limit_per_hour` уже есть) и общим ограничением на ключ. 429 от ИИ — повтор с паузой, после 3 неудач отвечать без ИИ (ключевые слова или «попробуйте позже»), а не молчать.
7. **Пропавший вебхук:** раз в час проверка `getWebhookInfo` у всех ботов в режиме server (пачками, не всеми сразу). Если вебхук снят, есть ошибка или `pending_update_count` > 50 — поставить вебхук заново, записать `webhook_error` и показать его в `GET settings` (программа покажет владельцу).
8. **Неверный токен** (401 от Telegram, бот удалён): `webhook_ok=false`, понятный `webhook_error`, бота не опрашивать по кругу.
9. **Нагрузочный тест перед выпуском:** 1 000 ботов × 5 сообщений за минуту (эмуляция Telegram, без реальной отправки). Цели: 95 % ответов ≤ 5 с, ни одного потерянного и ни одного дубля.
10. **Сервис здоровья для программы:** `GET telegram-bot/settings/` — добавить `last_update_at` (когда пришло последнее сообщение) и `last_reply_at` (когда бот последний раз ответил). Если `last_update_at` позже `last_reply_at` больше чем на 2 минуты, программа владельца покажет «бот на сервере не отвечает» и предложит временно вернуть его на компьютер.

### 1.2. Приёмка исправления

1. Владелец пишет боту «Ты работаешь?» — ответ ≤ 5 с.
2. Покупатель пишет «есть хлеб?» — ответ ≤ 10 с, запись появилась в `inquiries`, `stats.messages` увеличился.
3. Остановить воркер на 2 минуты, отправить 3 сообщения, запустить: все 3 получили ответ по одному разу, без дублей.
4. Отправить одно и то же обновление дважды (повтор Telegram): ответ один.
5. `settings` отдаёт `last_update_at` / `last_reply_at`.

## 2. Умная допродажа: серверная часть

**Что делает касса (делаем мы, сервер не нужен для работы):** по истории чеков касса находит товары, которые часто покупают вместе с товарами текущего чека. Кассиру показывается одна подсказка «С этим часто берут: Хлеб — 40 сом» с кнопками «Добавить» и «Пропустить». Порядок подсказок: совместные покупки 40 %, маржа 30 %, популярность 15 %, приоритет владельца 15 %. Предлагаются только товары в наличии, которых нет в чеке. Считается на самой кассе: без интернета работает, нагрузки на сервер нет.

**Что нужно от сервера:** общий журнал показов и нажатий со всех касс компании, статистика для программы владельца, приоритет товара и (позже) готовые пары для новых касс без истории.

### 2.1. Приоритет товара

Два поля товара (`/api/main/products/…`, чтение и запись, как остальные поля):

| Поле | Тип | Смысл |
|---|---|---|
| `upsell_priority` | int 0–100, по умолчанию 0 | владелец поднимает товар в подсказках (новинка, остатки, высокая маржа) |
| `upsell_excluded` | bool, по умолчанию false | товар никогда не предлагать (сигареты, алкоголь, товар под заказ) |

### 2.2. Журнал событий: `POST /api/main/recommendations/events/`

Касса копит события и отправляет пачкой: при оплате чека и раз в 5 минут. Без интернета — копит до появления связи.

```json
{
  "events": [
    {
      "client_event_id": "3f1c…-uuid",
      "event": "shown | accepted | skipped",
      "product_id": "<рекомендованный товар>",
      "trigger_product_ids": ["<товар в чеке, к которому подсказка>"],
      "cart_id": "<id корзины>",
      "sale_id": "<id продажи, если чек уже оплачен, иначе null>",
      "price": "40.00",
      "score": 0.73,
      "cashier_id": "<id сотрудника>",
      "device_id": "<id кассы>",
      "occurred_at": "2026-10-01T21:15:03+06:00"
    }
  ]
}
```

- Не больше 200 событий в запросе. Ответ: `{"accepted": N, "duplicates": M}`.
- **Повторная отправка не создаёт дублей:** уникальный ключ `(company_id, client_event_id)`. Касса отправляет повторно, если не получила ответ.
- После оплаты касса присылает `PATCH /api/main/recommendations/events/link-sale/` `{"cart_id": "...", "sale_id": "..."}` — проставить `sale_id` всем событиям корзины. По `sale_id` сервер знает, что добавленный товар действительно продан (а не удалён из чека перед оплатой).
- Хранить 13 месяцев, индексы `(company_id, occurred_at)` и `(company_id, sale_id)`.

### 2.3. Статистика: `GET /api/main/recommendations/stats/?date_from=&date_to=&branch=`

```json
{
  "shown": 1250, "accepted": 210, "skipped": 940,
  "acceptance_rate": 16.8,
  "revenue": "18450.00",
  "profit": "6120.00",
  "by_product": [{"product_id": "...", "name": "Хлеб", "shown": 300, "accepted": 80, "revenue": "3200.00"}],
  "by_cashier": [{"cashier_id": "...", "name": "Айгуль", "shown": 600, "accepted": 120, "revenue": "9800.00"}],
  "by_day": [{"date": "2026-10-01", "shown": 50, "accepted": 9, "revenue": "720.00"}]
}
```

- `revenue` / `profit` — только по принятым подсказкам, у которых `sale_id` есть и товар остался в оплаченном чеке (количество × цена продажи из строки чека; прибыль = минус себестоимость). Возвраты вычитаются.
- Права: `can_view_analytics` (как остальная аналитика).
- Ответ ≤ 2 с за месяц при 100 000 событий у компании.

### 2.4. Пары товаров для касс без истории: `GET /api/main/recommendations/pairs/?days=90&limit=10`

Новая касса (или переустановка) истории чеков не имеет — подсказок нет первые недели. Сервер считает пары по всем продажам компании.

```json
{
  "computed_at": "2026-10-01T03:10:00+06:00",
  "pairs": [
    {"product_id": "A", "together": [{"product_id": "B", "count": 42, "confidence": 0.31, "lift": 2.4}]}
  ]
}
```

- `count` — в скольких чеках A и B вместе; `confidence` = count / чеков с A; `lift` = confidence / доля чеков с B.
- Только пары с `count ≥ 3`, не больше `limit` товаров на каждый A, без `upsell_excluded`.
- **Масштаб:** считать **ночной задачей раз в сутки** (с разбросом по компаниям 00:00–06:00), хранить готовый результат; запрос только читает. Не считать на лету по запросу. Касса запрашивает не чаще раза в сутки, ответ с `ETag` / `If-None-Match` → 304, если не изменилось.

### 2.5. План продаж (вторая очередь, «Прогресс к цели»)

`GET/PUT /api/main/sales-targets/?month=2026-10&branch=` → `{"month": "2026-10", "revenue_target": "1500000.00"}`. Права на запись — владелец. Касса и программа владельца показывают: продано, нужный темп в день, успеваем ли, вклад допродажи (из 2.3).

### 2.6. Приёмка раздела 2

1. Отправить 3 события, повторить ту же пачку — `accepted: 3`, потом `duplicates: 3`, в базе 3 записи.
2. Принять подсказку, оплатить чек, `link-sale` — в `stats` выручка выросла на цену товара.
3. Принять подсказку, удалить товар из чека, оплатить — в выручку допродажи **не** попало.
4. Вернуть товар из п. 2 — выручка допродажи уменьшилась.
5. `pairs` для товара с 3+ совместными чеками отдаёт пару; товар с `upsell_excluded=true` не попадает.
6. Повторный `pairs` с `If-None-Match` → 304.
7. Нагрузка: 15 000 компаний × 1 пачка событий в 5 минут = 50 запросов/с — 95 % ответов ≤ 300 мс.

## 3. Технический бот: собирает логи программ и показывает команде только критичное

Владелец: «логи в программе — задание для технического бота, который разбирал, сортировал и показывал нам только критические логи и баги, которые мешают работать».

### 3.1. Что сейчас и почему так нельзя оставлять

- В программе (касса и программа владельца) есть кнопка «Журнал ошибок → Отправить в поддержку». Она упаковывает журналы и отчёты о падениях в zip и отправляет файлом в Telegram напрямую — токен бота лежит в файле `support-bot.json` на компьютере клиента. Отчёты о падении досылаются при следующем запуске.
- При 15 000 клиентах так нельзя: токен бота поддержки оказывается на 15 000 компьютерах, Telegram-группа тонет в файлах, одинаковые ошибки никто не сводит вместе, а критичные («не проходит оплата») теряются среди мелочей («сеть моргнула, повтор прошёл»).
- **Решение:** программа отправляет отчёты на сервер NurCRM. Сервер группирует одинаковые ошибки, считает, скольких магазинов они касаются, и только критичное шлёт в Telegram-группу команды. Остальное видно в сводке и по командам.

### 3.2. Приём отчётов: `POST /api/support/error-reports/`

Авторизация — токен пользователя (компания и логин берутся из него). Если программа не вошла (ошибка на экране входа), допускается без токена с `device_id` и лимитом 10 отчётов в час на устройство.

Программа отправляет пачкой (до 50 отчётов), одинаковые ошибки за 10 минут сворачивает в один отчёт с `count`.

```json
{
  "reports": [
    {
      "client_report_id": "uuid",
      "app": "kassa | owner",
      "version": "1.17.38",
      "os": "Windows 10 22H2",
      "device_id": "<id компьютера>",
      "login": "<логин сотрудника>",
      "level": "critical | error | warning",
      "category": "payment | shift | print | drawer | scales | sync | offline | login | bot | update | crash | ui | other",
      "fingerprint": "<sha1: тип ошибки + 3 верхних кадра стека + сообщение без чисел и id>",
      "message": "PAY failed: 500 от /api/main/pos/carts/…/checkout/",
      "stack": "<стек, до 8 КБ>",
      "context": ["<последние 50 строк журнала, до 16 КБ>"],
      "count": 3,
      "first_at": "2026-10-02T10:01:12+06:00",
      "last_at": "2026-10-02T10:08:40+06:00"
    }
  ]
}
```

- Ответ: `{"accepted": N, "duplicates": M}`. Повтор с тем же `client_report_id` дублей не создаёт.
- Полный zip журналов — только по кнопке «Отправить в поддержку»: `POST /api/support/error-reports/attachment/` (multipart, до 5 МБ, привязка к `client_report_id`). Хранить 30 дней.
- **Секреты:** программа уже вычищает токены, пароли и JWT (`SensitiveDataRedactor`). Сервер повторно прогоняет `message`, `stack` и `context` через свою чистку (Bearer, `bot<цифры>:`, ключи `AIza…`, пароли в JSON, номера карт), прежде чем сохранить.

### 3.3. Группировка: «проблема» вместо тысячи одинаковых отчётов

Отчёты с одинаковым `fingerprint` — одна **проблема** (issue):

| Поле | Смысл |
|---|---|
| `id`, `title` | номер и короткое название (первое сообщение) |
| `category`, `severity` | раздел и важность (п. 3.4) |
| `first_seen`, `last_seen` | первый и последний раз |
| `occurrences` | всего случаев (сумма `count`) |
| `companies` | сколько разных магазинов затронуто |
| `versions` | в каких версиях (список) |
| `status` | `new` / `acknowledged` (взяли в работу) / `fixed` (с версией исправления) / `muted` (до даты) |

### 3.4. Что критично (бот пишет сразу) и что нет

**Критично — «мешает работать»** (`severity = critical`):

1. Не проходит оплата: `category=payment`, уровень `error` и выше — любая ошибка оформления продажи.
2. Не открывается или не закрывается смена (`shift`).
3. Программа упала (`crash`) или не запускается.
4. Офлайн-продажи не досылаются на сервер дольше 30 минут (`offline`) — риск потери выручки.
5. Не печатается чек 3 раза подряд за 10 минут (`print`), не открывается денежный ящик 3 раза подряд (`drawer`).
6. Ошибка входа у всех сотрудников одной компании (`login`) или обновление не ставится (`update`).
7. Повреждение локальной базы (сообщения `database disk image is malformed`, `SQLite Error 11`).
8. Любая ошибка, затронувшая **5 и больше магазинов за час**.

**Не критично** (только в сводке): одиночные сетевые таймауты и 429, после которых повтор прошёл; предупреждения (`warning`); ошибки весов и экрана покупателя у одного магазина; ошибки ИИ и озвучки бота.

Правила задаются на сервере (таблица правил: категория, уровень, порог, окно времени), чтобы менять их без выпуска программы.

### 3.5. Что бот пишет в Telegram-группу команды

Бот — отдельный (технический), группа — только команда NurMarket. Клиенты его не видят.

1. **Новая критичная проблема** — сразу, один раз:
   > 🔴 Оплата: 500 при оформлении продажи
   > Магазинов: 3 · случаев: 7 · версия 1.17.38 · с 10:01
   > Пример: «Магазин N», касса, логин kassir1
   > /issue_412
2. **Всплеск**: уже известная проблема за час затронула ещё 5+ магазинов или 20+ случаев — одно сообщение в час, не чаще.
3. **Возврат исправленной ошибки**: проблема `fixed` в 1.17.38 появилась снова в 1.17.38 или новее.
4. **Новая версия хуже прошлой**: за первые 2 часа после выпуска доля магазинов с критичными ошибками в новой версии вдвое выше, чем в предыдущей.
5. **Сводка в 09:00**: 10 главных проблем за сутки (по числу магазинов), новые за сутки, сколько закрыто; доля магазинов без падений по версиям.

**Команды бота:** `/top` (главные открытые), `/issue <id>` (подробно + пример стека + список магазинов), `/company <slug>` (проблемы одного магазина за 7 дней), `/version 1.17.38`, `/ack <id>`, `/fixed <id> <версия>`, `/mute <id> 24h`, `/report <client_report_id>` (zip, если приложен).

Не больше 20 сообщений в час от бота в группу, даже при аварии — дальше одно «⚠ Массовый сбой: N проблем, смотрите /top».

### 3.6. Масштаб (15 000 клиентов)

- Приём — как вебхук бота (раздел 1.1): принять, проверить, положить в очередь, ответить ≤ 200 мс. Группировку и уведомления делает воркер.
- Ожидаемая нагрузка: в среднем ≤ 5 запросов/с, при массовом сбое — до 300 запросов/с несколько минут. Лимит: 30 отчётов в час на устройство (лишнее — 429, программа копит и сворачивает).
- Хранить отчёты 90 дней, проблемы — бессрочно. Индексы `(fingerprint)`, `(company_id, last_at)`, `(version)`.

### 3.7. Что сделаем в программе (после готовности API)

- Ошибки уровня `error` и выше, падения, «оплата не прошла», «смена не открылась» отправлять автоматически, свёрнутыми по `fingerprint`, без интернета — копить и досылать.
- Кнопку «Отправить в поддержку» перевести на `attachment/` вместо прямого Telegram. Файл `support-bot.json` больше не нужен.
- В «Журнале ошибок» показывать номер отчёта, чтобы клиент мог назвать его поддержке.

### 3.8. Приёмка раздела 3

1. 100 одинаковых отчётов от 1 магазина → одна проблема, `occurrences=100`, `companies=1`; в группу — одно сообщение (если критично) или ничего (если нет).
2. Одна и та же ошибка оплаты у 5 магазинов за час → одно сообщение «новая критичная», затем не больше одного «всплеска» в час.
3. Сетевой таймаут, после которого повтор прошёл (`warning`) → в группу не пишется, виден в `/top` только в сводке.
4. `/fixed 412 1.17.38`, затем тот же `fingerprint` от версии 1.17.38 → сообщение «возврат исправленной ошибки».
5. В `stack` отчёта специально вставлен `Bearer eyJ…` и `bot123:AA…` — в базе и в Telegram их нет.
6. Повтор той же пачки → `duplicates` = числу отчётов, дублей нет.
7. Нагрузка 300 запросов/с в течение 5 минут — без потерь, уведомления ≤ 1 мин.

## 4. Одежда: размеры и цвета — в боте на сервере и на онлайн-витрине; уточнения по прокату

Владелец (02.10): «бот тоже должен видеть размеры и цвета одежды», «и в онлайн-витрине на сайте тоже так же выбор должен быть», «реализуй аренду для услуг и магазина одежды — прокат», «в залоге и паспорт добавь».

Касса это уже делает (версия 1.17.39): окно выбора размера и цвета с остатками и акционной ценой, акция видна в чеке и в корзине, прокат с залогом деньгами или документом. Варианты берутся из `GET /api/main/products/{id}/variants/`, прокат — `/api/rentals/` (проверено на тестовом аккаунте 02.10, прокаты №1 и №2).

### 4.1. Бот на сервере видит размеры и цвета

1. В каталог для ИИ-консультанта (ответы покупателям) и в функцию владельца «товар» (ТЗ часть 6, F8) добавить варианты товара: размер, цвет, есть ли в наличии, акционная цена варианта, если она ниже цены товара. Покупателю — без точных остатков («есть / нет»), владельцу — с остатками.
2. Подсказка ИИ: называть только варианты в наличии; перед заказом **обязательно уточнять размер и цвет**.
3. Заказ из бота: в строке заказа — `variant_id` (а не только товар). Если покупатель не назвал размер или цвет, бот спрашивает, а не оформляет заказ на «просто товар».
4. Уведомление владельцу о заказе: «Джинсы мужские — 32, синий × 1».
5. **Масштаб:** варианты не запрашивать заново на каждое сообщение. Каталог для ИИ с вариантами собирать из базы одним запросом с `prefetch` и кэшировать на компанию 2–5 минут.

Приёмка: покупатель пишет «есть джинсы 32?» → бот отвечает про размер 32 и цвета в наличии; «хочу футболку» → бот спрашивает размер и цвет; заказ попадает в заказы витрины с вариантом.

### 4.2. Онлайн-витрина: выбор размера и цвета

1. Карточка товара с вариантами: кнопки размеров (по порядку XS…XXL, числа по возрастанию), под ними цвета выбранного размера (кружок цвета и название). Вариант без остатка — серый, «нет в наличии», выбрать нельзя.
2. Цена и остаток меняются при выборе варианта. Акционная цена варианта — новая цена, рядом зачёркнутая обычная и «−N%».
3. Кнопка «В корзину» неактивна, пока не выбраны размер и цвет. В корзине и заказе — название с вариантом («Платье летнее миди — 44, красный») и `variant_id`.
4. Остаток резервируется и списывается по варианту (как в кассе).
5. API витрины: в `GET` карточки товара отдавать `variants: [{id, size, color, quantity|in_stock, price}]` одним запросом (без отдельного запроса на каждый вариант), на списке товаров — признак `has_variants` и диапазон цен.

Приёмка: на витрине у «ТЕСТ Футболки» выбрать «L, чёрный» → цена 750 вместо 900 и «−17%»; заказ с витрины уменьшил остаток именно «L чёрный».

### 4.3. Прокат: уточнения

Найдено проверкой 02.10:

1. **`deposit_method`** принимает любое слово (проверено: `bogus` проходит). Нужно ограничить: `cash` | `transfer` (| `card`). Денежный залог `cash` — приход в кассу смены, как сейчас. Залог переводом — в безналичный приход, **не** в наличные смены (иначе касса ждёт в ящике лишние деньги). Сейчас касса принимает денежный залог только наличными.
2. **Стоимость проката.** В документе проката цены нет — касса берёт оплату обычной продажей строкой «Прокат №N…». Просьба: необязательное поле `rent_amount` (и `sale` — ссылка на продажу), чтобы в отчётах было видно, сколько принёс прокат. Касса будет передавать сумму.
3. **Паспорт в залоге** (`deposit_type=document`, `deposit_document` до 255 символов) работает. Просьба: не показывать `deposit_document` в списках сотрудникам без права на клиентов (это персональные данные) и удалять его через 30 дней после возврата.
4. **Штраф при залоге-документе.** Если залог — документ, а штраф больше 0, удерживать нечего. Нужно создавать долг клиента на сумму штрафа (`penalty_sale` со статусом «долг»), чтобы касса могла его принять, — опишите, как сделано сейчас.
5. **Просрочка.** `overdue` уже есть. Просьба: бот на сервере раз в день (утром, с разбросом по компаниям) присылает владельцу «Просроченные прокаты: №…, клиент, телефон, вещь, на сколько дней».
6. **Возврат части вещей** (взяли 2 вещи, вернули 1) — сейчас возврат только целиком. Если нужно — `items` в теле возврата.
7. **Штраф, удержанный из залога, — не двойной приход?** Проверка 02.10, прокат №3: залог 1000 (приход «Залог по прокату №3»), возврат с повреждением и штрафом 200 → расход «Возврат залога» 800 **и** приход 200 «Продажа (Зачёт (предоплата/обмен))» (`penalty_sale`). Наличными в ящике прибавилось 200 (1000 − 800). Если приход «Зачёт» тоже считается в ожидаемых наличных смены (`expected_cash`), касса будет ждать +400 вместо +200. Проверьте и опишите, как считается.
8. Список `GET /api/rentals/` не отдаёт `deposit_refunded` / `deposit_withheld` (они есть только в ответе на возврат) — добавьте их в список, касса пока считает удержание из `penalty`.

Приёмка: залог `transfer` не попадает в наличные смены; `rent_amount` виден в `GET /api/rentals/`; штраф 200 при залоге-паспорте создаёт долг клиента на 200.

### 4.4. Бот на сервере: прокат и аренда

Бот на компьютере (касса, программа владельца — версия 1.17.39) уже это делает. Нужно то же на сервере:

1. **Владелец** пишет «прокат», «кто не вернул», «залоги», «аренда», «ижара», «күрөө» → ответ: на руках N, просрочено M; список просроченных (№, клиент, вещь с размером и цветом, до какого числа, на сколько дней просрочен, залог: сумма или «документ»); сумма денежных залогов в кассе. Данные — `GET /api/rentals/?status=active`.
2. **Функция для ИИ владельца** (к F1–F20 из части 6): `F21 rentals(status)` — тот же список; вопросы «сколько вещей в прокате», «кто должен вернуть платье».
3. **Покупатель** (сферы «Одежда» и «Услуги»): ИИ-консультант знает, что вещи можно взять напрокат с залогом (деньги или паспорт); называет вещи в наличии с размерами и цветами; цену и срок — «уточните у продавца» (пока у проката нет поля цены, см. 4.3 п. 2).
4. **Утреннее сообщение** владельцу о просроченных прокатах — см. 4.3 п. 5.
5. Персональные данные: в ответах бота паспортные данные из `deposit_document` **не показывать** — только «залог: документ».

Приёмка: владелец пишет «кто не вернул прокат» → список с просроченными; покупатель пишет «можно взять платье напрокат?» → бот отвечает, что можно, называет платья в наличии и размеры.

### 4.5. Напоминания о сроке проката (добавлено 02.10, вечер)

Владелец: «уведомление об окончании и приближении срока аренды проката — в админке и в боте».

**Что уже сделано в программе (1.17.41):** касса и программа владельца раз в час берут `GET /api/rentals/?status=active` и `?status=overdue` (только в сферах «Одежда» и «Услуги») и делят прокаты на «просрочен», «вернуть сегодня», «вернуть завтра». В программе владельца — число у пункта «Прокат» и карточка в меню; в Телеграм владельцу — одно сообщение на событие («завтра» и «сегодня» по разу, «просрочен» — раз в день, с 8:00 до 21:00). Работает, **только пока на компьютере включена касса или программа владельца**.

**Что нужно от сервера**, чтобы напоминание приходило всегда:

1. Бот на сервере (режим `server`) сам шлёт владельцу то же сообщение: в 9:00 по времени магазина — «вернуть сегодня» и «просрочены», в 18:00 — «вернуть завтра». Формат: `• №5 Айбек — Платье (M, красный), до 03.10 · залог 500 сом`; паспортные данные не показывать (см. 4.4 п. 5).
2. Признак в настройках бота `GET /api/main/telegram-bot/settings/` → `rental_reminders: true`, когда сервер начал слать сам. Тогда программа перестанет слать свои (иначе владелец получит два сообщения).
3. В списке `GET /api/rentals/` — поле `due_in_days` (0 — сегодня, 1 — завтра, отрицательное — просрочен) по дате магазина, чтобы касса и сервер считали «сегодня» одинаково (часовой пояс компании).
4. Масштаб: 15 000 магазинов — одна выборка по всем компаниям раз в сутки на каждое время рассылки, а не опрос из программ.

Приёмка: прокат с `date_to` = завтра → в 18:00 владелец получил «вернуть завтра» один раз; при `rental_reminders: true` программа не дублирует.

Обратитесь к администратору магазина» | Найти «джинсы» в каталоге: цена, остаток, размеры и цвета; сказать, что выдать напрокат можно в кассе («Прокат» → «Новый прокат»); кто сейчас держит джинсы в прокате (`GET /api/rentals/?status=active`) |

2. Функция `rentals(status, query)` — см. 4.4 п. 2: прокаты (на руках, просрочены), поиск по вещи и клиенту.
3. Слова категории: «одежда», «одежды», «кийим», «обувь» → категория товара (поиск по названию категории, без учёта окончания).

## 1. СРОЧНО: у клиентов не работает ИИ бота

**Что видно.** У клиента palma бот работает в режиме `server`, но в `GET /api/main/telegram-bot/settings/`:

```
"ai_enabled": false, "ai_key_set": false
```

ИИ-консультант покупателей и ИИ владельца у него молчат. На тестовом аккаунте NBS ИИ работает только потому, что ключ ИИ туда перенесли с компьютера разработчика.

**Причина.** Программа при переносе бота на сервер (`PATCH settings/`) отправляет `ai_key` и `ai_enabled: true` только если ключ ИИ есть в настройках этого компьютера. У обычного клиента своего ключа нет.

**Что сделать на сервере:**

1. Общий ключ ИИ NurCRM (переменная окружения сервера, не в базе компаний). Если у компании нет своего ключа — бот использует общий.
2. `ai_enabled` по умолчанию `true` для всех компаний с ботом в режиме `server`. Выключает сам владелец.
3. В `GET settings/` добавить поле `ai_source`: `own` (свой ключ компании) или `shared` (общий). Программа покажет владельцу, чей ключ работает.
4. Лимиты на общий ключ, чтобы один магазин не съел квоту всех:
   - не больше 300 ответов ИИ в сутки на компанию;
   - сверх лимита — ответ без ИИ (поиск по каталогу), как сейчас при 429.
5. Масштаб: 15 000 компаний. Очередь запросов к ИИ общая, с повтором на 429 (сейчас голос `gemini-2.5-flash-preview-tts` часто отвечает 429).

**Приёмка:** у palma без своего ключа `ai_enabled: true`, `ai_source: shared`; покупатель пишет «есть памперсы 5?» — бот отвечает текстом ИИ с ценой и наличием.

## 2. «Движение денег» задваивает доход, а сверка №6 пишет «всё сходится»

`GET /api/main/analytics/cashflow/?period=month`, октябрь 2026:

| Компания | sales_cash + sales_card | other_income | Итого приход |
|---|---|---|---|
| NBS | 285 038,65 + 2 695,00 = 287 733,65 | 531 875,65 | 819 609,30 |
| palma | 55 577,22 + 48 667,64 = 104 244,86 | 120 338,01 | 224 582,87 |

`other_income` — это записи `api/construction/cashflows/` с названиями «Продажа», «Продажа (Перевод)», «Продажа (наличные)», «Продажа (Бакай)». У palma 40 из 40 последних записей прихода — именно они. Их сервер сам создаёт на каждую продажу (касса таких записей не делает). Получается, одна и та же продажа считается дважды: в `sales_cash`/`sales_card` и в `other_income`.

При этом `GET /api/main/analytics/reconcile/` — проверка №6 «Финансовый доход = уникальные платежи» — `ok: true, diff: 0.00`.

**Что сделать:**

1. В `cashflow` не включать в `other_income` записи, созданные продажей (у них есть ссылка на продажу / `source_business_operation`). Прочий доход — только внесения, залоги и ручные приходы.
2. Проверка №6 должна сравнивать доход из `cashflow` с суммой продаж плюс прочий доход и находить это задвоение. Сейчас она его пропускает.
3. Тот же фильтр — в разделе «Финансы» сайта. По словам владельца, там за месяц 6,11 млн дохода при продажах 5,15 млн.

**Приёмка:** у NBS за октябрь `other_income` = внесения + залоги проката, без продаж; итог прихода ≈ продажи + внесения; при задвоении проверка №6 показывает `ok: false` и разницу.

## 3. Штрихкоды: UPC-A (12 цифр) и EAN-13 с нулём — один и тот же код

Живой случай у palma:
- товар «Tomiko japan турсики 3шт 5Xl» записан со штрихкодом `0762497741537`;
- сканер присылает `762497741537` (на упаковке UPC-A);
- `GET /api/main/products/global-barcode/762497741537/` → 404, с нулём → 200.

В кассе 1.17.42 это исправлено: касса ищет обе записи. Нужно и на сервере, для сайта и мобильного приложения: `barcode/`, `global-barcode/`, `warehouse-barcode/`, `create-by-barcode/` и поиск `?search=` ищут код и как 12 цифр, и как 13 с ведущим нулём.

## 4. Продажи в убыток

Касса 1.17.42:
- показывает у строки чека «убыток N сом», если со скидкой товар продаётся дешевле закупки;
- предупреждает кассира;
- пишет такие чеки в журнал, который видит программа владельца **на этом же компьютере**.

Чтобы владелец видел их с любого компьютера и на сайте:

1. В строке продажи сервер уже хранит `cost_price`. Нужен отчёт `GET /api/main/analytics/loss-sales/?date_from=&date_to=` — продажи, где сумма строки после всех скидок меньше `cost_price × qty`: номер, дата, кассир, строки, убыток.
2. Касса тогда перейдёт на этот отчёт вместо локального журнала.

## 5. Предоплата при продаже в долг безналом

Касса 1.17.42 (если включено в настройках) отправляет предоплату долга с разбивкой: `payment.cash_amount` / `payment.card_amount` при `method: "debt"`. Нужно подтвердить:
- безналичная часть не попадает в ожидаемые наличные смены (`expected_cash`);
- в отчёте смены она идёт в «Безнал».

Приёмка: продажа в долг 1000, предоплата 300 безналом → в смене безнал +300, наличные без изменений, долг клиента 700.

## 6. Опт: цена строки по оптовой цене

Касса 1.17.42 даёт продать отдельный товар или весь чек по `wholesale_price` товара: в строке быстрой оплаты уходит `price` = оптовая цена. Нужно:
- сервер принимает такую цену без ошибки и без ручного разрешения, если она равна `wholesale_price` товара;
- в строке продажи — признак `is_wholesale: true`, чтобы отчёты показывали оптовые продажи отдельно.

## 7. Строки продаж «без товара» (доп. услуга)

## 8. Дубли товаров с одним штрихкодом: сервер их создаёт, а потом падает с 500

Тестовый аккаунт NBS, проверка 03.10:

| Штрихкод | Товары |
|---|---|
| 4011100091108 | «Батончик Mars 50г» 0138 (остаток 98) и 0143 (остаток 0, создан 01.10 16:23) |
| 1997079220448 | «Кир машина» 0125 и 0142 |
| 6921734900128 | «Патроны для Степлера» 0108 и 0141 |

Любой `PATCH /api/main/products/<id дубля>/`, даже `{"price": 100.0}` с тем же значением, → **500**. Тот же PATCH основного товара → 200. Из-за этого приёмка без поставщика не может принять дубль.

**Что сделать:**

1. При создании товара (`POST products/`, `create-by-barcode/`, импорт) не давать второй товар с тем же штрихкодом в компании: ответ 400 с id существующего товара.
2. PATCH дубля — не 500, а 400 «штрихкод уже у товара <код>».
3. Отчёт или админка: список дублей штрихкодов в компании, чтобы владелец их удалил или объединил.

Касса 1.17.42: при скане выбирает товар с остатком, а в приёмке объясняет, что есть дубль.

# ТЗ-BE-2026-09. Телеграм-бот на сервере: кнопки, вид ответов, ошибки в заказах, устойчивость ИИ

Дата: 04.10.2026. Касса — версия 1.17.45. Масштаб — 15 000 магазинов, у каждого свой бот.

Ответы покупателям и владельцу формирует сервер NurCRM (режим `server`). Касса бота только настраивает (`settings/`) и показывает статистику. Поэтому всё ниже делается на сервере.

Источник фактов:

- журнал обращений тестового аккаунта NBS (`GET /api/main/telegram-bot/inquiries/`, 28.09–04.10, @kssirBot);
- стресс-тест ИИ 04.10.

## 1. Ошибки в ответах (исправить в первую очередь)

| № | Что видит покупатель | Как должно быть |
|---|---|---|
| 1.1 | «Банан … цена 120.000 сом», «Худи … 1900.000 сом». Читается как «сто двадцать тысяч». | Цена без лишних нулей: «120 сом», «1 900 сом», «45,50 сом». Формировать сервером из `price` товара, а не текстом ИИ. |
| 1.2 | «Товар **Алма** есть в наличии»: звёздочки видны, рядом теги `<b>` работают. ИИ пишет Markdown, а сообщение уходит с `parse_mode=HTML`. | Один формат — HTML. Ответ ИИ перед отправкой переводить из Markdown в HTML (`**x**` → `<b>x</b>`) и экранировать `< > &`. В промпте ИИ указать: «только HTML-теги b, i, без Markdown». |

| 1.6 | «Наш адрес: 1234», «Телефон для связи: не указан». | Пустые и явно тестовые поля магазина не показывать. Если адреса или телефона нет, строку убрать целиком. |

## 2. Кнопки (Telegram Bot API: `reply_markup`)

Сейчас бот отвечает только текстом, кнопок нет совсем. Нужно три вида:

- меню внизу экрана (`ReplyKeyboardMarkup`, `resize_keyboard: true`, `is_persistent: true`);
- кнопки под сообщением (`InlineKeyboardMarkup` + обработка `callback_query`);
- меню команд (`setMyCommands`).

### 2.1 Меню покупателя (внизу экрана, постоянно)

```
[ 🛍 Каталог ]        [ 🔎 Найти товар ]
[ 🧺 Корзина (2) ]    [ 📦 Мои заказы ]
[ 📍 Адрес и время ]  [ 📞 Связаться ]
```

- Язык меню — по языку покупателя (ru/ky, по `language_code` или после «Кыргызча»).
- «Корзина (N)» — число товаров в текущем заказе.
- «📞 Связаться»: кнопка `request_contact` («Отправить мой номер»), чтобы покупатель не набирал номер вручную.

### 2.2 Карточка товара (ответ на «есть кока-кола?», «Алма»)

Одно сообщение на товар: фото (`sendPhoto`, если есть `image_url`) и подпись:

```
<b>Coca-Cola 1,5 л</b>
💰 95 сом · ✅ в наличии
```

Кнопки под ним:

```
[ − ]  [ 1 шт ]  [ + ]
[ 🧺 В корзину ]  [ ✅ Оформить ]
```

- «−/+» меняют количество через `editMessageReplyMarkup` (без новых сообщений).
- Весовой товар: шаги 0,5 / 1 кг.
- Если нашлось несколько товаров — список до 6 штук кнопками по одной в строке («Coca-Cola 1,5 л — 95 сом») и «Ещё ▶».

### 2.3 Оформление заказа

Сводка одним сообщением (сумма — сервером, см. 1.3):

```
🧺 <b>Ваш заказ</b>
Алма — 10 шт × 60 = 600 сом
<b>Итого: 600 сом</b>
Получение: самовывоз · Атай, 0779 124 523
```

Кнопки:

```
[ 🏪 Самовывоз ]  [ 🚚 Доставка ]
[ ✅ Подтвердить ]  [ ✏️ Изменить ]  [ ❌ Отменить ]
```

После «✅ Подтвердить» — «✅ Заказ №9 принят. Сообщим, когда будет готов.» и кнопка «📦 Мои заказы». Кнопки сводки после нажатия убирать (`editMessageReplyMarkup` с пустой разметкой), чтобы заказ нельзя было подтвердить дважды.

### 2.4 Каталог

- «🛍 Каталог» → категории кнопками по 2 в строке.
- Внутри категории — товары по 8 и строка навигации `[ ◀ ]  [ 2 / 5 ]  [ ▶ ]`.
- Листать редактированием того же сообщения (`editMessageText`), а не новыми.

### 2.5 Меню владельца (только в чате `owner_chat_id`)

```
[ 📊 Сегодня ]   [ 💰 Касса ]
[ 🧾 Долги ]     [ 📦 Остатки ]
[ 🛒 Заказы ]    [ 🔔 Прокат ]
```

- Под отчётом «Сегодня» кнопки `[ 🔄 Обновить ]  [ 📈 Неделя ]`.
- Под новым заказом из бота кнопки `[ ✅ Принять ]  [ ❌ Отклонить ]  [ 📞 Позвонить ]`.

### 2.6 Меню команд

`setMyCommands` для двух областей:

- для всех: `/start` «Главное меню», `/catalog` «Каталог», `/cart` «Корзина», `/orders` «Мои заказы», `/help` «Помощь»;
- для чата владельца (`scope: chat`): `/segodnya`, `/dolgi`, `/ostatki`, `/zakaz`, `/prokat`.

Описания на русском и кыргызском (`language_code`).

### 2.7 Общие правила

- На каждый `callback_query` сразу отвечать `answerCallbackQuery` (иначе у покупателя крутятся часики).
- `callback_data` ≤ 64 байт: короткие коды вида `p:<id>:+`, `o:<id>:ok`.
- Сообщение — не больше одного экрана телефона. Эмодзи только в начале строки, по одному.

## 3. Устойчивость ИИ (стресс-тест 04.10)

`POST /api/main/telegram-bot/test-ai/`, тестовый аккаунт NBS, свой ключ Gemini.

| Прогон | Запросов / одновременно | Итог | Время ответа |
|---|---|---|---|
| 1 | 3 / 1 | 3 из 3 ответили | 0,7 с |
| 2 | 40 / 10 | 35 ответили; **5 — HTTP 400 «Все модели Gemini недоступны. Последняя ошибка: HTTP 503»**; часть «успешных» — с **пустым ответом** (`"answer": ""`) | медиана 4,2 с, p95 10,2 с, макс 12,7 с |
| 3 | 30 / 10 | 30 из 30 с текстом | медиана 0,8 с, p95 10,4 с, макс 11,1 с |

Вывод: при 10 одновременных вопросах Gemini волнами отказывает (503) и иногда отдаёт пустой текст. Покупатель в этот момент получает ошибку или пустоту.

Что сделать:

1. Повтор при 503/429/пустом ответе: 2 повтора с паузой 1 и 3 с, затем следующая модель.
2. Пустой ответ ИИ никогда не отправлять. Если ИИ не ответил за 15 с:
   - ответить без ИИ (поиск по каталогу — та же карточка товара из 2.2);
   - или «Секунду, уточняю…», а ответ ИИ прислать следом, когда он придёт.
3. Очередь ИИ на компанию: не больше 3 одновременных запросов к Gemini от одного бота, остальные ждут. Общий лимит на сервер — по квоте ключа.
4. Кэш одинаковых вопросов о товарах на 5 минут («есть кока-кола?» от разных покупателей).
5. `test-ai/` при пустом ответе возвращать `ok: false` с понятной причиной (сейчас `ok: true, answer: ""`). Касса 1.17.46 уже показывает такой ответ как «ИИ вернул пустой ответ».

# ТЗ для бэкенд-программиста NurCRM, часть 10: бот знает размеры и цвета одежды и предлагает их

Дата: 04.10.2026. Заказчик — владелец NurMarket.

**Коротко:** бот на сервере (режим `server`) не видит варианты товара (размер, цвет, остаток размера). Покупатель спрашивает о размерах — бот их выдумывает. Нужно передать варианты в каталог для ИИ, научить бота самому предлагать размеры и цвета (с кнопками) и оформлять заказ на конкретный вариант. Это доделка раздела 4.1 ТЗ части 7 (от 02.10): он пока не сделан.

## 1. Что сейчас не так (живой случай)

Тестовая компания NBS, бот @kssirBot в режиме `server`, журнал обращений `GET /api/main/telegram-bot/inquiries/`:

| Время | Покупатель | Ответ бота |
|---|---|---|
| 04.10 02:16 | «мне нужны кросовки» | «Кросовки есть в наличии, 1200.000 сом… уточните ваш размер (если необходимо)» |
| 04.10 02:16 | «какие размеры есть?» | «…„ТЕСТ Худи с капюшоном оверсайз“ (1900.000 сом), модель представлена **в свободном размере оверсайз**» |

На самом деле у худи 7 вариантов: S, M, L, XL в цветах «Серый» и «Тёмно-синий» с остатками, а у XL тёмно-синего своя цена 1600. Бот этого не знает и выдумывает «свободный размер».

Ещё одна мелочь: цены идут как «1900.000 сом» вместо «1 900 сом». Это раздел ТЗ части 9 про вид ответов.

## 2. Что уже есть и работает (проверено 04.10 на NBS)

- `GET /api/main/products/{id}/variants/` → `[{id, size, color, barcode, quantity, price|null, is_active}]`. `price = null` означает цену товара.
- Продажа одним запросом `POST /api/main/pos/checkout/` принимает позицию с вариантом: `{"product": uuid, "variant": uuid, "qty": "1", "price": "1900.00"}`. Списываются и остаток товара, и остаток размера.
  - Стресс: 17 чеков по 4 одновременно, в каждом по 1–2 размера. Расхождений 0 по 2 товарам и 16 размерам.
  - Повтор с тем же `Idempotency-Key` возвращает 200 с `replayed: true`, второй раз не списывает.
  - Продать больше остатка размера нельзя: ответ 400 «Недостаточно остатка … L Серый. Требуется 2.000, доступно 1.000». Это правильно.
- Прокат `POST /api/rentals/` с `items: [{"variant": uuid}]`.
  - Стресс: 10 прокатов одновременно, номера не повторились, размеры списаны верно.
  - Последнюю вещь три кассира пытались выдать сразу: выдал один, двоим отказ 400. Правильно.
  - Возврат: 12 из 12. Повторный возврат того же проката — 200, остаток второй раз не прибавился.
  - Штраф 50 при залоге 300: вернули 250, удержали 50.
- Касса в следующей версии (после 1.17.47) продаёт одежду одним запросом с `variant`. Раньше был старый путь из 3+ запросов.
- Бот, когда работает в программе (не на сервере), уже передаёт ИИ размеры и цвета найденных товаров. Он сам предлагает размеры на вопрос без названия товара и берёт товар из прошлых сообщений покупателя. Ниже — то же самое для сервера.

## 3. Что нужно сделать

### 3.1. Варианты в каталоге для ИИ-консультанта (покупатели)

1. Для каждого товара из найденных по вопросу (как сейчас ищутся товары) добавлять в каталог строку размеров и цветов **только из активных вариантов**. Формат, который хорошо понимает ИИ (так делает программа):

   `- ТЕСТ Худи с капюшоном оверсайз: 1 900 сом, есть в наличии. Размеры и цвета — L: серый, тёмно-синий; M: серый, тёмно-синий; S: серый; XL: серый, тёмно-синий. Акция: xl тёмно-синий — 1 600 сом.`

   - Размер без остатка: «L: нет в наличии».
   - Цвет без остатка у размера, где другие цвета есть: «M: серый (нет: тёмно-синий)».
   - Свою цену варианта показывать, если она отличается от цены товара: ниже — «Акция», выше — просто цена.
   - Покупателю **не показывать количество штук**, только «есть / нет».
2. Порядок размеров: XS, S, M, L, XL, XXL, 3XL; числовые — по возрастанию (42, 44, 46…). Остальные — по алфавиту.
3. Товар не назван в текущем сообщении (например, «какие размеры есть?», «а синий есть?») — брать товар из **последних 3 сообщений покупателя** в этом чате. Если и там нет, а сфера магазина «Одежда» и в вопросе есть слова о размере или цвете («размер», «цвет», «өлчөм», «түс», size, color, beden, renk, o'lcham, rang) — дать варианты до 5 товаров в наличии.
4. Добавить в инструкцию ИИ-консультанта (системную подсказку). Текст как в программе:

   > Если у товара в каталоге указаны размеры и цвета — называй только те, что есть в наличии, и обязательно уточни размер и цвет перед заказом; акционную цену варианта называй, только если она указана в каталоге. Спросили про одежду и не назвали размер — сам перечисли размеры и цвета в наличии (коротко, по размерам) и спроси, какой нужен; нужного размера или цвета нет — предложи ближайший, который есть. Не говори «свободный размер», если в каталоге указаны размеры.

### 3.2. Кнопки размеров и цветов

Кнопки описаны в ТЗ части 9. Здесь — для вариантов:

1. В ответе про товар с вариантами — inline-кнопки размеров, у которых есть остаток. Не больше 8, в строку по 4.
2. Нажали размер — ответ без ИИ: «Худи, размер M: серый, тёмно-синий — 1 900 сом» и кнопки цветов этого размера.
3. Нажали цвет — «Оформить заказ: Худи M серый, 1 900 сом?» и кнопки «Оформить» / «Другой размер».
4. Остаток размера кончился, пока покупатель выбирал: «Этот размер только что закончился. Есть: …».
5. callback_data — короткий ключ варианта (≤ 64 байт по правилам Telegram), а не текст.

### 3.3. Заказ из бота — на конкретный вариант

1. В строке заказа витрины хранить `variant_id`, а не только товар. Размер и цвет — в составе заказа, видны продавцу на сайте и в программе.
2. Если у товара есть активные варианты, а покупатель размер/цвет не выбрал — заказ не создавать, бот спрашивает размер.
3. Остаток резервировать и списывать по варианту (как продажа в кассе).

### 3.4. Бот владельца

1. «Худи остатки», «какие размеры кончились», «что заказать из одежды» — таблица по размерам и цветам с количеством штук (владельцу количество показывать можно).
2. Список «заканчивается» (порог как у товаров) — и по вариантам: «Худи L тёмно-синий — 1 шт».

### 3.5. Остаток товара и сумма остатков размеров

На NBS остаток худи — 21, а сумма по размерам — 23. У платья — 17 и 19. Так получается, когда товар с размерами продают без варианта: списывается только товар, а размер — нет. Нужно решить на стороне сервера:

- **вариант А (рекомендую):** если у товара есть активные варианты, продажа, прокат и заказ без `variant` → 400 «Выберите размер/цвет». Остаток товара = сумма остатков активных вариантов, сервер пересчитывает сам;
- **вариант Б:** продажу без варианта разрешить, но в карточке товара и в отчётах показывать расхождение «на складе 21, по размерам 23».

Сообщите владельцу, какой вариант выбран: касса подстроится.

### 3.6. Масштаб (15 000 клиентов × касса и программа владельца)

1. Варианты брать из базы одним запросом на все найденные товары (JOIN или `variant__product__in`), а не через HTTP и не по запросу на товар.
2. Кешировать каталог для ИИ вместе с вариантами на 2–5 минут на компанию. Сбрасывать кеш при продаже, прокате, возврате и правке варианта (сигнал после сохранения).
3. Не больше 5 товаров с вариантами в одном ответе: ограничение размера подсказки ИИ.

## 4. Как принять работу

1. Компания NBS, бот в режиме `server`. Покупатель пишет «есть худи?» — бот называет размеры и цвета в наличии и спрашивает, какой нужен. Есть кнопки размеров.
2. Следом «а синий в L есть?» без названия товара — бот отвечает про худи L тёмно-синий: есть / нет.
3. «какие размеры есть?» в начале чата (магазин одежды) — бот перечисляет размеры товаров в наличии и не выдумывает «свободный размер».
4. Размер и цвет кнопками → «Оформить» → в заказе витрины `variant_id`. Остаток размера уменьшился на 1, у других размеров не изменился.
5. Продали на кассе последний M серый — в следующем ответе бота M серого нет (кеш сбросился).
6. Владелец пишет «худи остатки» — таблица размеров и цветов с количеством.
7. Принято решение по п. 3.5. После него остаток товара равен сумме остатков размеров.

## 5. Что передать владельцу

- Что сделано из пунктов 3.1–3.6 и что отложено.
- Решение по п. 3.5 (А или Б).
- Есть ли в API витрины `variants` в карточке товара (ТЗ часть 7, 4.2) — касса и мобильное приложение будут их использовать.

# ТЗ для бэкенд-программиста NurCRM, часть 11: свои сценарии и команды бота, управление ботом из ИИ-советника, фото товаров в ответах

Дата: 05.10.2026. Заказчик — владелец NurMarket.

**Коротко.** Бот магазина работает на сервере (режим `server`, ТЗ части 5, 7, 9, 10). Сейчас владелец может только включать и выключать готовые функции (`PATCH /api/main/telegram-bot/settings/`: команды, ИИ-консультант, голос, сводка смены, напоминания о прокате). Нужно три вещи:

1. **Свои сценарии и команды** — владелец сам добавляет боту ответы: «на слова "доставка", "привезёте" — ответить таким-то текстом», «команда /adres — адрес и график работы».
2. **Управление ботом из программы владельца через ИИ-советник** — владелец пишет советнику «добавь боту команду /akcii со списком акций», советник готовит сценарий, владелец подтверждает кнопкой, программа сохраняет его на сервере через API из п. 1.
3. **Фото товара в ответах** — когда бот (и ИИ-консультант, и обычный поиск) называет товар, у которого есть фото, он присылает фото.

Программа владельца (Windows и Android) со своей стороны будет готова к API из этого ТЗ: экран сценариев и действия ИИ-советника делаются в программе. Без API сервера они не работают.

## 1. Свои сценарии и команды

### 1.1. Что такое сценарий

Сценарий — правило «если покупатель написал X — ответить Y». Два вида:

| Вид | Срабатывает | Пример |
|---|---|---|
| `command` | Сообщение — ровно команда `/имя` (с параметром или без) | `/adres` → адрес и график |
| `keywords` | В сообщении есть хотя бы одно из ключевых слов или фраз (без учёта регистра, ё = е, кыргызские буквы ң ө ү — как есть) | «доставка», «привезёте», «жеткирүү» → условия доставки |

### 1.2. Модель данных (таблица `telegram_bot_scenarios`, на компанию)

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `id` | uuid | — | |
| `company` | FK | — | Компания (из токена, как во всех API) |
| `kind` | `command` \| `keywords` | да | |
| `command` | строка 1–32, `[a-z0-9_]` | для `command` | Без «/». Не совпадает со встроенными командами (`start`, `help`, `segodnya`, `nedelya`, `top`, `abc`, `zakaz`, `ostatki`, `dolgi`, `dolg`, …) → 400 |
| `keywords` | массив строк, 1–30 шт., каждая 2–60 символов | для `keywords` | |
| `title` | строка до 80 | да | Название для владельца («Доставка») |
| `reply_text` | строка 1–3500 | да | Ответ. Разметка Telegram HTML (`<b>`, `<i>`, `<a href>`); сервер проверяет, что HTML валиден для Telegram |
| `buttons` | массив до 6 `{text, url}` или `{text, command}` | нет | Inline-кнопки под ответом |
| `photo_product` | uuid товара | нет | Прислать фото этого товара вместе с ответом (см. раздел 3) |
| `audience` | `customers` \| `owner` \| `all` | да, по умолчанию `customers` | Кому отвечать: покупателям, владельцу (чат `owner_chat_id`) или всем |
| `languages` | массив `ru`, `ky`, `en`, `tr`, `uz` или пусто (все) | нет | Если язык покупателя известен |
| `priority` | число 0–100, по умолчанию 50 | нет | Сработало несколько — берётся с большим приоритетом |
| `is_active` | bool | да, по умолчанию true | |
| `show_in_menu` | bool | нет | Только для `command`: добавить в меню команд бота (`setMyCommands`) с описанием `title` |
| `created_by`, `updated_by`, `created_at`, `updated_at` | | — | Кто и когда (для журнала, п. 2.4) |
| `source` | `owner` \| `ai_advisor` | — | Создано вручную или через ИИ-советник (п. 2) |
| `hits` | число | — | Сколько раз сработал (для статистики) |

Ограничение: не больше 100 сценариев на компанию.

### 1.3. API

Все адреса — под `api/main/telegram-bot/`, доступ — владелец и пользователи с правом «Настройки» (как у `settings/`).

| Метод | Адрес | Что делает |
|---|---|---|
| GET | `scenarios/` | Список: `[{…все поля…}]`, сортировка по `priority` убыв., потом `title` |
| POST | `scenarios/` | Создать. Ответ 201 + объект. Ошибки 400 с полями, как в DRF (`{"command": ["Такая команда уже есть"]}`) |
| PATCH | `scenarios/{id}/` | Изменить любые поля |
| DELETE | `scenarios/{id}/` | Удалить. 204 |
| POST | `scenarios/test/` | `{"text": "а доставка есть?", "audience": "customers"}` → `{"matched": {id, title, kind} \| null, "reply_text": "…", "buttons": […]}`. Ничего не отправляет в Telegram — проверка «что ответит бот» |
| POST | `scenarios/sync-menu/` | Пересобрать меню команд Telegram (`setMyCommands`) из встроенных команд и сценариев с `show_in_menu`. Вызывать и автоматически после каждого изменения команд |

### 1.4. Как бот применяет сценарии

1. Порядок обработки входящего сообщения:
   1. Служебное (кнопки, оформление заказа по ТЗ части 9) — как сейчас.
   2. **Сценарий `command`**, если сообщение — команда и она есть среди активных сценариев компании.
   3. Встроенные команды — как сейчас.
   4. **Сценарий `keywords`** — если нашлось совпадение.
   5. ИИ-консультант / поиск товара — как сейчас.
2. Сценарий отвечает **без ИИ** (быстро и бесплатно): `reply_text` + кнопки + фото (если указано).
3. Учитывается `audience`: сценарий `owner` в чате покупателя не срабатывает, и наоборот.
4. После ответа — `hits += 1`, запись в журнал обращений (`inquiries/`) с отметкой `scenario_id` и `scenario_title` (новые поля в ответе `inquiries/`).
5. Ключевые слова совпадают по границам слов: «доставка» срабатывает на «доставка есть?», но «ока» не срабатывает на «кока-кола».
6. Защита от петель и спама — как для обычных ответов (лимиты части 7).

### 1.5. Сценарии в подсказке ИИ-консультанта

Если покупатель спросил своими словами, а ключевые слова не совпали («а вы домой привозите?»), ИИ должен ответить по сценарию. Для этого в системную подсказку ИИ-консультанта добавлять блок:

```
ОТВЕТЫ МАГАЗИНА (используй их, если вопрос о том же):
• Доставка: <reply_text без HTML>
• Адрес и график: <reply_text без HTML>
```

Только активные сценарии с `audience` = `customers`/`all`, не больше 30, общий размер блока до 4000 символов.

## 2. Управление ботом из программы владельца через ИИ-советник

В программе владельца есть раздел «ИИ-советник» (с версии 1.17.49): владелец пишет вопросы о магазине, ИИ отвечает по его данным. Следующий шаг — советник по просьбе владельца **меняет настройки бота и добавляет сценарии**. Всё, что советник предлагает изменить, программа показывает владельцу карточкой «Применить / Отмена»; на сервер уходит только после «Применить».

### 2.1. Что делает программа (сделаем мы)

- Нейросеть советника получает список действий, которые ей можно предложить: включить/выключить функцию бота (поля `settings/`), создать/изменить/выключить сценарий (п. 1.3).
- Ответ нейросети с действием программа превращает в карточку: «Создать команду /adres: "Адрес: …"», «Выключить голосовые ответы».
- После «Применить» программа вызывает `PATCH settings/` или `POST/PATCH/DELETE scenarios/` с токеном владельца и показывает результат («Готово» или текст ошибки сервера).
- Перед сохранением сценария программа вызывает `scenarios/test/` и показывает владельцу, что ответит бот.

### 2.2. Что нужно от сервера

1. API из п. 1.3.
2. Поле `source` при создании: программа передаёт `"source": "ai_advisor"`. Сервер сохраняет как есть.
3. **Ничего не применять без запроса программы** — сервер сам ИИ-советника не вызывает.
4. Ошибки — понятным текстом на русском (программа показывает их владельцу как есть).

### 2.3. Безопасность

- Менять сценарии и настройки — только владелец и пользователи с правом «Настройки». Кассир без права → 403.
- `reply_text` и `buttons.url`: запрещены `javascript:`, `data:` и ссылки на другие Telegram-боты (`t.me/...bot`); разрешены `https://`, `tel:`, `t.me/<канал или пользователь>`. Иначе 400.
- Токен бота и ключ ИИ через эти API не возвращаются и не меняются.

### 2.4. Журнал изменений

`GET api/main/telegram-bot/audit/?limit=50` → `[{at, user_name, action: "scenario.create"|"scenario.update"|"scenario.delete"|"settings.update", object_title, source: "owner"|"ai_advisor", changes: {поле: [было, стало]}}]`. Программа покажет его в разделе «Телеграм-бот».

## 3. Фото товара в ответах бота и ИИ

### 3.1. Где присылать фото

1. **Ответ ИИ-консультанта**, если в ответе названы товары из каталога, который ему передали (поиск по вопросу): после текста ответа — фото этих товаров.
2. **Ответ на поиск товара без ИИ** (ИИ выключен или нет ключа) — как в ТЗ части 9, п. 2.2: карточка товара — фото с подписью.
3. **Сценарий** с `photo_product` — фото этого товара вместе с ответом.
4. **Чат владельца**: на «покажи фото кока-колы» / «фото <товар>» — фото товара (поиск по названию, как у покупателя).

### 3.2. Как определить, какие товары назвал ИИ

Вариант, который работает в программе: в каталоге для ИИ у каждого товара есть название; после ответа ИИ сервер ищет в тексте ответа названия товаров из переданного каталога (без учёта регистра, по целому названию или по названию без объёма/веса: «Coca-Cola 1,5 л» и «Coca-Cola»). Совпавшие товары, у которых есть фото, — в ответ. Порядок — как в тексте ответа.

### 3.3. Как присылать

- Один товар — `sendPhoto` с подписью `<b>Название</b>\n💰 95 сом · ✅ в наличии` (как карточка в части 9) **после** текстового ответа ИИ.
- 2–5 товаров — одно сообщение `sendMediaGroup` (альбом) с подписью у каждого фото. Больше 5 — только первые 5.
- Фото только у товаров **в наличии** (покупателю нет смысла смотреть на то, чего нет), владельцу — всегда.
- Фото берётся из `image_url` товара. Telegram должен суметь его скачать: адрес публичный, `https://`, ответ `200` с `Content-Type: image/*`, до 5 МБ. Если адрес внутренний или фото больше — сервер сам скачивает и отправляет файлом (multipart), уменьшив до 1280 px по большей стороне.
- **Кэш `file_id`**: после первой отправки Telegram возвращает `photo[-1].file_id` — сохранить его у товара (`telegram_photo_file_id`, сбрасывать при смене фото) и дальше отправлять по `file_id` — быстрее и без повторной загрузки.
- Ошибка отправки фото **не должна** ломать ответ: текст уже ушёл; ошибку — в журнал сервера.

### 3.4. Настройка

Новое поле в `settings/`: `"send_product_photos": true` (по умолчанию `true`). Программа добавит переключатель «Присылать фото товаров» в раздел «Телеграм-бот».

# ТЗ для бэкенд-программиста: сервер удалённой поддержки NurMarket

Дата: 04.10.2026 (дополнено вечером: архив с кодом, установка рядом с nginx, домен, сроки). Заказчик — владелец NurMarket.

**Коротко:** нужно поднять готовый сервер (Docker, код уже написан и проверен) на VPS или на нашем сервере, привязать к нему поддомен с HTTPS и сообщить владельцу адрес. Оценка работы — 2–4 часа.

## 1. Зачем это нужно

Своя замена AnyDesk для поддержки клиентов. Кассир в программе открывает «Тех. поддержка» и получает код из 9 цифр и PIN из 4 цифр. Оператор поддержки входит в браузере на наш сайт поддержки, вводит код и PIN. Кассир нажимает «Разрешить», и оператор видит экран кассы и может управлять мышью и клавиатурой.

Касса и браузер оператора подключаются к серверу сами, исходящими соединениями. Поэтому роутеры и NAT клиентов не мешают, у клиентов ничего настраивать не нужно.

## 2. Что уже готово (писать с нуля не нужно)

Всё лежит в папке `NurRemoteSupport`. Владелец передаёт её архивом **`NurRemoteSupport-server-2026-10-04.zip`** (лежит рядом с этим ТЗ в `docs/`, 85 КБ: только исходники, без собранных файлов; паролей, ключей и журналов в нём нет). Распаковать на сервере в `~/NurRemoteSupport`.

| Что | Где |
|---|---|
| Протокол: все сообщения, ошибки, правила безопасности. Единственный источник правды | `PROTOCOL.md` |
| Сервер-ретранслятор: ASP.NET Core 8, WebSocket, журнал сеансов, вход операторов | `Server/` |
| Страница оператора (HTML+JS, отдаёт сам сервер) | `Server/wwwroot/` |
| Запуск в Docker вместе с Caddy (сам получает HTTPS-сертификат Let's Encrypt) | `deploy/docker-compose.yml`, `deploy/Caddyfile`, `deploy/Dockerfile` |
| Пошаговая инструкция по установке на VPS | `deploy/README.md` |
| Поддельная касса, чтобы проверить без настоящей кассы | `Tools/FakeHost/` |
| Автотесты и нагрузочный тест | `Tools/RelayTests/` |

Проверено 04.10.2026 на Windows-ПК (сервер на 127.0.0.1):

Код подключения в кассе написан и собирается. Клиентам он уйдёт с обновлением, когда будет боевой сервер и мы проверим его с настоящей кассой. Вписывать в кассу достаточно домена: путь `/ws/host` и `wss://` касса добавит сама.

## 3. Что нужно сделать

1. **Сервер.** Отдельный VPS или контейнер на нашей инфраструктуре:
   - Ubuntu 22.04 или 24.04, Docker;
   - минимум 1 ядро, 1 ГБ памяти, 10 ГБ диска;
   - главное — канал (см. раздел 4);
   - размещение — поближе к клиентам (Бишкек или Алматы). Европа тоже подойдёт, но из-за задержки 80–120 мс мышь у оператора будет заметно запаздывать.

   Ставить можно двумя способами:
   - **А — отдельный VPS.** Проще всего: установка строго по `deploy/README.md`, HTTPS получает Caddy;
   - **Б — уже работающий сервер NurCRM, где порты 80/443 занимает nginx.** Caddy тогда не нужен, см. раздел 3а.
2. **Домен.** Поддомен с A-записью на IP сервера, на домене, которым вы управляете. Например, `support.nurcrm.kg` или `support.nurmarket.kg`; имя обязательно сообщить владельцу. Если DNS идёт через Cloudflare, запись делать без проксирования («серое облако»): так проще с сертификатом и нет лишних обрывов WebSocket.
3. **Установка (способ А)** строго по `deploy/README.md`:
   - заполнить `.env` (`RELAY_DOMAIN=…`);
   - выдать права на папку `data` (uid 1654);
   - открыть порты 80 и 443 (TCP и 443/UDP) в ufw и в панели хостера;
   - выполнить `docker compose up -d --build`.
4. **Операторы.** Завести учётные записи сотрудников поддержки: `docker compose run --rm relay add-operator <логин> "<Имя>"` (пароль вводится с клавиатуры, не короче 8 символов). Пароли передать сотрудникам лично, в репозиторий и чаты не писать.
5. **Резервная копия.** Каждую ночь архивировать папку `deploy/data` (операторы, журнал, ключ подписи), хранить 30 дней. Строка cron есть в README.
6. **Перезапуск.** После перезагрузки VPS сервер должен подниматься сам (`restart: unless-stopped` уже стоит, проверить на деле).
7. **Наблюдение.** Проверять `GET https://<домен>/health` (ответ `ok`) раз в минуту любым мониторингом. При недоступности больше 5 минут — уведомление ответственному. Логи контейнеров уже ограничены по размеру (20 МБ × 5).
8. **Безопасность:**
   - SSH только по ключу, вход root по паролю выключить;
   - наружу открыты только 22, 80, 443;
   - сервер `relay` наружу не открыт, к нему ходит только Caddy (при способе Б — ваш nginx через 127.0.0.1);
   - секретов в репозитории нет: ключ подписи токенов создаётся сам в `data/token-secret`.
9. **Обновление сервера** — по разделу «Обновление» в README. Идущие сеансы при этом обрываются, поэтому обновлять вне рабочего времени магазинов.

## 3а. Способ Б: на сервере, где уже работает nginx

Запускается только контейнер `relay` из того же `docker-compose.yml`; HTTPS и WebSocket принимает ваш nginx.

1. Файл `.env` всё равно нужен (`RELAY_DOMAIN=<ваш поддомен>`): без него compose не прочитает файл.
2. Рядом с `docker-compose.yml` создать `docker-compose.override.yml`. Порт открывается **только на 127.0.0.1**: сервер верит заголовку `X-Forwarded-For`, и если порт будет открыт наружу, по нему можно подделать IP и обойти пределы.

   ```yaml
   services:
     relay:
       ports:
         - "127.0.0.1:5080:8080"
   ```
3. Папка данных и запуск только `relay`:

   ```bash
   cd ~/NurRemoteSupport/deploy
   mkdir -p data && sudo chown 1654:1654 data && chmod 700 data
   docker compose up -d --build relay
   curl http://127.0.0.1:5080/health      # ok
   ```
4. Сертификат на поддомен — как у вас принято (например, `certbot --nginx -d <поддомен>`).
5. Сайт в nginx:

   ```nginx
   map $http_upgrade $connection_upgrade {
       default upgrade;
       ''      close;
   }

   server {
       listen 443 ssl;
       server_name <поддомен>;
       ssl_certificate     /etc/letsencrypt/live/<поддомен>/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/<поддомен>/privkey.pem;

       location / {
           proxy_pass http://127.0.0.1:5080;
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection $connection_upgrade;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-For $remote_addr;   # именно $remote_addr: настоящий IP клиента
           proxy_set_header X-Forwarded-Proto $scheme;
           proxy_buffering off;
           proxy_read_timeout 1h;    # сеанс поддержки идёт долго
           proxy_send_timeout 1h;
       }
   }
   ```

   Если `map $http_upgrade` у вас уже объявлен в другом файле, второй раз его не объявлять.
6. `sudo nginx -t && sudo systemctl reload nginx`, затем проверка по разделу 5.

Пункты 4–9 раздела 3 (операторы, копия, перезапуск, наблюдение, безопасность, обновление) для способа Б те же. Только команда обновления — `docker compose up -d --build relay`.

## 4. Масштаб и нагрузка

Масштаб NurMarket: до 15 000 клиентов, на каждом касса и программа владельца.

Соединение кассы с сервером открыто только пока кассир держит открытым окно «Тех. поддержка», а не постоянно. Поэтому нагрузку дают только одновременные сеансы поддержки, а не число клиентов.

| Что | Оценка |
|---|---|
| Один реальный сеанс | 0,5–3 Мбит/с (передаются только изменившиеся куски экрана в JPEG) |
| Канал 100 Мбит/с | примерно 30–50 одновременных сеансов |
| Канал 1 Гбит/с | сотни сеансов; процессор и память не ограничивают (см. нагрузочный тест) |
| Трафик | считать по худшему случаю: 3 Мбит/с × длительность сеанса. 15 минут ≈ 340 МБ исходящего |

Нужно выбрать тариф VPS с достаточным каналом и без жёсткой платы за трафик или с запасом трафика. Сообщите владельцу выбранный тариф и предел одновременных сеансов.

Встроенные пределы сервера (меняются переменными окружения, см. `Server/appsettings.example.json`):
- до 2000 сеансов;
- до 10 ожидающих кодов с одного IP;
- 30 подключений касс в минуту с одного IP;
- 10 попыток входа оператора в минуту с IP.

Если много касс сидят за одним IP (сеть магазинов), пределы на IP может понадобиться поднять.

## 5. Как принять работу

1. `curl https://<домен>/health` отвечает `ok`, сертификат действительный.
2. Страница `https://<домен>/` открывается, оператор входит своим логином.
3. Проверка поддельной кассой с любого Windows-ПК с .NET 8 SDK (из распакованной папки `NurRemoteSupport`): `dotnet run -c Release --project Tools/FakeHost -- --url wss://<домен>/ws/host`. Она покажет код и PIN. Оператор вводит их, видит движущуюся картинку, клики рисуются на ней. После завершения сеанс виден на странице «Журнал».
4. Перезагрузка VPS → через минуту `/health` снова `ok`.
5. Ночная копия `data` появилась и распаковывается.
6. После этого владелец с нашей стороны проверяет сервер настоящей кассой: код, PIN, «Разрешить», управление, завершение. Только потом адрес уходит клиентам в обновлении.

## 6. Что передать владельцу после установки

- Адрес сервера (домен). Его впишем в кассу по умолчанию, и он уйдёт клиентам с обновлением.
- Каким способом поставлено (А — отдельный VPS, Б — рядом с nginx).
- Список логинов операторов (без паролей). Один логин — для владельца, чтобы проверить с настоящей кассой.
- Тариф VPS, канал, предел трафика.
- Кто отвечает за сервер и куда приходят уведомления мониторинга.

## 7. Что НЕ входит в эту работу (на будущее)

- Вход операторов через учётные записи NurCRM (сейчас у операторов свои логины на сервере поддержки).
- Подключение без кассира («неприсмотренный доступ»). В v1 его нет намеренно: каждый сеанс только с согласия кассира.
- Передача файлов и звук.
