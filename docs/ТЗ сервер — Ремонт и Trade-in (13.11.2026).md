# ТЗ бэкенду — «Ремонт и сервис» и «Trade-in / скупка» (13.11.2026)

Для Умара. Решение владельца 13.11: ремонт и trade-in — **не часть сферы «Электроника»**, а две отдельные подключаемые функции Маркетплейса (любой магазин: электроника, телефоны, техника, часы, обувь). Сейчас касса работает **локально** (файлы на ПК кассы, без сервера); это ТЗ — чтобы потом перевести хранение и деньги на сервер без переделки окон. Всё добавляется **новыми полями и новыми адресами** — старая касса и мобилка работают как раньше.

Связанные документы: `Сервер 13.11 — серийные номера, гарантия, Электроника.md` (серийные номера и гарантия уже на сервере — используем), `ТЗ Сфера Электроника (12.11.2026).md` (Б-ЭЛ3 «Приём в сервис», Б-ЭЛ4 «Trade-in» — это они, но теперь отдельными функциями).

## 1. Подключение функций (addons)

- Коды в `GET api/users/company/addons/`: **`kassa-repair`** и **`kassa-trade_in`** (формат тот же: `{code, active, until, source}`; `source` — `key` / `trial` / `support`, как в `ev1311`). Касса уже понимает оба кода (`ServerAddons.Slugs`: `repair`, `trade_in`). Пока сервер их не выдаёт, функцию включает поддержка через заявку «Подключить» (`api/support/addon-requests/`, `item: kassa-repair` / `kassa-trade_in`) или ключ.
- В `GET public/sphere-profiles/` и в `capabilities` компании: `features.repair`, `features.trade_in` — `true`, когда функция включена **и** сервер умеет эндпоинты ниже. Касса до этого работает локально и ничего не шлёт.
- Цены (для Маркетплейса на сайте): подключение + абонплата — решает владелец (в кассе стоит «Платно», суммы в коде нет).
- Сервер **не пускает** запросы к эндпоинтам ниже, если addon выключен: `403 {"code": "feature_off", "feature": "repair"}`.

## 2. Ремонт — квитанции (`repair-orders`)

Модель (поля = то, что касса уже хранит локально):

| Поле | Тип | Заметка |
|---|---|---|
| `id` | uuid | |
| `number` | int | сквозной по компании (и филиалу — вопрос 1); касса показывает `Р-0001` |
| `status` | `accepted` / `in_work` / `ready` / `issued` / `cancelled` | переходы — таблица ниже |
| `client_id` | uuid \| null | клиент NurCRM, если выбран; иначе только имя и телефон |
| `client_name`, `client_phone` | string | телефон ≥ 9 цифр |
| `device` | string ≤ 200 | «Samsung A54», «Часы Casio» |
| `serial` | string ≤ 64 \| null | серийный номер / IMEI; нормализация та же, что у `serial_numbers` |
| `fault`, `equipment`, `note` | string | неисправность, комплектация, заметка |
| `estimate` | decimal(12,2) | ориентир |
| `prepay` | decimal(12,2) | внесено при приёме (см. 2.3) |
| `refunded` | decimal(12,2) | возвращено из предоплаты |
| `final_price` | decimal(12,2) | итог работ, задаётся при `ready` |
| `due_date` | date \| null | срок |
| `accepted_at`, `ready_at`, `issued_at`, `notified_at` | datetime | |
| `accepted_by`, `issued_by` | user | |
| `sale_id` | uuid \| null | продажа-услуга, которой оплачена доплата (2.4) |
| `log[]` | `{at, by, action}` | кто и когда менял статус и деньги |

Деньги — только `decimal`, два знака, округление «от нуля вверх» (как на кассе: `Math.Round(x, 2, AwayFromZero)`).

### 2.1 Эндпоинты

- `POST repair-orders/` — принять (тело: поля без `number`, `status`, дат; ответ — квитанция с `number`). Идемпотентно по `Idempotency-Key` (касса шлёт ключ на каждый денежный POST).
- `GET repair-orders/?status=&q=&from=&to=&page=` — список; `q` ищет по номеру, имени, телефону, устройству, **хвосту серийного номера** (от 4 знаков).
- `GET repair-orders/<id>/`, `PATCH repair-orders/<id>/` (правка полей до статуса `issued`).
- `POST repair-orders/<id>/status/` — `{"to": "in_work" | "ready" | "cancelled", "final_price": "1700.00"}` (`final_price` обязателен для `ready`, если не задан раньше).
- `POST repair-orders/<id>/issue/` — выдача (2.4).
- `POST repair-orders/<id>/notify/` — отметить, что клиенту написали (`notified_at`); сам текст касса формирует и открывает чат WhatsApp сама (отправляет человек).
- `GET repair-orders/by-serial/?serial=` — квитанции по серийному номеру (поиск «чинили ли это устройство»; удобно вместе с `GET serials/?serial=`).

### 2.2 Переходы статусов (сервер обязан проверять, касса уже проверяет)

`accepted → in_work → ready → issued`; `accepted → ready` (мелкий ремонт); `ready → in_work` (вернули в работу, только если нет неподтверждённой оплаты); `accepted/in_work/ready → cancelled` — **только если предоплата полностью возвращена** (`refunded == prepay`). `issued` и `cancelled` — конечные, правка запрещена. Ошибки: `409 {"code": "bad_transition"}`, `409 {"code": "prepay_not_refunded"}`.

### 2.3 Предоплата и возврат — деньги

Сейчас касса: предоплата = **внесение** в смену (`Внесение`, основание «Предоплата за ремонт Р-0001»); возврат = **изъятие** («Возврат предоплаты по ремонту Р-0001»). Деньги идут существующим путём движения денег смены (`ShiftCashFlowSync`), без отдельного денежного адреса.

Для сервера (чтобы связать квитанцию и деньги, а не держать в тексте основания):
- в `POST` движения денег смены принять необязательное `source: {"kind": "repair_prepay" | "repair_refund", "id": "<repair_order_id>"}`; сервер сам пишет в квитанцию `prepay` / `refunded` из подтверждённых движений. Либо (вариант Б) `POST repair-orders/<id>/prepay/` и `POST repair-orders/<id>/refund/` с суммой и `shift` — сервер сам создаёт движение. **Выбор — за вами**, касса подстроится; важно одно: **движение и запись в квитанции — одной транзакцией**, иначе деньги расходятся.
- Возврат не больше `prepay − refunded`; изъятие по-прежнему проверяется на наличные в кассе (запрет «в минус» — уже в ТЗ 1.17.48).

### 2.4 Выдача и оплата работ

Оплата работ — **обычная продажа услуги** (строка «Доп. услуга» в чеке кассы, ничего нового для сервера в денежном пути): сумма строки = `final_price − prepay` (не меньше нуля). Нужно только связать продажу с квитанцией:
- строка корзины/продажи принимает необязательное `repair_order_id` (рядом с `serial_numbers`); при оплате чека сервер ставит `sale_id` в квитанции.
- `POST repair-orders/<id>/issue/` проходит, только если: статус `ready`; доплата (`final_price − prepay`, если > 0) закрыта оплаченной продажей с этим `repair_order_id` (иначе `409 {"code": "payment_missing"}`); переплата возвращена (`refunded ≥ prepay − final_price`, иначе `409 {"code": "overpay_not_refunded"}`). Результат — `issued`, `issued_at`, `issued_by`.
- Сейчас касса не знает, оплачен ли чек (ТЗ: «чек оплачен» подтверждает кассир кнопкой). С сервером — выдача по факту оплаты без ручного подтверждения.

### 2.5 Связь с серийным номером и гарантией

- Если `serial` продавался этим магазином (`GET serials/?serial=`), в ответе квитанции отдать `warranty_active` и `warranty_until` — касса покажет «гарантийный ремонт» и предложит не брать оплату (владелец решит правилом; в первой версии только подсказка).
- Квитанция с серийным номером попадает в историю номера: `GET serials/<sn>/` → `repairs: [{id, number, status, accepted_at}]`.

### 2.6 Права

Новые права (как у остальных разделов): `repair.view`, `repair.manage` (приём, статусы), `repair.refund` (возврат предоплаты). Кассир по умолчанию — `view` и `manage`; возврат — со старшим (PIN), как возврат товара.

## 3. Trade-in / скупка (`trade-in`)

Модель выкупа:

| Поле | Тип | Заметка |
|---|---|---|
| `id`, `number` | uuid, int | в кассе — `Т-0001` |
| `status` | `appraised` / `bought` / `stocked` / `cancelled` | см. 3.2 |
| `client_name`, `client_phone` | string | |
| `client_document` | string ≤ 200 | паспорт / ID клиента (скупка у физлица). **Персональные данные**: хранить зашифрованно, отдавать только с правом `trade_in.view_documents` |
| `device`, `serial`, `condition`, `equipment` | string | серийник обязателен |
| `photos[]` | файлы | по желанию, до 8 (касса пока хранит только пути на своём ПК) |
| `appraisal`, `amount` | decimal(12,2) | оценка (справочно) и сумма выкупа |
| `paid_out` | decimal | выплачено наличными из кассы |
| `credit_confirmed` | decimal | зачтено в оплаченные продажи |
| `credit_pending` | decimal | зачёт в неоплаченном чеке |
| `resale_price` | decimal \| null | цена продажи при оприходовании |
| `product_id` | uuid \| null | товар склада «Б/у …» |
| `log[]` | `{at, by, action, amount}` | |

Инвариант (сервер обязан держать): `paid_out + credit_confirmed + credit_pending ≤ amount`; статус `bought` — когда `paid_out + credit_confirmed == amount` и `credit_pending == 0`.

### 3.1 Эндпоинты

- `POST trade-in/` (создать, `Idempotency-Key`), `GET trade-in/?status=&q=&page=`, `GET trade-in/<id>/`, `PATCH` до статуса `bought`.
- `POST trade-in/<id>/payout/` — `{amount, shift}`: **выплата наличными** — сервер создаёт изъятие смены (движение денег `withdrawal`, `source: {"kind": "trade_in_payout", "id"}`, статья «Закупка у физлиц») и увеличивает `paid_out` **одной транзакцией**; проверка «в кассе хватает наличных» — как у любого изъятия.
- `POST trade-in/<id>/cancel/` — только пока `paid_out == 0` и нет зачётов.
- `POST trade-in/<id>/stock/` — `{resale_price, warehouse?}` — оприходование (3.4).

### 3.2 Зачёт в покупку — деньги не проходят через ящик дважды

Сейчас касса кладёт в чек **отрицательную строку «Доп. услуга»** (итог чека не уходит в минус; кассир подтверждает «чек оплачен»). Для сервера нужен нормальный способ оплаты:
- способ оплаты продажи **`trade_in_credit`**: `payments: [{"method": "trade_in_credit", "amount": "7000.00", "trade_in_id": "<id>"}, {"method": "cash", ...}]`. Это не наличные: в ящик не попадает, в «наличных смены» не учитывается, в отчёте — отдельная строка «Зачёт trade-in».
- Сервер проверяет: `amount ≤ amount_выкупа − paid_out − credit_confirmed − credit_pending`; при оплате чека `credit_confirmed += amount` (**автоматически**, без ручного подтверждения); возврат/аннулирование такой продажи возвращает сумму в остаток выкупа.
- Выручка и маржа: продажа с зачётом — полноценная продажа на полную сумму; зачёт — способ оплаты (поэтому выкуп **не** уменьшает выручку, а учитывается как закупка товара «Б/у» — 3.4). Это отличается от текущего локального варианта (отрицательная строка уменьшает чек) — **вопрос 3**.
- Остаток выкупа после зачёта можно выплатить наличными (`payout`) — как сейчас.

### 3.3 Серийный номер

При создании выкупа проверка: серийник не числится «проданным и не возвращённым» у этой компании (`serial_already_sold`, как в `sn1311`) — иначе предупреждение кассиру (возможно, это наше же устройство, пришедшее в trade-in; тогда оно продаётся снова — возвращённым серийник становится по `trade_in/…/stock/`).

### 3.4 Оприходование как б/у

`POST trade-in/<id>/stock/` создаёт **новый товар** «Б/у <device>» (категория «Б/у», `track_serials: true`, штрихкод = серийный номер), приход 1 шт. **без поставщика** (без долга поставщику и без расхода из кассы — деньги уже прошли выплатой или зачётом), закупочная цена = `amount`, цена продажи = `resale_price`, серийный номер заносится в учёт серийников. Идемпотентно. Сейчас касса делает то же обычной приёмкой без поставщика (создаёт товар и пишет остаток), без серийной записи.

## 4. Отчёты и смена

- X/Z-отчёт: строки «Предоплата за ремонт» (внесения с `source.kind = repair_prepay`), «Выкуп trade-in (выплата)» (изъятия с `trade_in_payout`), «Зачёт trade-in» (способ оплаты, не наличные).
- Журнал ремонтов и выкупов для программы владельца: те же `GET` списки (сейчас владелец видит журнал только того ПК, где лежит файл).
- Telegram-сводка: «ремонтов в работе / готово не выдано», «просрочено» — по желанию (не блокер).

## 5. Перенос локальных данных на сервер

В кассе данные лежат в `repair-orders.json` и `trade-in-records.json` (`%LOCALAPPDATA%\NurMarketKassa`, данные компании). Нужны:
- `POST repair-orders/import/` и `POST trade-in/import/` — пакетная загрузка существующих записей с их `number`, датами и суммами; повторный запуск не плодит дубли (ключ — `device_id + local_id`; `local_id` касса присылает);
- пересечение номеров между кассами (сейчас у каждого ПК своя нумерация) — сервер выдаёт новые `number`, локальный — в `local_number` (вопрос 1).
- После импорта касса переключается на сервер по признаку `features.repair` / `features.trade_in`; до этого — локальная работа, как сейчас.

## 6. Общие требования

- Идемпотентность всех денежных POST (`Idempotency-Key`; касса уже шлёт на денежные пути — `check-money-keys`).
- Офлайн: касса копит операции в очереди; сервер принимает с `client_created_at`; офлайн-приём квитанции не отклоняется (как офлайн-чек в `sn1311`). Выплата и изъятие офлайн — по общим правилам очереди кассы.
- Лимиты: текстовые поля — как выше; список — постранично; фото — до 8 на выкуп, до 5 МБ каждое.
- Аудит: все изменения статусов и денег — в `log` (кто, когда, что), неизменяемо.
- Разделение по компании и филиалу; другая компания квитанций и выкупов не видит.

## 7. Вопросы

1. **Нумерация**: сквозная по компании или по филиалу? Что делать с локальными номерами при импорте (предлагаю новый `number`, старый — в `local_number`).
2. **Предоплата**: вариант А (`source` в движении денег) или Б (отдельные `prepay`/`refund` адреса)? Какой удобнее вам для единой транзакции.
3. **Зачёт trade-in**: способ оплаты `trade_in_credit` (предлагаю, выручка полная) или оставить отрицательную строку (как сейчас на кассе, выручка уменьшается)? Это вопрос учёта — решает владелец с бухгалтерией.
4. **Гарантийный ремонт**: делает ли сервер автоматически цену 0 для устройства «на гарантии» или это только подсказка кассиру (в первой версии — подсказка)?
5. **Документ клиента** (паспорт): нужно ли хранение по закону/политике — можно ли хранить в открытом виде или шифровать; срок хранения.
6. **Фото выкупа**: загрузка файлов на сервер (хранилище, лимит) или только список ссылок.
7. **Права**: подтверждаете набор `repair.*` / `trade_in.*` и что возврат предоплаты — со старшим (PIN).

## 8. Что уже сделано на кассе (для сверки)

- Локальные функции под addon-ключами `repair` и `trade_in` (Маркетплейс → карточки «Ремонт и сервис», «Trade-in / скупка»; «Подключить» — заявка, ключ — как у остальных).
- Деньги — только существующими путями кассы: внесение/изъятие смены с основанием и номером квитанции, строки «Доп. услуга» в чеке (оплата работ +, зачёт −), приём на склад — обычная приёмка без поставщика. **Новых денежных адресов на сервере касса не вызывает.**
- Кнопки в меню кассы и разделы программы владельца — только при подключённой функции.
