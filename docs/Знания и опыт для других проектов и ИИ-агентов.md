# Знания и опыт NurCRM Kassa — для других проектов и ИИ-агентов
Составлено 21.11.2026 по работе над кассой NurCRM (Avalonia 11 / .NET 8; Windows, Linux, Android; мобилка Flutter). Секретов здесь нет (ключи, пароли, токены, телефоны не записаны).

## 1. Как работать с этим владельцем
- Отвечать по-русски, коротко (5–10 строк), без воды; ссылки на отчёты вместо пересказа. «Максимум экономно используй токены».
- Все надписи в программе — на 5 языках: `Tr.T(ru, ky, en, tr, uz)`. Комментарии в коде — по-русски, с датой и причиной (`// 2026-11-21: …`).
- Минимальный дифф в стиле кода. Не менять зависимости, схему базы, сборку без спроса.
- Коммит и выкладка только по просьбе («выгрузи» = выпуск). Автор коммитов только `noreply` (не личная почта), последняя строка: `Co-Authored-By: … <noreply@anthropic.com>`.
- Секреты не печатать и не коммитить: token.txt, ключи подписи, JWT, пароли, списки серийных ключей.
- Решение владельца не пересматривать. Новая задача от владельца важнее старой инструкции: «релиз для клиентов, не prerelease» отменил более раннее «тестовый prerelease».
- Честно сообщать, что НЕ проверено вживую (железо, eKassa/ККМ, весы, устройства). Не писать «готово», если проверена только сборка.
- Своё решение сообщать с рекомендацией, не списком вариантов. Вопросы владельцу — только если решение его.

## 2. Оркестрация агентов (что сработало)
- Один оркестратор + исполнители по узким задачам; каждому — цель, файлы, что уже исключено, формат отчёта (≤20 строк).
- Приёмку делает отдельный агент (сильнее модель), правки — исполнитель. Исполнитель не коммитит и не выкладывает, если ему не сказано.
- Раз в проверку: ListAgents; остановленных лимитом возобновлять через SendMessage; живых не дублировать и не опрашивать.
- Заморозка кода перед выпуском: сборка → unit → ключевые UI-тесты → разбор красных → пересоздание эталонов только после просмотра снимков.
- Ловушка: исполнитель мобилки закоммитил чужое индексированное удаление файла кассы. Перед коммитом смотреть `git status`/`git diff --cached`, добавлять только свои пути (`git add <путь>`, не `-A`).
- Если лимит API кончился — поставить таймер на время сброса и продолжить самому.

## 3. Проект кассы: ловушки
- Тесты: `dotnet test` ТОЛЬКО через `tools/qa/test-safe.ps1` (`-Phase unit|ui|all`, `-Filter`, `-UpdateSnapshots`): он подменяет папку данных и хэшем проверяет, что настоящие `pos_local.db` и `user-settings.json` не тронуты. Прямой запуск блокирует хук. Пути данных — только `AppPaths.Roaming/Local`.
- UI-автоматизация только по hwnd окна, никогда по координатам экрана. Своя экранная клавиатура запрещена (только osk.exe).
- Окна запуска через WMI не передают переменные среды (`NURMARKET_DATA_ROOT`) — касса может открыть настоящую базу.
- Память ПК 7,8 ГБ: при OutOfMemory в XAML — `dotnet build-server shutdown` и повтор. Сборку вести под замком (build-locked.ps1).
- Деньги не округлять во view: есть проверки `check-money-in-views`, `check-money-keys`, `check-tr`.
- Поля форм не должны налезать: у каждого нового окна — тест перекрытия полей.
- Двойное открытие модальных окон, потоки UI и ресурсы темы — AI_HANDOFF.md раздел 10.
- Тестовые снимки (эталоны) нестабильны при совместном запуске; пересоздавать только после просмотра.
- Тесты кассы однажды стёрли товары на живой базе — поэтому хук и test-safe обязательны.
- Название программы видимое — NurCRM; технические имена `NurMarket*` не менять.

## 4. Выпуск (порядок)
1. Версия: касса X.Y.Z → Android versionCode (1.17.92 → 11792).
2. Пакеты только из чистого worktree коммита, не из рабочей копии.
3. Windows: `tools/release/gh_release.py` (нужен token.txt в корне). `gh` не установлен — Android/Linux/мобилка через свои Python-скрипты по API (образцы — папка прошлого выпуска).
4. Linux: `pack_linux.py` даёт `*-adapt.tar.gz` — переименовать в `nurmarket-kassa-linux-x64-X.tar.gz`.
5. Репозитории выпусков: Windows `Nurmarket` (тег `v1.17.X`), `Nurmarket-Android` (`android-X`), `Nurmarket-Linux` (`linux-X`), `Nurmarket-Mobile` (`mobile-X`).
6. После публикации: сверить размер и SHA-256 каждого файла по API, apksigner verify, отпечаток сертификата должен совпасть с прошлым выпуском.
7. Установка на ПК владельца: `tools/qa/deploy_both.ps1`; программа владельца — тот же exe с `--owner`. Перед перезапуском смотреть журнал (владелец может работать в кассе). После установки в журналах не должно быть Error/Critical.
8. prerelease=true — тестовый канал, prerelease=false — клиентам. Что именно — решает владелец.
- Мобилка: свой ключ (не кассы), `key.properties` не коммитится; `flutter analyze/test/build apk --release`; тест `tester_mode_test` требует `AppBuild.build = pubspec+N` и пунктов чек-листа под версию; для клиентского релиза `isTestBuild=false`.
- Android-ключ кассы хранится вне репозитория; все APK подписывать им.
- `sed` ломается на путях с кириллицей (quotepath): `git -c core.quotepath=false`.

## 5. Контракты сервера (облачная CRM, подтверждено на тестовом аккаунте)
- Цены тарифов и модулей — только серверные; касса ничего не хардкодит. Год = 10 месяцев. Пробный: «Мини» 14 дней, остальные 10; модули 7 дней.
- Снятие пакета со Стандарта превращает тариф в «Своё»: Старт + оставшиеся пакеты + модули.
- `pos/checkout/`: тело — shift, client, items (product, qty, price, discount, variant_name до 128 знаков), payment, order_discount; флаги `override_credit_limit`, `accept_late`, `allow_negative_stock`. Без `allow_negative_stock` при нулевом остатке — 409 `insufficient_stock` (у компании своя `negative_stock_policy` forbid|warn|allow; перебивает ли флаг политику — вопрос к бэкенду).
- Идемпотентность: заголовок Idempotency-Key на всех изменяющих запросах; «исход неизвестен» только при обрыве/5xx, отказ по существу (409 и т.п.) ключ забывает.
- Приход упаковками: в строке `sale_unit_id`, qty и цена за упаковку, сервер делит цену на factor; годятся только `for_receipt=true`.
- Возвраты поставщику: правка после 24 ч — владелец/админ с If-Match, Idempotency-Key, X-Confirm-Token (PIN).
- Право `can_delete_products`: без него DELETE товара — 403 `permission_denied`. История: `main/products/{id}/change-history/`, `main/product-history/`. Корзина: `main/trash/`.
- Заголовок `X-NurMarket-Client` касса шлёт всегда (версия в журнале сервера).
- Модули: PUT enable включает сразу, If-Match по version, 409 version_conflict.
- Серверная база знаний техподдержки (kb) пополняется списком разделов и кнопок после каждого выпуска.

## 6. Что владелец решил (продуктовые правила)
- Продажа без остатка разрешена кассиру (настройка «Продавать без остатка», по умолчанию включена). Это надо согласовать с политикой склада на сервере.
- Перенос данных, весы, принтер, сотрудники, ИИ, бот — только в программе владельца; в кассе только операции.
- Данные eKassa «Авангард» не записывать. Весовые этикетки: префикс «вес» и «сумма» не должны смешиваться (общий список префиксов «сумма» раньше перебивал «вес»).
- Аренда по умолчанию только у «Строймага»; у остальных — модуль Маркетплейса. Старые данные проката модуль сам не включают.
- Цель: 1-е место в Кыргызстане по удобству, дизайну и функционалу. Номер 2.0 отложен до идеала.
- Видеоуроки и FAQ — после всех задач, только ru/ky/uz.

## 7. Приёмы отладки
- Заявка «товар пропал/цена изменилась» без журнала не разбирается: брать `%LOCALAPPDATA%\NurMarketKassa\Logs\nurmarket-kassa.log` (владелец — `NurMarketOwner`) за нужное время и заголовок `X-NurMarket-Client` у запроса.
- «Баг на скриншоте»: сначала сверить, не старая ли сборка и не старая ли строка в чеке; но если после второго скриншота проблема осталась — это баг, искать общую причину, а не объяснять.
- Не объяснять баг догадкой: либо воспроизвести, либо сказать «причина неизвестна, нужен журнал».
- Перед удалением или перезаписью смотреть цель; живую базу не трогать (хэши до/после).
- Большие файлы (AI_HANDOFF.md, журналы) — Grep по разделу, не читать целиком. Граф кода: `graphify explain/path/query` из `NurMarketKassa.Avalonia`.
