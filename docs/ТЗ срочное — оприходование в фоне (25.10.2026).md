## 0. Коротко

**Почему «анимация долго грузится».** Это не анимация. В «Склад → Приёмка» кнопка «Оприходовать» ставит `IsBusy = true`, и на всё окно
ложится модальный слой `#60000000` с бегущей полосой «Сохранение данных…» (`WarehouseWindow.axaml`, «Модальный индикатор загрузки»). Слой
снимается только когда закончится ВСЯ цепочка запросов к NurCRM, идущих в основном по очереди: чтение цен до прихода → документ прихода →
PATCH цен → повторное чтение и возврат цен → размеры → полная перезагрузка каталога (если были новые товары, ~50 страниц по 300 товаров подряд) →
запись долга поставщику. На стенде одна приёмка — **12–20 запросов подряд**: при ответе сервера за 0,5 с слой висит **6–10 с**, за 2 с — **22–40 с**,
за 5 с — **55–100 с**, за 20 с — **2–4 мин**. Таймаут одного запроса — 55 с (`NurMarketApiClient`), общего ограничения у склада нет.
Потерянный ответ — 55 с ожидания и ошибка «The request was canceled due to the configured HttpClient.Timeout…».

**Что делаем.** Нажатие «Оприходовать» → снимок строк уходит в **очередь фоновых приходов** (`BackgroundReceivingQueue`, файл на диске) →
список приёмки сразу очищается, окно доступно. Короткий индикатор на кнопке — не дольше 0,5 с; если сервер за 0,5 с не подтвердил, под
кнопкой плашка **«Операция выполняется в фоне — можно продолжать работу»** и значок «в фоне: N». По завершении — лёгкое уведомление
«Приход оприходован» или «Ошибка — Повторить» (данные не теряются). Один приход = один документ: ключ идемпотентности создаётся до отправки и
хранится в очереди, повтор после обрыва сначала ищет уже проведённый приход, очередь переживает закрытие окна и перезапуск программы.

| Где | Что сейчас | Что нужно |
|---|---|---|
| Склад → Приёмка | Модальный слой на всё окно до конца всех запросов (6 с … минуты) | ≤ 0,5 с индикатор на кнопке → фон, список очищен |
| Закупки → Приём товара | Кнопка заблокирована, «Оприходую… не закрывайте окно», ждёт приход + деньги (до 3 мин + 2 мин + 45 с) | То же, деньги (долг/расход/изъятие) — шагом фоновой задачи |
| Нур Советник → закупка по накладной | «Провожу закупку…», нельзя закрыть окно, ждёт приход + каталог + долг | То же; окно закрывается сразу с текстом «в фоне» |
| Ревизия → «Применить» | Свой прогресс «часть N из M», черновик на диске, продолжение с места | **Не трогаем** (см. 1.4) |

### 2.3. Выводы для реализации
1. Ждать сервер в окне нельзя ни в каком виде: даже 0,5 с на запрос — это 6–10 с слоя.
2. `PostAsync` при таймауте/аварии бросает `OperationCanceledException` (фильтр `when (ex is not OperationCanceledException)`) — фоновая задача
   должна считать это «исход неизвестен», а не падать.
3. Ключ `_pendingReceiptKey` в `PurchaseReceivingService` — **один на всё приложение**: если в очереди два прихода, ключ первого затрётся вторым и
   повтор первого уйдёт с новым ключом (дубль). Очереди нужен свой ключ на каждую задачу.
4. Автоповтор прихода после неизвестного исхода безопасен **только после сверки** «нет ли уже такого прихода на сервере» (п. 4.6), пока
   сервер не подтвердил ключ.
5. Состояние повторов (`_pendingStockPatches`, `_createdSalePrice`, `_priceBefore`) живёт в памяти и привязано к объекту строки — для очереди
   на диске его нужно хранить в задаче.

## 3. Целевое поведение (что видит кассир)

1. Нажал «Оприходовать» (или «Провести закупку»): проверки и подтверждение цен — как сейчас (это диалоги, ждут человека).
2. Сразу после подтверждения (без сети, < 50 мс): задача записана в очередь на диск, список приёмки **очищен** и готов к следующей накладной,
   поставщик и «оплачено/в долг» остаются выбранными. Модального слоя нет. На кнопке — короткий индикатор (текст «Оприходую…» + маленькая
   полоса/точки внутри кнопки или справа от неё), **не дольше 0,5 с**.
3. Если за 0,5 с задача завершилась — обычный итог (как сейчас `SummaryText`), только **лёгким уведомлением** (не модальным окном), ошибки —
   плашкой в окне.
4. Если нет — индикатор гаснет, под кнопкой плашка (жёлто-нейтральная, не красная):
   **«Операция выполняется в фоне — можно продолжать работу»** (ru), «Операция фондо аткарылууда — иштей берсеңиз болот» (ky),
   «The operation is running in the background — you can keep working» (en), «İşlem arka planda yürütülüyor — çalışmaya devam edebilirsiniz» (tr),
   «Amal fonda bajarilmoqda — ishni davom ettirishingiz mumkin» (uz). Рядом значок **«в фоне: N»** (кнопка → окно «Приходы в фоне»).
5. По завершении фоновой задачи (даже если окно склада закрыто):
   - успех: лёгкое уведомление «Приход оприходован: N поз. на S сом (поставщик «X»)» + текст долга (`SupplierDebtRecorder.ResultText`);
     остатки в каталоге кассы уже обновлены; значок уменьшился;
   - ошибка: значок красный «ошибка: K», уведомление «Приход не оприходован — откройте „Приходы в фоне“», в окне списка — причина и кнопки.
   Лёгкое уведомление — `MainStatusViewModel.TryShowInfoToast(text)` (плашка под шапкой кассы); если главного окна нет (программа владельца) —
   плашка в окне, где стоит значок, а при его отсутствии — `IUserPrompts.ShowToast` (единственный модальный запасной путь).
6. Окно «Приходы в фоне» (немодальное): строки задач новые сверху — время, откуда (Склад / Закупки / Накладная), поставщик, позиций, сумма,
   **статус**: «в очереди» / «отправляется…» / «повтор через N с (попытка k из 6)» / «ждёт связь с сервером» / «оприходован HH:mm» /
   «частично: принято a из b» / «ошибка: причина». Кнопки у строки: **«Повторить»** (ошибка), **«Вернуть строки в приёмку»** (только строки,
   которые точно НЕ проведены — отказ сервера 4xx или не отправлялись), **«Подробнее»** (ошибки строк), **«Убрать из списка»** (только
   завершённые или после подтверждения «Я проверил остаток вручную» для «исход неизвестен»). Готовые задачи видны 7 дней (не больше 200).
7. Закрытие окна склада/закупок во время фоновой задачи — без вопросов (задача в очереди). Выход из программы при незавершённых задачах —
   одно предупреждение «В фоне N приходов — они догрузятся при следующем запуске программы» с «Выйти» / «Подождать»; не блокировать.
8. После запуска программы (после входа и загрузки компании) очередь догружается сама; значок показывает остаток.

## 4. Архитектура (минимально-инвазивно)

### 4.1. Новый сервис `BackgroundReceivingQueue` (Infrastructure)
Файл: `NurMarketKassa.Infrastructure/Services/BackgroundReceivingQueue.cs` (при желании + `BackgroundReceivingQueue.Store.cs`).
`public sealed class BackgroundReceivingQueue` с `Instance`, по образцу `SupplierDebtRecorder` (журнал JSON, замок файла, повреждённый файл
переименовывается в `queue.bad-<время>.json` и очередь закрывается с понятным текстом).

Хранилище (НЕ SQLite, схему не трогаем):
`Path.Combine(GetFolderPath(ApplicationData), AppMode.DataFolderName, "background-receipts", "queue.json")` — у кассы и программы
владельца разные файлы (`NurMarketKassa` / `NurMarketOwner`), вне папки `data` (её уносит `AccountDataIsolation`), у каждой задачи — `CompanyId`;
`public static string? DataDirOverride` для стендов. Запись атомарная: `queue.json.tmp` → `File.Move(..., overwrite: true)` (или `File.Replace`),
под `lock` + межпроцессный замок `queue.lock` (FileShare.None) на время попытки, как `SupplierDebtRecorder.AcquireFileLockAsync`.
Почему не офлайн-очередь продаж: `OfflinePendingSalesStore` лежит в SQLite (`OfflineDatabase`) — новая таблица = изменение схемы; механизм
повторов `SyncService` заточен под чеки. Переиспользуем подход `SupplierDebtRecorder` (JSON + замок + метки) и `RevisionDraftStore`.

  Attempts, NextAttemptAt, LastError, Errors (List<string> — тексты сервиса, уже на языке кассира)
  ReceiptId, ReceiptTotal, ReceiptAt, Created (кол-во созданных товаров), DebtDone, FinisherDone, Summary, FinishedAt
```
Снимок строк делает статический помощник `JobLine.From(ReceivingLineVm)` / `JobLine.ToVm()` в этом же файле (копия значений; `ToVm`
использует `SetVariants`, `init`-свойства задаются инициализатором). Окна передают в очередь **копию**, а не свои объекты строк.

Публичный API (минимум):
```

### 4.2. Изменение `PurchaseReceivingService.PostAsync` — состояние повторов извне (единственная правка «денежного» файла)
Добавить необязательный параметр в конец: `ReceivingPostState? state = null`. **При `state == null` поведение побайтно прежнее** (все прочие
вызовы — склад старым путём, `BulkScanSession`, закупки до пакета Q4 — не меняются).

`public sealed class ReceivingPostState` (в `PurchaseReceivingService.cs` или рядом): `ReceiptKey`, `ReceiptFirstSentUtc`, `ReceiptOutcome`
(`NotSent | Posted | Rejected | Unknown`), словари по `JobLine.Key`: `StockPatches {Key → (PreStock, Target)}`, `CreatedSalePrice {Key → цена}`,
`PriceBefore {Key → цена}`, `CreateAttempted {Key}`, `LineOutcome {Key → posted|rejected|unknown|check}`; `Func<ReceivingLineVm,string> KeyOf`;
событие `Changed` (очередь сохраняет задачу на диск при каждом вызове — синхронно, до следующего запроса).

Что делает `PostAsync`, когда `state != null`:
1. Ключ прихода: `state.ReceiptKey ??= Guid.NewGuid().ToString()` и `Changed` **до** `CreateSupplierReceiptAsync`; `_pendingReceiptKey` не трогать.
   Отказ по существу (`!PendingIdempotencyKey.IsOutcomeUnknown(ex)`) → `ReceiptOutcome = Rejected`, ключ сбросить; успех → `Posted`;
   иначе → `Unknown`, `ReceiptFirstSentUtc ??= сейчас`.
2. Вместо `ConditionalWeakTable` (`_pendingStockPatches`, `_createdSalePrice`, `_priceBefore`) — словари `state` по `KeyOf(line)`; каждая запись —
   `Changed`. Логика трёх исходов PATCH остатка (стр. ≈ 530–580) — та же, только хранилище другое.
3. Создание товара: перед запросом `CreateAttempted.Add(key)` + `Changed`; если ключ уже был и `ProductId` пуст — сначала
   `FindWarehouseProductByBarcodeAsync(barcode)` (при непустом штрихкоде): найден → взять его id, не создавать второй; штрихкода нет → строка
   `check` с текстом «Товар мог быть создан при прошлой попытке — проверьте склад» (без автосоздания). После получения id — `Changed`.
4. **Сверка перед повтором прихода** (`supplier != null`, `ReceiptOutcome == Unknown`): `ListSupplierReceiptsAsync(1, 50)` → найти приход этого
   поставщика, созданный не раньше `ReceiptFirstSentUtc − 2 мин`, с тем же набором `(product, qty, purchase_price)` (сравнение как в подписи
   `signature`, округления те же). Нашёлся → считать проведённым (id/сумма/время из него), POST не слать. Не прочитали список → POST не слать,
   оставить `Unknown` (повтор позже). Не нашёлся → POST с тем же ключом.
5. `OperationCanceledException`/`TaskCanceledException` от таймаута или аварии (когда `!ct.IsCancellationRequested`): не выпускать наружу, а
   пометить текущий шаг `Unknown` и вернуть `PostResult` с тем, что успели (строки, проведённые до сбоя, — в `PostedLines`). Отмена по `ct`
   (выход из программы) — выпускать, задача останется `sending` → при старте = `Unknown` → сверка.
6. Размеры (`VariantQuantities`): шаг после прихода; отметить строку `variantsDone` в `state` до/после, чтобы повтор не прибавил размеры дважды
   (повтор размеров только если отметки нет; при неизвестном исходе — `check` с текстом «проверьте „Размеры и цвета“»).
Больше в сервисе ничего не менять (тела запросов, цены, наценка, история — как есть).

### 4.3. Воркер (последовательная очередь)
- Один фоновый цикл (`Task.Run`), задачи строго по `CreatedAt` текущей компании: `queued`/`retry_wait` (по `NextAttemptAt`)/`sending`
  (после перезапуска). Одновременно — одна задача (порядок операций над одним товаром сохраняется). Задачи `failed`/`partial`/`needs_check`
  очередь не держат.
- Попытка: `CancellationTokenSource(3 мин)` + токен остановки программы; `PurchaseReceivingService.Instance.PostAsync(оставшиеся строки
  (Outcome pending/unknown) → ToVm, supplier, PaidNow, Employee, ct, PaymentFields, state)`.
- После ответа: строки `posted` → `StockApplied`: остаток плитки = ТЕКУЩИЙ `tile.Quantity + line.Quantity` через
  `StockSyncService.ApplyQuantityToTileOnUi` + `CatalogCacheService.PersistProductStock` (ровно как сейчас в окнах; только `!IsNew`; флаг
  `StockApplied` сохраняется сразу — второй раз не прибавлять). **Остатки — только после подтверждения сервера, не оптимистично**: откат
  оптимистичной прибавки при отказе сложнее и опаснее (кассир мог уже продать «призрачный» товар).
- Новые товары → один фоновый `CatalogCacheService.RefreshFromApiAsync()` (не ждать; не чаще раза в 60 с при пачке задач) +
  `ProductActions.RequestCatalogRefresh` (через событие для окна).
- Шаги после прихода (статус `finishing`, каждый с отметкой в задаче до перехода к следующему): долг поставщику, если `!PaidNow` и Source
  `warehouse`/`invoice` — `SupplierDebtRecorder.RecordAfterReceiptAsync(api, supplier, result, DebtDays, Source == "invoice" ? "invoice" : "receipt", ct)`
  (свой журнал и метки защищают от двойного долга; `DebtDone` — после ответа любой природы, текст в `Summary`); для Source `purchases` —
  зарегистрированный финишер (пакет Q4). Затем `Summary = PurchaseReceivingService.SummaryText(result)` + тексты, статус `done` / `partial`.
- Повторы: исход `Unknown`, сеть/5xx/408/429/таймаут → `retry_wait`, паузы **5 с, 15 с, 30 с, 1 мин, 2 мин, 5 мин** (6 автоматических попыток),
  затем `failed` («Ошибка — Повторить», ключ и состояние сохраняются; «Повторить» обнуляет счётчик попыток, ключ тот же).
  Пауза не меньше `ApiThrottle.RemainingBlock`. Пока `ServerOutageMonitor.IsOutage` / `OfflineModeHelper.SellLocally` / нет токена (401 «Сессия
  недействительна») — статус «ждёт связь с сервером», попытки НЕ расходуются, воркер ждёт `ServerOutageMonitor.StateChanged` (или 30 с).
  Отказ по существу (4xx кроме 408/429) — без автоповтора: строки `rejected`, статус `failed`/`partial`, доступно «Вернуть строки в приёмку».
- Задача другой компании ждёт (в списке: «другая компания — войдите в неё»).

### 4.4. Защита от дублей (деньги и остатки)
- Двойное нажатие: окно ставит флаг на время синхронной части (проверка → подтверждение → `Enqueue`), список после `Enqueue` пуст → кнопка
  выключена; `Enqueue` дополнительно отклоняет задачу с той же подписью (поставщик + строки), созданную < 3 с назад.
- Один приход = один ключ: ключ создаётся в задаче до отправки и хранится на диске; повтор после обрыва → сверка (4.2 п. 4) → тот же ключ.
- Без поставщика — прежние три исхода PATCH остатка (`PreStock/Target` теперь в задаче на диске) — после перезапуска не задвоит.
- Новые товары — `CreateAttempted` + поиск по штрихкоду (4.2 п. 3).
- Долг — `SupplierDebtRecorder` (журнал и метки, не меняем). Расход/изъятие закупок — см. Q4.
- Падение программы между ответом сервера и записью задачи: при старте задача `sending` → `Unknown` → сверка найдёт приход (с поставщиком) /
  три исхода PATCH (без поставщика). Возможный повтор локальной строки истории закупок (`AppendHistory`) — допустим (только локально), описать
  в журнале.

### 4.5. Тонкая привязка в окнах
Окна делают только: снимок строк → `Enqueue` → очистить список → `WaitAsync(id, 0,5 с)` (индикатор на кнопке) → итог или плашка «в фоне» →
подписка на `JobFinished` пока окно открыто (этикетки размеров `ReceivingPosted`, перерисовка истории закупок, `ProductActionPlan.ShowChangedProducts`).
Обработчики событий — через `Dispatcher.UIThread.Post`, отписка в `Closed` (без утечек).

### 4.6. Чего нельзя менять
Формулы и тела запросов прихода/цен/остатков/долга/расхода; `ReceivingPricing`; `PendingIdempotencyKey` (можно только вызывать
`IsOutcomeUnknown`); схему SQLite; `*.csproj`; зависимости; поведение `PostAsync` при `state == null`; ревизию; `BulkScanSession`;
`OfflinePendingSalesStore`/`SyncService`.

## 8. Критерии приёмки (измеримые, на стенде; живая проверка — после, с разрешения владельца)

8.1. **Окно доступно сразу.** Стенд с настоящим `WarehouseWindow` (по образцу `receiving-b1`, сервер — `bg-receiving` с задержкой 20 с):
от нажатия «Оприходовать» до `ReceivingLines.Count == 0` и снятия индикатора — **≤ 0,5 с**; модальный слой `IsBusy` не появлялся ни разу
(проверка каждые 50 мс); через 0,6 с виден текст «Операция выполняется в фоне…» и значок «в фоне: 1»; сразу после этого скан следующего
товара добавляет строку. То же для Закупок (Q4) и Накладной (Q3: окно закрыто ≤ 0,5 с).
8.2. **Быстрый сервер.** Задержка 0 с: итог показан тем же текстом `SummaryText`, плашки «в фоне» нет.
8.3. **Нет дублей при обрыве.** Сервер проводит приход и теряет ответ (F1), режим «сервер НЕ смотрит ключ»: после автоповтора на сервере
**ровно 1 приход**, 1 сделка долга, остаток плитки +qty один раз. Тот же сценарий без поставщика: остаток на сервере = до + qty (один раз).
С новым товаром, ответ на создание потерян: на сервере 1 товар.
8.4. **Перезапуск.** Убить процесс стенда во время `sending` (после POST, до ответа) → новый процесс, `Resume` → задача догружается, приход 1,
статус `done`. Файл `queue.json` после каждого шага читается (не битый); битый файл → `queue.bad-*.json`, очередь закрыта, текст понятный.
8.5. **429 и авария.** 429 Retry-After 5 на POST прихода → повтор не раньше чем через 5 с, приход 1. Нет связи 2 мин → статус «ждёт связь»,
попытки не расходуются; связь вернулась → проведён. 6 неудачных попыток → `failed`, «Повторить» → проведён тем же ключом.
8.6. **Порядок.** Три задачи подряд на один товар без поставщика (+1, +2, +3) при задержке 2 с → на сервере остаток +6, PATCH-и по порядку.
8.7. **Двойное нажатие.** Два клика за 100 мс → одна задача.
8.8. Не изменились: `PostAsync` без `state` (стенд `receiving-b2` и `bg-receiving delays` дают те же числа запросов), ревизия, массовое
добавление. 5 языков у всех новых надписей, светлая и тёмная тема (снимки значка и плашки ru/ky × light/dark).
