## 2. Общие правила для всех пунктов

**О1. Ошибка — всегда JSON:**
```json
{"detail": "Сумма больше долга клиента. Максимум: 190.00", "code": "amount_exceeds_debt",
 "field": "amount", "data": {"max": "190.00"}, "errors": [{"index": 6, "field": "variant", "code": "variant_required", "detail": "…"}]}
```
- **`detail` первым ключом.** Старые разборщики кассы (`RentalsApi.Describe`, `ServerTelegramBotApi.DescribeFields`) показывают первое строковое поле.
- `detail` — по-русски или по `Accept-Language` (`ru|ky|en|tr|uz`). Решения касса принимает только по `code`.
- Прежний формат DRF можно отдавать **дополнительно** — для сайта.
- 5xx — только при настоящем сбое. Бизнес-проверки отдают 4xx с `code`.

**О2. Три разных 404** (с 26.10 это обязательно):
- `route_not_found` — адреса нет;
- `not_found` — объекта нет;
- `idempotency_key_not_found` + `found:false` — ключа повтора нет.

Старый сервер уже отдаёт `{"code":"not_found"}` на любой неизвестный адрес. Поэтому прежнее правило «404 без JSON = адреса нет» больше не действует.

**О3. Ключ повтора (идемпотентность)** — у всех запросов, которые двигают деньги или склад:
- Заголовок `Idempotency-Key` (16–64 символа `[A-Za-z0-9_-]`, касса шлёт 32 hex). Для совместимости — то же значение в теле, `idempotency_key`. Разные значения → 400 `idempotency_key_mismatch`.
- Область ключа — компания + адрес. Хранить **≥ 7 суток** (офлайн-чек лежит в очереди выходные). Если меньше — написать.
- **Ключ проверяется до всех остальных проверок** (права, смена, долг, остаток). Повтор успешной операции → 200, `replayed:true` и прежний ответ.
- Тот же ключ с другим телом → **409 `idempotency_conflict`**. Так решили 25–26.10, 422 не вводим: на любой другой 4xx касса уходит старым путём, и 422 дал бы вторую продажу.
- Первая обработка ещё идёт → 409 `idempotency_in_progress` + `Retry-After`.
- Отказ 4xx (кроме 409, 423, 425, 429) значит «ничего не создано».

**О4. Списки:**
- Формат `{count, next, previous, results}`, параметры `page` и `page_size` (до 500). Порядок стабильный: вторичная сортировка по `id`.
- Страница за последней — пустой `results` (или 404 `page_not_found`), **не 500**.
- Даты `date_from`/`date_to` — включительно, в часовом поясе компании.
- **Старые кассы читают только первую страницу.** Если список, который был массивом, становится постраничным, без параметров он отдаёт всё (до 500) одной страницей.

**О5. Время** — ISO 8601 со смещением (`+06:00`). Даты без времени — `YYYY-MM-DD` в поясе компании.

**О6. Деньги и количества:**
- В ответах деньги — строкой с 2 знаками (`"387378.89"`), количество — строкой до 3 знаков.
- В запросах принимать и строку, и число. Округление до копейки, половина вверх.

**О7. Права** проверяет сервер в каждом API. Без права → 403 `{"detail":"Нет доступа: Товары","code":"permission_denied","required":"can_view_products"}`. Денежные операции хранят и отдают автора (`created_by {id, name}`).

**О8. Совместимость.**
- Новые поля — только добавлением, без переименований и удалений. Переименование делается через приём обоих имён.
- Новые значения перечислений: старая касса разбирает JSON вручную, неизвестное значение обычно показывает как есть. Описать новое значение в схеме до выкатки.
- 429 — JSON с `code` и заголовком `Retry-After`.
- Все фильтры и параметры — в схеме `swagger/?format=openapi`.

## 3. Что касса и мобилка сделают у себя

**До выкатки (касса 1.17.61, мобилка 1.18.5)** — ТЗ «Касса — адаптация к изменениям API сервера (26.10.2026)», пакеты П0–П7:
1. **Признак нового API** — по `capabilities/` (раз в 6 ч) или по `code: idempotency_key_not_found` + `found:false`, а не «404 в JSON». Правило `IsEndpointMissing` («404 без тела») на этом сервере не срабатывает.
2. **Заголовок** `X-NurMarket-Client: kassa/1.17.61` (`owner/…`, `mobile/1.18.5`) во всех запросах `NurMarketApiClient` и мобилки. Сейчас версия серверу не видна.
3. **Разбор `code`:** сначала `code`, потом прежняя подстрока текста. Тексты на 5 языков касса делает по `code` и `required`.
4. **«Расход» в чеке** больше не уходит отрицательной строкой: отдельное изъятие из ящика (`shift_drawer_outflow`) или скидка на чек — по решению владельца. До решения касса не даёт отправить такой чек.
5. **409 в чекауте** делится по `code`. Окончательные (`idempotency_conflict`, `total_mismatch`, `variant_out_of_stock`) — отказ без очереди и без старого пути. 409 без `code` — как сейчас.
6. **`ShiftCashFlowSync`:** на 403 и 400 — «отказано» и сообщение кассиру, без вечного повтора.
7. **Возвраты по строкам** — через `RequestAsync`, чтобы видеть тело ошибки.
8. **Ключ функций:** при 409 и 429 своей проверки ключа нет (сейчас любая ошибка → `TryValidateSerial` на ПК).
9. **Наличная оплата долга без серверной смены** (офлайн-открытая) запрещена: «Смена ещё не записана на сервере». Безнал разрешён.
10. **Прокат** — по `next` (касса понимает и массив, и `results`).
11. **Мобилка:** 409 в продаже — по `code`; поставщиков в должниках отсеивает сама до выкатки Б-14.

**После выкатки (по пунктам — блок «После» в каждом пункте):**
- убираем обходы: «вернуть цену», «Поправка сервера», свой расчёт возврата, ручную сделку прихода;
- переходим на новые адреса;
- пакеты по клиентским ТЗ: Г2 (группа заказов), Т1/Т2 (Telegram на витрине), Л6 (логотип), СФ1–СФ3 (сферы), Ф1 (тариф по `code`);
- мобилка — эталоны и черновик накладной.

**Для проверок витрины одежды** на NBS вернём сферу `clothing` (26.10 у NBS `grocery`) или возьмём другой тестовый аккаунт.

### Б-06 (P0). Закупочная цена не меняет цену продажи (Н-04; ТЗ Склад 24.10 «К Н-04»)
- **Зачем.** Приход с новой закупкой меняет наценку, а следующий `PATCH purchase_price` пересчитывает цену продажи. Пример: закупка 11→1 даёт наценку 36 % → 1400 %; вернули закупку 11 — цена продажи с 15 стала 165. Владелец теряет деньги незаметно. Касса и телефон вторым `PATCH {price}` возвращают цену, но между запросами она неверна на витрине и в других кассах.
- **Сейчас (26.10).** `OPTIONS main/products/{id}/`: в PATCH нет `recalc_price` и `price_changed`.
- **Контракт.**
  1. `PATCH products/{id}/` с `purchase_price` **не меняет `price`**, если `price` не передан. Пересчёт цены — только с `"recalc_price": true`.
     - `markup_percent` при этом — производное: пересчитывается от неизменной цены (решение Умара 25.10 «меняется только наценка» принимаем). На следующих запросах он **не** служит основанием менять `price`.
  2. `PATCH {price, markup_percent}` вместе — `price` берётся как прислан, не пересчитывается (подтвердить письменно).
  3. В ответе `price_changed: true|false` и `markup_percent`.
  4. Приход (`suppliers/{id}/receipt/`) не меняет `price`. Пересчёт — флагом `recalc_price: true` в строке прихода.
- **Права.** `can_view_products` (Б-16).
- **Деньги и повтор.** Цена продажи — деньги магазина. Изменение цены пишется в журнал товара.
- **Совместимость.** Шаг 2, желательное поведение для всех: обход «вернуть цену» у старой кассы станет холостым.
- **Приёмка.** Товар: закупка 11, цена 15.
  - `PATCH {"purchase_price":"1.00"}` → `price 15.00`, `price_changed:false`.
  - Приход с закупкой 1.00 → цена 15.00.
  - `PATCH {"purchase_price":"11.00","recalc_price":true}` → цена пересчитана, `price_changed:true`.
- **После.** Касса и телефон удаляют «вернуть цену» по полю `price_changed`.

- **Зачем.** Мобилка держит черновик накладной только на телефоне (`invoice.draft`, папка `invoice_draft/`, 7 дней). `app-settings` не годится: лимит, нет фото, устройства затирают друг друга.
- **Сейчас.** Нет (`document-drafts` в схеме нет).
- **Контракт.** `GET/POST/PATCH/DELETE api/main/document-drafts/`:
  - поля:
    - `type` (`receipt|revision|order`), `title`, `supplier?`;
    - `lines[{product?, name, barcode?, qty, purchase_price?, price?, variant?}]`;
    - `photos[]` (id медиа, `purpose:"invoice"`, Б-37);

  - `PATCH` с `If-Match` → 409 `version_conflict` + текущие данные;
  - лимит 500 строк и 256 КБ; (по желанию) `POST …/{id}/lock/` на 5 мин.

  Проведение — обычным `suppliers/{id}/receipt/` с `draft_id`; после него черновик удаляется.
- **Права.** Автор и владелец.
- **Деньги и повтор.** Проведение — с ключом (Б-17).
- **Совместимость.** Шаг 2.
- **Приёмка.** Черновик с телефона открывается на ПК; правка на ПК видна на телефоне; одновременная правка → 409 у второго; через 7 дней черновик пропадает.

**Источник:** «ТЗ Вид магазина — Хозмаг и стройматериалы (26.10.2026)» (`docs/`). Там же — что касса и мобилка делают без сервера (пакеты ХМ1–ХМ13, МХ1–МХ5) и вопросы владельцу.

**Требование владельца (26.10.2026):** «добавь вид магазина хозмаг или строительный маркет!»

**Пунктов — 10** (Б-52…Б-61). Формат и общие правила О1–О8 — как в разделах 2 и 4. Новые поля — только добавлением (шаг 2). Всё, что меняет цену или количество в уже существующем запросе, — за отдельным флагом компании **`hardware_2026_11`**: включается только компаниям с `market_profile = "hardware"` и только для клиентов с `X-NurMarket-Client` не ниже версии, которую назовёт касса.

**Факты по схеме 26.10** (сохранённая `openapi.json`, без новых запросов):
- `CompanyUpdate.market_sphere` — `enum ["grocery","clothing","services"]`, значение `hardware` будет отклонено;
- `Product.unit` — свободная строка;
- `ProductPackage {id, name, quantity_in_package, unit, piece_unit_price}` — своего штрихкода и направления «товар = штука, продаём коробкой» нет;
- `SaleItem.quantity` — строка-десятичное;
- `ProductCharacteristics` — только габариты, вес и `description`;
- у `Client` нет уровня цены и лимита долга;
- есть `GET main/recommendations/pairs/`, `upsell_priority`, `upsell_excluded`, но связи «товар → сопутствующий товар» вручную нет.

Модули `api/warehouse/*` и `api/building/*` (сектора сайта «Склад» и «Строительство») касса **не использует**. Розничный хозмаг — это профиль магазина (`main/products`, `pos/*`), а не сектор «Строительство» (вопрос 1 ниже).

### Б-52 (P1). Дробное количество штучного товара: правило, шаг, минимум, единица кодом
- **Зачем.** Хозмаг продаёт 2,5 м кабеля и 1,44 м² плитки. Касса и мобилка округляют штучный товар до целого: так сделано, потому что правило сервера для `is_weight=false` неизвестно. Сервер в части мест сливает строки (Б-50, 19.8) и считает акции по сумме.
- **Сейчас (26.10).** `SaleItem.quantity` — decimal; дробное для `is_weight=false` не описано; `unit` — текст.
- **Контракт.**
  1. **Подтвердить письменно**: `quantity` до 3 знаков для `is_weight=false` принимается и одинаково проводится в `pos/carts/{id}/items/`, `checkout/` и `checkout/batch/`, возвратах (`returnable_qty`), приходе поставщика, ревизии (`quantity_fact`, Б-41), перемещениях, `stock/movements/`, заказах витрины (Б-34), журнале движения (Б-27). Округление: количество — 3 знака, сумма строки — до копейки, половина вверх (О6).
  2. Поля товара (необязательные, `null` = как сейчас):
     - `unit_code` ∈ `pcs|m|m2|m3|kg|l|t|pack|box|bag|roll|sheet|set|pair` (рядом со старым `unit`-текстом, который не меняется);
     - `quantity_step` (decimal, > 0, например `0.1`);
     - `min_sale_quantity` (decimal ≥ 0);
     - `quantity_decimals` (0–3).
  3. Проверка в продаже и чекауте **только под флагом** `hardware_2026_11` и только для новых клиентов: не кратно шагу → 400 `quantity_step_mismatch` (`index`, `data:{step}`), меньше минимума → 400 `quantity_below_min` (`data:{min}`). Старые клиенты — без проверки.
  4. Строки одного товара с дробным количеством **не сливать** с соседними, если у них разная цена, скидка или упаковка (Б-53). Правило слияния — написать.
  5. (по желанию) `GET api/users/company/devices/` → `[{client:"kassa/1.17.61", last_seen_at, user}]` по заголовку `X-NurMarket-Client` (Б-01). Касса предупредит владельца, что в магазине есть старые кассы, округляющие метры.
- **Права.** Поля товара — `can_view_products` (Б-16). Список устройств — владелец.
- **Деньги и повтор.** Сумма строки считается сервером из количества и цены; ключ повтора — как в Б-10.
- **Совместимость.** Поля — шаг 2. Проверки шага и минимума — шаг 3 под `hardware_2026_11`. Старая касса шлёт целое: проходит, как сейчас.
- **Приёмка (NBS, 1 сом).** Товар «Тест м» (`unit_code=m`, `is_weight=false`, `quantity_step=0.1`) → продажа 2,5 → `line_total "2.50"`, остаток −2,5 → возврат 1,5 → `"1.50"`, остаток +1,5 → повтор ключом → `replayed:true`. С флагом: 2,55 → 400 `quantity_step_mismatch`; 0,5 при `min_sale_quantity=1` → 400 `quantity_below_min`.

### Б-53 (P1). Единицы продажи и закупки: коэффициент, свой штрихкод, своя цена
- **Зачем.** «Саморез — штука, продаём и коробкой 200 шт»; «цемент — кг, продаём мешком 50 кг»; «плитка — м², продаём упаковкой 1,44 м²». Сейчас `packages` описывает обратное направление («товар — пачка, продаём штуки»), у упаковки нет штрихкода. Доп. штрихкод с «кол-вом в упаковке» — только описание, в продаже касса его не умножает.
- **Сейчас (26.10).** `packages` (только чтение) + `packages_input`; `alternate_barcodes[{barcode, name, quantity}]`.
- **Контракт.**
  1. Новое поле товара `sale_units[]` (старое `packages` не меняется):
     `{id, name, unit_code, factor, barcode?, price?, wholesale_price?, for_sale:true, for_receipt:true, is_default_sale:false, is_default_receipt:false, sort_order}`:
     - `factor` — сколько базовых единиц товара в одной такой единице (200 шт, 50 кг, 1.44 м²), decimal до 4 знаков;
     - `price` — своя цена единицы (если `null` — `factor × price` товара);
     - `barcode` уникален в компании вместе с `barcode` и `alternate_barcodes` (409 `barcode_taken`).
  2. Запись — `sale_units_input` (полная замена списка) в `PATCH products/{id}/` и при создании. Удаление единицы, которая есть в открытой корзине, → 409 `sale_unit_in_use`.
  3. `GET products/barcode/{код}/` для штрихкода единицы → `{product, sale_unit, matched_by:"sale_unit_barcode", quantity: factor}` (как Б-50 для варианта).
  4. Строка продажи: `sale_unit_id` + `quantity` **в единицах продажи** (3 мешка). Сервер списывает `quantity × factor` базовых, цена строки — `price` единицы. В ответе строки: `sale_unit {id, name, factor}`, `base_quantity`.
  5. Приход поставщика и заказ поставщику: `sale_unit_id` в строке. Остаток — в базовых, закупочная цена базовой = цена строки / `factor`. Рекомендуемый заказ округляет до `is_default_receipt` (связь с `pack_size`, Б-45).
  6. Возврат по строке с `sale_unit` — в тех же единицах (`returnable_qty` в единицах продажи).
  7. Публичная карточка витрины — `sale_units` (без закупочных полей), а также `unit_code`, `quantity_step`, `min_sale_quantity` из Б-52.
  8. Витрина: заказ `items[{product, sale_unit?, qty}]`; резерв — в базовых.
- **Права.** Как у товара. Публично — только продажные поля.
- **Деньги и повтор.** Цена единицы — серверная; ручная цена строки — как сейчас (`price_manually_edited`). Ключ — Б-10.
- **Совместимость.** Шаг 2: старые клиенты `sale_units` не видят и продают базовую единицу, как сейчас. Строка с `sale_unit_id` в истории для старой кассы — `quantity` в базовых (`base_quantity`) **в старом ключе `quantity`**? Ответить, какой ключ увидит старая касса (вопрос 2 ниже). Предложение: `quantity` = в единицах продажи только для клиентов ≥ версии кассы; для остальных `quantity` = базовые и `unit_price` = цена базовой.
- **Приёмка.** «Саморез» (цена 2 сома/шт) + `sale_units: [{name:"Коробка", factor:200, barcode:"2000000000017", price:"350.00"}]` → скан коробки → строка 1 × 350, остаток −200 → возврат коробки → +200. Мешок 50 кг × 3 → остаток −150 кг. Приход 10 коробок по 300 → +2000 шт, закупка 1,50.

### Б-55 (P1). Уровни цен, цена клиента, цены от количества
- **Зачем.** Прораб и бригада покупают по своей цене; «от 10 мешков — 480». Сейчас одна `wholesale_price` и ручной переключатель «Опт».
- **Сейчас (26.10).** Нет. У `Client` нет уровня цены.
- **Контракт.**
  1. Справочник компании `GET/POST/PATCH api/main/price-levels/` → `[{id, code, name, sort_order, is_system}]`. Системные: `retail` (= `price`), `wholesale` (= `wholesale_price`). Своих — до 5 (например «Прораб», «Бригада»).
  2. Товар: `prices[{level, price}]` (для `retail`/`wholesale` — зеркало старых полей), `volume_prices[{min_qty, price, level?}]` (min_qty в базовых единицах или в `sale_unit` — указать).
  3. Клиент: `price_level` (id или `null` = розница).
  4. Продажа: клиент в корзине → сервер считает цену строки по уровню клиента, затем по объёму (большее из скидок или «лучшая цена» — правило написать). Ответ строки: `price_source: retail|wholesale|level:<code>|volume|manual`, `base_price`.
  5. `is_wholesale` строки — как сейчас (ручной опт важнее уровня клиента).
- **Права.** Справочник и цены — владелец и `can_view_products`. Уровень клиента — `can_view_clients`. Кассир не меняет уровень клиента без права.
- **Деньги и повтор.** **Опасно:** если сервер начнёт ставить цену по уровню клиента, а старая касса показала розничную — сумма в кассе и на сервере разойдётся (Б-15, `total_mismatch`). Поэтому пересчёт по уровню — **только** для клиентов с `X-NurMarket-Client` ≥ версии, которую назовёт касса, и под флагом `hardware_2026_11`. Для старых — как сейчас.
- **Совместимость.** Справочник и поля — шаг 2. Цена по уровню в продаже — шаг 3 (флаг).
- **Приёмка.** Уровень «Прораб» 480, розница 520 → продажа клиенту-прорабу новой кассой → строка 480, `price_source:"level:foreman"`; старой кассой (без заголовка) → 520, как в кассе; `volume_prices [{min_qty:10, price:470}]` → 10 мешков по 470.

### Б-56 (P2). Клиент-прораб: лимит долга, срок по умолчанию, объекты
- **Зачем.** Строительный маркет даёт прорабам в долг по объектам. Нужно видеть, сколько должен по объекту, и не отпускать сверх лимита.
- **Сейчас (26.10).** Долг со сроком «Вернуть до …» есть; лимита у клиента и «объекта» нет.
- **Контракт.**
  1. Клиент: `credit_limit` (decimal или `null`), `default_due_days` (int или `null`), `client_kind` ∈ `person|foreman|team|company`.
  2. Объекты: `GET/POST/PATCH clients/{id}/objects/` → `[{id, name, address, is_active}]`.
  3. `object` (id, необязательно) в продаже, долге, оплате долга, клиентском документе (Б-28). Должники `?include=objects` → долг по объектам.
  4. Продажа в долг сверх лимита → 409 `credit_limit_exceeded` (`data:{limit, debt, requested}`) — **только** для новых клиентов (под флагом); владелец может провести с `override_credit_limit:true` (право `can_override_credit_limit`).
- **Права.** Лимит — владелец. Объекты — `can_view_clients`.
- **Деньги и повтор.** Отказ 409 — ничего не создано. Ключ — Б-10.
- **Совместимость.** Поля — шаг 2; проверка лимита — шаг 3.
- **Приёмка.** Лимит 1000, долг 900 → долг 200 → 409; с `override` владельцем → проходит; должники по объекту показывают сумму объекта.

### Б-57 (P2). Характеристики-атрибуты, поиск и фильтры по ним
- **Зачем.** Хозмаг ищет «труба 20», «ВВГ 3×2,5», «RAL 9016»; витрине нужны фильтры по диаметру и длине; калькулятору — «м² в упаковке» и «расход на м²».
- **Сейчас (26.10).** `characteristics` — габариты, вес и `description`.
- **Контракт.**
  1. Товар: `attributes[{key, value, unit?}]` (до 30; `key` — `[a-z_]{1,32}`, `value` — строка ≤ 64 или число).
  2. Справочник ключей компании `GET/POST api/main/attribute-keys/` → `[{key, name{5 языков}, type:"number|text|enum", unit?, options?[], filterable}]`. Типовые для `hardware`: `diameter_mm`, `length_m`, `width_mm`, `thickness_mm`, `section_mm2`, `cores`, `color_ral`, `grade` (марка), `gost`, `pack_area_m2`, `consumption_per_m2`, `coverage_m2_per_l`, `layers`.
  3. Поиск `products/list/?attr.diameter_mm=20&attr.color_ral=9016`; полнотекстовый `search` ищет и по значениям атрибутов.
  4. Витрина: `attributes` в публичной карточке; `showcase/facets/` (Б-33) отдаёт `attributes[{key, name, values[{value, count}]}]` для `filterable`.
- **Права.** Как у товара; ключи — владелец.
- **Деньги и повтор.** —
- **Совместимость.** Шаг 2. `characteristics` не меняется.
- **Приёмка.** Труба с `diameter_mm=20` находится по `attr.diameter_mm=20` и по поиску «20»; `facets` считает `count`.

### Б-59 (P2). Сопутствующие товары и аналоги вручную, с нормой
- **Зачем.** «К плитке — клей, затирка, крестики» и «нет этого — возьмите аналог». Статистика пар (`recommendations/pairs/`) новому магазину ничего не даёт.

- **Права.** Владелец и `can_view_products`.
- **Деньги и повтор.** —
- **Совместимость.** Шаг 2.

### Б-60 (P2). Заказ покупателя: резерв, предоплата, доставка, связь с заказом поставщику
- **Зачем.** «Нет 40 мешков — возьмём предоплату 50 %, закажем у поставщика, позвоним». Сейчас это делают КП/счётом и долгом, а товар никто не резервирует.
- **Сейчас (26.10).** Резерв только у заказа витрины (Б-34, не выкачен); заказ поставщику — Б-44.
- **Контракт.**
  1. `GET/POST/PATCH api/main/customer-orders/`:
     - `{number, client, object?, items[{product, sale_unit?, qty, price}], status: draft|confirmed|reserved|waiting_supply|ready|delivered|closed|canceled}`;
     - `prepayment {amount, method, shift}`;
     - `delivery {type: pickup|delivery, address?, floor?, lift?, date?, price?}`;
     - `due_date`, `source: kassa|showcase|bot`.
  2. `reserve/` — резерв того, что есть (как Б-34); нехватка → строка `waiting_supply` и (по кнопке) черновик заказа поставщику Б-44 с `customer_order`.
  3. Приход по связанному заказу поставщику → строки `ready` + событие `customer_order_ready` (Б-46) и сообщение клиенту (Б-30, если согласие).
  4. Выдача (`deliver/`) — обычная продажа с зачётом предоплаты одной транзакцией. Отмена — возврат предоплаты по правилам Б-04.
  5. Заказ с витрины с «Нужна смета» (`needs_quote:true`) приходит как `draft` с `source:showcase`.
- **Права.** `can_use_pos` — создать, принять предоплату, выдать; отмена с возвратом денег — владелец или право.
- **Деньги и повтор.** Предоплата — движение в смене (как предоплата долга, Б-03/Б-07: **не выручка до выдачи**). Ключ на `POST`, `reserve`, `deliver`, `cancel` (Б-10).
- **Совместимость.** Шаг 2 (новые адреса).
- **Приёмка.** Заказ 40 мешков при остатке 25: 25 в резерве, 15 `waiting_supply`; предоплата 1 сом → `expected_cash +1`, выручка без изменений; приход 15 → `ready`, событие; выдача → продажа на остаток суммы, предоплата зачтена; повтор `deliver` ключом → `replayed:true`.

### Б-61 (P3). Партии с оттенком и калибром; отрезной товар и обрезки
- **Зачем.** Плитка и краска разных партий отличаются цветом — в одном чеке нужна одна партия. Бухта кабеля и труба оставляют обрезки, которые продают дешевле.

### Б-62 (P2). Задачи сотрудникам: приоритет, напоминание, автор, отчёт, фильтры, уведомление
- **Зачем.** Владелец голосом: «поставь Нурлану задачу пересчитать полку до завтра, срочно», «кто что не сделал за неделю». Сотрудник видит свои задачи на телефоне и отмечает «сделано» с отчётом. Сейчас мобилка вынуждена писать приоритет и напоминание служебной строкой в `description`, а «мои задачи» — искать перебором всех страниц.
- **Сейчас (26.10).** Поля — выше. Нет `priority`, `remind_at`, `created_by`, `completed_at`, отчёта, фильтров по исполнителю и статусу, уведомления.
- **Контракт.**
  1. Поля `Task`: `priority: low|normal|high` (по умолчанию `normal`), `remind_at` (дата и время), `created_by` (только чтение), `completed_at` (ставит сервер при `done`), `report` (текст ≤ 2000), `report_files` (фото, как `building/tasks/{id}/files/`), `source: web|pos|mobile|voice_ai|telegram`.
  2. Статус `overdue` **не хранить** — фильтр `overdue=true` (`due_date` раньше сегодня и не `done`).
  3. Фильтры: `GET tasks/?assigned_to=<id>|me&status=&overdue=&due_from=&due_to=&priority=&ordering=due_date`.
  4. `GET tasks/summary/?date_from&date_to` → по сотрудникам `{assigned_to, total, done, in_progress, pending, overdue, done_on_time}` — отчёт «кто что не сделал».
  5. Уведомление исполнителю при создании и в `remind_at`: Telegram-бот компании (если сотрудник привязан) и событие для будущих пушей.
  6. `POST tasks/` с `Idempotency-Key` → повтор отдаёт ту же задачу.
- **Права.** Создаёт, назначает и удаляет — владелец, администратор, `can_view_employees` (или новый `can_manage_tasks`). Исполнитель меняет **только** `status`, `report`, `report_files` своей задачи (иначе 403 `only_status_for_assignee`).
- **Деньги и повтор.** Денег нет. Ключ повтора на создание.
- **Совместимость.** Шаг 2. После выкатки мобилка перестанет писать служебную строку `⟦nm: …⟧` в `description`. Сервер её не трогает.
- **Приёмка.**
  - Задача владельца кассиру с `priority=high` и `remind_at` → кассир видит её в `?assigned_to=me`, Telegram приходит в `remind_at`.
  - Кассир меняет `due_date` → 403; ставит `status=done` с `report` → 200, `completed_at` заполнен.
  - Повтор `POST` тем же ключом → одна задача.
  - `summary` за неделю совпадает с ручным подсчётом.

### Б-63 (P2). Зарплата: штрафы, премии, авансы как записи периода, сменная ставка, выписка по сотруднику (дополняет Б-24)
- **Зачем.** «Оштрафуй Айбека на 500 за опоздание», «аванс 10 000», «сколько я должен Айбеку за октябрь» — ответ должен совпадать на сайте, ПК и телефоне. Сейчас штрафов нет совсем, аванс — просто расход «Аванс: …», а «должен» мобилка и ПК считают по меткам в названиях расходов («проверено частично»).
- **Сейчас (26.10).** `tab=salary` даёт начисление по схеме. `market-salary/payouts/` → 404 (Б-24). Сменной ставки в `pay_scheme` нет.
- **Контракт.**
  1. В Б-24 `kind` добавить `fine` (штраф) и `bonus` (премия) — это **записи начисления без движения денег**: `{employee, kind, amount, date, period_from, period_to, reason}`. `advance` и `salary` — выплаты с движением денег (как в Б-24).
  2. В `pay_scheme` добавить варианты `per_shift` и `per_shift_plus_percent`, поле `per_shift_amount`. Смены считаются по `construction/shifts/` сотрудника: только закрытые, день — по дате открытия.
  3. `GET api/main/market-salary/statement/?employee=&period_start=&period_end=` → `{accrued_base, accrued_percent, accrued_per_item, accrued_per_shift, bonuses, fines, advances, paid, left, shifts, hours, lines:[…]}`. Одно число «осталось к выплате» для всех клиентов.
  4. `tab=salary` по сотруднику — те же `bonuses`, `fines`, `advances`, `paid`, `left`.
  5. Отмена записи — `DELETE …/{id}/` (для выплаты — с обратным движением, как в Б-24). Повтор — по `Idempotency-Key`.
  6. Ошибки — как в Б-24, плюс `fine_exceeds_accrued` (предупреждение, не отказ).
- **Права.** Смотреть — владелец и `can_view_salary`. Создавать и отменять — владелец и `can_edit_salary`.
- **Деньги и повтор.** `fine` и `bonus` — без движения денег. `advance` и `salary` — как в Б-24, ключ создаётся первым.
- **Совместимость.** Шаг 2. Старые расходы с меткой `[#user период]` учитываются в `paid` (до выкатки касса и мобилка пишут так).
- **Приёмка.**
  - Штраф 1 сом → `fines 1.00`, `left` −1, касса без движения.
  - Аванс 1 сом → `advances 1.00`, расход «Зарплата», `left` −1.
  - Повтор аванса тем же ключом → `replayed:true`.
  - Сменная ставка 100 × 3 закрытые смены → `accrued_per_shift 300`.
  - Старый расход с меткой `[#user 01.10.2026–31.10.2026]` попал в `paid`.

### Б-76 (P1). Единый приём вебхуков: подпись, дедупликация, очередь; запись бота Telegram в ящик
- **Зачем.** Сообщения не теряются и не дублируются, чужие вебхуки отбрасываются. Ответы серверного бота и ИИ видны в ящике.
- **Сейчас (26.10).** Несколько приёмников (`telegram-bot/webhook/{bot_uuid}/`, `consalting/wazzup|greenapi|whatsapp/webhook/`, `integrations/whatsapp/webhook/`).
- **Контракт.**
  1. `POST api/inbox/webhooks/{channel_uuid}/` (GET — для верификации Meta `hub.challenge`). Старые адреса работают и пишут туда же.
  2. Подпись проверяется **до разбора тела**:
     - Meta — `X-Hub-Signature-256`;
     - Telegram — `X-Telegram-Bot-Api-Secret-Token`;
     - Wazzup и 360dialog — их схема.
     Не сошлось → 401, событие в журнал `signature_ok=false`.
  3. Ответ ≤ 2 с. Тело — в `WebhookEvent {provider_event_id, payload (≤ 30 дней), received_at, processed_at, error}`, обработка — воркером.
  4. Дедупликация:
     - входящие — по `(channel, external_message_id)`;
     - статусы — монотонно `sent < delivered < read`, `failed` — отдельно;
     - статус раньше сообщения — сохранить и применить, когда сообщение появится.
  5. Порядок: внутри диалога — последовательно, разные диалоги — параллельно.
  6. Исходящая очередь:
     - повторы 1 с, 5 с, 30 с, 2 мин → `failed` с `error.code`;
     - лимиты Telegram — 1 сообщение в секунду на чат, `retry_after`; Meta — 429 и `Retry-After`.
  7. **Серверный Telegram-бот:** каждое входящее и каждый ответ бота или ИИ пишутся в диалог (`sender=ai` или `system`). Когда отвечает человек (`sender=user`), бот и ИИ в этом диалоге молчат `ai_pause_minutes`. Команды, сценарии, «Группа заказов» и коды владельца работают как прежде. Чат владельца и группа заказов в ящик **не попадают**.
  8. `GET api/main/inbox/webhooks/health/` — владельцу: по каналу последнее событие, ошибки за 24 ч, длина очереди.
- **Права.** Вебхук — без входа, только подпись. Здоровье — владелец и админ.
- **Деньги и повтор.** Дедупликация — ключом события.
- **Совместимость.** Шаг 2. Бот не ломается.
- **Приёмка.** Подменный стенд (`NurMarket-test\inbox-replay`):
  - тот же update дважды → одно сообщение;
  - `read` раньше `delivered` → итог `read`;
  - неверная подпись → 401;
  - 200 сообщений из 50 чатов за минуту → все в ящике, p95 ≤ 10 с;
  - `/start` у бота → в ящике, ответ бота — `sender=ai`.

### Б-88 (P2). ИИ на открытом сайте: прокси, бюджет вызовов, капча, проверка чисел (дополняет Б-79 и Б-83)
- **Зачем.** Чат на витрине (Б-83) открыт всему интернету. Без отдельного бюджета один бот или конкурент за час съест суточный лимит Gemini магазина (бесплатно — около 15 запросов в минуту и 500–1000 в сутки **на проект Google**, и этот лимит общий с ботом Telegram). Ключ ИИ во фронт отдавать нельзя.
- **Сейчас (26.10).** Чата на витрине нет. ИИ есть только у серверного бота.
- **Контракт.**
  1. **Только сервер.** Модель вызывает сервер при `POST public/…/chat/sessions/{id}/messages/` (Б-83), если у канала `web_widget` `ai_mode=auto`. Ключ, имя модели и инструкции в публичных ответах **не отдаются никогда**.
  2. **Капча:** Cloudflare Turnstile (или аналог). Токен — в `POST chat/sessions/` (`captcha_token`) и повторно после 15 сообщений сеанса или при подозрении (ответ 403 `captcha_required`). Секрет Turnstile — только на сервере.
  3. **Бюджет вызовов модели** (сверх лимитов сообщений Б-83 п. 3):
     - сеанс — 6 в минуту, 40 в сутки;
     - IP — 120 в сутки, не больше 10 новых сеансов в сутки;
     - компания — `chat_widget.ai_daily_calls`: по умолчанию 300 при бесплатном ключе, 3000 при платном;
     - при бесплатном ключе сайт берёт не больше 60 % суточного лимита, остальное — боту Telegram.

     Сверх бюджета сообщение доходит до продавца без ИИ, посетителю — `{"ai":"busy"}`: фронт показывает «Помощник занят» и кнопки Telegram, WhatsApp, телефон. 429 от Google — так же.
  4. **Ответ — структурой**, а не только текстом:
     ```json
     {"text": "...", "cards": [{"product":"…","variant":"…","name":"…","price":"2450.00","old_price":null,"image_url":"…","sizes_in_stock":["44","46"]}],
      "actions": [{"type":"add_to_cart","product":"…","variant":"…","qty":1}], "needs_human": false, "ai_run_id": "…"}
     ```

  5. **Проверка чисел после модели.**
     - Каждую сумму («сом», «с», «KGS», «₸» и число рядом с ценой) и каждое количество в `text` сверить с результатами инструментов этого хода.
     - Нет совпадения — заменить фразой «уточню у продавца», поставить `needs_human=true`, в журнале `hallucination_blocked=true`.
  6. **Инструменты** — как в Б-79 п. 2, плюс для одежды:

     - `size_chart.get(product|category)` (Б-50) и `size.advise(chart, height_cm?, weight_kg?, chest_cm?, waist_cm?)` — размер только по таблице магазина; без таблицы — `null` и «подскажет продавец»;

     **Заказ из чата сайта ИИ не создаёт**: оформляет посетитель обычной корзиной сайта (вопрос В-9 владельцу). Если владелец разрешит — только по Б-79 `order.create` с явным «да» и телефоном с согласием.

**Б-96 (P1). Проверка покупок на сервере (аудит редакторов 27.10).** Платные функции кассы (редактор этикеток, массовая печать ценников и остальные — список в `LicenseKeys`) сейчас проверяются только на кассе: серийные ключи лежат в коде открытым текстом, а флаги покупки `*Unlocked` — обычные true/false в `user-settings.json` (синхронизируются по компании через app-settings), поэтому любой может открыть платное правкой файла или взять ключ из репозитория. Нужно: (1) покупка хранится на сервере и привязана к компании: `GET api/main/purchases/` отдаёт список купленных функций со сроком, подписью сервера и `updated_at`; (2) активация — `POST api/main/purchases/activate/` с серийным ключом, ключи одноразовые, проверяются и отзываются на сервере, повторная активация на другой компании — 409; (3) касса хранит только кэш ответа с подписью и сверяет его при входе и раз в сутки; без связи действует последний подписанный кэш; (4) флаги `*Unlocked` из `SettingsCloudSync` убрать — право определяется ответом сервера, а не значением настройки; (5) существующие покупки перенести без повторной оплаты, мастер-ключ для тестов оставить только в тестовой компании. Приёмка: правка `user-settings.json` ничего не открывает; ключ, использованный в одной компании, во второй даёт 409; после отзыва покупки платное окно закрывается при следующей сверке.
