## 2. Общие правила для всех пунктов

**О1. Ошибка — всегда JSON:**
```json
{"detail": "Сумма больше долга клиента. Максимум: 190.00", "code": "amount_exceeds_debt",
 "field": "amount", "data": {"max": "190.00"}, "errors": [{"index": 6, "field": "variant", "code": "variant_required", "detail": "…"}]}
```
- **`detail` первым ключом.** Старые разборщики кассы (`RentalsApi.Describe`, `ServerTelegramBotApi.DescribeFields`) показывают первое строковое поле.
- `detail` — по-русски или по `Accept-Language` (`ru|ky|en|tr|uz`). Решения касса принимает только по `code`.
- Прежний формат DRF можно отдавать **дополнительно** — для сайта.
- 5xx — только при настоящем сбое. Бизнес-проверки отдают 4xx с `code`.

**О2. Три разных 404** (с 26.10 это обязательно):
- `route_not_found` — адреса нет;
- `not_found` — объекта нет;
- `idempotency_key_not_found` + `found:false` — ключа повтора нет.

Старый сервер уже отдаёт `{"code":"not_found"}` на любой неизвестный адрес. Поэтому прежнее правило «404 без JSON = адреса нет» больше не действует.

**О3. Ключ повтора (идемпотентность)** — у всех запросов, которые двигают деньги или склад:
- Заголовок `Idempotency-Key` (16–64 символа `[A-Za-z0-9_-]`, касса шлёт 32 hex). Для совместимости — то же значение в теле, `idempotency_key`. Разные значения → 400 `idempotency_key_mismatch`.
- Область ключа — компания + адрес. Хранить **≥ 7 суток** (офлайн-чек лежит в очереди выходные). Если меньше — написать.
- **Ключ проверяется до всех остальных проверок** (права, смена, долг, остаток). Повтор успешной операции → 200, `replayed:true` и прежний ответ.
- Тот же ключ с другим телом → **409 `idempotency_conflict`**. Так решили 25–26.10, 422 не вводим: на любой другой 4xx касса уходит старым путём, и 422 дал бы вторую продажу.
- Первая обработка ещё идёт → 409 `idempotency_in_progress` + `Retry-After`.
- Отказ 4xx (кроме 409, 423, 425, 429) значит «ничего не создано».

**О4. Списки:**
- Формат `{count, next, previous, results}`, параметры `page` и `page_size` (до 500). Порядок стабильный: вторичная сортировка по `id`.
- Страница за последней — пустой `results` (или 404 `page_not_found`), **не 500**.
- Даты `date_from`/`date_to` — включительно, в часовом поясе компании.
- **Старые кассы читают только первую страницу.** Если список, который был массивом, становится постраничным, без параметров он отдаёт всё (до 500) одной страницей.

**О5. Время** — ISO 8601 со смещением (`+06:00`). Даты без времени — `YYYY-MM-DD` в поясе компании.

**О6. Деньги и количества:**
- В ответах деньги — строкой с 2 знаками (`"387378.89"`), количество — строкой до 3 знаков.
- В запросах принимать и строку, и число. Округление до копейки, половина вверх.

**О7. Права** проверяет сервер в каждом API. Без права → 403 `{"detail":"Нет доступа: Товары","code":"permission_denied","required":"can_view_products"}`. Денежные операции хранят и отдают автора (`created_by {id, name}`).

**О8. Совместимость.**
- Новые поля — только добавлением, без переименований и удалений. Переименование делается через приём обоих имён.
- Новые значения перечислений: старая касса разбирает JSON вручную, неизвестное значение обычно показывает как есть. Описать новое значение в схеме до выкатки.
- 429 — JSON с `code` и заголовком `Retry-After`.
- Все фильтры и параметры — в схеме `swagger/?format=openapi`.

## 3. Что касса и мобилка сделают у себя

**До выкатки (касса 1.17.61, мобилка 1.18.5)** — ТЗ «Касса — адаптация к изменениям API сервера (26.10.2026)», пакеты П0–П7:
1. **Признак нового API** — по `capabilities/` (раз в 6 ч) или по `code: idempotency_key_not_found` + `found:false`, а не «404 в JSON». Правило `IsEndpointMissing` («404 без тела») на этом сервере не срабатывает.
2. **Заголовок** `X-NurMarket-Client: kassa/1.17.61` (`owner/…`, `mobile/1.18.5`) во всех запросах `NurMarketApiClient` и мобилки. Сейчас версия серверу не видна.
3. **Разбор `code`:** сначала `code`, потом прежняя подстрока текста. Тексты на 5 языков касса делает по `code` и `required`.
4. **«Расход» в чеке** больше не уходит отрицательной строкой: отдельное изъятие из ящика (`shift_drawer_outflow`) или скидка на чек — по решению владельца. До решения касса не даёт отправить такой чек.
5. **409 в чекауте** делится по `code`. Окончательные (`idempotency_conflict`, `total_mismatch`, `variant_out_of_stock`) — отказ без очереди и без старого пути. 409 без `code` — как сейчас.
6. **`ShiftCashFlowSync`:** на 403 и 400 — «отказано» и сообщение кассиру, без вечного повтора.
7. **Возвраты по строкам** — через `RequestAsync`, чтобы видеть тело ошибки.
8. **Ключ функций:** при 409 и 429 своей проверки ключа нет (сейчас любая ошибка → `TryValidateSerial` на ПК).
9. **Наличная оплата долга без серверной смены** (офлайн-открытая) запрещена: «Смена ещё не записана на сервере». Безнал разрешён.
10. **Прокат** — по `next` (касса понимает и массив, и `results`).
11. **Мобилка:** 409 в продаже — по `code`; поставщиков в должниках отсеивает сама до выкатки Б-14.

**После выкатки (по пунктам — блок «После» в каждом пункте):**
- убираем обходы: «вернуть цену», «Поправка сервера», свой расчёт возврата, ручную сделку прихода;
- переходим на новые адреса;
- пакеты по клиентским ТЗ: Г2 (группа заказов), Т1/Т2 (Telegram на витрине), Л6 (логотип), СФ1–СФ3 (сферы), Ф1 (тариф по `code`);
- мобилка — эталоны и черновик накладной.

**Для проверок витрины одежды** на NBS вернём сферу `clothing` (26.10 у NBS `grocery`) или возьмём другой тестовый аккаунт.

### Б-06 (P0). Закупочная цена не меняет цену продажи (Н-04; ТЗ Склад 24.10 «К Н-04»)
- **Зачем.** Приход с новой закупкой меняет наценку, а следующий `PATCH purchase_price` пересчитывает цену продажи. Пример: закупка 11→1 даёт наценку 36 % → 1400 %; вернули закупку 11 — цена продажи с 15 стала 165. Владелец теряет деньги незаметно. Касса и телефон вторым `PATCH {price}` возвращают цену, но между запросами она неверна на витрине и в других кассах.
- **Сейчас (26.10).** `OPTIONS main/products/{id}/`: в PATCH нет `recalc_price` и `price_changed`.
- **Контракт.**
  1. `PATCH products/{id}/` с `purchase_price` **не меняет `price`**, если `price` не передан. Пересчёт цены — только с `"recalc_price": true`.
     - `markup_percent` при этом — производное: пересчитывается от неизменной цены (решение Умара 25.10 «меняется только наценка» принимаем). На следующих запросах он **не** служит основанием менять `price`.
  2. `PATCH {price, markup_percent}` вместе — `price` берётся как прислан, не пересчитывается (подтвердить письменно).
  3. В ответе `price_changed: true|false` и `markup_percent`.
  4. Приход (`suppliers/{id}/receipt/`) не меняет `price`. Пересчёт — флагом `recalc_price: true` в строке прихода.
- **Права.** `can_view_products` (Б-16).
- **Деньги и повтор.** Цена продажи — деньги магазина. Изменение цены пишется в журнал товара.
- **Совместимость.** Шаг 2, желательное поведение для всех: обход «вернуть цену» у старой кассы станет холостым.
- **Приёмка.** Товар: закупка 11, цена 15.
  - `PATCH {"purchase_price":"1.00"}` → `price 15.00`, `price_changed:false`.
  - Приход с закупкой 1.00 → цена 15.00.
  - `PATCH {"purchase_price":"11.00","recalc_price":true}` → цена пересчитана, `price_changed:true`.
- **После.** Касса и телефон удаляют «вернуть цену» по полю `price_changed`.
