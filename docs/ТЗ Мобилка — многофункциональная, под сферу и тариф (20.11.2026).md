## 0. Коротко

- **Основа уже есть, но узкая.** В мобилке есть «режим магазина» `ShopMode` (4 значения: Продукты, Одежда, Услуги, Хозтовары) — он меняет плитки главной, подсказку поиска, блок в карточке товара и выбор размера в продаже [код] `core/shop_mode.dart`. **Тарифа мобилка не знает вообще** [код]. Новых сфер (Автозапчасти, Электроника, Канцтовары, Контейнер розница/опт) в ней нет [код].
- **Предложение: один объект `ModeProfile`**, который считается из пяти входов — сфера × тариф × роль × признаки сервера × размер экрана — и читается всеми экранами. Данные профилей — **таблицы-конфиги**, не `if` по коду. Новая сфера = одна строка в таблице + её блоки в реестре.
- **Главное правило безопасности:** право даёт сервер, клиент только прячет и подсказывает. Продажу, офлайн-очередь и уже введённое не блокируем никогда.
- **Порядок сфер для мобилки:** Контейнер-розница (совпадает с «Мини») → Автозапчасти → Одежда (уже есть, дотянуть) → Контейнер-опт → Строймаркет (Хозтовары, есть, дотянуть) → Электроника → Канцтовары. Обоснование — раздел 6.
- **Размер:** каркас (E1–E2) — M + M; каждая сфера — S…L (раздел 6). Без ответа Умара про `plan`/`limits`/поля сфер этапы E2–E3 упираются в заглушки.
- 8 вопросов владельцу — раздел 8. Самый важный: **считаем ли Flutter-мобилку единственным телефонным клиентом** (тогда всё ниже — обязательно), или параллельно живёт Android-касса Avalonia.

## 1. Цель и принципы

1. **Один код — разные режимы.** Профиль = сфера × тариф × роль × размер устройства (телефон / планшет). Никаких форков приложения, никаких «сборок под сферу».
2. **Скрываем, а не ломаем.** Чего нет на тарифе или в сфере — **не показывается**. Подсказка «Доступно на тарифе …» только там, где человек сам пытается сделать недоступное (кнопка «Добавить сотрудника», пункт «Заказ под клиента»), и **никогда во время продажи** (правило ТЗ Мини §3.1 и ТЗ Тарифы §4).
3. **Данные не теряются.** Смена сферы, понижение тарифа, выключение функции только прячет экран. Товары, цены, варианты, долги, заказы, черновики, очередь неотправленного остаются и возвращаются при включении (как у кассы для `bazaar`, ТЗ Контейнер §1.4).
4. **Безопасность: сервер — источник права.** Клиент можно подменить (заголовок `X-NurMarket-Client`, файл настроек). Поэтому: (а) профиль — только интерфейс; (б) сервер отвечает 403 `plan_feature_required` / `plan_limit` / `plan_client_not_allowed`, мобилка превращает это в понятную подсказку, а не в красное окно; (в) неизвестный план ≠ «Стандарт» (урок `TariffGate`, 23.09: сбой связи открывал платное на всю сессию [код] `TariffGate.cs`).
5. **Продажа не блокируется ничем** — ни лимитом, ни просрочкой тарифа, ни отсутствием признака (ТЗ Тарифы §4.1, принцип 2; ТЗ Мини §3.1).
6. **Только данные, а не ветки.** Включение функции = строка в таблице. Все надписи — на 5 языках (в мобилке — ARB, `lib/l10n/*.arb`).

## 3. Архитектура `ModeProfile`

### 3.1 Входы

| Вход | Источник | Офлайн |
|---|---|---|
| **Сфера** (`sphere`) | `company.market_sphere` + `MarketSphereDetail` (расширить: `electronics`, `stationery`, `autoparts`, `bazaar_retail`, `bazaar_wholesale`, `hardware`); позже `market_profile` (Б-38) | кэш, как `shop.mode` |
| **Тариф** (`tier`) | `capabilities.plan.code`: `mini / start / standard / custom` (Б-М1, Б-39) | кэш `mode.plan` на аккаунт; срок — не 14 суток, а «последнее известное» |
| **Лимиты** | `plan.limits` (`max_staff`, `max_devices`, `max_cashboxes`, `cross_numbers_per_product`, `price_tiers_per_product`, `open_orders`, `price_import_rows`) | кэш там же |
| **Допустимые клиенты** | `plan.allowed_clients` (`["mobile"]` и т. д.) | кэш; сервер проверяет сам |
| **Оплаченные пакеты** | `features[]` / `features_detail[]` из `GET api/users/company/features/` (`ai, clients, sales_analytics, restock, salary, debts, service` + новые `autoparts_pro, bazaar_opt, customer_orders, price_import, client_prices, credit_control, invoice_numbering, shipment, fx_purchase`) | кэш |
| **Что сервер умеет** | `capabilities`: `company_flags` (`hardware_2026_11`, `electronics_2026_11`, `autoparts_2026_11`, `bazaar_2026_11`), `volume_prices`, `multi_currency`… | кэш 14 дней как сейчас |
| **Роль и права** | `Session.isAdmin`, `perms` | как сейчас |
| **Размер устройства** | `MediaQuery`: телефон / планшет; ширина ≥ 600 dp — планшет | всегда |
| **Выбор владельца** | локально: «Простой режим» вкл/выкл, скрытые разделы (аналог `SectionVisibility`) | настройки телефона |

Правило открытия функции (то же, что у кассы по ТЗ Тарифы §5.1, с добавлением роли):

`открыто = сфера_даёт ∧ сервер_умеет ∧ (план_включает ∨ пакет_оплачен ∨ в_пределах_лимита) ∧ роль_разрешает ∧ владелец_не_скрыл`

Разные причины «закрыто» **различаются** (чтобы «сервер ещё не умеет» не превратился в «не оплачено»): `notInSphere` (молча скрыть), `serverNotReady` (скрыть, без подсказки), `planLocked` (замок и подсказка «Доступно на тарифе …»), `roleDenied` (как сейчас — скрыть), `hiddenByOwner` (скрыть).

**Неизвестный план** (`tier = unknown`: ответа ещё не было, нет связи, сервер старой версии) = «как сегодня»: мобилка показывает всё, что показывает сейчас, но **не включает ничего нового, зависящего от плана**. Сервер всё равно проверит. Это обратная совместимость и защита от урока `TariffGate`.

### 3.3 Таблицы-конфиги (как подключать сферы: одна строка, не `if`)

**Таблица сфер** `kSpheres` (аналог `SphereCatalog` кассы, но короче):

| Колонка | Значение |
|---|---|
| `id` | `grocery / clothing / services / hardware / stationery / electronics / autoparts / bazaar_retail / bazaar_wholesale` |
| `base` | базовая сфера для сервера (`grocery / clothing / services`) — **остаётся `ShopMode`** для совместимости; новые — `grocery` |
| `title`, `short`, `icon`, `accent` | название на 5 языках, значок, цвет (как `ShopMode.accent`) |
| `defaultFeats` | какие функции сфера даёт по умолчанию |
| `cardBlocks`, `searchRules`, `checkoutRules`, `receiveFields`, `homeTiles` | ключи реестра |
| `needsServerFlag` | какой флаг компании нужен (`autoparts_2026_11`, `electronics_2026_11`, `hardware_2026_11`, `bazaar_2026_11`) |

**Таблица тарифов** `kTiers`: для каждого `tier` — набор вкладок по умолчанию, разрешённые функции (`allow`), функции «только через пакет» (`packs`), `simple` по умолчанию.

**Таблица функций** `kFeatureMeta`: для каждого `Feat` — путь(и) экранов, минимальный тариф, код пакета, флаг сервера, нужное право роли, режим подсказки (`hide` / `lock`).

Подключение новой сферы = (1) строка в `kSpheres`; (2) если нужны новые блоки — их виджеты в `mode_blocks.dart` по ключу; (3) строки ARB; (4) golden-снимки. Код экранов не правится — они просят у профиля.

**Совместимость с `ShopMode`:** `ShopMode` остаётся как «базовое поведение» (его читают разбор весовых этикеток, сканер, `legacyClothingKey`). `ModeProfile.sphere` — расширение; `ShopModeSync` дополняется чтением `MarketSphereDetail` для новых значений. **Неизвестное значение (новая сфера → старая мобилка) не теряется и ведёт себя как `grocery`**, как у кассы (`SphereCatalog`, ТЗ СФ1).

### 3.4 Когда профиль пересчитывается

| Событие | Что происходит |
|---|---|
| Вход / смена аккаунта | `ServerCapabilities.refresh` + чтение `plan` и `features`; профиль собирается заново (кэш чужого аккаунта не действует) |
| Открытие приложения / возврат из фона | фоновое обновление не чаще раза в 6 часов; ответ не пришёл — остаётся кэш |
| Событие `plan_changed` / `features_changed` (Б-46) по push, если сервер пришлёт | мгновенный пересчёт, плашка «Тариф изменён» |
| Ответ 403 `plan_feature_required` / `plan_limit` на действие | пересчёт + подсказка «Доступно на тарифе …» |
| Смена сферы в Профиле | пересчёт; перед сменой окно «Что изменится» (как у кассы, ТЗ Контейнер §1.4) |
| Поворот экрана / планшет | пересчёт только `form` |

**Без перелогина.** Текущий маршрут, который в новом профиле закрыт, не обрывает работу: корзина, отложенные чеки, очередь остаются; пользователя возвращают на «Продажу» с плашкой «Раздел недоступен на этом тарифе».

### 3.5 Тесты

- `ModeProfile.compute` — чистая функция: таблица «вход → ожидаемый профиль» (юнит-тесты `flutter test`), на 9 сфер × 4 тарифа × 2 роли = 72 строки, плюс «неизвестный план» и «флаг сервера выключен».
- **Golden-снимки** (`flutter test --update-goldens` для проверки): нижняя панель, главная, «Управление», карточка товара и чек для каждого профиля; светлая тема, телефон 360×800 и планшет 800×1280; снимок **Мини / Простой режим**.
- Тест «**данные не теряются**»: смена профиля туда-обратно не меняет Drift-таблицы и очередь.
- Тест «**продажа всегда доступна**»: при любом профиле вкладка продажи и оплата открыты.
- Живая проверка — на тестовых компаниях (NBS, «ТЕСТ Хозмаг», «ТЕСТ Автозапчасти»), **не** на настоящем магазине. Правила проекта: настоящие данные и ключи не трогать; мобилка собирается и проверяется отдельно (`flutter analyze`, `flutter test`).

## 5. «Простой режим» (Мини) и его сочетание с профилем сферы

Подробности — ТЗ Мини (М1–М24). Здесь — как он ложится на `ModeProfile`.

- **Простой режим — не отдельная оболочка в обход профиля, а одно из значений `ModeProfile.simple`.** По умолчанию включается при `tier = mini`; владелец на любом тарифе может включить его переключателем «Простой режим» (удобно кассиру на базаре и на «Старте»).
- **Оболочка:** 3 вкладки — «Продать», «Товары», «Итоги дня» (+ значок ⚙ с профилем и выходом); кнопки от 56 px; сдача крупно (40–48 px); авто-выбор кассы и автосмена (М2); плитки 2 в ряд.
- **Сфера внутри Простого режима работает полностью, но в тех же трёх вкладках:**
  - блоки карточки (`cardBlocks`) и правила поиска сферы остаются; быстрая карточка — «фото + название + цена», остальные поля сферы — под «Потом»;
  - «Продать» показывает плитки сферы (размеры у одежды — выбор варианта после касания плитки; «Аналоги» у запчастей — кнопка на плитке);
  - «Товары» — каталог + быстрое добавление; «Итоги» — набор отчётов сферы, но крупно.
- **Что Простой режим скрывает всегда:** «Управление», ИИ, зарплата, КП, заказы сайта, второй сотрудник, настройки принтера (пока не нужны), закупки.
- **Если сфера Мини — не контейнер** (например, одежда на Мини): работает та же оболочка из 3 вкладок, а размер и цвет выбираются в продаже; «Размеры» — внутри «Товары».
- **Выход из режима:** на «Старте» и выше — «Обычный режим» в ⚙; на Мини возможен только Простой (лишнего всё равно нет).
- **Принцип:** Простой режим *убирает вкладки и украшательства*, но не убирает поля, обязательные для сферы (серийник у электроники, гарантия у запчастей — иначе потеряем смысл сферы и закон).

## 8. Риски и вопросы владельцу

### 8.1 Риски

1. **Мобилка тариф не знает; сервер план пока не отдаёт.** Без Б-Мб1–Б-Мб3 E2 — на заглушках. Пока `plan` нет, профиль = «как сегодня» (безопасно, но тариф не работает).
2. **Касса считает любой неизвестный план «Стандартом»** — открывает всё (`TariffGate`). Если мобилка получит `mini`, касса на ПК всё равно откроется на нём, пока сервер не запретит вход с `pos` (ТЗ Мини, риск 1).
3. **Схема Drift.** Автозапчасти и электроника требуют новых колонок (нормализованный номер, ячейка, состояние, гарантия, серийники). По правилам проекта — только с «да»; миграция должна быть обратимой, старые строки — без потерь.
4. **Объём `Prefs` / `ShopMode`.** Расширение `ShopMode` с 4 до 9 значений ломает `switch` без `default` (весы, одежда, `legacyClothingKey`). Поэтому `ShopMode` остаётся «базовым», а `sphere` — отдельное поле профиля.
5. **Дублирование логики** (Dart и C#): торг, нормализация номера, цены — два кода. Принимаем, делаем по ТЗ кассы, тесты на примерах.
6. **Скорость на слабых телефонах не измерена вживую** (аудиты 05.11 и 13.11 — по коду). Профиль не должен пересчитываться на каждый кадр: считается при событиях (3.4), выдаётся иммутабельно.
7. **Вход 7 суток и чек старше 7 суток** — самый чувствительный риск для рынка; решает Умар (ТЗ Мини Б-М8).
8. **Не фискальный чек.** Для контейнеров на патенте может понадобиться eKassa; в мобилке eKassa нет [не проверено] (ТЗ Мини вопрос 6).
9. **Мобилка единственная ли?** Если параллельно живёт Android-касса Avalonia (отложена владельцем), профили придётся вести в двух клиентах.
10. **Размеры:** APK уже 114 МБ (1.17.75); блоки сфер — только код и ARB, без тяжёлых ресурсов.
11. **Ничего из этого документа не проверялось на телефоне.** Все «есть / нет» — по чтению кода.

### 8.2 Вопросы владельцу (8, с рекомендацией)

1. **Мобилка — единственный телефонный клиент или параллельно держим Android-кассу Avalonia?** **Рекомендую:** Flutter-мобилка — единственный телефонный клиент; Android-касса остаётся отложенной (ТЗ Мини §2.3). Тогда этот документ обязателен целиком.
2. **В каком порядке делаем сферы в мобилке?** **Рекомендую:** Контейнер-розница → Автозапчасти → Одежда → Контейнер-опт → Строймаркет → Электроника → Канцтовары (раздел 6). Если «Автозапчасти» важнее базара — поменять 1 и 2.
3. **Нужно ли в мобилке «Сканер для кассы», сборка заказов и КП для всех сфер?** **Рекомендую:** «Сканер для кассы» — только «Старт» и выше (на Мини нет ПК); КП / Смета — строймаркет и по пакету; сборка заказов с сайта — «Старт» и выше, если есть сайт; «Заказ под клиента» — автозапчасти и опт.
4. **Как показывать тариф и апгрейд?** **Рекомендую:** один экран «Тариф и возможности» в профиле (текущий тариф, дни, что недоступно, цена «Старта» с сервера — не зашита в приложении); подсказка «Доступно на тарифе …» только при попытке сделать недоступное и не во время продажи; кнопка «Написать в WhatsApp». Оплату в самом приложении — **не делаем** (ELQR — в кассе, `billing_elqr`).
5. **Можно ли менять сферу в мобилке самому?** Сейчас можно (Профиль → «Режим магазина»); у кассы смена закреплена через поддержку (`MarketSphereLock`). **Рекомендую:** в мобилке выбор сферы только владельцем, с окном «Что изменится», и на сервер пишется базовая сфера (как сейчас); точные сферы (запчасти, электроника, контейнер) — тоже только владельцем.
6. **Печать на телефоне.** Нужны ли этикетки `autoparts_58x40`, ценник на полке, накладная A4 с телефона? **Рекомендую:** чек и этикетка (Bluetooth/Sunmi) — да; ценник на полке — для контейнера да; накладная A4 и акт сверки — только PDF в WhatsApp, печать на ПК.
7. **Разрешаете ли изменить схему базы телефона?** Нужны колонки под номер запчасти (нормализованный), ячейку, состояние, гарантию, серийники, ступени цены. **Рекомендую:** да, одной миграцией (как с PLU 05.11), только для сфер, которые включаются.
8. **Как поступать со Стартом: клиенты и долги (вопрос 3 ТЗ Тарифы)?** Если «клиент-лайт» на Старте — мобилка показывает клиента и срок долга без аналитики. **Рекомендую:** да (иначе у запчастей и опта на Старте нет главного сценария); решение влияет на `kTiers`.
