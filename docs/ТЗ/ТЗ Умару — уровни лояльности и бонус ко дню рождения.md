# ТЗ Умару — уровни лояльности и бонус ко дню рождения (26.11.2026)

От: Бекназар (касса NurCRM). Пункт №8 отчёта о конкурентах (Poster: кэшбэк, бонус ко дню рождения, накопительные скидки). Общие правила — «ТЗ Умару — общие правила денег и расчёта (26.11).md».

## 0. Что есть сегодня

- Баллы на сервере, одни на все кассы и в приложении покупателя: `bonus_balance` клиента; `POST api/main/clients/{id}/bonus/ {delta, reason: earn|redeem|manual, sale, note, idempotency_key}` (списание больше баланса → 400 «Недостаточно бонусов»); разовая выгрузка `clients/bonus/import/`; настройка `app-shop-settings {points_enabled, points_percent}` — **один процент для всех**.
- Касса: начисляет и списывает **после** продажи двумя операциями с ключом (`ServerLoyalty`, очередь `loyalty-queue.json`, журнал ключей `idempotency_lookup_bonus_transfers`); списанные баллы уходят в продажу как **скидка на чек** (сервер их не отличает). Возврат снимает баллы операцией кассы.
- «День рождения» — только шаблон сообщения бота (`BotMessagesWindow`); уровней нет; дата рождения в карточке клиента — есть ли на сервере поле, уточнить (см. вопрос 1).

## 1. Что видит пользователь

**Владелец → «Программа лояльности»:**

```
┌ Программа лояльности ──────────────────────────────────┐
│ Начисление: [ ] Баллы  [ ] Скидка уровня  [ ] Оба      │
│ Уровни (по сумме покупок за [365] дней):               │
│  Базовый   от      0 сом   баллы 2 %   скидка 0 %      │
│  Серебро   от 20 000 сом   баллы 3 %   скидка 3 %      │
│  Золото    от 60 000 сом   баллы 5 %   скидка 5 %      │
│  [+ уровень]  (до 5)                                   │
│ Понижение уровня: (•) нет  ( ) раз в год по сумме      │
│ Оплата баллами: не больше [30] % чека                  │
│ Сгорание баллов: через [180] дней без покупок / нет    │
│ День рождения: +[300] баллов за [3] дня до — [7] после │
│   срок жизни подарка [14] дней; поздравление ботом [x] │
│                                   [Сохранить]          │
└────────────────────────────────────────────────────────┘
```

**Кассир:** при выборе клиента — метка уровня «Серебро · 3 %», баланс, «до Золота 4 200 сом», значок 🎂 если подарок ко дню рождения доступен; в окне оплаты — «Скидка уровня: −36,00» и «Можно оплатить баллами: до 54,00».

**Покупатель:** в приложении NurCRM и в Telegram-боте — уровень, прогресс, баланс, история; в день рождения — поздравление (по согласию `service`/`marketing`).

## 2. Модель данных

```
loyalty_program (company 1:1)
  mode: points | discount | both
  period_days (365), downgrade: none | yearly
  redeem_max_percent (30), points_expire_days (null = не сгорают)
  birthday_bonus_points, birthday_window_before (3), birthday_window_after (7), birthday_bonus_ttl_days (14)
  gift_card_earns_bonus (false), version
loyalty_level  (id, program, title{ru,ky,en,tr,uz}, threshold "20000.00", earn_percent, discount_percent, position)
client  + birth_date (date, без года допустимо — month/day), level_id, level_since,
          period_spent "18200.00" (кэш), level_locked bool (вручную назначено владельцем)
bonus_transaction (существующая) + kind: earn|redeem|manual|birthday|expire|reverse, expires_at, source_sale
```

Сумма для уровня = сумма продаж клиента за `period_days` **минус** возвраты, без доставки, без оплаты подарочными картами (если `gift_card_earns_bonus=false`) и без оплаты баллами.

## 3. Расчёт на сервере

1. **Уровень** пересчитывается в транзакции продажи и возврата (повышение — сразу после продажи; понижение — только по `downgrade=yearly` ночной задачей 1 января или в годовщину). Возврат не понижает уровень мгновенно (иначе «вернул — потерял скидку на возврат»).
2. **Скидка уровня** — процент на чек после акций (порядок — общая часть, шаг 5). Строки с акцией получают скидку уровня только если у акции `stackable_with_promos=true`. И-1 (не ниже закупки) — скидка уровня обрезается по строке.
3. **Начисление** = `earn_percent уровня` × (итог − `bonus_redeem` − оплата картами при `false`), округление до 0,01 вниз. Начисляет **сервер в транзакции продажи** (без отдельного `clients/{id}/bonus/` от кассы). В ответе checkout: `bonus: {earned, redeemed, balance, level, level_changed}`.
4. **Оплата баллами** = поле продажи `bonus_redeem` (общая часть). Не больше `redeem_max_percent` от итога и не больше баланса; 1 балл = 1 сом. Списание и продажа — одна транзакция (две кассы одновременно → вторая получает 409 `bonus_insufficient {balance}`, ничего не создано).
5. **День рождения**: ночная задача в 00:05 по времени компании начисляет `birthday` баллы клиентам, у кого день рождения через `before` дней (один раз в год: ключ `(client, year)`), `expires_at = +ttl`. Поздравление — в `telegram-bot/outbox/` kind `birthday` по согласию. Дата без года — ок. Смена даты рождения чаще раза в год — только владелец (защита «каждый месяц день рождения»).
6. **Сгорание**: ночная задача, операция `expire` с суммой, журнал; за 7 дней — уведомление ботом (по согласию).
7. **Возврат**: начисленные за чек баллы снимаются пропорционально возвращённому (`reverse`), списанные баллами — возвращаются на баланс (И-5). Если баллы уже потрачены и баланс меньше снимаемого — баланс **не уходит в минус**: снимается сколько есть, остаток удерживается из суммы возврата деньгами (`refund.bonus_shortfall`), кассир видит строку «Удержано за потраченные бонусы: 12,00». (Решение владельца — альтернатива: разрешить минус баланса; см. вопрос 3.)
8. **Офлайн-касса**: уровень и процент — последние известные (кэш), начисление/списание — в составе офлайн-чека; при досылке сервер проверяет баланс на момент досылки: не хватает → чек проводится, списание урезается до баланса, `warnings[].bonus_shortfall` (касса пишет в «Некорректные чеки» — механизм `BonusRejected` уже есть).

## 4. Эндпоинты

```
GET   api/main/loyalty/program/                       → программа + уровни (ETag)
PUT   api/main/loyalty/program/                       (владелец) — новая version; пересчёт уровней — фоном
GET   api/main/clients/{id}/loyalty/                  → {level, discount_percent, earn_percent, balance, period_spent,
                                                         next_level: {title, threshold, left}, birthday_bonus: {available, amount, expires_at}}
PATCH api/main/clients/{id}/  {birth_date, level_id, level_locked}   (уровень вручную — только владелец)
GET   api/main/clients/{id}/bonus/history/?page=
GET   api/main/loyalty/report/?date_from=&date_to=    начислено / списано / сгорело / по уровням / день рождения
```

Пример `clients/{id}/loyalty/`:

```json
{ "level": { "id": "lv2", "title": "Серебро" }, "discount_percent": "3.00", "earn_percent": "3.00",
  "balance": "540.00", "period_spent": "15800.00",
  "next_level": { "title": "Золото", "threshold": "60000.00", "left": "44200.00" },
  "birthday_bonus": { "available": true, "amount": "300.00", "expires_at": "2026-12-10" } }
```

В `pos/checkout/` и `pos/quote/`: вход `bonus_redeem`, выход `order_discounts[{kind: "loyalty_level", amount}]` и `bonus {earn_preview|earned, redeem_max, balance}`.

## 5. Ошибки

400 `loyalty_level_invalid` (пороги не по возрастанию, проценты >100), 409 `bonus_insufficient {balance}`, 400 `bonus_redeem_over_limit {max}`, 403 `birth_date_change_limited`.

## 6. Признаки, права, миграция

- Признаки: `loyalty_levels`, `loyalty_birthday`, `sale_bonus_redeem` (баллы как средство оплаты внутри продажи).
- Право `can_manage_loyalty` (владелец, админ); ручная корректировка баллов — существующее `manual`.
- Миграция: из `app-shop-settings.points_percent` создать программу `mode=points` с одним уровнем «Базовый» (порог 0, `earn_percent = points_percent`) — поведение не меняется, пока владелец не добавит уровни. `period_spent` — разовый пересчёт по продажам за 365 дней.
- Старые кассы (без `sale_bonus_redeem`) продолжают слать `clients/{id}/bonus/` после продажи — сервер должен не начислить дважды: если продажа уже начислила баллы сама, повтор `earn` с тем же `sale` → 200 без изменения (`already_applied`).

## 7. Тесты приёмки

1. Уровни 0/20 000/60 000; клиент 19 900 → чек 200 → уровень «Серебро» с **следующего** чека (в этом чеке начислено по 2 %: 4,00).
2. Серебро, чек 1 200, скидка 3 % = 36,00, итог 1 164, начислено 3 % от 1 164 = 34,92.
3. Оплата баллами 30 %: итог 1 000, баланс 500 → максимум 300; начисление от 700 = 21,00 (3 %).
4. Две кассы списывают 400 из баланса 500 одновременно → одна проходит, вторая 409 `bonus_insufficient`.
5. Возврат половины чека: начислено 34,92 → снять 17,46; если баланс 10,00 → снять 10,00, удержать 7,46 из возврата.
6. День рождения 05.12, окно −3: 02.12 00:05 начислено 300, `expires_at` 16.12; повтор задачи — второй раз не начисляет.
7. Офлайн-чек со списанием 300, при досылке баланс 100 → проведён, списано 100, `warnings.bonus_shortfall = 200`.
8. Миграция: компания с `points_percent=2` — до и после миграции одинаковые начисления.

## 8. Этапы

- **Ф1**: уровни (программа, пороги, процент начисления и скидки), `clients/{id}/loyalty/`, начисление и `bonus_redeem` внутри продажи, возврат баллов сервером, миграция.
- **Ф2**: день рождения (задача + бот), сгорание, понижение по году, отчёт по программе, приложение покупателя (прогресс уровня).

## 9. Что подхватит касса

- метка уровня, прогресс, 🎂 в карточке клиента в чеке и окне оплаты (`clients/{id}/loyalty/`, кэш на клиента);
- скидка уровня в разборе итога (локальный расчёт по кэшу программы, сверка `expected_total`);
- `bonus_redeem` в теле продажи вместо скидки на чек; отключение отдельных `earn/redeem` при признаке `sale_bonus_redeem` (`ServerLoyalty` остаётся для старых серверов и ручных операций);
- окно «Программа лояльности» в программе владельца: уровни, день рождения, сгорание — 5 языков; поле «Дата рождения» в карточке клиента.

## 10. Вопросы Умару

2. Пересчёт уровня — в транзакции продажи или фоном (задержка до минуты допустима)?
3. Возврат при потраченных баллах: удержание из денег (наше предложение) или минус на балансе?
