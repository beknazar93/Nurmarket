# ТЗ Умару — статус ремонта на витрине сайта (26.11.2026)

**Обновление 26.11 (вечер): сервер выкатил этап 1** — `PUT api/main/repair-orders/{external_id}/` (201 created:true, затем 200, unchanged:true), публичный `POST public/companies/{slug}/repair-status/`, признак `repair_status_public` при включённом модуле «Ремонт» (право `repair.manage`). Касса подогнана под ответ Умара: тело — number, code, status, device, client_name, client_phone, accepted_at, due_date, ready_at, estimate, prepay, final_price + serial, problem, accessories, note (без `external_id` и `amount_due`); `public_url` из ответа печатается на квитанции, иначе наша ссылка; очередь повтора при отсутствии сети. Разделы ниже остаются как исходная постановка (этап 2: серверная нумерация, чтение заказов с сервера, `public_token`, уведомление клиенту, страница `/catalog/{slug}/repair`).

От: Бекназар (касса NurCRM). Цель: клиент магазина электроники и ремонта сам узнаёт, в каком статусе его устройство, на **витрине магазина** (`market.nurcrm.kg/catalog/{slug}`), и получает сообщение «готово». Сегодня сервер ремонт не знает вообще.

## 0. Что есть сегодня (по коду кассы, 26.11.2026)

- Заказы ремонта («Ремонт и сервис», окно кассы и программы владельца) хранятся **только локально**: файл `repair-orders.json` в `%LOCALAPPDATA%\NurMarketKassa` на одном ПК (`RepairOrderStore`). Между компьютерами и на сервер **не уходят**. Модуль на сервере называется `repair` (витрина Маркетплейса), но своей таблицы заказов ремонта у сервера нет.
- Статусы: `Принят → В работе → Готов → Выдан`, ещё `Отменён`. Переходы: принят→в работе→готов→выдан; готов→в работу (вернули); принят/в работе/готов→отменён.
- В квитанции приёма печатается: номер (код `Р-0001`), клиент, телефон, устройство, серийный номер/IMEI, неисправность, комплектация, заметка, ориентир, предоплата, срок, условия, подписи.
- Деньги (предоплата, возврат, оплата работ) касса проводит **своими** путями (внесение/изъятие, строка «Доп. услуга» в чеке). Сервер деньги ремонта не видит и **не должен** двигать — он только показывает.
- Витрина: публичные `public/companies/{slug}/showcase/`, `…/orders/`, `…/chat/`, `…/cart-link/`; оформление — `showcase/design/`. Страницы статуса ремонта нет.
- Касса уже готова (в рабочей копии, выключено): печатает на квитанции ссылку `…/catalog/{slug}/repair?code={номер}` и шлёт заказ на сервер — но **только если** в `GET api/main/capabilities/` есть признак `repair_status_public`. Пока признака нет, касса в сеть ничего не шлёт, а на квитанции печатает «позвоните в магазин, назовите код» (если задан телефон магазина).

Имена ниже (признак, пути, поля) — **наше предложение**. Скажи, если у вас иначе, подстроим кассу.

## 1. Что нужно от сервера (по приоритету)

### 1.1. Приём заказов ремонта от кассы (P0)

`PUT api/main/repair-orders/{external_id}/` — upsert по `external_id` (это `Id` квитанции в кассе, 32 hex). Авторизация как у остальных методов (Bearer, компания из токена). Идемпотентно (повтор тем же телом — 200 без изменений).

Тело (поля, которые касса шлёт сегодня):

| Поле | Тип | Смысл |
|---|---|---|
| `external_id` | string | Id квитанции в кассе |
| `number` | int | сквозной номер (в рамках компании) |
| `code` | string | `Р-0001` (для показа) |
| `status` | string | `accepted` / `in_work` / `ready` / `issued` / `cancelled` |
| `device` | string | «Samsung A54» |
| `client_name` | string | для приветствия в сообщении |
| `client_phone` | string | для проверки «последние 4 цифры» и уведомления; наружу не отдавать |
| `accepted_at` | datetime | |
| `due_date` | date / null | ориентировочная дата готовности |
| `ready_at` | datetime / null | |
| `estimate` | "1500.00" | ориентир при приёме |
| `prepay` | "500.00" | сколько предоплаты внесено |
| `final_price` | "1700.00" / null | итог работ (при «Готов» и «Выдан») |
| `amount_due` | "1200.00" / null | к оплате при выдаче = итог − предоплата (при «Готов») |

Не шлём (намеренно): неисправность, серийный номер/IMEI, заметку, комплектацию, журнал, имя кассира. Если нужно показывать на странице «что чиним» — скажи, добавим отдельным полем `public_fault` (владелец решит, показывать ли).

Ответ: 200 `{ "id": "...", "public_code": "Р-0001", "updated_at": "..." }`. Ошибки — как везде (`{detail|code}`), 404/405/501 касса понимает как «сервер не умеет».

Нумерация: `number` назначает касса (последовательно на ПК). При двух кассах в одной компании номера могут совпасть — поэтому **ключ на сервере `(company, external_id)`, а публичный код — `(company, number)` с проверкой уникальности**: при конфликте вернуть 409 с `suggested_number`, касса перепечатает/сменит (договоримся). Если проще — серверу выдавать номер самому (ответ содержит `number`), тогда кассе достаточно прочитать его из ответа; предпочитаем этот вариант на этапе 2.

Нужно также `GET api/main/repair-orders/?updated_since=&status=&page_size=` — чтобы другая касса/программа владельца/мобилка видели те же заказы (синхронизация между устройствами). Этап 2; на этапе 1 хватит upsert.

### 1.2. Публичная проверка статуса (P0)

`POST public/companies/{slug}/repair-status/` (без авторизации), тело: `{ "code": "12" | "Р-0012", "phone_last4": "3456" }`.

Ответ 200:

```json
{
  "code": "Р-0012",
  "status": "in_work",
  "status_title": "В работе",
  "device": "Samsung A54",
  "due_date": "2026-11-30",
  "ready_at": null,
  "amount_due": null,
  "currency": "KGS",
  "shop_phone": "+996 …",
  "updated_at": "2026-11-26T14:03:00+06:00"
}
```

- `status_title` — на языке из `Accept-Language` (ru, ky, en, uz; `kk` как на витрине).
- `amount_due` — только при `status=ready`; при `issued` — не показывать сумму (или показать «Выдан»).
- Любая ошибка (нет такого кода, не совпали цифры, заказ старше 90 дней после выдачи/отмены) — **один и тот же** ответ 404 `{ "code": "not_found" }`, без подсказок, что именно не так.
- **Личных данных в ответе нет**: ни имени, ни телефона, ни неисправности, ни серийного номера, ни кассира, ни предоплаты. Только статус, устройство (название модели), дата, сумма к оплате, телефон магазина.

### 1.3. Уведомление клиенту (P1)

При переходе в `ready` (и по настройке — в `in_work`, `cancelled`) сервер отправляет клиенту сообщение: «Здравствуйте, {имя}! Ваше устройство «{device}» (Р-0012) готово — можно забирать. К оплате: 1200 сом. {магазин}».

Каналы (в порядке приоритета, по согласию клиента — как `service`-согласие в карточке клиента, Б-30/Б-74):
1. **Telegram** — если клиент привязал номер к боту магазина («Чеки и бонусы в Telegram», `/start receipts` + «Поделиться номером»). Для ремонта нужен ещё deep-link `/start r_<token>` с квитанции («Получать уведомления о ремонте») — привязывает чат к заказу без поделиться номером.
2. **WhatsApp / SMS** — если у вас есть провайдер (скажи какой). Сегодня касса только открывает чат WhatsApp, отправляет человек.
3. Если канала нет — ничего не шлёт; статус виден на странице.

Одно уведомление на один переход (идемпотентность по `(order, status)`); запись в `telegram-bot/outbox/` (kind `repair_ready`); при 429/блокировке бота — не повторять бесконечно.

Касса тоже умеет (уже сделано, без сервера): кнопка «Написать клиенту (Telegram)» — только тому, кто сам привязал номер к боту.

### 1.5. Модуль для `public/modules` (P1)

- id: `repair_status_site` (или как у вас принято), название: «Статус ремонта на витрине».
- Цена: на ваше усмотрение, предлагаю **150 сом/мес** (в вилке модулей 100–300).
- Условия: у компании включён модуль `repair` и онлайн-витрина (`can_view_showcase`).
- Когда модуль включён — в `capabilities.features` приходит `repair_status_public` (касса включается сама). Без модуля признака нет — страница отвечает 404, касса молчит.
- Профили по умолчанию: «Электроника» (включать со скидкой/в пакет), «Услуги».

## 2. Синхронизация заказов ремонта кассы с сервером

События, которые касса отправляет (всегда `PUT` целого состояния, не дельты):

1. создание заказа (приём);
2. «Взять в работу»;
3. изменение предоплаты (внесена / возвращена);
4. «Готово» (итог работ, `ready_at`, `amount_due`);
5. «Вернуть в работу»;
6. «Выдан»;
7. «Отменён».

Правила:
- Источник истины по **деньгам и статусу** — касса. Сервер ничего не проводит и не меняет статус сам (кроме отображения). Конфликт «две кассы» — этап 2 (серверная нумерация и `updated_at`/`version`, как у накладных).
- Офлайн: сейчас повторов нет. Если сервер недоступен — статус на странице отстаёт; при следующем изменении заказа касса отправит актуальное состояние. Очередь повторов (как у чеков) касса добавит, когда сервер подтвердит контракт.
- Удаление: заказы не удаляются; отменённые и выданные скрываются со страницы через 90 дней.
- Размер: ориентир — до 100 заказов в день на магазин; массовый импорт не нужен.

## 3. Безопасность

- Публичный метод **без** персональных данных (см. 1.2); ответ на любую ошибку одинаковый; задержка ответа одинаковая (без timing-различий).
- Лимиты: не более 5 запросов/мин с IP на `slug`; не более 20 попыток/сутки на один код; после 10 неудачных попыток по коду за час — блок кода на час. Капча как в чате витрины (Turnstile), когда включится.
- Угадать нельзя: проверка `номер + последние 4 цифры` — это ≈10⁴ комбинаций на один номер, поэтому лимит по коду обязателен. Усиление (рекомендуем на этапе 2): сервер выдаёт непредсказуемый `public_token` (22 символа, как `cart-link`), касса печатает ссылку `…/repair/{token}` и QR, цифры телефона тогда не нужны.
- CORS публичного метода — только домены витрины.
- Телефон хранить как есть для уведомлений, но в публичные ответы и логи не выводить (в логах — хэш).
- Согласие на сообщения — по существующей модели (`service`-категория); без согласия не писать.
- Журнал: кто и когда сменил статус (из `external_id` и авторизованного пользователя).
- Retention: заказы и диалоги — как у вас принято (чат 90 дней); для ремонта предлагаем хранить 3 года (гарантия).

## 4. Что сделает касса (когда сервер ответит)

- включится само при `repair_status_public`: ссылка на квитанции, отправка статусов;
- перепечатка квитанции с актуальной ссылкой;
- QR на квитанции — отдельный пункт (термопринтер по тексту QR не печатает; нужен графический режим) — после договорённости про `public_token`;
- программа владельца и мобилка — читают заказы с сервера (этап 2).
