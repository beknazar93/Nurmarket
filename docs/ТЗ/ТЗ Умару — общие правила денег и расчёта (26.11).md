## 1. Главный принцип: цену и скидку решает сервер

1. **Источник истины — сервер.** Касса показывает и отправляет; сервер пересчитывает и проводит. Касса никогда не «додумывает» скидку, которую сервер не применит.
2. **Один расчёт на двоих.** Для всего, что меняет сумму (акции, уровень, промокод, карта, доставка, модификаторы), сервер отдаёт кассе **правила в виде данных** (как `promotion_rules` сегодня), а не только результат. Касса считает по тем же правилам без сети. Формулы описываются в ТЗ **на примерах с числами**, и на каждый пример — тест у вас и у нас.
3. **Предпросмотр.** Новый метод `POST api/main/pos/quote/` (общий для всех функций): тело как у `pos/checkout/`, но без `payment`; ответ — итог и разбор скидок. Ничего не пишет, не списывает, не резервирует (кроме явного `hold` у подарочной карты — см. её ТЗ).

```json
// POST api/main/pos/quote/
{ "client": "c1…", "items": [{ "product": "p1…", "qty": "3", "price": "100.00" }],
  "promo_code": "OSEN10", "gift_cards": ["NC-7H2K-9QPL"], "at": "2026-11-26T14:03:00+06:00" }
// 200
{
  "subtotal": "300.00",
  "lines": [{ "index": 0, "line_total": "300.00", "discount": "100.00",
              "applied": [{ "kind": "promotion", "id": "pr_12", "title": "2+1 на воду", "amount": "100.00" }] }],
  "order_discounts": [{ "kind": "promo_code", "code": "OSEN10", "amount": "20.00" },
                      { "kind": "loyalty_level", "level": "silver", "amount": "0.00" }],
  "total": "180.00",
  "gift_card_payable": [{ "code": "NC-7H2K-9QPL", "available": "500.00", "will_use": "180.00" }],
  "bonus": { "earn_percent": "3.00", "earn_preview": "5.40", "redeem_max": "54.00" },
  "warnings": [], "rules_version": "2026-11-26T10:00:00Z"
}
```

4. **Защита от расхождения.** В `pos/checkout/` новое поле `expected_total` (итог, который видел кассир). Если итог сервера отличается больше чем на 0,01 → **409 `total_mismatch {expected_total, server_total, lines[]}`**, продажа **не** создаётся. Касса показывает «Цена изменилась: было X, стало Y» и пересчитывает. Для офлайн-очереди (`accept_late`/досылка) — не отказ, а `warnings[].total_mismatch` с суммой (чек уже пробит, деньги взяты).
5. **В продаже сохранять разбор**: `applied[]` по строке и `order_discounts[]` — для отчёта «сколько дала каждая акция», для возврата и для печати чека («Скидка по акции “2+1”: −100,00»).
6. **Бонусы отдельно от скидки.** Новое поле продажи `bonus_redeem` (сумма баллов в оплату). Сегодня баллы смешаны со скидкой кассира — отчёт «скидки» врёт. Сервер сам списывает баллы в рамках продажи (одна транзакция), а не отдельным `clients/{id}/bonus/` после неё.

## 2. Порядок применения скидок (один для всех функций)

1. Цена строки (прайс, оптовая, упаковка, `price_override`).
2. Модификаторы / доплаты к строке (кафе, доставка не сюда).
3. **Акции на строку** (конструктор акций: N+M, % на товар/категорию, по времени, комбо). Из пересекающихся — по правилу приоритета акции (см. её ТЗ); по умолчанию «лучшая для покупателя одна».
4. **Ручная скидка кассира на строку** — только если строка без акции или акция разрешает «суммироваться с ручной».
5. **Скидка уровня лояльности** (процент на чек; на строки с акцией — по флагу акции).
6. **Промокод** (на чек или на строки).
7. **Скидка кассира на чек.**
8. **Доставка** (+, не скидка; не участвует в базе процентов).
9. Итог → округление один раз (как сейчас).
10. **Оплата**: баллы (`bonus_redeem`) → подарочные карты → деньги (`cash/transfer/mixed/debt`). Баллы и карты — **средства оплаты**, а не скидки: база для начисления бонусов = итог − баллы (карта считается деньгами, если так решит владелец — флаг `gift_card_earns_bonus`, по умолчанию `false`).

## 3. Жёсткие инварианты денег (для всех функций; на каждый — тест приёмки)

| № | Инвариант | Поведение сервера |
|---|---|---|
| И-1 | Цена строки после всех скидок **не ниже закупки**, если у сотрудника нет `can_sell_below_cost` **и** у акции нет флага `allow_below_cost` (ставит только владелец) | 400 `price_below_cost` (как сейчас), в `quote` — `warnings[].below_cost` заранее |
| И-2 | Итог строки и чека ≥ 0; скидка ≤ суммы строки | обрезать до 0 и вернуть `warnings[].discount_clamped` |
| И-3 | Подарочная карта **не уходит в минус**; списание = атомарная операция с блокировкой строки карты (`SELECT … FOR UPDATE`) | 409 `gift_card_insufficient {available}` |
| И-4 | Одна операция — один эффект: повтор с тем же `Idempotency-Key` возвращает прежний результат; **двойное погашение** карты / промокода / баллов невозможно даже при двух кассах одновременно | повтор → 200 `replayed`; второй чек с той же одноразовой картой → 409 |
| И-5 | Возврат чека возвращает ровно то, чем платили, пропорционально: деньги — деньгами, карта — на карту, баллы — баллами; промокод с лимитом использований возвращается в счётчик только при **полном** возврате | см. раздел 5 |
| И-6 | Сумма всех оплат = итог чека (± 0,01); переплата только наличными (сдача) | 400 `payments_mismatch` |
| И-7 | Деньги — строки `"1234.50"` (decimal), не float; валюта компании; часовой пояс компании (`Asia/Bishkek`) для «по времени», «день рождения», сроков | — |
| И-8 | Правила, действовавшие **в момент пробития** (`sold_at` чека, а не время досылки), — для офлайн-чека | хранить версии правил (`rules_version`) |
| И-9 | Любое изменение правил/балансов — в журнал: кто, когда, было/стало | `audit` |
| И-10 | Отказ по существу (4xx) ничего не создаёт и ничего не списывает | транзакция целиком |

## 4. Идемпотентность и офлайн

- Все денежные `POST/PUT` принимают `Idempotency-Key` (заголовок) и/или `idempotency_key` (тело) — как сейчас у чеков и бонусов. Ключ живёт ≥ 90 суток (офлайн-чек до 90 суток).
- Журнал `GET api/main/idempotency/{key}/` должен знать **все** новые операции (погашение карты, выпуск карты, промокод, подтверждение QR, запись, заказ доставки, SMS-рассылка).
- **Офлайн-касса**: акции, уровень клиента (последний известный), техкарты, тарифы доставки — считает по кэшу правил. **Подарочные карты и одноразовые промокоды без сети не принимаются** (касса покажет «нужна связь»), потому что иначе двойное погашение. Многоразовые промокоды — по флагу `offline_allowed` (владелец решает, риск его).
- Досылка офлайн-чека: сервер пересчитывает по правилам на `sold_at`; расхождение — не отказ, а `warnings[]` (касса пишет в «Некорректные чеки» для владельца — механизм уже есть).

## 5. Возврат (общее)

`POST api/main/pos/sales/{id}/return/` сегодня. Добавить в ответ **раскладку возврата по средствам**:

```json
{ "return_id": "r1…", "refund_total": "180.00",
  "refund": [{ "method": "cash", "amount": "80.00" },
             { "method": "gift_card", "code": "NC-7H2K-9QPL", "amount": "100.00" },
             { "method": "bonus", "amount": "0.00" }],
  "bonus_reversed": "5.40", "promo_code_released": false }
```

Правила: частичный возврат — возвращается **реально уплаченное** за возвращаемые единицы: (итог строки после всех скидок по `applied[]` и доли скидки на чек) / кол-во × возвращаемое кол-во (2+1, ×3 за 200, вернули 1 → 66,67, а не 100: покупатель не «выигрывает» бесплатную единицу). Пересчёт «как будто купили только оставшееся» не делаем — он непонятен кассиру и покупателю; порядок возврата средств — обратный оплате: сначала деньги до суммы, уплаченной деньгами, потом карта, потом баллы (или по выбору кассира в пределах уплаченного каждым средством — `refund_methods` в теле). Начисленные за чек баллы снимаются пропорционально (сервер сам; сегодня это делает касса отдельной операцией).

## 6. Признаки и модули

- Каждая функция — свой признак в `capabilities.features` и свой модуль в `public/modules` (цены — ваши/владельца, вилка 100–300 сом/мес). Без признака касса ведёт себя как сегодня и **ничего нового не отправляет**.
- Права сотрудника — новые флаги в `employees/{id}` (как `can_sell_below_cost`), сервер проверяет сам; владелец и админ — по роли.
- `rules_version` (или `ETag`) у всех справочников правил — касса перечитывает только при изменении (как `modules.version`).

## 7. Ошибки (общий формат)

`{ "code": "<машинный>", "detail": "<текст на языке Accept-Language>", ...поля }`. 404/405/501 касса понимает как «сервер не умеет» и прячет функцию. 429 — `Retry-After`.

## 8. Что сделает касса по общей части

- `expected_total` в `pos/checkout/` + окно «Цена изменилась» на 409 `total_mismatch`;
- вызов `pos/quote/` в окне оплаты при наличии признака `pos_quote` (показ разбора скидок, без сети — локальный расчёт по кэшу правил);
- печать разбора скидок в чеке из `applied[]` / `order_discounts[]`;
- `bonus_redeem` вместо смешивания со скидкой (признак `sale_bonus_redeem`); снятие отдельной операции `clients/{id}/bonus/` после продажи;
- возврат: показ раскладки «куда вернуть» из ответа сервера.
