# ТЗ Умару — автоподтверждение QR-оплаты в магазине (26.11.2026)

От: Бекназар (касса NurCRM). Пункт №11 отчёта о конкурентах («нет эквайринга» — главный минус против MBANK MKassa, О!Кассы, Kaspi). Разбор вариантов — `docs/Отчеты/Идеи — бесплатный тариф и эквайринг 26.11.2026.md`, часть Б. Общие правила — «ТЗ Умару — общие правила денег и расчёта (26.11).md».

**Принцип:** деньги магазина идут **на счёт магазина** в его банке, через NurCRM не проходят (иначе мы платёжный агент — нужна лицензия). Сервер только **узнаёт** об оплате и сопоставляет её с чеком. Ключи банка магазина — **только на сервере**, никогда в кассе/мобилке/сайте.

## 0. Что есть сегодня

- Касса показывает статический QR банка магазина (картинка в Настройки → Операции) или **QR с вписанной суммой** (`DynamicPaymentQrService` + `ElqrQrBuilder`, ELQR/EMVCo, по умолчанию выключено, проверено только с MBank). Об оплате касса не узнаёт — кассир смотрит в телефон покупателя и жмёт «Оплачено» (способ `transfer`).
- Оплата **подписки NurCRM** через ELQR Элдик Банка — ваш `users/billing/…` (признак `billing_elqr`): счёт, QR, опрос статуса, callback с HMAC и белым списком IP, сверка раз в час. Это **образец** механики, но мерчант там — NurCRM. Для магазина мерчант — сам магазин.

## 1. Что видит пользователь

**Кассир, окно оплаты «Безнал → QR»:**

```
┌ Оплата по QR ─────────────────────── 1 180,00 сом ┐
│        ┌──────────┐                               │
│        │  QR с    │   Банк: MBank (магазин)       │
│        │  суммой  │   Счёт №4711 · действует 4:52 │
│        └──────────┘                               │
│  ◌ Ждём оплату…  (проверка каждые 3 с)            │
│  ✓ Оплачено 14:03:12 · MBank · ****1234           │
│  [Отмена]   [Подтвердить вручную (PIN)]           │
└───────────────────────────────────────────────────┘
```

- Пришло подтверждение банка → чек проводится сам (способ `transfer`, подспособ `qr`, ссылка на платёж).
- Нет ответа банка за время жизни счёта → «Оплата не подтверждена. Проверьте телефон покупателя» → «Подтвердить вручную» (право + PIN) или «Отмена».
- Экран покупателя — тот же QR и «Спасибо, оплата получена».

**Владелец:** «Приём оплаты по QR» — мастер подключения банка (выбор банка, ввод ключа/логина, проверка «тестовый платёж 1 сом»); отчёт **«Сверка QR»**: платежи банка без чека, чеки «QR вручную» без платежа банка, расхождения сумм.

## 2. Варианты источника подтверждения (по этапам)

| Этап | Источник | Как | Надёжность |
|---|---|---|---|
| Ф1 | **Merchant API банка с динамическим QR** (ELQR Элдик — договор у нас уже есть, затем MBank/Optima/Bakai по мере открытия API) | сервер создаёт счёт в банке с `order_id`, банк присылает callback / сервер опрашивает статус | высокая — сопоставление по `order_id` |
| Ф2 | **Уведомления банка бизнеса** (webhook/e-mail выписки, где есть: MBusiness, Bakai Business) для статического QR | сервер получает «пришло 1 180,00 от …1234 в 14:03» и ищет ожидающий счёт | средняя — по сумме и времени, нужен «уникализатор» суммы |
| Ф3 | Агрегатор / POS-терминал | отдельное ТЗ после замера спроса | — |

## 3. Модель данных

```
bank_connection
  id, company, branch (null = все), provider: eldik | mbank | optima | bakai | odengi | ...,
  mode: dynamic_api | statement_webhook, status: pending_test | active | disabled | error,
  credentials_ref (ссылка на секрет в хранилище, ключ шифрования вне БД), webhook_secret,
  merchant_name, account_mask, last_ok_at, last_error
payment_intent
  id (uuid), company, branch, cashbox, shift, sale_draft_key (= Idempotency-Key будущей продажи),
  amount "1180.00", currency, unique_tail (Ф2: копейки-уникализатор), provider, provider_invoice_id,
  qr_payload, status: created | waiting | paid | expired | cancelled | refunded | mismatch,
  paid_amount, paid_at, payer_mask, provider_tx_id, expires_at, sale_id (после проведения), confirmed_by: bank | manual
bank_event (сырые callback/выписки: provider, raw (без персональных данных сверх нужного), signature_ok, received_at, matched_intent)
```

## 4. Расчёт и правила сервера

1. **Создание счёта**: касса просит `payment_intent` на сумму итога (после всех скидок, `expected_total`). Сервер создаёт счёт в банке (Ф1) с `order_id = intent.id`, отдаёт `qr_payload` и `expires_at` (по умолчанию 5 мин).
2. **Подтверждение** только по банку: callback с проверкой подписи (HMAC/сертификат) и IP из белого списка **или** ответ запроса статуса к банку. Картинка «оплачено» в телефоне покупателя — не подтверждение.
3. **Сопоставление (Ф1)**: по `provider_invoice_id/order_id` — однозначно. **(Ф2)**: статический QR без номера — сервер делает сумму уникальной копейками (по умолчанию **вычитает**: 1 180,00 → 1 179,93, разница — скидка покупателю за счёт магазина, отражается в чеке как скидка; прибавлять или вычитать — решение владельца, см. вопрос 3) и ищет ожидающий счёт этой компании с той же суммой ±0 и временем ±10 мин. Два кандидата → `mismatch`, ручное решение.
4. **Сумма не совпала** (покупатель ввёл другую в статическом QR): `paid < amount` → статус `mismatch`, касса показывает «Оплачено 1 000 из 1 180 — доплатите 180 другим способом» (смешанная оплата: `transfer` 1 000 + наличные 180); `paid > amount` → чек на сумму чека, переплата — в отчёт «Сверка» (возврат вручную).
5. **Проведение продажи**: касса шлёт обычный `pos/checkout/` с `payment {method: "transfer", payments: [{method: "qr", amount, payment_intent: id}]}` и **тем же** `Idempotency-Key`, что `sale_draft_key`. Сервер проверяет: intent `paid`, сумма совпадает, intent ещё не привязан к другой продаже (**одна оплата — один чек**, И-4). Привязка — в транзакции продажи.
6. **Касса закрылась/упала после оплаты**: intent `paid` без продажи → касса при запуске спрашивает `payment-intents/?status=paid&sale=null&cashbox=` и предлагает «Провести оплаченный чек» (ключ и тело чека у кассы на диске — механизм неясной оплаты уже есть). Через 30 мин без продажи — в отчёт «Сверка» как «оплата без чека».
7. **Офлайн-касса**: динамический QR без сети невозможен → касса предлагает статический QR и ручное подтверждение (как сегодня). Чек офлайн с `transfer/qr_manual` → при досылке сервер пытается сопоставить с выпиской (Ф2), иначе — «QR вручную» в отчёте сверки.
8. **Возврат**: Ф1 — возврат деньгами вручную (наличные или перевод магазином), в чеке возврата способ `transfer`; Ф2 — Refund API банка там, где есть (у Элдик в договоре есть check/create/execute/state): `POST payment-intents/{id}/refund/ {amount}` (Idempotency-Key), не больше оплаченного минус уже возвращённое.
9. **Комиссия банка** — между магазином и банком, в чеке не участвует (чек на полную сумму). В отчёте «Сверка» — колонка «комиссия» из выписки, если банк её даёт.

## 5. Эндпоинты


## 6. Ошибки

| Код | Когда |
|---|---|
| 409 `no_bank_connection` | у компании/филиала нет активного подключения → касса показывает статический QR |
| 502 `bank_unavailable` | банк не ответил при создании счёта → статический QR + ручное подтверждение |
| 409 `intent_expired` / `intent_cancelled` | продажа по просроченному счёту (оплата не пришла) |
| 409 `intent_already_used {sale_id}` | эта оплата уже привязана к другому чеку |
| 409 `intent_amount_mismatch {paid, expected}` | сумма оплаты не равна сумме продажи |
| 403 `manual_confirm_forbidden` | ручное подтверждение без права/PIN |

## 7. Безопасность

- Секреты банка — в отдельном хранилище, шифрование ключом вне БД; доступ только у сервиса платежей; в логах — маски. Смена ключа — только владелец + повторная проверка.
- Callback: подпись, белый список IP, защита от повтора (`provider_tx_id` уникален), ответ банку не раскрывает внутренние данные.
- Ручное подтверждение: право `can_confirm_qr_manually` + PIN руководителя; всё ручное — в отчёт «Сверка» и в «события риска» (`FraudEvents` в кассе уже есть).
- Персональные данные плательщика: только маска карты/телефона.

## 8. Признаки, права, модуль

- Признаки: `qr_payment_intents` (Ф1), `qr_statement_match` (Ф2), `qr_refund_api` (Ф2).
- Права: `can_manage_bank_connections` (владелец), `can_confirm_qr_manually`.
- Модуль «Приём оплаты по QR» — цена решает владелец (в отчёте предложение 100–300 сом/мес); доли с платежей нет (мы не агент).

## 9. Тесты приёмки

1. Счёт 1 180 → callback paid 1 180 → касса провела чек сама; повтор callback → ничего не меняется.
2. Повтор `POST payment-intents` тем же ключом → тот же intent, второй счёт в банке не создан.
3. Касса упала после оплаты → при запуске «Провести оплаченный чек» → одна продажа, intent привязан.
4. Попытка провести второй чек с тем же intent → 409 `intent_already_used`.
5. Callback с неверной подписью → `bank_event.signature_ok=false`, intent не меняется.
6. Оплачено 1 000 из 1 180 (Ф2) → `mismatch`, касса предлагает доплатить 180 наличными; чек `transfer 1000 + cash 180`.
7. Счёт истёк, оплата пришла через 7 мин → intent `paid` без продажи → в «Сверке» «оплата без чека» + касса при следующем опросе предлагает провести.
8. Банк недоступен → 502 → статический QR, ручное подтверждение с PIN → в «Сверке» «QR вручную».
9. Возврат через Refund API 500 из 1 180 дважды тем же ключом → возвращено 500 один раз.

## 10. Этапы

- **Ф1** (после договора магазина с банком и sandbox): `bank_connections` для ELQR Элдик (dynamic), `payment_intents`, callback + опрос, привязка к продаже, ручное подтверждение с PIN, восстановление после падения кассы, отчёт «Сверка».
- **Ф2**: выписки/уведомления банков бизнеса для статического QR (уникальные копейки), Refund API, второй и третий банк.
- Зависимость: юридическая схема «деньги идут магазину» подтверждена юристом; у магазина свой договор с банком.

## 11. Что подхватит касса

- окно «Оплата по QR» с таймером, опросом статуса (3 с) и автопроведением; ручное подтверждение с PIN (механизм `X-Confirm-Token` уже есть);
- `payments[{method: "qr", payment_intent}]` в теле продажи, тот же ключ, что у intent;
- восстановление «оплачено, но чек не проведён» при запуске (рядом с механизмом неясной оплаты);
- без признака или без подключения — как сегодня (статический QR / QR с суммой, ручное «Оплачено»);
- программа владельца: мастер подключения банка, отчёт «Сверка QR» — 5 языков.
