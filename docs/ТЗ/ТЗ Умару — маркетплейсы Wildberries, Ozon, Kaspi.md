## 3. Правила сервера

1. **Остатки → маркетплейс**: событие `stock.changed` (продажа, приход, возврат, ревизия, резерв) кладёт товар в очередь выгрузки; выгрузка пачками раз в 1–5 мин (в пределах лимитов API). Отправляется `max(0, floor(правило(available)))` — **никогда не больше доступного** (защита от продажи несуществующего: штраф маркетплейса). При ошибке связи — повтор с нарастающей паузой; через 30 мин без успеха — отправка 0 на все связанные товары **не делается** автоматически (решение владельца, флаг `zero_on_failure`), но владелец получает уведомление.
2. **Цены → маркетплейс**: только при `price_rule ≠ none`; изменение цены в NurCRM → выгрузка; И-1 — цена не ниже закупки × 1 (без флага `allow_below_cost` у подключения) — иначе товар в «Ошибки», цена не отправляется.
3. **Заказы → NurCRM**: опрос новых заказов раз в 1–2 мин (или вебхук, где есть). На новый заказ:
   - `reserve_then_sale`: создаётся **резерв** (`reservations`) на наш склад; при статусе маркетплейса «передан в доставку/отгружен» — **продажа** (способ оплаты `marketplace:<provider>`, клиент-организация «Wildberries» и т. п., долг маркетплейса перед магазином) и снятие резерва;
   - `sale_on_receive`: сразу продажа.
   - Идемпотентность — уникальность `(connection, mp_order_id)`; повторный опрос не создаёт второй резерв/продажу (И-4).
4. **Отмена** маркетплейсом до отгрузки → резерв снимается; после продажи — **возврат** (`pos/sales/{id}/return/` сервером), товар на склад по флагу «возврат годен» (по умолчанию — в карантин, не в продажу).
5. **Нехватка** при приходе заказа (продали в кассе раньше, чем ушёл остаток) → заказ в статусе `conflict`, уведомление; резерв не создаётся в минус без `allow_negative_stock`.
6. **Деньги**: выручка по заказам маркетплейса — не наличные смены; отдельный способ оплаты, долг маркетплейса; комиссия/логистика — из отчёта маркетплейса (Ф2: загрузка финансового отчёта, сверка выплат).
7. **Фискализация**: продажи маркетплейса фискализирует сам маркетплейс (WB/Ozon как агент) — в нашем чеке `fiscal: skip` (уточнить по КР/КЗ у вас и у юриста, см. вопросы).
8. **Связь товаров**: авто по штрихкоду, затем по артикулу (`offer_id`/`vendorCode`); неоднозначность → `conflict`, вручную.
9. **Лимиты API** (ориентир, уточнить по документации на момент разработки): WB — лимиты на метод в секунду/минуту, Ozon — по методу, Kaspi — по токену; сервер держит свой ограничитель на подключение и уважает 429 / `Retry-After`. Ключи — только на сервере.

## 5. Ошибки

400 `mp_credentials_invalid`, 409 `mp_link_conflict`, 409 `mp_order_conflict {product, need, available}`, 429 `mp_rate_limited` (у нас — повтор, пользователю — «выгрузка отложена»), 502 `mp_unavailable`, 403 `plan_limit {limit: "marketplaces"}`.

## 6. Признаки, права, модуль

- Признаки: `marketplace_sync`, `marketplace_orders`, по провайдерам — `mp_wildberries`, `mp_ozon`, `mp_kaspi`.
- Права: `can_manage_marketplaces` (владелец), `can_process_marketplace_orders` (кладовщик).
- Модуль «Маркетплейсы» — цена решает владелец (предложение 300 сом/мес за один маркетплейс; только «Стандарт»).

## 7. Тесты приёмки

1. Остаток 10, правило «доступный − 2» → на WB 8; продали 3 в кассе → на WB 5 в течение 5 мин.
2. Резерв 2 по заказу витрины → на WB уходит `available − 2` (резервы учитываются).
3. Новый заказ WB → резерв; повторный опрос того же заказа → второго резерва нет.
4. Заказ «отгружен» → продажа `marketplace:wildberries`, резерв снят; наличные смены не изменились.
5. Отмена после продажи → возврат, товар в карантин.
6. Заказ при остатке 0 → `conflict`, уведомление владельцу, минуса нет.
7. Цена × 1,35 ниже закупки (закупка 1 200, розница 850) → цена не отправлена, товар в «Ошибки».
8. 429 от маркетплейса → повтор после `Retry-After`, задача не потеряна.
