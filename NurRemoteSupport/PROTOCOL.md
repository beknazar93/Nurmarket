# NurMarket Remote Support — протокол v1

Своя удалённая поддержка вместо AnyDesk (решение владельца 2026-09-29: «полностью своё с нуля», свой VPS).

Этот файл — **единственный источник правды** для трёх частей: хоста (касса), ретранслятора (`Server/`) и страницы оператора (`Server/wwwroot/`).

## ВАЖНО: уточнения ретранслятора (2026-09-29) — что обязательно учесть хосту

Сделаны при написании сервера; всё ниже по тексту уже исправлено. Коротко, что важно для кассы:

1. **Пинг — на уровне JSON, не кадрами WebSocket.** В .NET 8 сервер не может слать WebSocket-ping и не видит pong-кадры. Поэтому ретранслятор каждые 15 с шлёт `{"type":"ping"}`, хост **обязан** ответить `{"type":"pong"}` (сразу, в любом состоянии — и до сеанса, и во время). Нет никаких сообщений от стороны 45 с — соединение рвётся. Хост тоже может слать `{"type":"ping","t":…}` — сервер ответит `{"type":"pong","t":…}` (то же `t`), так хост может мерить задержку. Сообщения `ping`/`pong` сервер никому не пересылает.
2. **После любого конечного состояния сервер закрывает соединение хоста.** `declined`, `locked`, `expired`, конец сеанса — хост получает сообщение и закрытие сокета. Чтобы получить новый код, хост подключается заново и шлёт новый `hello`. Код и PIN не переиспользуются.
3. **Сообщения хосту о завершении до начала сеанса:** `{"type":"expired"}` (15 мин прошло, никто не подключился), `{"type":"locked"}` (5 неверных PIN), `{"type":"end","reason":"declined"|"consent-timeout"|"operator"|…}` (оператор ушёл, пока кассир думал; кассир отказал; нет ответа).
4. **Ответ на согласие сервер тоже ограничивает:** хост сам считает 60 с, а сервер через 90 с считает отказом (`consent-timeout`).
5. **Зарезервированные типы не пересылаются.** Во время сеанса сервер пересылает всё как есть, *кроме* текстовых сообщений служебных типов (`hello`, `session`, `join`, `join-request`, `consent`, `waiting-consent`, `started`, `locked`, `expired`, `error`, `ping`, `pong`, `end`) — их обрабатывает сам или отбрасывает. Так оператор не может подделать служебное сообщение для кассы.
6. **Двоичные кадры от оператора к хосту в v1 не пересылаются** (сервер их отбрасывает).
7. **Размеры:** двоичное сообщение ≤ 4 МБ, текстовое ≤ 256 КБ. Больше — сервер закрывает соединение (код 1009) и завершает сеанс с `reason:"error"`.
8. **`hello` — первое сообщение хоста, не позже 10 с** после подключения; иначе соединение закрывается. Строки в `hello` обрезаются: `company`/`machine`/`app`/`version` — до 100 символов. `protocol` ≠ 1 → `{"type":"error","code":"protocol"}` и закрытие.
9. **Колесо мыши:** `delta` — в единицах Windows: 120 = один щелчок колеса **вверх** (от себя), отрицательное — вниз. Горизонтальной прокрутки в v1 нет.
10. **`started` дополнен** (поля добавлены, старые не менялись), `bad-pin` дополнен полем `left`, добавлены коды ошибок `rate-limited`, `server-busy`, `protocol`, `bad-request`, `not-joined`.
11. **Кнопки мыши:** `button` как `MouseEvent.button` в браузере: `0` — левая, `1` — средняя (колесо), `2` — правая.

## v1.1 (2026-10-16): программа сотрудника поддержки

Совместимо с v1: `protocol` в `hello` по-прежнему `1`, новые поля и сообщения необязательны, старые кассы и страница оператора работают как раньше.
Программа оператора — `Operator/` (Avalonia, `NurMarketSupport.exe`); страница в браузере остаётся запасной.

**Ретранслятор:**
- `hello` хоста: необязательные `"user"` (кассир, ≤100) и `"note"` (что случилось — пишет кассир, ≤500). Попадают в `/api/sessions` (`active[].user`, `active[].note`) и в журнал (`user`, `note`).
- `join` оператора: вместо `code` можно `"session":"<sessionId из /api/sessions>"` — вход из очереди, кассир диктует только PIN. Проверки те же (PIN, 5 попыток, согласие кассира). Код и PIN в `/api/sessions` не отдаются.
- Заметки операторов (история обращений, общая для всех операторов, файл `{DataDir}/notes.jsonl`):
  - `GET /api/notes?company=&machine=&limit=` → `{"notes":[{"id","created","operator","operatorName","company","machine","sessionId","text"}]}` (новые сверху; без `company` — по всем кассам);
  - `POST /api/notes` `{"company","machine","sessionId","text"}` → `200` запись | `400` пустой текст или длиннее 4000.

**Сообщения сеанса (текст, идут насквозь, только во время сеанса):**

| Кто → кому | Сообщение | Что делает |
|---|---|---|
| оба | `{"type":"chat","text"}` (≤2000) | чат кассира и оператора; у кассы окно чата поверх программы и кнопка «Чат» на красной полосе |
| оператор → касса | `{"type":"info-request"}` | касса отвечает `{"type":"info","text"}` — версия, магазин, кассир, очередь чеков, принтер, ОС, память, диски, принтеры Windows, COM-порты (без паролей и токенов) |
| оператор → касса | `{"type":"diag-request"}` | касса отвечает `{"type":"diag","items":[{"name","ok":true/false/null,"detail"}]}` — связь с NurCRM, время, чеки без связи, принтер, диск, память, ошибки в журнале, версия |
| оператор → касса | `{"type":"logs-request","lines":N}` | касса отвечает `{"type":"logs","text"}` — последние N строк журнала (≤200 КБ) |
| оператор → касса | `{"type":"logs-zip-request"}` | касса присылает zip журналов и отчётов о сбоях файлом (см. ниже) |
| оба | `{"type":"file-begin","id","name","size"}`, `{"type":"file-chunk","id","index","data":"<base64 ≤96 КБ>"}`, `{"type":"file-end","id"}` | файл частями в тексте (двоичное от оператора сервер v1 не пересылает). Касса кладёт файл в «Загрузки\NurMarket поддержка» (до 100 МБ, ничего не запускает), отвечает `{"type":"file-saved","id","name"}` или `{"type":"file-error","id","error"}` и показывает кассиру уведомление |
| оператор → касса | `{"type":"clipboard-set","text"}` / `{"type":"clipboard-get"}` | положить текст в буфер обмена кассы / получить его: `{"type":"clipboard","text"}`. При «только просмотр» `clipboard-set` не выполняется |

## Участники

| Кто | Где | Что делает |
|---|---|---|
| **Хост** | касса (NurMarketKassa, Windows) — окно «Тех. поддержка» | передаёт экран, принимает мышь/клавиатуру, спрашивает согласие кассира |
| **Ретранслятор** | VPS владельца (`NurRemoteSupport/Server`, ASP.NET Core 8, Docker) | регистрирует сеансы, проверяет PIN, соединяет пару, пересылает сообщения, журнал сеансов |
| **Оператор** | браузер (страница, которую отдаёт ретранслятор) | вход по логину, ввод кода и PIN, просмотр и управление |

Обе стороны подключаются к ретранслятору сами (исходящие соединения) — NAT и роутеры клиентов не мешают.
Транспорт — WebSocket поверх TLS (`wss://`). В разработке допускается `ws://127.0.0.1`.

## Адреса ретранслятора

- `GET /` — страница оператора (HTML+JS, без сборщиков).
- `POST /api/login` `{"login","password"}` → `200 {"token","name","login","expiresAt"}` (токен живёт 12 ч) | `401` неверный логин/пароль | `429` слишком много попыток. Операторы — в файле `operators.json` сервера, пароль — хэш PBKDF2-SHA256.
- `GET /api/me` (с токеном) → `{"login","name"}` — проверка токена.
- `GET /api/sessions?limit=100` (с токеном) → `{"active":[…],"recent":[…]}` — активные сеансы и последние записи журнала (новые сверху).
- `WS /ws/host` — хост.
- `WS /ws/operator` — оператор. Токен — заголовком `Authorization: Bearer <токен>` (программа оператора, с 19.10.2026: адреса попадают в журналы прокси). Браузер не умеет заголовки у WebSocket — ему по-прежнему `?token=...` в адресе (сервер адреса с токеном в журнал не пишет). Без токена или с плохим — `401` до установки WebSocket.
- `GET /health` → `ok`.

Токен передаётся заголовком `Authorization: Bearer <token>` (для `/api/*`). Токен — `base64url(данные).base64url(HMAC-SHA256)`, подписан секретом сервера; сброс пароля оператора или его удаление делает старые токены недействительными.

## Сообщения

Текстовые кадры WebSocket — JSON (UTF-8) с полем `type`. Двоичные — кадры экрана (см. ниже).

### Служебные (любая сторона ↔ ретранслятор, в любом состоянии)

- Ретранслятор → `{"type":"ping"}` каждые 15 с. Ответ `{"type":"pong"}` обязателен.
- Сторона → `{"type":"ping","t":<число>}` → ретранслятор отвечает `{"type":"pong","t":<то же>}`.
- Нет ни одного сообщения от стороны 45 с → соединение закрывается, сеанс завершается с `reason:"timeout"`.
  (Совместимость: пока хост ни разу не прислал `pong`, 45-секундное правило к нему не применяется — только чтобы ранние сборки не рвались; полагаться на это нельзя.)

### Хост ↔ ретранслятор (до начала сеанса)

1. Хост → `{"type":"hello","role":"host","protocol":1,"app":"NurMarketKassa","version":"1.17.28","company":"NBS","machine":"DESKTOP-…","screen":{"w":1920,"h":1080}}`
2. Ретранслятор → `{"type":"session","code":"482915736","pin":"5093","expiresIn":900}` — код 9 цифр (кассир диктует «482 915 736»), PIN 4 цифры, одноразовые.
3. Ретранслятор → хосту при попытке входа (верный код и PIN): `{"type":"join-request","operator":"Айбек","login":"aibek","ip":"…"}`.
4. Хост → `{"type":"consent","accept":true|false}` — после кнопки кассира «Разрешить»/«Отклонить» (нет ответа 60 с = отказ, хост шлёт `accept:false`; сервер сам считает отказом через 90 с).
5. Ретранслятор → обоим `{"type":"started","sessionId":"…","operator":"…"}`.
   Оператору дополнительно: `"login"`, `"host":{"app","version","company","machine","screen":{"w","h"}}`.

Возможные завершения до начала сеанса (сервер после них закрывает соединение хоста):
- `{"type":"expired"}` — прошло 15 мин, оператор не подключился.
- `{"type":"locked"}` — 5 неверных PIN подряд.
- `{"type":"end","reason":"declined"}` — кассир отказал; `"consent-timeout"` — нет ответа 90 с; `"operator"` — оператор отменил или ушёл, пока ждали согласия.
- `{"type":"error","code":"protocol"|"bad-request"|"server-busy"|"rate-limited"}` — плохой `hello`, сервер переполнен, слишком много подключений с одного IP.

### Оператор ↔ ретранслятор

1. Оператор → `{"type":"join","code":"482915736","pin":"5093"}` (пробелы в коде допускаются).
2. Ретранслятор → `{"type":"waiting-consent"}` | `{"type":"error","code":"…"}`:
   - `bad-pin` (+ `"left":N` — сколько попыток осталось),
   - `no-session` — такого кода нет (или уже использован),
   - `locked` — 5 неверных PIN подряд (хосту `{"type":"locked"}`, кассир начинает заново),
   - `busy` — к этой кассе уже подключается/подключён другой оператор,
   - `declined` — кассир отказал (или не ответил),
   - `expired` — код устарел (15 мин),
   - `rate-limited` — слишком много попыток входа с этого IP/логина, подождать минуту,
   - `bad-request` — непонятное сообщение,
   - `not-joined` — `end` без сеанса.
   После ошибки соединение оператора остаётся открытым — можно ввести код снова.
3. После согласия — `started`, дальше ретранслятор пересылает все кадры пары как есть (кроме служебных типов, см. уточнение 5).
4. Отмена ожидания: оператор → `{"type":"end","reason":"operator"}` — хосту уходит `end` с `reason:"operator"`.

### Во время сеанса (пересылаются насквозь)

Хост → оператор, текст:
- `{"type":"screen","w":1920,"h":1080,"monitor":0,"monitors":1}` — при старте и смене разрешения/монитора. После него хост шлёт полный кадр.
- `{"type":"cursor","x":…,"y":…}` — положение курсора (если не отрисован в кадре).
- `{"type":"stats","fps":…,"kbps":…}` — по желанию.

Хост → оператор, **двоичный кадр экрана** (little-endian):

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | вид: `1` = кусок экрана JPEG, `2` = конец кадра |
| 1 | 4 | номер кадра (uint32) |
| 5 | 2 | x (uint16) |
| 7 | 2 | y |
| 9 | 2 | ширина |
| 11 | 2 | высота |
| 13 | … | JPEG (для вида 1), пусто для вида 2 |

Кадр = несколько кусков (только изменившиеся области, первый кадр — весь экран) + «конец кадра». Одно двоичное сообщение WebSocket = один кусок.

Оператор → хост, текст:
- `{"type":"ack","frame":N}` — после отрисовки кадра N. Хост держит не больше 2 неподтверждённых кадров (защита от забивания медленного канала). Сервер сам кадры не выбрасывает: у каждого соединения ограниченная очередь отправки (16 МБ); если она полна, сервер перестаёт читать от отправителя (давление назад по TCP), а через 30 с такого застоя завершает сеанс с `reason:"error"`.
- `{"type":"mouse","action":"move"|"down"|"up"|"wheel","x":…,"y":…,"button":0|1|2,"delta":…}` — координаты в пикселях экрана хоста; `button` как в браузере (0 левая, 1 средняя, 2 правая); `delta` только для `wheel`: 120 = щелчок вверх, отрицательное — вниз. Движение оператор шлёт не чаще ~60 раз/с.
- `{"type":"key","action":"down"|"up","code":"KeyA","key":"a"}` — `code` как `KeyboardEvent.code`. При потере фокуса страница отпускает все нажатые клавиши (`up`).
- `{"type":"text","text":"…"}` — ввод текста (кириллица, вставка из буфера оператора, до 10 000 символов).
- `{"type":"quality","value":10..90}`, `{"type":"monitor","index":N}`.
- `{"type":"view-only","value":true|false}` — оператор сам отключает управление.

Любая сторона: `{"type":"end","reason":"host"|"operator"|"timeout"|"error"}` — ретранслятор закрывает обе стороны и пишет итог в журнал.
Другой стороне уходит `{"type":"end","reason":…}`, где `reason` — кто/что завершил: `host`, `operator`, `timeout` (нет сообщений 45 с), `error` (слишком большое сообщение, застой очереди), `disconnect` (соединение оборвалось без `end`), `shutdown` (сервер остановлен).

## Журнал сеансов

Файл `journal.jsonl` (одна JSON-строка на сеанс, только дописывается). Пишется для каждого сеанса, где был оператор (верный код и PIN) или блокировка:

```json
{"sessionId":"…","code":"482915736","operator":"aibek","operatorName":"Айбек","operatorIp":"…","company":"NBS","machine":"DESKTOP-…","app":"NurMarketKassa","version":"1.17.28","hostIp":"…","created":"2026-09-29T10:00:00Z","start":"2026-09-29T10:01:10Z","end":"2026-09-29T10:15:00Z","durationSec":830,"reason":"operator","bytesToOperator":12345678,"bytesToHost":23456}
```
`start` = null, если сеанс не начался (`declined`, `consent-timeout`, `locked`, оператор отменил). Сеансы, к которым никто не подключался (просто истёк код), в журнал не пишутся — только в лог сервера.

## Безопасность (обязательно)

- Никакого доступа без согласия: каждый сеанс — код + PIN + кнопка кассира «Разрешить». Автоподключения («неприсмотренный доступ») в v1 нет.
- Во время сеанса поверх всех окон кассы — полоса «Идёт сеанс поддержки: <оператор> · [Завершить]».
- Код и PIN одноразовые, живут 15 мин до подключения; перебор PIN блокируется (5 неверных подряд → `locked`).
- Ограничение частоты: вход оператора — 10 попыток в минуту с IP и 10 неудачных за 15 мин на логин; `join` — 20 в минуту с IP и с оператора; подключений хоста — 30 в минуту с IP и не больше 10 ожидающих кодов с одного IP.
- Только TLS в боевом режиме; операторы — по логину; журнал: кто, к какой кассе, когда, сколько длилось, итог.
- Хост не принимает ничего, кроме описанных сообщений; размеры и координаты проверяются.
